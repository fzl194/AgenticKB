## 3. 迁移步骤（生产库，部署重启完成后）

```bash
# 1) 干跑，人工复核报告
python backfill_user_domains.py --dry-run
# 重点看：
#   - [WARN-zero-binding] 行：无库且无兜底域的用户（需人工决定是否给 fallback）
#   - 无库用户将被兜底到的域（未指定 --fallback-domain 时取 active KB 数最多的域）
# 2) 正式跑（建议显式指定兜底域，避免依赖 KB 分布推断）
python backfill_user_domains.py --fallback-domain <域>
# 3) 再跑一次验证全 skipped（幂等证明）
python backfill_user_domains.py --fallback-domain <域>
# 期望输出：inserted 0 binding rows, N skipped (already present)
```

连接参数走环境变量 `PG_HOST/PG_PORT/PG_DBNAME/PG_USER/PG_PASSWORD`。

测试库演练证据（kb_db_test，2026-09-17）：

## 5. Deferred：curl 端到端（Task 9/10 审查遗留，部署后逐条执行）

假设：`$MC`=main_control 地址，`$MN`=mining 地址，`$SEC`=auth.yaml 的
`internal_verify_secret`。

```bash
# 1) 无 token 访问受保护端点 → 401
curl -s -o /dev/null -w '%{http_code}\n' "$MC/api/v1/domains"
# 期望 401（免鉴权白名单只有 /health、/api/v1/version、login/identify）

# 2) 内部 secret 全量：带正确 X-Internal-Auth → 域列表不受登录人过滤
curl -s -H "X-Internal-Auth: $SEC" "$MN/api/kb/internal/users/<user_id>/domains"

# 3) member 过滤：普通用户 token → 只见自己绑定域
TOKEN=$(curl -s -X POST "$MC/api/v1/auth/login" -H 'Content-Type: application/json' \
  -d '{"username":"<普通用户>","password":"<密码>"}' | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" "$MC/api/v1/domains" | jq

# 4) 删域 409 保护：域下仍有活跃 KB 时删除 → 409 domain_has_kbs
curl -s -X DELETE -H "Authorization: Bearer $ADMIN_TOKEN" \
  "$MC/api/v1/domains/<有库域>" -w '\n%{http_code}\n'

# 5) 停 mining 503：mining 不可达时经网关的 KB 读写 → 503（fail-closed，
#    不静默放行）；验证后恢复 mining
```

## 7. 回归中发现并修复的本批缺陷（Task 12）

**根因**：`KbDB.upsert_user_by_username`（网关身份惰性建档路径，
`current_user` → `IdentityCache.get_user` 每请求走）直接 INSERT kb_users，
**没有绑默认域**——Task 6 只覆盖了 `user_service.create_user`。结果：凡经
X-KB-User 头惰性建档的 member 一律零绑定，建库全部 403 `domain_not_bound`
（16 个 kb 路由测试因此挂掉）。

**修复**（`knowledge_mining/mining/kb/db.py`）：

- upsert RETURNING 增加 `(xmax = 0) AS _inserted` 区分新插入与已存在；
- 仅新插入且非 admin 时 `INSERT INTO user_domains ... ON CONFLICT DO NOTHING`
  绑 `get_default_domain()`（运行时读 registry，与 user_service 一致）；
  绑定失败降级不挡认证（身份建档优先）。
- 已存在用户不碰——解绑语义仍归 admin 分配端点 / backfill 脚本。

**佐证**：修复后 16 个失败用例（test_mining 7 / test_mining_auto_queue_pg 3 /
test_documents 4 / test_overview_queries 1 / test_kb_lifecycle_contract_31fix 1）
连同相关用例 18/18 全绿；tests/kb/ 全目录 348 passed，26 failed 全部与基线
环境性失败重合（其中 test_routes_kb::test_create_list_get_update_delete 单跑
即绿，属共享库脏数据导致的顺序性 flake）。
