## 1. 战略方向(已定,不再讨论)

三条已锁定的方向,源自本轮研讨用户决策:

1. **内置 `/api/v1/search` 的写死 pipeline 要下架**——不再往一个要废弃的东西上投入修 bug / 优化的成本。
2. **未来统一基于算子 / 范式(`operator/` package)构建检索**——不同检索需求 = 不同范式。
3. **下一阶段 = 算子化后的"应用"**:在 KB 管理新需求基础上做泛化性调整,让范式真正可用、可配置、可替代内置。

**性能("检索慢")不是独立议题,而是算子化统一的约束条件**:算子路径替代内置时,延迟必须 ≤ 内置,且要把内置现有的"慢"一并解决。**优化只发生在算子路径上,内置 pipeline 不再投入。**

### 2.4 并行度特征

`ParadigmExecutor.java:84-117`:波次内 ready 节点用虚拟线程真并行(`runAsync(..., newVirtualThreadPerTaskExecutor)`),**波次间是硬 barrier**(`allOf(futures).join()`)。比内置 `SearchService` 手动 `CompletableFuture` 链粗——多路检索若因 DAG 拓扑被划入不同波次,会被强制串行。**结论:算子路径并行度 ≤ 内置,除非范式 DAG 把可并行的检索算子放在同一波次。**

### 2.5 一个必须澄清的误判

F1_full_replica_assemble 范式延迟低于内置(`retrieval-paradigm-test-set.md:36`),**不是"同等质量下更快"**,而是因为它没接 multi_query fan-out(C2)、子查询分解(C3)、tree nav(C4),LLM 调用少(2 次 vs 内置 4~5 次)。**用它对标 `/api/v1/search` 的召回率 / precision 会偏低**——这正是 test-set §3 "F1 vs /api/v1/search" 对照要量化的差距。替代内置前必须先补齐 C2~C4,否则是退步。

## 3. 检索慢:根因与算子路径的解法

### 3.1 内置 pipeline 慢在哪(诊断瀑布)

```
QU ‖ HyDE ‖ MultiQuery   200ms~2s      ← LLM,三路并行但等最慢的
scope resolve             5~20ms        ← SQL,2 查询
tree nav                  5~30ms        ← SQL,JSONB 聚合
cache lookup              5~20ms        ← pgvector,命中跳过下游全部
多路召回 ‖ 变体 ‖ 子查询   50ms~3s       ← SQL + fan-out 到 7 路并行
fusion / hydrate          <50ms         ← 内存 + 1 次 IN 查询
Rerank 级联               50ms~3s       ← 🔴 LLM,model 失败兜底 llm 可能 2 次
assemble                  10~100ms      ← GraphExpander BFS + 压缩
```

**Top 3 瓶颈**(占端到端 80%+):
1. 🔴 **Rerank 级联**(`RerankPipeline.java:74-130`):cascade 模式下 model_rerank 失败兜底 llm_rerank,可能连吃两次大延迟 LLM。
2. 🔴 **LLM 调用密度**:单请求最多 7 次 LLM 调用,且都同步打 llm_service `/execute`(60s 超时,租约队列可能排队)。
3. 🟡 **无效串行点**(`SearchService.java:189→213→224→250`):scope resolve 只依赖 domain/channel 却等 QU join;cache lookup 只依赖 queryEmbedding 却排在 scope+tree nav 之后——**命中缓存也白等这两步**。

**关键判断:慢在 LLM,不在 SQL。** SQL 层(scope/tree nav/召回)总和在几十~几百 ms 量级,LLM 层在秒级。

### 3.2 算子路径的性能杠杆(替代内置时一并解决)

既然优化只在算子路径做,且内置的坑不再修,杠杆是:

| 杠杆 | 对应缺口 / 新增 | 收益 |
|---|---|---|
| **接入语义缓存(C1)** | 新增 | 近义 / 重复查询短路到 ms 级——**单点最大收益**,且内置的"缓存污染 / store 同步阻塞"两个坑从零做对 |
| **Rerank 不级联** | 范式设计 + 算子 | model 失败直接 score 兜底,砍掉 cascade 里那次 llm_rerank——单点省最多 LLM 延迟 |
| **范式级裁剪** | 范式设计 | 简单查询用简单范式(如 `dense→collect`,零 LLM 重排),复杂查询才上全链。比内置"单 pipeline 内自适应"更彻底 |
| **并行度优化** | 范式 DAG 编排 + executor | 把可并行的检索算子放同波次;或 executor 支持"跨波次投机并行"(消除不必要 barrier) |
| **LLM 调用按需** | 范式设计 | HyDE 只在 dense 主路时启用;multi_query(C2 接通后)按 complexity 启用 |

> **注意**:C2(multi_query fan-out)/ C3(子查询)补齐后,算子路径的 LLM 调用会**回升**(因为能力补全了)。届时"范式级裁剪"是抵消这部分延迟的关键——简单查询坚决不走重链。

## 4. 工作分解(四主线)

### 主线 A —— 补齐算子能力(等价替代内置)

让算子路径具备内置全部检索能力,按 P0→P1:

- **A1 [P0] 语义缓存接入算子路径**:在 `ParadigmExecutionService.run()` 前后接 lookup/store。**缓存契约分叉**:assemble 终点产 `CONTEXT_PACK` 可直接复用内置 `SemanticCacheService`;collect 终点产 `CANDIDATE_LIST` 需扩展契约(见 §6-Q3)。同时从零做对:空 / 降级不写、store 异步、`evict` 接 release 发布钩子。
- **A2 [P0] multi_query fan-out 接通**:二选一(见 §6-Q1):(a) 新增 `map/flatMap` 算子,STRING_LIST 展开成多个检索节点实例;(b) 扩展 `SlotType` 支持 `STRING_LIST→CANDIDATE_LIST_MULTI` 展开 + executor 支持节点实例化。配套补 `embedBatch` 批量嵌套(operator 包零使用)。
- **A3 [P0] 子查询分解算子**:新增算子消费 `understanding.subQueries`,每条独立召回再合并。机制上与 A2 的 fan-out 同源(都是"一次输入→多次检索→合并"),建议统一成一个 fan-out 机制。
- **A4 [P1] tree navigation 算子**:新增 `tree_nav` 算子,产 hardFilter(章节前缀)+ softSections,下推到检索算子 SQL。检索算子要加 section 过滤参数。
- **A5 [P1] 运行时路由(最难,见 §6-Q2)**:让范式能按 `complexity/intent` 自适应。三种候选:范式内条件分支 / 外层范式路由器 / 靠 fusion 自然降级不显式路由。
- **A6 [P1] 重排保留 understanding 信号**:rerank 算子不再重建 stub,把 entities/evidenceNeed/intent 喂给 reranker。
- **A7 [P2] 观测性**:trace 细化到检索语义(候选数 / 分数分布 / 每路 latencyMs);补 Prometheus metrics。

### 主线 B —— 范式承载 KB 集合(KB 需求 v0.2 §6 的落地)

KB 需求已定"KB 集合在设计态绑进范式",检索侧的改造面:

- **B1 scope_resolve 支持 KB 收窄**:`ScopeResolveOperator` 扩展,范式绑定的 KB 集合 → 收窄 `snapshotIds` 到这些 KB 的文档(KB→document→snapshot 链)。**依赖 KB 模块先把 `asset_documents.kb_id` 建起来**(KB 需求 D7)。
- **B2 结果来源标注**:通过 `unit→snapshot→link→document→kb_id` 回溯,把 `kb_id` 塞进 `ContextPack.items` / candidate metadata。
- **B3 范式绑定 KB 集合的机制(见 §6-Q4)**:范式 JSON 加 `kb_ids` 字段(范式→KB 死绑),或范式 scope 参数化(一个范式 + 不同 KB 集合)。KB 需求 §6 原文:"不同 KB 组合 = 不同范式(或范式的不同 scope 配置),机制细节留实现设计"。
- **B4 前端范式画布(kb-ui)**:让用户可视化编排范式 DAG + 选 KB 集合。后端 catalog/CRUD API 已就绪,这是"算子化应用"的 UI 落地——**工作量最大的单项,优先级见 §6-Q5**。

### 主线 C —— 算子路径性能优化(检索慢)

见 §3.2,与主线 A 的 A1/A5/A7 同源,不单列。核心:缓存(A1)+ 范式裁剪 + rerank 不级联 + 并行度优化。

### 主线 D —— 内置 pipeline 下架(收尾)

- **D1** A 主线补齐后,用一个等价内置范式对标 `/api/v1/search`(test-set §3 的 F1 对照),召回率 / precision / 延迟三项达标后才下架。
- **D2** `/api/v1/search` 改成"跑默认范式"的薄壳,或直接废弃(看 §6-Q6)。
- **D3** 死代码清理:`RetrievalRouter.BUILTIN_ROUTES`、过时文档(`pipeline-0X-*.md` / `code_guide.md`)。

## 6. 待讨论的设计分叉(拍板点)

> 编号用 Q(Question),避免与"主线 D(内置下架)"混淆。

### Q1 —— multi_query fan-out 的实现机制(A2)
- **(a) 新增 `map/flatMap` 算子**:STRING_LIST → 显式展开成多个检索节点实例。DAG 清晰,引擎改动小,但范式 JSON 会膨胀。
- **(b) 扩展 `SlotType` 展开 + executor 节点实例化**:`STRING_LIST→CANDIDATE_LIST_MULTI` 语义内置,executor 自动 fan-out。引擎改动大,但范式更简洁,且 A3 子查询分解可复用同一机制。
- **倾向 (b)**:A2 和 A3 同源,统一成一个 fan-out 机制更干净。

### Q2 —— 运行时路由(A5,最难)
- **(a) 范式内条件分支**:DAG 支持 if/switch 节点,按 `complexity/intent` 走不同支路。引擎要从纯 DAG 升级到条件 DAG,改动最大但表达力最强。
- **(b) 外层范式路由器**:QU 先跑(或轻量规则),按 complexity 选一个范式跑。多个范式 + 一个选择层,引擎不动。
- **(c) 不自适应,靠 fusion 自然降级**:一个全功能范式,简单查询靠各路 SKIP_WITH_EMPTY + fusion 加权自然平衡。最省事但效果不可控。
- **倾向 (b)**:改动可控,且与"不同检索需求 = 不同范式"的战略一致(简单查询本来就该用简单范式)。代价是 QU 要前置(不能和其他阶段并行),或用规则预估 complexity 选范式。

### Q3 —— 缓存契约:collect vs assemble(A1)
- **(a) 只缓存 assemble 终点**(产 ContextPack,直接复用内置契约)。collect 是测试终点,不缓存。
- **(b) 扩展缓存支持 CANDIDATE_LIST**。collect 范式也能缓存。
- **倾向 (a)**:collect 服务评测,重复跑反而要测稳定性;生产用 assemble,缓存它就够。

### Q4 —— 范式绑定 KB 集合的机制(B3)
- **(a) 范式 → KB 死绑**:范式 JSON 加 `kb_ids` 字段,不同 KB 组合 = 不同范式。简单,但范式数量膨胀。
- **(b) 范式 scope 参数化**:一个范式定义 + 运行时传 KB 集合参数。范式可复用,但"设计态确定"的语义弱化(又回到查询时传参)。
- **倾向 (a)**:与 KB 需求 §6"设计态确定"和"不同 KB 组合 = 不同范式"最一致。代价靠"范式模板 + 一键派生"缓解(范式可基于模板克隆改 KB)。

### Q5 —— 前端范式画布的优先级(B4)
- **(a) P2 立即做**:让范式真正可用,是"算子化应用"的核心。但工作量 ~2~3 周。
- **(b) P3 推后**:先用 API / 配置文件管理范式,画布延后。能更早交付算子能力。
- **倾向看 KB 模块节奏**:画布是 KB 管理 UI 的延伸(选 KB 集合),建议和 KB 前端一起做。

### Q6 —— 内置 `/api/v1/search` 的处置(D2)
- **(a) 改薄壳**:`/api/v1/search` 内部改成"跑默认范式",保持 URL 兼容。
- **(b) 直接废弃**:新范式的 `/api/v1/paradigm/{id}/search` 取代。
- **倾向 (a)**:向后兼容,存量调用方(前端 / mcp_server)无感迁移。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| C2~C4 补齐后算子路径 LLM 调用回升,延迟反超内置 | 范式级裁剪(简单查询走轻范式)+ rerank 不级联 + 缓存兜底 |
| A5 运行时路由选型错误导致引擎大改返工 | 先用 D2(b) 外层路由器过渡,验证效果再决定是否上 D2(a) |

| 范式数量随 KB 组合爆炸(D4-a) | 范式模板 + 一键派生机制;长期可上 D4-b 参数化 |
