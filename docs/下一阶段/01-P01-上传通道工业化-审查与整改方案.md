**清单遗漏的发现（本次审查新增）：**

1. **无任何应用层大小限制**。KB 上传路由没有 max size 校验；100MB/500MB 限制只存在于**未被 KB 链复用**的旧域上传路径（`api/routes/uploads.py:48-50` + `infra/upload_config.py:17-19`）。nginx `client_max_body_size 600M`（`docker/nginx.conf:31`）**只作用于 `/api/control-plane/` location**；直连 8901 时连这层都没有。→ 一个未鉴权的 `POST /api/uploads`（见 08 号文档 P13）或超大 KB 上传可以把进程内存直接打爆。
2. **router.py:5-7 的"legacy surface continues to write storage_path"注释已过时**——KB 上传早已写 `storage_object_id`，真正 legacy 的只剩磁盘回落分支（delete `document_service.py:255-265`、download_path `:345-358`）。整改时应一并清理这条注释误导。
3. **~~put_stream 已流式~~（对抗审查推翻此判断）**：`put_stream` 签名虽接受 `AsyncIterator[bytes]`，但实现里 `_drain`（`minio.py:181`、`:518-522`）仍是 `chunks.append + b"".join` 整包物化后才写盘上传——**签名流式、实现整包**，与 get_stream 的"落盘再分块"（05 号发现 1）同构。修上传内存必须先改 MinIO 适配器（S1 第 0 项前置），"修复面小"不成立。
4. **（对抗审查新增）multipart 三件套是空壳**：`initiate_multipart/upload_part/complete_multipart/abort_multipart`（`minio.py:406-456`）后三者直接 `raise NotImplementedError("wired in M1 smoke")`——**当前没有分片上传与断点续传的实现基础**，S2 的"断点续传"必须先补适配器。
5. **（对抗审查新增）** docker-compose.yml **没有 19000 端口映射**——MinIO 是外部端点 `121.89.90.178:19000`（`main_control_service/config/system/storage.yaml:24`，明文 HTTP）。presigned 直传 = 浏览器直连公网 IP 明文 MinIO，需评估 CORS/HTTPS/签名 URL 泄漏面，不可达时回落后端中转。

## 3. 运行时实测（2026-08-24，真库只读盘点）

- `asset_storage_objects`：source bucket 10 个对象、parse bucket 24 个——当前 demo 体量下直传通道工作正常。
- 三个 KB（test/test2/test23）共 16 个文档全部经直传通道入库（均有 `storage_object_id`、rev=1）。
- 结论与清单一致：**当前实现可用，风险在未来规模**，不是功能故障。

## 4. 根因分析

这不是一个 bug，是**同一能力的两个世代并存**：工业版（UploadSessionService + 配额 + outbox，M1 规划产物）完整躺在 `file_management/`，而 KB 产品化时（后做的 `kb/` 路由）为了快速打通，另写了一条 12 行的直传捷径。两侧从未合流，于是：

- 直传侧缺会话状态机、幂等键、断点续传、配额、补偿清理；
- 工业侧缺生产调用方，处于"零接线"状态（连 router 都没挂）。

`await file.read()` 的内存放大在 P05（IR 读取）、P11（解析读取）各有一个同构副本——**三处独立整包环节**，修一处不影响另两处。

## 5. 修改方案（分阶段，均待批准后实施）

### 方案选型结论

**推荐双通道合流（清单建议 2）**：直传保留为"小文件通道"（补上限与流式化），大文件切 UploadSessionService 的 presigned 直传 + complete 提交，两通道汇合到同一个 verify/commit 校验点。理由：
- 直传通道已被 16 个文档 + 全部现有 UI 使用，推翻重写风险大；
- UploadSessionService 的幂等键（kb_id, actor, idempotency_key）与 presigned 分片能力正是弱网大文件刚需；
- 两通道最终都写 `asset_storage_objects` + `asset_documents`，汇合点天然存在。

### S1（P0，止血：内存与上限）

| # | 改动 | 位置 |
|---|---|---|
| 0 | **前置（对抗审查追加）**：重写 MinIO `put_stream` 为增量 sha256 + 流式落盘再上传（消灭 `_drain` 整包 join）——端口契约不动，适配器动。未做此前置，后续任何"分块上传"都只是把 join 挪进适配器 | `minio.py:173-201`、`:518-522` |
| 1 | 路由加大小上限：**新增 KB 专用配置键**（如 `kb_max_upload_mb`），不要改 `infra/upload_config.py` 共享默认值（否则连带收紧 legacy `/api/uploads`）；同步评估 nginx——**经 8080 网关的 KB 上传当前受 nginx 默认 1M 限制，超 1M 根本到不了 8901**（600M 只在 control-plane location），需为网关上传路径单独设 `client_max_body_size` | `kb/routes/documents.py:94` 前、`docker/nginx.conf` |
| 2 | `await file.read()` → 分块循环（64KB）+ 流式 sha256 + `put_stream`（依赖第 0 项）；新签名接受 `AsyncIterator[bytes]` 返回 sha256/size；**zip 内成员从磁盘文件转流复用同一签名** | `document_service.py:108-138`、`:162-206` |
| 3 | zip 通道补解压总额度防护（zip-bomb：解压总量上限 = 成员数 × 单成员上限） | `document_service.py:162-206` |
| 4 | 修正 router.py:5-7 过时注释 | `file_management/router.py` |

验收点：上传 100MB 文件时 mining 进程 RSS 增量 < 10MB（依赖第 0 项，否则此验收不可能达成——对抗审查结论）。

### S2（P1，接线 UploadSessionService 大文件通道）

1. **装配**：`api/app.py` lifespan 增加 `app.state.upload_session_service` / `file_management_service` 的构造（组合根注入 MinIO 适配器 + PG 仓储池，与 KB 通道共用同一 `ObjectStorePort` 实例）。
2. **挂载路由**：include `file_management/router.py`（**必须同步补 current_user 鉴权**，见 08 号文档——不能裸挂）。
3. **状态机补环（对抗审查追加，CRITICAL）**：`complete` 的 `_assert_committable`（`service.py:354-364`）要求 state ∈ {OBJECT_STAGED, VERIFYING}，而浏览器 presigned 直写 MinIO 后**没有任何接口把会话从 INITIATED 推到 OBJECT_STAGED**。complete 改为"stat staging 对象成功即视同 staged"或新增 confirm-staged 端点，二选一。
4. **multipart 补实现**：断点续传依赖的 `upload_part/complete_multipart/abort_multipart` 当前全是 `NotImplementedError`（`minio.py:440-456`）——S2 若承诺断点续传，必须先补这套（依赖 S1-0 的适配器重写）；**否则 S2 降级承诺为"单次 presigned PUT 大文件"（无断点续传）**，作为第一版可接受。
5. **actor 服务端派生（对抗审查追加，HIGH）**：幂等三元组 `(kb_id, actor, idempotency_key)` 中 actor 当前是请求体自由字符串（`InitiateUploadRequest`，`router.py:89-95`）——必须改为从 `current_user` 派生、忽略客户端值，否则幂等键可伪造碰撞。
6. **登记语义合流（对抗审查升级为明确任务，MEDIUM→显式）**：两通道 `asset_documents` 字段不一致——KB 通道 `document_key=build_document_key(directory, filename)` + `directory_path` + `file_size`（`kb/db.py:848`），fm 通道 `document_key="doc:/{name}"` + `folder_id` 且缺 file_size/directory_path（`file_management/repositories_pg.py:385-405`）。complete 的"新文档"分支必须复用 KB 通道的 key 推导与目录模型，否则大文件文档在 KB 列表与挖掘关联上表现异常。
7. **前端**：按大小分流（≤上限走直传；超限走 initiate → presigned PUT → complete；失败按 idempotency_key 重试）。

### S3（P2，配额与补偿闭环）

1. `DocumentService.upload` 与 `UploadSessionService.complete` 统一经过 quota reserve（上传前）→ commit（登记后）→ release（删除/失败时）。**前置（对抗审查追加，HIGH）**：`QuotaRepository.get` 对无配额行的 KB 默认 `limit=0` 且 fail closed（`contracts/file_management.py:107-114`）——接线前必须为**存量 KB 批量 seed 配额**，否则所有上传立即 QuotaExceeded 全拒。
2. MinIO 写成功但 PG 登记失败的补偿：捕获后调 `ObjectStorePort.delete`（已存在，`contracts/storage/port.py:84`）回滚 source 对象，或写 `asset_storage_operations` PENDING 行交给 GC（与 07 号文档 P12 的 outbox 消费者合并实现——**建议后者**，与 purge/GC 共用一套执行器）。
3. staging 会话过期清理：`asset_upload_sessions` 增加 sweeper（可与 P12 GC worker 同进程），过期 abort 释放配额 + 删 staging 对象（abort 逻辑已有，`service.py:536`）。

## 6. 风险与兼容

- **S1 改动上传签名**：`DocumentService.upload` 的调用方（单文件 + zip + 可能的测试）需同步；建议保留旧签名作薄包装避免测试大面积重写。
- **S2 挂 file_management router 是安全敏感操作**：该 router 当前零鉴权，裸挂会把未鉴权写面直接暴露到 8901（P13 已实测直连可达）。**S2 必须与 08 号文档的鉴权整改同 PR 或在其后**。
- 锚点勘误（对抗审查）：quota reserve PG 实现实际在 `file_management/repositories_pg.py:593`（非 :686）；大小限制函数在 `api/routes/uploads.py:43-46`（非 :48-50）；测试挂载方完整路径为 `knowledge_mining/tests/file_management/test_file_router.py:87-89`。
- **presigned 直连 MinIO**（对抗审查修正）：MinIO 为外部端点 `121.89.90.178:19000` 明文 HTTP（compose 无该映射）——浏览器直传需评估 CORS、HTTPS、签名 URL 进代理日志的泄漏面；不可接受时回落"后端分片中转"（依赖 S2-4 multipart 补实现）。
- **nginx 反向限制**：经 8080 网关的 KB 上传当前被 nginx 默认 `client_max_body_size 1M` 拦截——S1 落地时网关路径上限必须同步调整，否则大文件直传根本到不了后端（对抗审查发现）。
- **回滚**：S1/S2 均为通道级改动，回滚 = 恢复直传路由旧实现；DDL 无破坏性变更（008 已在线上库存在）。
