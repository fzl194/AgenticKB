**清单遗漏的发现（本次审查新增，两项都重要）：**

1. **质量指标在生产链连落库都没有**。M4 主线走 `shadow.execute()`（不写投影行）；`quality_metrics` 只在 shadow `run()` 路径进 `asset_parse_runs`。**实测：真库 22 条 parse run，含 quality_metrics 的 = 0**。快照 metadata（`snapshot_store/service.py:214-231`）也只有 decision/issues 无数值。即当前生产连 evidence_locatability 等已算指标都不可观测。
2. **AttemptBudget 默认值漂移**：契约默认 `max_backend_attempts=2`（`parse_plan.py:37`），而生产 options 默认 3（`options.py:170-177`、`new_chain_services.py:188`）。当前链恒 1 无影响，但补 fallback 后语义会分裂。
3. `table_grid_consistency` 计算后（`metrics.py:97-105`）Gate 完全不消费、也不进 metadata——清单只说了前半。
4. ParserRouter 自身 M3 初版 fallback 也恒空（`file_inspector/router.py:105-106`）——**即使把 Router 接进 plan_factory，也得不到备用链**；P02 修复必须同时改 Router 与 plan_factory。
5. Run 幂等复用探针（`parse_operator/service.py:126-135`）只匹配 primary 指纹——接入 fallback 后，"曾被 fallback 成功"的 Run 不被复用判定覆盖（会重复解析，幂等性弱化）。
6. `FrozenInputService.freeze` 的 `original_filename` 恒为空串（`frozen_input/service.py:130`），快照标题回退 `title or frozen.original_filename`（`snapshot_store/service.py:139`）在生产退化为空标题。

## 3. 运行时实测（2026-08-24，真库只读）

- `asset_parse_run_attempts`：22 行，**全部 attempt_kind=primary**（legacy_markdown 21、native_pdf 1）；fallback=0；多 attempt 的 run=0。清单所述"fallback 从未实际发生"坐实。
- `asset_parse_runs` 22 行中含 `quality_metrics` 的 **0 行**——生产链质量数值完全不可观测（比清单描述更严重）。
- 存在 1 个零快照文档（王灿-…-镍基MOF…，解析失败无产物）——失败路径有记录但无质量叙事。

## 4. 根因分析

三个缺口是同一条时间线的三个断层，不是三个独立 bug：

1. **M3（路由）→ M4（编排）顺序倒置**：Router 先按"单 mime 单 parser"现实设计（fallback 恒空），M4 编排在 Router 之上又只取 registry 首个——两层都没有"链"的生产者，而执行器（消费者）与审计（attempts 表）先建好了。**执行框架等米下锅**。
2. **质量门禁设计以"有独立基准"为前提**（source_text 是外部输入），但没有任何一环负责生产这个基准——文本格式明明唾手可得（冻结源就是文本），也没接。于是 Gate 的最强武器（覆盖率）在生产恒哑火。
3. **配置表面先行**：qualityProfile/max_duration_seconds 都是契约完整、执行缺位——与 P03 的 `_no_stale` 同属"接口已定义、组合根没喂参"模式（本仓库最高频的欠账类型）。

## 5. 修改方案（分阶段）

> 主线判断：**先让质量基准落地（S1-S2），再谈第二后端（S3-S4）**。没有覆盖率基准，fallback 触发条件本身就不成立（Gate 只能靠 element_count==0 和 WARN 级信号，换了后端也无法判定是否更好）。

### S1（P0）：质量指标接线 + 可观测性

| # | 改动 | 位置 |
|---|---|---|
| 1 | 文本类格式（md/txt）从冻结源对象构造独立 source_text 传入 execute（读源已在 `shadow_parse/service.py:335-339`，聚合 bytes 即基准，零额外 IO；需把 `_read_and_parse` 的聚合 data 透出给 `_evaluate_quality`——签名改动）。**HTML 单列（对抗审查 HIGH）**：`_MEANINGFUL_RE`（`metrics.py:30`）会把标签名/属性名（div/class/href…）全计为实义字符，原始 HTML 直接当基准会系统性压低 char_coverage 造成误杀——HTML 必须先标签剥离（复用 HtmlNormalizer 文本化路径）再作基准 | `new_chain_services.py:250` / `shadow_parse/service.py:347-379` |
| 2 | PDF 用 pdfminer 第二遍文本抽取作对照基准（已有依赖；pdfminer 纯抽取比主链便宜，实际开销 <1 倍主解析；仅 strict/default 档启用） | `shadow_parse/service.py` 新增基准分支 |
| 3 | Office（docx/pptx/xlsx）文档级基准：用解包文本流长度 + 段落数/页数/幻灯片数做**结构基准**而非字符精确覆盖（精确对照成本高，先做页级锚点：expected_page_count vs IR 空页率） | 同上 |
| 4 | quality_metrics（含 char_coverage、table_grid_consistency、空页率）持久化：**必须写 parse run 投影，snapshot metadata 只是补充**（对抗审查 HIGH：FAIL/FALLBACK 的 attempt 不产生 snapshot，只写 snapshot metadata 的路线会让低质样本——恰恰是最需要观测的部分——完全不可见；`outcome.quality_meta` 需穿进 DocumentParseService 的状态写回） | `snapshot_store/service.py:214-231` + `parse_operator/service.py` |
| 5 | 按页记录 expected/observed（gate 的 empty_container_ids 已有底子 `gate.py:213-237`），文档级平均之上保留页级明细 | `parse_quality/metrics.py` |
| 6 | lenient 档"关闭 PDF 双遍基准"的开关**在编排层**（决定是否构造 source_text），不在 QualityProfile（gate 管不到基准是否计算）——对抗审查指出 S2 的档位语义需落在此处 | `shadow_parse/service.py` 基准分支 |

### S2（P0）：qualityProfile 生效 + 预算修正

1. plan_factory 读 `params["qualityProfile"]` 写入 `ParsePlan.quality_profile`；组合根按 plan 选择 `QualityProfile`（strict/lenient 阈值表补进 `gate.py:77-85`，建议 strict：coverage≥0.95/WARN≥0.99、evidence≥0.90；lenient：coverage≥0.70，仅 FAIL 级阻断）。
2. 统一 AttemptBudget 默认值（契约 2 → 3，或 options 3 → 2，取一；建议契约跟 options 走 3）。
3. `max_duration_seconds` 接线：`asyncio.to_thread` 包 `wait_for`（解析器不可中断时超时后放弃该 attempt、标 TIMEOUT，与 fallback 推进逻辑天然衔接）。

### S3（P1）：真实 fallback 链（无新外部依赖版）

1. plan_factory 遍历 registry 时**收集全部** `supports(mime) && license ok` 的 parser 排序成链（当前每 mime 恰 1 个 → 链长仍 1，但机制通、RouteDecision 可版本化记录）。
2. FileInspector 接入：扫描 PDF（无文本层/页数异常/表格密度）→ 生成 RouteDecision（版本化、写入 plan.reason_codes）。
3. 语义修复：**mime 内主备**而非"换格式"。现实可落地的第一组：**新增薄适配器 `pdf_text_layer`**（pdfminer 纯文本层抽取，~60 行——对抗审查确认 `pdfminer.high_level.extract_text` 单入口可行，注册进 `factory.py:64-74` 的 `_PIPELINE_FACTORIES` 即自动入 registry；结构全丢但内容可保，char_coverage 可守住）→ 链变 `native_pdf → pdf_text_layer`。**注册顺序约束（对抗审查 MEDIUM）**：plan_factory 与 Router 都取"首个 supports+license ok"，`pdf_text_layer` 必须排在 `native_pdf` 之后注册，否则反客为主成 primary——需为顺序加契约测试。注意**不能**用 legacy_txt 当 PDF 兜底（它只解析 text/plain，`legacy_txt.py:27`，喂 PDF 字节必失败——初稿曾犯此错，对抗审查前自行修正并留档）。
4. 修 Run 幂等复用探针覆盖 fallback 成功的 Run（复用指纹改为 chain 级）。
5. **REPAIR 分支是死代码，必须改 `_resolve_decision`（对抗审查 CRITICAL）**：`execute` 在 `service.py:199` 先调 `_resolve_decision`，后者（:367-398）**无条件**把 REPAIR 降级为 WARN（不感知链长）——L225 的 `("FALLBACK","REPAIR")` 里 REPAIR 永不可达。接链后空页 REPAIR 仍会以 WARN 提交而非推进链。修法：`_resolve_decision` 增加 `attempt_index/chain` 参数，链有余量时透传 REPAIR。**"接链后自动生效"的原判断是错的**。

### S4（P2）：第二解析后端（产品决策前置）

三选一（按数据外发容忍度排序）：
- **A. docling 本地引入**：license 审核后从 `pending_review` → `ok`，实现工厂条目；适合扫描 PDF + 复杂表格；代价：镜像 +~2GB、CPU 推理。
- **B. cloud_vlm 受控接入**：provider/endpoint/超时/脱敏白名单进配置；扫描件 OCR 质量最好；代价：数据外发合规评审。
- **C. 暂不引入**，S3 的保底链 + 质量基准已能挡住"静默低质"，S4 挂起。

**建议**：先 C 后 A——在 S1 质量基准跑出真实低质样本分布（多少 PDF 覆盖率 <85%）之前，引入重后端是盲投。

## 6. 风险与兼容

- S1-2 PDF 双遍解析使 PDF 耗时上升（pdfminer 纯 extract_text 比主链 pdfplumber 便宜，实际通常 <1 倍主解析——对抗审查修正原"×2"的保守估计）；用档位开关控制，且基准抽取失败不阻断主链（降级为 None 并记 warning）。
- S3 保底链 `native_pdf → pdf_text_layer` 会在质量差时**放弃结构化产物换内容完整性**——Snapshot 语义需明确"fallback 产物也是合法快照"，UI 需展示 attempt 链让用户理解产物形态变化。（初稿 §6 曾残留 `native_pdf → legacy_txt` 错误配对，对抗审查抓出，已改。）
- S2 超时接线（对抗审查 HIGH 修正）：`asyncio.wait_for` + `to_thread` 是**伪超时**——超时后线程继续占 CPU/内存直至自然结束，且共享 executor 线程池会被批量超时耗尽、阻塞后续所有文档解析。必须配套：泄漏线程计数/熔断、被弃协程禁写或幂等写。另 **TIMEOUT 落库与词表矛盾**：attempt outcome 词表 `{SUCCEEDED, FAILED}`（`shadow_parse/contracts.py:53-55`，与 010 DDL CHECK 对齐）——超时记 FAILED + error_message 标 TIMEOUT（无 DDL 变更），或改词表（有 DDL 变更），**取前者**（原"无 DDL 变更"承诺由此保住）。
- **灰度前置（对抗审查 MEDIUM 采纳）**：S1 质量基准对存量 22 个 legacy_markdown run 重挖时首次生效——若 legacy MD 解析器天然丢字符（去重/合并），可能批量 <0.85 FAIL，文档从"可入库"变"不可入库"（行为回归）。上线顺序：先 WARN 观察一轮真实覆盖率分布，再启用 FAIL 阻断。
- 回滚：全部为组合根/工厂层改动，逐项独立可回滚；无 DDL 变更（TIMEOUT 采用 FAILED+message 方案）。
