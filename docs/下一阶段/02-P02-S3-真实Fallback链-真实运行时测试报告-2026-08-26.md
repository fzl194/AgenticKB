## 一、交付内容复核

- 新增 `pdf_text_layer` 适配器（pdfminer 文本层提取 + PdfNormalizer），注册于 `native_pdf` 之后（`_PIPELINE_FACTORIES` 插入序即 registry 序，Router 与生产 plan 同源）。
- `ParserRouter._select_locals`：按注册序返回全部可用 local 后端，primary=首个、fallback=其余；扫描件（`has_text_layer is False`）fallback 置空。
- `DocumentParseService._resolve_decision`：REPAIR 且链上还有后端 + 预算未耗尽 → 升级为 FALLBACK；无后端时保留 M4 的 WARN 兼容语义。
- workflow `default_plan_factory`：`fallback_parser_ids=parser_ids[1:budget.max_backend_attempts]`，plan_id 仍按 primary 命名（幂等探针兼容）。
- pdfminer.six 已在 pyproject（infra 既有依赖），镜像无需变更。

## 四、观察与留档（非阻塞）

1. **ParserRouter 未接线到生产挖掘路径**：workflow plan 由 registry 顺序直接构链，不消费 `has_text_layer`。扫描件的实际保护来自 FAIL 终态语义而非「空 fallback」——交付件中「避免伪降级」的声明只在（当前未接线的）file_inspector 路由面成立。真正的扫描件治理属 S4（OCR/第二解析后端，待产品决策）。
2. `metadata_json.quality_attempts[]` 条目无 `kind` 字段（primary/fallback）；`asset_parse_run_attempts.attempt_kind` 已正确填充，纯观测口径差异。
3. 批次直跑通道（`upload_batch_id` 无 `kb_id`）不支持 v2 解析链（`document_parse_unavailable`），与 master 同构——本次测试先误走此通道后纠正，属测试方法论踩坑，非缺陷。
