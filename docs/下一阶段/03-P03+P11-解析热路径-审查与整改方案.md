**清单遗漏的发现（本次审查新增，其中第 1 条使 P03 比清单更严重）：**

1. **生产链根本没走 `freeze()`——是"双空转"**。`DocumentParseFacade._parse`（`new_chain_services.py:232-249`）**内联手搓 `FrozenInput`**（`captured_at="1970-01-01..."` 占位值），既绕过了 freeze 的 `AVAILABLE` 状态校验（`frozen_input/service.py:53,107-112`），又叠加 `_no_stale`。清单只发现了后一半。
2. `snapshot_store/service.py:22-23` docstring 自称"生产编排层注入 check_stale"，与组合根实际注入空函数**直接矛盾**——留档这对矛盾，防止后来者按注释理解。
3. `freeze()` 的 `original_filename` 恒为空串（`service.py:130`），快照标题回退链（`snapshot_store/service.py:139`）在生产退化为空标题。
4. **legacy 链不写 revision 戳**：真库 5 个 legacy 文档（test/new_doc/good/readme 等，links 共 48 条）`source_content_revision` 全为 NULL，文档 `content_revision=0`。而结构化读取按 `source_content_revision` 过滤（`snapshot_store/read_service.py:57-62`）——legacy 快照在 revision 过滤下如何被命中需要迁移补数（见 S4）。
5. 生产无任何接通的内容替换路径（file_management router 未挂载，见 01 号文档），所以当前触发窗口确实近乎为零——与清单"demo 难触发"一致。

**清单遗漏的发现：**

1. **MinIO get_stream 本身先整份落临时文件**（`infra/object_store/minio.py:235-252`：`tempfile.mkstemp` → 整对象写盘 → 再分块读回）。即源对象路径是"MinIO→磁盘临时文件→64KB chunks→join 成完整 bytes→parser"四跳，**内存整包是第三跳人为制造的**——磁盘临时文件这层意味着修复素材已经在手。
2. **`materialize_temp` 已存在但热路径未用**（`source_reader.py:122-146`，run 级临时文件落盘）——修复 P11 不需要新基建，是把现成能力接进 `_read_and_parse`。
3. 并发度现状：workflow 链 DocumentExecutor `max_workers` 默认 **1**（`workflow/runtime.py:46,91`）；legacy 链各 stage max_workers=4（`run.py:2180-2191`）但 parse/segment/db_write 并发=1——**当前实际近乎串行，内存叠加风险主要来自单文档大小而非并发**。这把 P11 的紧迫度从"并发爆炸"修正为"单文件上限无界"。
4. Parse IR 序列化侧同样整包：`json.dumps(doc.to_dict())` 一次成型（`shadow_parse/service.py:392-394`）。

## 3. 运行时实测（2026-08-24，真库只读）

- 快照 vs 当前内容：21 文档最新链接 **真实错配 0**（P03 无数据事故结论坐实）；但 6 个文档最新链接 revision 为 NULL（legacy 链遗留），1 个文档（王灿-…）零快照（失败解析）。
- source bucket 最大对象 ~14MB 级（10 个对象），当前单文档体量小——P11 是规模风险不是现役故障，与清单判断一致。

## 4. 根因分析

两个问题共享同一根因模式：**契约/服务层按工业标准建成，workflow 组合根（`new_chain_services.py`）在产品化赶工时用最小实现占位**——手搓 FrozenInput、`_no_stale`、join 整包，都是"先跑通再回头接线"的占位代码，且没有留 TODO 追踪，于是占位变成了事实标准。P03 的 stale 检查与 P11 的流式读取在 `shadow_parse/service.py` 同一函数族里，**一次改造可以同时收口**。

### S2（P1）：P11 内存治理——分格式输入策略

**方向修正**：契约 v1.1 的"bytes-only"是刻意设计（无网络/文件 IO、可重放），**不建议直接推翻**。方案是给它加一个受控的兄弟形态：

1. **契约演进 v1.2**：`ParserAdapter.parse(data=None, *, path=None, mime=...)`——`path` 为受控临时文件（spool），adapter 二选一；对抗审查逐一核实：pdfplumber/Presentation/python-docx/load_workbook **全部原生接受路径**（当前实现分别经 `BytesIO` 中转：`native_pdf.py:110`、`native_pptx.py:99`、`native_docx.py:93`、`native_xlsx.py:88-89`——注意 xlsx 开两次，path 形态是同一路径开两遍，契约测试需覆盖）。**同步改写契约文本**：`parser_adapter.py:359-360` 的 "no filesystem IO" 声明与重放不变量需显式修订（sibling 形态放弃了该纯度承诺），不只是加参数过测试。
2. **热路径**：`_read_and_parse` 对 `mime ∈ {pdf, docx, pptx, xlsx}` 改走 `materialize_temp` → 传 path。**（对抗审查 HIGH 修正）**materialize_temp 确已流式算 sha256 并比对（`source_reader.py:135-141,148-170`，不匹配抛 StorageObjectCorrupt）——原"需确认"可定案；但接通后路径是 **MinIO→get_stream 的 tmp1→64KB 读回→materialize 的 tmp2 双重临时文件**——真正省内存/IO 需给 MinioObjectStore 加 `get_to_file(location, path)` 直落盘（与 05 号 S2-4 同一改动，**归并实施**），materialize_temp 直接吃文件。
3. **清理生命周期（对抗审查 HIGH）**：`cleanup_temp` 当前生产零接线——需在 run 生命周期四个出口（成功/失败/取消/恢复）挂清理，且 P07 daemon 线程模型下"进程死亡"出口无人执行：**启动时扫描 tmp_root 陈旧 run 目录**列入验收（与 06 号 S1 启动扫描同批）。
4. **tmp 配额**：容器内 tmp_root 需显式指向（默认 /tmp 可能仅 64MB 或与根分区共享）——500MB 单文件上限 × 并发文档数可能写满磁盘；配额监控与告警列入运维项。
5. **文本格式**（md/txt/html）：维持 bytes 聚合但加上限（如 32MB，超限拒绝并提示走大文件通道），同时这份数组**直接复用为 P09 的 source_text 基准**（02 号 S1）。**接口形状（对抗审查 MEDIUM）**：谁持有 chunks、解码后 str 还是 bytes、32MB 上限对字节还是字符——与 02 号同批定义，避免并行实施撞车。
6. **背压与预算**：Run 级加"同时解析文档数"信号量；单文档 source_size 超配置上限（默认 500MB）直接拒绝入 Run。
7. **观测**：Run metadata 记 source_size / parse 耗时 / IR 大小——为容量基线积累数据（当前完全没有）。
8. **序列化侧**（后置）：`json.dumps` 整包 → 分块流式写（encoder iterencode + 64KB 切片），与 get_stream 对称。

### S3（P2）：三处同构 join 收口

`parse_operator/service.py:461-464`（replay）、`snapshot_store/read_service.py:169`（IR 回读）、`segment_compiler/service.py:135`（编译读 IR）——replay/raw 与 IR 读取各自按需改 tempfile 直读。**（对抗审查修正措辞）**"json.load(fh) 直吃句柄省 join+loads 双份"依赖**尚不存在**的 `get_to_file()`（get_stream 不暴露句柄/路径，tempfile 在 finally 已 unlink）；且收益仅省 join 一份字节拷贝，json.load 内部仍整读构建对象图——真实峰值改善来自 05 号的分页/缓存改造而非此处。IR 回读与 05 号（P05）是同一处，**归并到 05 号 S2 实施**，本方案不重复列。

### S4（P1，数据补齐）：legacy 链 revision NULL 迁移

**（对抗审查 HIGH 修正补数规则）**原"按文档当前 content_revision 一刀切补 0/1"存在反例：`file_migration/service.py:446-461`（`_switch_pointer`）在 legacy 文档迁移 MinIO 时也会 `set_current_content` 使 revision 0→1，而其 legacy 快照是迁移前 revision=0 时产生的——一刀切会把旧快照错标 1，恰好制造想消除的错配。修正规则：
- 文档当前 `content_revision=0` → 链接补 0（安全）；
- `>0` 的 legacy 文档 → 按快照 `created_at` vs 文档 `content_updated_at` 逐条判定，不适用一刀切；
- 当前真库 5 个 legacy 文档 revision 全 0（实测），本次未踩雷，但规则必须按上述写死。
补数前备份 links 表。这是 S1 生效后 revision 过滤对 legacy 快照正确命中的前提。
