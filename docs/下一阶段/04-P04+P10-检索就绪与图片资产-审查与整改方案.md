4. **没有任何 readiness 概念存在于代码/UI**（全仓 grep 无命中）——清单建议 1 是从零新建，不是接线。
5. Java KB scope 是 **per-document** 解析（`selectLatestKbSnapshots`：`DISTINCT ON (document_id)` 取每文档最新 validated/published build 的 active selection，`AssetBuildDocumentSnapshotMapper.xml:36-57`），不是"KB 最新 Build 再取 selections"。这个语义对 07 号（P08）的 tombstone 方案是**关键利好**：removed 决策天然压住旧 active。

## 4. 根因分析

- **P04 是"状态语义缺口"而非"功能缺口"**：fast_retrieval 范式、RU/embedding 算子、Java 召回 SQL 全部存在，但 (a) demo KB 选了 minimal；(b) validate_build 不按范式能力校验；(c) 无 readiness 表达。三者叠加制造了"validated"一词的系统性误导。
- **P10 是"控制面先行、数据面断头"**：检测/建模/契约/bucket/编译策略五层都建了，唯独"字节进 MinIO"这一跳没人写——因为这一跳需要 Parser 契约（bytes-only，D-028）向外传 payload，触犯了 v1.1 的封闭性设计，被留到了"以后"，然后就没了下文。

## 5. 修改方案（分阶段）

### P04 部分

**S1（P0）：范式切换 + readiness 派生（不改执行语义，先消除误导）**

1. **产品决策（需用户拍板，二选一）**：
   - A. KB 默认范式切 `fast_retrieval`（KB 创建默认值 + 存量 KB 迁移开关）——目标"KB 就是给 Agent 检索的"；
   - B. 保持 minimal，但 UI/API 明示"该 KB 仅解析入库，未启用检索"。
   - **建议 A**：三个 demo KB 的存在意义就是检索演示；minimal 作为显式降级选项保留。
2. **readiness 派生视图**（无 DDL，纯查询/物化视图）：按 KB 汇总 `docs / segments / units / embeddings / embedding_fallback_docs`，推导 `parsed → segmented → lexical_ready(units>0) → vector_ready(embeddings>0 且 fallback 数=0)` 四档；挂到 KB detail API + kb-ui 概览卡片。
3. **validate_build 按范式能力校验**：含 `retrieval_units` 能力时，validated 前置条件加"每 active snapshot ≥1 unit"；含 `embedding` 时加"units 中 ≥1 有 embedding，或 metadata 记录 embedding_fallback"（FALLBACK 不阻断但**必须留痕**——修发现 1 的静默）。**能力来源的时点问题（对抗审查 HIGH）**：validate_build（`publishing.py:240-286`）签名只收 (asset_db, build_id)，build 行不带 manifest——应改为 **assemble_build 时把 capability 集冻进 build.summary_json**（validate 直接读 build 行，不 join mining_runs；legacy 引擎产的 build 无该字段→降级为现行三条检查，语义向后兼容）。
4. demo_quality_summary 的 `_fetchall` 直查改走仓储接口（顺手治）。

**S2（P1）：检索端到端验收**

新增验收（CI 门控，PG+MinIO 真环境）：上传 → 挖掘（fast_retrieval）→ Java serving 按 KB scope 查询 → 至少一条 FTS 命中正确证据 → dense 通道非空（嵌入服务可用时）。这是清单建议 5 的落地，也是 P04 整改的"完成定义"。

**S3（P2，可选）**：FTS 直查 raw_segments 的降级通道（minimal KB 未建 unit 时兜底）——**不建议做**：与其加第二条召回 SQL 语义，不如 S1-A 直接保证 unit 必建（retrieval_unit_build 的 raw_text unit 本来就每 segment 一个）。列在此处仅为完整性。

### P10 部分

**S1（P1）：Parser artifact 契约 v1.2 携带二进制 payload**

1. `BackendParseArtifact` 增加二进制通道——**首选引用形态而非 bytes（对抗审查 HIGH 修正）**：`binaries: dict[binary_asset_id, BinaryRef]`（BinaryRef = sha256 + size + 本地临时路径/spool 句柄），持久化阶段流式 `put_stream`；bytes-in-artifact 仅作小图（如 <1MB）快捷路径。理由：`dict[id, bytes]`（上限 50MB）正是 P11 批判的"artifact 整包驻留内存"的加强版，与 03 号治理目标自相矛盾。契约演进与 03 号 S2 的 path 输入**同批定稿 v1.2**（一次 bump，同时收 path 输入与 binaries 输出引用形态）。
2. `ShadowParseService` 持久化阶段扩展：遍历 `ParsedDocument.binary_assets` → `build_object_key("binary", sha)` → `put_stream` → `asset_storage_objects` 登记（artifact_class=binary）→ FigureAsset.original_image_ref 保持逻辑 id，另在 FigureAsset 增补 `storage_object_id`（或经 binary_assets[id]["storage_object_id"] 回填——取改动小者）。**（对抗审查 MEDIUM 前置）**对象登记必须在物化同一事务内同步落 `asset_storage_objects` + snapshot 级引用行——否则首版物化产物无引用记录，07 号 GC 后补建模需回溯。
3. PPTX 先行（唯一有字节的格式），DOCX 第二刀（python-docx 的 image part blob 可直接取，`native_docx.py` 的 blip 计数处升级为提取）；HTML/MD 的远程图片冻结抓取、PDF 页面渲染后置（S3）。

**S2（P2）：figure 检索内容闭环**

1. **扩展 Reconciler `_rule_caption_binding` 的 target 到 figure**（图片下方最近文本框→figure 的 caption 候选关系；PPTX normalizer 配合标记候选）——这是 figure 切片非空的前提，且是唯一正确的主刀位置（对抗审查定案：caption_of 的实际生产点是 reconciler 而非 normalizer）。
2. HTML `alt` → caption 回填。（include_figure_captions 默认已是 True，无需开关动作——对抗审查纠正初稿误判。）
3. `derived_annotations`（契约已留）作为 VLM/OCR 描述的挂点，产物**只追加不覆盖**原图与原始 caption。
4. 引用计数：binary 对象登记时写入 source snapshot 引用（与 07 号 P12 GC 共享引用计算）。

**S3（P3）**：PDF 内嵌图提取 / 页面 crop 渲染；XLSX 图表导出为图片。依赖 S1 的物化框架，逐格式排期。

## 6. 风险与兼容

- S1-A 范式切换对存量 KB（**对抗审查 CRITICAL 修正**）：不存在"增量补 RU 作业"的需求也不存在该机制——现成机制是**范式签名自动 force_redo**（`kb/routes/mining.py:130-153`：signature = workflow_id:version:graph_hash 与上一完成 Run 比对，不同即自动全量重挖）+ `clear_snapshot_derived_assets`（`jobs/run.py:1108-1116`：不清空旧派生资产则 persist 见已有切片会跳过、零写入）。**正确操作：PATCH `mining_workflow_id` → 点一次"更新知识"，自动完成全量重生**。评估点因此改为"全量重挖成本"（重解析 + LLM 嵌入全量重放，非分钟级补跑）。
- **切换前清未终态 Run（对抗审查 MEDIUM）**：范式切换若发生在 KB 有 interrupted/running Run 期间，resume 的 Run 仍按旧 binding 跑完、随后签名变更又触发 force_redo 重挖一遍（浪费一次恢复执行）——切换前先让该 KB 的未终态 Run 收敛（resume 完毕或 cancel）。
- embedding 依赖 llm_service（:8900）可用性：S1-3 的留痕机制是关键，否则 FALLBACK 又是静默。
- P10 契约 v1.2 与 03 号 S2 的契约演进**必须同批定稿**（一次 bump 到 v1.2，同时收 path 输入与 binaries 输出），fingerprint 契约测试整批更新。
- binary 物化后 MinIO 容量开始真实增长——P12（07 号）的 GC 不上线，binary 对象只进不出，需在 S1 里同步登记引用（为 GC 预备）。
