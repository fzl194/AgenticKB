**清单遗漏的发现（本次审查新增）：**

1. **get_stream 的"流式"是落盘再分块**：`infra/object_store/minio.py:235-252` 先整对象下载到 tempfile 再按 64KB 产出。叠加 `_load_ir` 的 join+loads，一次 parse-result 请求 = **磁盘整份文件 + 内存完整 bytes + 反序列化对象图** 三重全量。清单只讲了后两重。
2. **outline 与 tables 在响应层也无界**：千级 heading/表格的超大文档，HTTP 响应体本身可无限膨胀——即使不做内存改造，也该先补响应层 limit。
3. **ETag 素材已在手未用，但语义有裂缝（对抗审查 HIGH 修正）**：`read_service.py:77` 的 `snapshot_fingerprint` 是**输入身份哈希**（`contracts/snapshot_store.py:49-74`：对 domain/source_raw_hash/pipeline/compiler_fingerprint/workflow 五字段 JSON 做 sha256），**不是 IR 对象内容哈希**。对 IR 派生部分（snapshot/outline/elements/tables）作 ETag 安全；但响应中的 **segments 来自 PG segment 表**——`replace_for_snapshot` 重编译替换、字段迁移回填、手工修数都会"segments 变了而 fingerprint 不变"→ 304 错误命中。ETag 必须混入 segments 维度（如 `fingerprint:segments_max_updated` 复合值）。
4. **放大链**：文档详情页打开（无论停留哪个页签）→ 全量 IR 下载+反序列化。多用户开多文档即叠加。前端还有刷新重复全量（无任何缓存头）。

## 4. 根因分析

- **P05**：`get_parse_result` 是"一个接口返回整个结构化世界"的早期形态，后来 b8ba6cf 修了**原文件预览**链路（presigned 直连/流式/分段），但**结构化数据**链路没有跟着改——前端重构（可折叠卡片）只动了展示层，后端仍在"整份读、内存截"。读写两端改造节奏错位。
- **P06**：KB 路由切换完成了热路径迁移，但旧入口没删——本仓库"迁移不收口"模式的又一例（与 P13 的 legacy 路由家族同源，但 P06 是死码、P13 是活裸奔，处置不同）。

### P05（P2，按投入产出排三刀）

**S1（第一刀：前端懒加载 + 响应层限界——kb-ui 迭代顺手做，后端只加 limit）**

1. `loadParseResult()` 从 `load()`（:550）挪到"结构化数据"页签首次激活（el-tabs `@tab-change` **新增绑定**——当前无现成挂点，对抗审查确认改动小但非复用）+ `loaded` 标记；预览页签用户（占多数）不再触发任何 IR 读取。下载/复制走独立 API（`downloadDocument`/`getDocumentKnowledge`），不依赖 parseResult 已加载（对抗审查核实零连带）；:96 的重试按钮保留。
2. 后端补响应层 limit：outline ≤200（超限截断+`truncated:true`）、tables ≤50、每表行数维持 5、**preview 单元格加字符上限**（header/preview 文本当前无截断——对抗审查补充）。此项同时防响应体撞代理缓冲上限（与请求侧 client_max_body_size 对称的响应侧问题）。
3. segments 分页：`?segment_offset=&segment_limit=`——**需扩展 Protocol 及三处实现**（`segment_compiler/service.py:65-69` 签名、memory/PG 两个 repository、测试 fake；对抗审查指出括号里"支持 offset"的原文像已有能力，实际没有）。若 S2 拆接口排期紧随其后，本项可并入 S2-1 避免重复劳动。
4. **懒加载配套（对抗审查 MEDIUM）**：结构化页签 label 上的 quality_status 徽标依赖 `parseResult` 非空——懒加载后未激活前徽标消失（行为变化，可接受但需知会）；`openCards` 默认五卡全开（:362）+ outline `default-expand-all`（:139）在千级节点下 DOM 成本高，懒加载落地时把 elements/segments 卡默认收起。

**S2（第二刀：后端读模型改造——独立分页接口 + 缓存）**

1. 拆分接口：`GET .../parse-result/outline|elements|tables|segments` 各自 `offset/limit`；聚合端点保留兼容（内部调子接口）。
2. **ETag**：**复合值** `snapshot_fingerprint + segments 内容版本`（如 `f"{fingerprint}:{segments_max_updated_or_count_hash}"`，对抗审查修正——单用 fingerprint 会因 segments 表独立变更而 304 错误命中，见第 1 节发现 3）+ `Cache-Control: private, must-revalidate`；If-None-Match → 304。
3. **内容缓存（可选）**：进程内 LRU（容量按字节计，如 64MB）——**只缓存 IR 派生部分（snapshot/outline/elements/tables），segments 每次查库**，或缓存聚合体但加 TTL（5-10 分钟）兜底 segments 变更（对抗审查 HIGH：无 TTL 且键只含 fingerprint 时，重编译替换/迁移回填会命中过期 segments）。
4. `_load_ir` 改 `json.load(fileobj)` 直读——依赖 MinIO 适配器新增 `get_to_file()`（`_get_to_file_blocking` 已在 `minio.py:254`，公开薄封装即可，比预想还小）；收益仅省 join 一份字节拷贝（json.load 仍整读构建对象图），真实峰值改善靠本项+S3 分页组合。

**S3（第三刀：大 IR 分片——超大文档专项，明确后置）**

manifest + 按页/章节内容寻址分片对象 + PG 轻量目录（element_id→chunk）——仅在出现单 IR >20MB 的真实文档后立项，当前 2.1MB 总量下不投入（YAGNI）。清单建议 4/5 归此档。

## 6. 风险与兼容

- S1 前端懒加载改变行为：切页签才加载——需处理"页签激活时 loading 态"与错误重试，避免用户切过去看到空白（kb-ui 已有骨架组件可复用）。
- S2 接口拆分保持旧聚合端点不变，前端渐进切换。
- **缓存失效正确性（对抗审查改写）**：`snapshot_fingerprint` 是输入身份哈希（五字段 JSON 的 sha256，`contracts/snapshot_store.py:49-74`），**不是** IR 对象内容哈希——初稿"hash 来自对象 sha，天然成立"是事实错误。segments 变更（`replace_for_snapshot` 重编译/字段回填/修数）不改变 fingerprint。ETag 与 LRU 均须按 S2-2/S2-3 的复合键/TTL 方案，"绝对安全"措辞作废。
- P06 删除唯一风险是"有未知外部调用方"——已全仓检索（后端零 import、前端零调用），且旧 URL 404 已持续多版本无人报障，删除窗口安全。
