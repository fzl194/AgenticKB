**清单遗漏的发现（本次审查新增）：**

1. **僵尸 Run 已真实存在**：实测真库有 1 条 `status='running', stage='mining', started_at='2026-08-21T07:35'` 且 `finished_at IS NULL` 的 Run——**滞留 3 天无人接管、无人标记**。这不是假设风险，是已发生且持续发生的事实（每次容器重启都会再生一批）。
2. **`interrupted` 状态有入口无出口**：schema/resume 都认 'interrupted'（`contracts/models.py:104`、`runs.py:1421`），但生产代码**没有任何路径写入它**——`interrupt_run`（`runtime/__init__.py:77-78`）与 `get_interrupted_runs`（`infra/db.py:1285-1286`）零调用方。S1 修复的素材（函数）已经写好，和 P03/P11 一样是接线题。
3. **resume 线程没有 _mark_thread_failure 兜底**（`runs.py:1485-1495` 异常只 logger.error）——resume 崩溃时 Run 卡中间态，与首跑不对称。
4. `_run_locks` 永不清理（内存泄漏级轻微）且**重启后锁归零但 DB 残留 running 行不阻塞新 Run**——同域可立刻再跑一个 Run，与僵尸行并存造成状态噪音。
5. `started_at/finished_at` 是 **TEXT ISO 字符串**（`002_...sql:27-28`）不是 timestamptz——做 lease/超时判定前的额外摩擦。
6. cancel 在 `current_stage='publishing'` 被拒（`runs.py:1219-1234`）与发布 advisory lock 配套——这是**正确设计**，留档避免误改。
7. 文档处理并行度（**对抗审查修正论据**）：`workflow/runtime.py:46,91` 的 `getattr(..., "max_workers", 1)` 默认值在生产**不可达**——`jobs/run.py:1287/:1325` 总是注入 `MiningConfig().max_workers`（默认 4，`infra/mining_config.py:36`）。结论方向不变（并发度有限），但正确锚点是 config 默认而非 getattr 兜底。**执行模型改造与并发度扩展是两件事**，别混在 P07 里做。

## 3. 运行时实测（2026-08-24，真库只读）

- mining_runs：completed 48 / failed 7 / **running 1（僵尸，2026-08-21 起）**。
- 该僵尸 Run 按 `_is_run_resumable` 判定（running && finished_at IS NULL）**当前即人工可 resume**——但 3 天来无人处理，证明"人工 resume"作为恢复闭环在实践中不成立。

## 4. 根因分析

执行权与状态持久化是**同一批人（线程）写同一批行**，没有认领协议——数据库只是线程的记事本，不是任务队列。于是：

- 进程死 → 记事本停在"进行中"且永远没人翻页（发现 1 的僵尸即证据）；
- 两个实例 → 各写各的记事本，互相不知情（_run_locks 进程内）；
- "恢复"只能靠人肉看到记事本再点按钮。

修复方向不是"把线程改结实"，而是把**认领协议**引入数据库层——代码素材（interrupt_run、CAS resume、advisory lock 模式）都已存在。

## 5. 修改方案（分阶段）

### S1（P0，最小闭环：启动自愈——不引架构变更，当天可上）

| # | 改动 | 位置 |
|---|---|---|
| 1 | lifespan 启动时扫描：`status IN ('queued','running') AND finished_at IS NULL` 的 Run → 全部标 `interrupted`——单实例部署下"进程重启"即"执行者全灭"（对抗审查核实：单 program、uvicorn 无 workers/reload 参数 `__main__.py:50`、mcp/main_control 均不执行挖掘——判定安全）。**注意** `interrupt_run`（`runtime/__init__.py:77-78`）签名只收 counters 不写 metadata——附 `interrupted_by=restart` 需扩展该函数或走 update_run_status 的 metadata 通道（对抗审查 MEDIUM） | `api/app.py` lifespan |
| 2 | 标记后自动 re-enqueue：默认**开**，可配置关。**按引擎分流（对抗审查 HIGH）**：`_is_run_resumable`（`runs.py:1420-1424`）里 `interrupted` 仅 workflow 引擎可续，legacy Run 被标 interrupted 后 resume 会 400——**workflow Run 自动 re-enqueue，legacy Run 只标 interrupted 留人工**。且 re-enqueue 成本语义是"未完成文档全量重放"（`workflow/runtime.py:63-64` resume=execute 全图重跑，committed 文档幂等跳过）而非节点级续跑——风暴控制：跨 domain 限并发（信号量 ≤2），同 domain 本就受域锁串行 | 同上 |
| 3 | resume 线程补 _mark_thread_failure（对称性修复） | `runs.py:1485-1495` |
| 4 | 僵尸 Run 处置：S1 上线即自动清理（实测那条 2026-08-21 的行会被首个重启周期回收） | — |
| 5 | **不可用现有 CAS 充当认领（对抗审查 HIGH）**：`resume_running` 的 expected_statuses 含 `"running"`（`runtime/__init__.py:107-111`）——两个并发 resume 都会 CAS 成功各自执行，它只挡终态不挡双执行。S1 单实例下靠进程内锁兜底可容忍；S2 必须新写认领 CAS（worker_id 维度） | — |

**为什么"重启即全标"在当前是安全的**：单实例（supervisord 一份 mining program）、执行线程在本进程内——进程起来时不存在"别的进程还在跑"的可能（对抗审查逐项核实成立）。多实例化之前必须先上 S2。

### S2（P1，认领协议：租约 + DB 级域锁）

1. **DDL 增列**：`mining_runs` 加 `worker_id TEXT / lease_until TIMESTAMPTZ / heartbeat_at TIMESTAMPTZ / attempt_no INT`；顺带 `started_at/finished_at` TEXT→TIMESTAMPTZ 迁移（**对抗审查补充**：`kb/routes/mining.py:140` 已有 `ORDER BY finished_at` 的 TEXT 排序依赖，双写过渡期必须统一写入格式，否则新旧 isoformat 混排出错序）。
2. **执行器侧**：新认领 CAS `UPDATE ... SET worker_id, lease_until=now()+5min WHERE id=? AND (worker_id IS NULL OR lease_until<now())`；执行循环每 30s 续 lease；认领失败说明被接管，本线程自杀。
3. **接管判定**：S1 的启动扫描从"重启全标"升级为"`lease_until < now()` 才标 interrupted + re-enqueue"——多实例安全。**排队超时真空（对抗审查 MEDIUM）**：租约只覆盖已认领 Run——**queued 但从未被认领的 Run 无超时机制**，worker 全挂时它们永远排队。补：queued 超过阈值（如 1h）标 failed + `never_claimed`。
4. **域级互斥（对抗审查 CRITICAL 重写）**：原"换 pg_try_advisory_lock（run 级 key）"方案有三重错误——(i) 参考模板 `acquire_domain_publish_lock` 是 **xact 级**锁，事务提交即释放，不能套分钟级 Run；(ii) session 级锁绑定取锁连接，而执行链路用 psycopg 连接池（`run.py:289-312`，max_idle=300 会回收轮换），Run 线程必须**独占一条不入池的专用连接**才能持锁到 Run 结束；(iii) **key 粒度写错**：`_run_locks` 的语义是域级互斥（同域 409），run 级 key 不提供该保证。**修正方案**：domain 级 key + session 级 `pg_try_advisory_lock` + 专用连接；或更简——直接用行锁 `SELECT 1 FROM mining_runs WHERE domain=? AND status IN ('queued','running') FOR UPDATE` 做域互斥（避免连接绑定问题，推荐起步）。进程内 dict 删除。
5. **cancel 增强**：UPDATE 时同时置 `cancel_requested=true`，执行器检查点读取（协作取消保持，但状态对多实例可见）。

### S3（P2，架构分离：独立 Worker 进程）

1. supervisord 增加 `mining-worker` program（同一镜像，入口 `python -m knowledge_mining.mining.worker`）：循环 `SELECT ... WHERE status='queued' AND lease_available FOR UPDATE SKIP LOCKED LIMIT 1` 认领执行。
2. API `/mine` 与 resume 只写 queued 行不再起线程（现有 `jobs.run.run` 调用整体迁移到 worker 入口）。
3. 单实例先跑通（worker 数=1），多 worker 随 S2 租约天然支持。**SKIP LOCKED 与域互斥是并存不是替代（对抗审查 MEDIUM）**：两个 worker 可同时认领同域两个 queued Run——S2-4 的域级互斥必须在 S3 保留叠加，或认领 SQL 加 `AND NOT EXISTS (同域 active run)`。
4. **明确不引入外部队列**（Kafka/RQ 等）：mining_runs 表 + SKIP LOCKED 已满足规模，少一个组件少一分运维（清单建议 4 的取舍说明）。
5. worker 可观测性（对抗审查 MEDIUM）：worker liveness 告警 + 排队超时兜底（S2-3），否则"线程 start 失败至少标 failed"的现有保证（`mining.py:223-236`）在拆分后反而丢失。

## 6. 风险与兼容

- S1 "重启全标"在误双开实例时会把活 Run 误标 interrupted → 文档明确"上 S1 前禁止双实例"；S2 落地后解除该约束。
- S2 DDL 变更走既有 ensure/迁移机制（mining_runtime schema 演进已有先例 005/007）。
- S3 把执行移出 API 进程后：API 重启不再杀 Run（收益），但 worker 崩溃恢复完全依赖 S2 租约（依赖顺序不可倒置）。
- 行为兼容：/mine 响应结构不变（仍 202 + run_id），前端零改动。
- 回滚：S1 独立可回滚；S2/S3 每步向后兼容（worker 不在时 API 线程兜底可保留一个开关周期）。
