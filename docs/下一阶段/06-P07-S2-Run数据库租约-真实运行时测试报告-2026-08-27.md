## 二、审查发现并修复（3ebd7bf + d12af64 + 2255928）

### 1. CRITICAL——workflow 引擎（生产默认）完全不认领
认领只接在 `_run_legacy`；routes 传入 run_id 后按持久化引擎分派，workflow 走 `_execute_workflow_job`（无任何租约逻辑）。交付核心声明「执行入口在 ingest 前原子认领」对主路径不成立。修复：提取 `_claim_run_lease`/`_stop_run_lease` 共享助手接入 execute/resume（publish 作用于 completed Run 不认领），取消检查点并入租约丢失检测。

### 2. resume 状态集断裂
`claim_run` 只认 queued/running；resume 的目标是 interrupted/failed/awaiting_review（与 `resume_running(recover_workflow)`、`_is_run_resumable` 对齐）——原样接线会使 S1 自愈链全部认领失败。修复：`allowed_statuses` 参数 + `_claim_statuses_for_action`；renew 去 status 过滤（worker_id 即栅栏，否则 resume 认领后状态仍为 interrupted 的窗口期误判丢租约）。

### 3. RunLeaseLost 误标 failed（连带）
租约丢失时旧路径会 `tracker.fail_run`/`_mark_thread_failure` 把（可能正被新持有者推进的）Run 标 failed。修复：workflow 侧 except RunLeaseLost/WorkflowCancelled→RunLeaseLost 还原语义；routes 两处线程启动器跳过误标。

### 4. 自愈回归修复——延迟租约到期复扫
崩溃重启时有效租约（≤300s）会挡住首轮启动恢复且此后无人复扫（单实例「永不自愈」）。新增 `schedule_lease_expiry_sweep`：+360s 重跑同一恢复逻辑。多实例下活 worker 心跳保租约、复扫照旧跳过。

### 5. 对抗测试实锤的两个 SQL 参数 bug（mock 单测无法发现）
- **tuple→record 适配**：psycopg 把 Python tuple 适配为 PG record 字面量，`ANY(%s)` 以 `malformed array literal: "(queued,running)"` 崩溃（d12af64）。
- **参数序错位**：`$n` 按 SQL 文本出现序绑定，statuses 放错元组位置后生产全灭 claim（`malformed array literal: "generic"`，E2E 实测 Run 秒败）（2255928）。已加占位符计数/位置/类型三重断言回归锁。

## 四、留档观察（非阻塞，均为 master 既有）

1. **resume 已 finalize 的 Run 不回写终态**：`runtime.resume()`→`execute()` 走已提交快速路径，~4s 内存态返回 completed 但无人写 DB，行滞留 running；每次重启形成 interrupted→自动 resume→快速退出→running 的回弹。master 行为一致（租约分支无回归），属 P04 范畴终态回写缺口。
2. **KB 认证池瞬时耗尽**：请求风暴下 `upsert_user_by_username` 池 30s 超时（观察到一次 401/500 窗口后自愈）。与本分支无关（租约代码不触碰该池），池容量/认证缓存值得后续关注。
3. 交付件声明的「38 passed」复跑通过，但其租约测试全部为 SQL 字符串断言（mock 级）——本报告两处 SQL 参数 bug 均为其盲区，已补参数序回归锁。
