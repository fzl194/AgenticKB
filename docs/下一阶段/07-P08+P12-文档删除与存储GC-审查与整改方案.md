**清单遗漏的发现（第 1 条直接决定 P08 方案形态）：**

1. **withdrawal 与 KB scope 存在维度错配**：`_withdraw` 按 `(domain, channel)` 加锁并取 `get_active_build(domain, channel)`（`withdrawal.py:70-77`）——即**域级 release 的 Build**；而 KB Build 永不发布（护栏 :320-329），KB 文档的撤回直接复用该函数会作用于错误的 Build 族。**KB 维度需要自己的 withdrawal 变体**（清单建议 2"不能不加设计地直接套用"在代码层坐实，且指明了错配点在哪）。
2. **软删列已存在**：`asset_documents.deleted_at/restored_at`（`008_...postgresql.sql:200-201,206-207` partial index）+ `FileManagementService.soft_delete/restore`（`file_service.py:434-453`，未挂载）——KB 切软删是**接线**不是新建 DDL。
3. **Java per-document 解析是 tombstone 的天然消费端**：`selectLatestKbSnapshots` 按文档取最新 build 的 active selection（`AssetBuildDocumentSnapshotMapper.xml:36-57`，`DISTINCT ON (document_id)`）——只要 KB removal Build 成为该文档"最新"，`selection_status='removed'` 行经 active 过滤即生效。历史 Build 不动一行。
4. **删除即"孤儿化"对象**：当前路径删了身份行后，source/parse/binary 对象与 `asset_storage_objects` 行永久留存（实测 source 10 + parse 24 无一回收）——P08 与 P12 在"对象生命周期"上交叉（清单已提，代码层确认无任何回收调用）。
5. legacy 磁盘分支有 resolve 越界保护、失败仍删 DB 行（`document_service.py:255-265`）——设计合理，留档。

### P12 核实

| 清单论断 | 核实结果 | 证据 |
|---|---|---|
| purge 只写审计意图不删字节 | **属实** | `file_management/file_service.py:455-471`（docstring "Does NOT delete bytes... deferred to M1 GC"，实现仅 append purge_request 审计事件）；**且 purge 无路由暴露** |
| asset_storage_operations 无生产消费 | **属实且更彻底：连生产者都没有** | 全仓 `knowledge_mining/mining/**` 对该表零 INSERT/SELECT（仅 DDL `008:165-184` 与契约测试） |
| ObjectStorePort.delete 存在 | **属实** | `contracts/storage/port.py:84`；MinIO 实现 `minio.py:301`。生产调用仅 2 处且都在未挂载的 file_management 链（abort staging :557、replace 临时对象 :398） |
| retention_until 字段存在 | **属实** | 仅 `asset_storage_objects`（`008:42`） |

**清单遗漏的发现：**

1. **operations 表缺租约列**：DDL 有 state(PENDING/IN_PROGRESS/DONE/FAILED/CANCELLED)/attempts/next_retry_at/last_error + `(state,next_retry_at)` 索引，但**无 lease_owner/lease_expires_at**——直接当 GC 任务队列用会在多 worker 下重复删除（幂等可救但审计会脏）。补列代价小。
2. retention_until 全链无写入方（repositories 读写接口在、没有任何生产路径设置它）——"保留期"目前是纯摆设。
3. GC 需要的引用计算面已经可枚举：source 对象 ← asset_documents.storage_object_id；parse/binary 对象 ← snapshot/Parse IR 引用 + asset_storage_objects 自身。当前规模（34 对象）一次全量引用扫描毫秒级。

## 3. 运行时实测（2026-08-24，真库只读）

- `asset_storage_objects`：source 10 / parse 24 / **binary 0**；已删文档的对象全部滞留（孤儿化验证）。
- `asset_storage_operations`：表存在、0 行（无生产者坐实）。
- Build：validated 45（incremental）+2（full）——历史 Build 数量可观，FK cascade 的"改写历史"面随 Build 数放大。

## 4. 根因分析

P08 与 P12 是同一条生命周期链的两端断头：

- **产品语义端（P08）**：KB 产品化时选了最快的"DELETE 身份行"，借用 FK cascade 顺带实现了"从检索消失"的视觉效果——但这把**三种语义**（身份删除/知识撤回/物理清理）压进了一次硬删，绕开了已建好的 Build 版本机制。
- **物理执行端（P12）**：M1 规划了 retention/operations/outbox 全套概念，但"删除字节"这最后一跳因为**必须先有正确的引用语义**（P08 不定，GC 不敢删——删错共享对象比不删更糟）而搁置。于是两端互为等待：P08 等 GC 兜底才敢软删，P12 等 P08 语义才敢删字节。

**破局点**：先落 P08 的软删+removal Build（纯语义层，不碰字节），P12 的 GC 随后即可在明确引用图上安全执行——顺序不能反。

## 5. 修改方案（分阶段）

### P08 部分

**S1（P0）：KB 删除改软删（可见性立即正确，历史 Build 不再被改写）**

1. `DocumentService.delete()` 改调 `documents.set_deleted(document_id)`（盖 `deleted_at`；软删列已在；`repositories_pg.py:498-507` 与 KB 同表同库，对抗审查核实可直接复用 repository 层方法）；保留 `_assert_write` 与 legacy 磁盘分支行为。
2. **读面过滤（对抗审查 HIGH：枚举完整清单，9 类查询点）**：`kb/db.py` 当前对 `asset_documents` 的查询**没有任何一处**过滤 deleted_at，需逐一补：
   - `list_documents_in_kb`（kb/db.py:891-918）
   - **`get_document_identity`（:920-935）——它是详情/删除/撤回/改名/下载/预签名的共同入口**，不过滤则已删文档仍可被 patch/presign/download/再次 delete
   - KB overview 的 document_count 子查询两处（:298、:317）
   - 状态汇总计数（:486-492）
   - 文件夹计数/列举（:1049-1059、:1093-1104）
   - 挖掘入口 `/mine` 的文档筛选（`_prepare_document_states`）
   - parse-result/结构化读取链
   - `get_document_knowledge`（:648）
   - Java `selectLatestKbSnapshots`：`Mapper.xml:47-49` WHERE 加 `AND d.deleted_at IS NULL`（JOIN 已含 d，无结构性障碍）
   规则：**身份读取默认过滤；restore 走单独的含软删查询**。
3. 效果：删除不再触发 FK cascade → 历史 Build selection 完整保留（S1 即修复"改写历史"事故面）；检索退出由 deleted_at 过滤实现（效果与 cascade 相同）。（勘误：`008:206-207` 的 partial index 是 `WHERE deleted_at IS NOT NULL`——服务"找已删"，活文档过滤走既有 kb_id 索引；对抗审查纠正原"为该查询预备"的反向表述。）
4. 恢复入口：`restore`（已有 `file_service.py:444-453`）挂 KB 路由（需 admin/owner 权限）。

**S2（P1）：KB 维度 withdrawal——removal Build + tombstone**

1. 新增 **`withdraw_kb_documents(kb_id, document_ids)`（对抗审查 MEDIUM：批量签名，一次删 N 文档只 +1 Build，避免批量 UI 产生 N 个 Build 使 Java DISTINCT ON 查询面线性膨胀）**——withdrawal.py 的 KB 变体：
   - 父 Build = 该 KB 最新 validated Build（`asset_builds WHERE kb_id=? ORDER BY created_at DESC`，非域级 get_active_build——修发现 1 的维度错配）；
   - 新 incremental Build：目标文档 `selection_status='removed', reason='remove'`，其余文档继承父 selections；
   - **（对抗审查 CRITICAL）目标文档不在父 Build 的分支必须显式处理**：选择性挖掘（`meta_patch.document_ids`）下 KB Build 是 full-mode 无 parent、只含当次 run 的文档（`Mapper.xml:32-34` 注释）——目标文档的 active 行可能只在更早 Build。**不能复用域级 `withdrawal.py:95` 的父 Build 交集判定**（交集为空会抛 ActiveResourceNotFound）。正确做法：按**与 Java DISTINCT ON 同口径的跨 Build per-document 查询**取该文档最新 active 行的 snapshot_id（`document_snapshot_id` 列 NOT NULL，removed 行也要填该 snapshot），再写入新 Build；
   - **summary_json 必须写 `operation: "withdrawal"`**（对抗审查发现：`publishing.py:276-279` 空 Build 仅在该 operation 值下允许 validate——删最后一个文档的场景）；
   - `validate_build(allow_empty=True)` → validated（不发布——KB 护栏保持）；
   - 同文档"最新 Build 的 active 过滤"使 Java 端立即生效（发现 3 的天然消费；对抗审查逐行推演 DISTINCT ON 语义确认 removed 行被选中后被 active 过滤→文档整体退出，不回退旧 active 行）。
2. `DocumentService.withdraw()` 接上述实现（替换 NotImplementedError）；KB 路由 DELETE 增加模式参数：`mode=quick`（S1 软删，默认）/`mode=withdraw`（S2 removal Build，适合已进 Build 的文档）。**建议产品默认**：已挖掘文档自动走 withdraw、未挖掘走 quick（对用户透明，无模式选择心智）。
3. `get_document_knowledge` 等 KB 知识读取同步消费"每文档最新决策"。
4. **与进行中 Run 互斥（对抗审查 MEDIUM）**：软删/withdraw 时若同 KB 有挖掘中 Run，finalize 会为该文档写更新的 active selection 把 removed 压回去——withdrawal 与同 KB 进行中 Run 需互斥（kb 级 advisory lock 或复用 06 号域锁语义）。另**同毫秒 Build 的排序脆弱性**：`ORDER BY b.created_at DESC, b.id DESC` 的 id 是 uuid4 非单调——removal Build 写入时用显式 created_at 偏移或序列规避与并发 Build 同毫秒决胜。
5. **注意**：S2 上线前 S1 必须已生效（否则 cascade 还在，removal Build 建完身份行一删照样断链）。

**S3（P2）：永久删除显式化**

- 单独的 purge 动作（admin）：软删 + retention 窗口（默认 30 天）+ 引用检查后交 P12 GC 执行物理清理；UI 明确"不可恢复"二次确认。

### P12 部分

**S1（P1）：outbox 生产者 + 租约列**

1. DDL 补列：`asset_storage_operations` 加 `lease_owner TEXT / lease_expires_at TIMESTAMPTZ`（+索引随 state 查询走）。
2. 生产者接线（写 PENDING 行）：
   - S3-P08 purge 动作；
   - 文档永久删除后的 source 对象候选；
   - snapshot 被新版本整体替换后的 parse/binary 旧对象候选（内容寻址共享对象不直接候选——先全量引用计算再入队，见 S2）；
   - 上传中断补偿（01 号 S3 的 staging 清理复用本队列）。
3. retention_until 写入方：purge 时 `now()+window` 回填对象行。

**S2（P2）：GC 执行器（可挂 06 号 worker 或独立 supervisor program）**

1. 认领：`FOR UPDATE SKIP LOCKED` + lease 续期（与 06 号 S2 租约同模式；operations 表已有 attempts/next_retry_at/last_error 列，语义兼容）。
2. **引用计算（删除前强制，对抗审查补 SQL 骨架）**：
   ```sql
   -- source 对象：身份行引用
   SELECT count(*) FROM asset_documents WHERE storage_object_id = :oid AND deleted_at IS NULL;
   -- parse/binary 对象：两处引用都要数（缺一处就会误删仍被引用对象）
   SELECT count(*) FROM asset_document_snapshot_links l
     JOIN asset_document_snapshots s ON s.id = l.document_snapshot_id
     WHERE s.parse_ir_object_id = :oid;          -- snapshot 行上的 IR 指针（以实际列名为准）
   SELECT count(*) FROM asset_build_document_snapshots bs
     JOIN asset_document_snapshots s ON s.id = bs.document_snapshot_id
     WHERE bs.selection_status = 'active' AND s.parse_ir_object_id = :oid;
   -- 叠加：审计证据引用 + retention_until hold 检查
   ```
   引用数>0 → CANCELLED（记原因）；**快照共享（两文档同 snapshot）在此框架下天然安全**。
3. 执行：`ObjectStorePort.delete`（:84 已在）→ 删 `asset_storage_objects` 行 → DONE；对象不存在记 DONE（幂等）；hash 不匹配记 FAILED 人工介入。
4. **dry-run 模式 + 容量报表**：先只读跑引用计算输出"可删清单"，人工核对一周期后再开真删。**（对抗审查 HIGH 补充）dry-run 报表加"历史损伤盘点"**：各历史 Build 的 `summary_json.snapshot_count` vs 实际 selection 行数失配清单——存量硬删已造成的 cascade 损伤面在报表中显式标出（S1 只保未来，不修历史；盘点让审计者知道哪些 Build 的 summary 不可信）。
5. **保留策略（对抗审查 HIGH 反置原方案）**：parse IR 是不可再生的历史证据（删了只能重挖掘，且 Build 里残留的 snapshot 指针将悬空）——**parse IR 默认不 GC**（或 retention 窗口显著长于 source）；真删灰度从**零风险子集**开始："孤儿 parse 对象"（document 已不存在且无任何 snapshot 引用）而非按桶灰度。原"parse/binary 先行小流量灰度"的排序把最不可再生的对象放进了第一批，是错误的。
6. MinIO versioning 场景：当前部署未开版本——DDL/配置留 `delete_all_versions` 决策位，开版本时再定。

## 6. 风险与兼容

- S1-P08 软删后**存量已硬删文档不可逆**（cascade 已发生）——不做数据找回承诺；测试库无重要数据（用户已确认），生产化前该方案必须先落地。
- S1 读面过滤遗漏点风险：所有读 `asset_documents` 的入口要过一遍（KB 侧路由 + Java Mapper + legacy 域接口 08 号处置时一并）——验收用例必须含"删除后全端不可见"矩阵。
- S2-P08 的 removal Build 会使 Build 数量增长（每次删除+1）——per-document 解析语义下这是必要成本；批量删除合并为单个 removal Build（`withdraw_source_batch` 模式可参考）。
- P12 GC 最大风险是**误删共享对象**：引用计算必须先于删除且 dry-run 先行；内容寻址（sha key）使"误删"可由源文件重传恢复，但 parse IR 不可再生（需重挖掘）——GC 顺序建议 parse/binary 先行小流量灰度。
- 回滚：S1-P08 可回滚（回 DELETE）；S2-P08 新增路径独立；P12 全增量，dry-run 前零字节删除。

## 8. 与其他问题的依赖关系

- **P08-S1 ← 无依赖可先行**；P08-S2 依赖 S1；P08-S3 依赖 P12-S1。
- **P12-S2 依赖 P08 语义定稿**（引用图才可信）——顺序锁死。
- P12 GC 执行器复用 **06 号 S2/S3** 的租约/worker 基建（同一个 SKIP LOCKED 模式，甚至同一 worker 进程的第二个轮询队列）。
- **04 号 P10** 的 binary 物化上线后 GC 引用面扩一类——P12 引用计算预留 binary 分支。
- 上传补偿（**01 号 S3**）复用 P12 队列：三处消费一队列，outbox 才够本。
