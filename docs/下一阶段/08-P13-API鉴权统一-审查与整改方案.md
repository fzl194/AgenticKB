**清单遗漏的发现（本次审查新增，其中 1/2/3 使风险等级显著高于清单表述）：**

4. **`POST /api/uploads` 无鉴权 + `GET /api/uploads` 枚举全部域批次文件名**（uploads.py:79/:193）——未鉴名写盘 + 信息泄露双风险。

7. 无全局兜底鉴权（create_app 无 `dependencies=[...]`、无 auth middleware）——鉴权完全靠每个 router 自觉，这正是 8 族漏网的机制性原因。

结论：**legacy 族在 8901 直连下全裸**（含写面）；UI 端口（8080）不暴露该面；但 8901 publish 于 0.0.0.0。组合第 1 节发现 1（secret 可伪造 KB 族），当前真实暴露面 = **全部 mining API**。

## 4. 根因分析

鉴权是按"路由家族"分批建设的：KB 族（后建）带完整模型，legacy 族（先建）从未回填。因为没有**全局默认拒绝**，每挂一个 router 都是一次"是否记得加鉴权"的人肉检查——8 族漏网不是疏忽一次，是机制缺失（发现 7）。同时 secret 随配置文件入库，使纵深防御的第二层（网关头）对内失效。

## 5. 修改方案（分阶段）

> 原则：**先收口（默认拒绝），再逐族处置**——顺序反了会造成"改一半更大面积 404"。

### S0（P0，立即止血——部署面，非代码）

1. **端口收敛（对抗审查 CRITICAL 扩面）**：裸奔的不止 8901——同容器另有三个已 publish 且零鉴权端口：
   - `8900` llm_service：无任何鉴权中间件（仅 CORS）；
   - `8081` serving（Java）：`X-KB-User` 均为 `required=false`（`SearchController.java:25`、`FullTextController.java:46`）——**匿名可检索/取全文**；
   - `9000` mcp_server：FastMCP 无 auth，且默认上游是公网 IP（`client.py:27`）。
   只改 8901 等于"关了前门留着三扇窗"。处置：四端口（8900/8901/8081/9000）全部改 `127.0.0.1:` 绑定或移除 publish——**当前部署为单容器 supervisord，全部子服务经 localhost 互访**（nginx→`127.0.0.1:8910`、main_control→`localhost:8901`，`domain_registry.yaml` 5 处），绑定回环零影响；kb-ui 走 8080 相对路径（`proxyClient.ts`）不断。**单容器假设写为显式前提**：未来拆容器时 `domain_registry.yaml` 的 5 处 `localhost:8901` 即断点清单。
2. **轮换 secret + bootstrap 密码**：auth.yaml 换新值（`:6`）；**`:7` 的 `bootstrap.admin_password: admin12345` 同批处置**（对抗审查发现，与文件头"首次登录后应移除"注释冲突且仍在 git）。新值走 .env/部署注入，不回写 git 追踪文件。
3. CORS 收敛（对抗审查加重）：starlette 实测行为是 `allow_origins=["*"] + allow_credentials=True` 时**主动把 `*` 展开为 echo 请求 Origin**——不是"浏览器会拒绝"，而是服务端替任意 Origin 放行凭据跨域。收敛为显式白名单（8080 源）；**同款问题在 `llm_service/main.py:251-255` 还有一份**，同批修。

> S0 属配置变更，与本审查"不改代码"约束不冲突，列为方案第一步；实施时单独 PR。

### S1（P0）：全局默认拒绝（机制性堵漏）

1. `create_app` 增加 ASGI 级鉴权中间件（纯中间件而非 app 级 dependencies——对抗审查核实 FastAPI 全局 dependencies 无"本路由豁免"逃逸机制，health 需要）：
   - 拦截 `/api/*` 全部方法；
   - **白名单（对抗审查 CRITICAL 修正）**：`/health`、`/api/system/status`、**`/api/kb/auth/identify`、`/api/kb/auth/verify`**（登录入口无 X-KB-User 可言，漏掉即全站登录死锁——登录链路经 main_control 服务间调 mining verify，`main_control_service/auth.py:130` 注释证实）；`POST /api/kb/admin/reload-auth-config` 归 admin（挂 require_admin 不进白名单）；
   - 校验逻辑复用 `current_user` 的双头 + 现查库（提为可共享函数）；
   - KB 族路由的**细粒度授权**（成员/admin）仍留在路由层——中间件只做"已认证"，不做"有权访问该资源"。
2. **性能（对抗审查 HIGH）**：`current_user` 每请求一次 `upsert_user_by_username`（DB 写）——中间件 + 路由层会双查。中间件认证结果挂 `request.state`，路由层 current_user 改读 state（FastAPI 依赖缓存不跨中间件，必须显式传递）；或加短 TTL 缓存。
3. legacy 族通过中间件后获得身份，但**资源级授权**（如 KB 归属）按 S2 逐族补。
4. 兼容期开关：`AUTH_ENFORCE=warn` 模式（只记日志不 401）跑一个观察周期。**观察期真实风险修正（对抗审查）**：不是零调用方——main_control proxy 转发 `{path}` 不做路由族过滤，**全部 legacy 族都可经网关被已登录 UI 用户触达**（实测 kb-ui `SystemStatusTab.vue:297` 在调 `/api/knowledge/stats`、mining.ts 保留 legacy download/delete 方法）。warn 日志只记"非白名单且无身份头"命中，避免 SystemStatus 轮询刷屏。

### S2（P1）：legacy 8 族逐族处置（决策表）

| 族 | 处置 | 理由 |

| document_lifecycle.py | **优先下线或收编**：DELETE 与 KB 路由同写 `asset_documents` 族（绕行实锤）；download 与 KB download 重复。**下线时同步删除 kb-ui 的 legacy 死方法**（对抗审查 HIGH：`mining.ts:213/228/235/398` 的 downloadDocument/deleteDocument/deleteBatch/deleteEntity 仍在——后者打到 ontology 族 `/api/graph/entities/*`；页面已全走 kbApi 新方法，死方法是"能调通就调"的诱饵） | 与 KB 路由同资源双入口是最大越权面；KB 路由已有完整校验 |

### S3（P1）：服务间身份与审计闭环

1. service identity：网关注入的 `X-KB-User` 之外，服务间调用显式 service token（mcp→serving 等），不依赖"端口恰好没 publish"。
2. actor 审计：legacy 写接口（保留者）统一记录操作者到既有审计事件表。
3. 路由枚举测试固化：遍历 app.routes 断言"非白名单端点必须有认证依赖或经中间件"——防止第 9 族漏网（CI 常驻）。
4. "绕过网关直连 8901 调旧写接口必须失败"的集成测试（清单建议 9 落地）。
