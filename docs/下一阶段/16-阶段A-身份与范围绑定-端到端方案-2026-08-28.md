## 2. 总体设计

### 2.1 身份链路（谁在搜）

```
Agent ──(Authorization: Bearer kbm_xxx)──► MCP
   MCP ──(POST mining /api/kb/auth/mcp-key-verify, internal)──► mining 按 domain 连域库
        校验 sha256(key) → 命中 → 返回 {username, display_name, key_id}
        未带 Authorization → 匿名（维持现状，仅 public）
        带错钥/已吊销 → 401（整个会话拒绝）
   MCP ──(X-KB-User: <username>)──► serving 全部调用
   serving KbAccessService 按 username 授权（public OR owner OR member）——零改动复用
```

### 2.2 范围与范式解析（用哪条管线搜哪些库）

一次 MCP `search_knowledge(query, domain, kbIds?, paradigm?)` 的解析顺序：

```
① paradigm 显式指定              → 直接用该范式执行（现状保留）
② 否则 kbIds 恰好 1 个且该库设了
   default_paradigm_id（库级默认）→ 用库级范式
③ 否则域有默认绑定范式（领域默认） → 用域默认（现状 /paradigm/resolve 逻辑）
④ 否则                            → 官方默认检索范式（本批 seeding；C 阶段替代 legacy 回落）
                                   ④暂不可用时仍回落 legacy /api/v1/search（现状，C 阶段删除）
```

范式选定后，**搜索范围（kbIds）优先级**：

```
图内 scope_resolve.kbIds 非空（设计期写死，专属用法） → 用图内（忽略请求 kbIds，响应标记）
图内留空 → 用请求级 kbIds（MCP/UI 现场指定）
请求也没带 → 域级 active release（现状语义）
```

这就是"菜谱+运行时范围"的落地：范式是通用菜谱，库组合在执行现场决定。

## 3. 分模块设计

### 3.1 MCP 用户密钥（新）

**表**（`databases/kb/schemas/008_mcp_api_keys.sql`，域库）：

```sql
CREATE TABLE IF NOT EXISTS mcp_api_keys (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL REFERENCES kb_users(id),
  name          TEXT NOT NULL,              -- 用途备注，如 "dify-agent"
  key_prefix    TEXT NOT NULL,              -- 明文前 8 位，便于人肉识别
  key_hash      TEXT NOT NULL UNIQUE,       -- sha256(明文) hex；不存明文
  status        TEXT NOT NULL DEFAULT 'active',  -- active | revoked
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_used_at  TIMESTAMPTZ,
  revoked_at    TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS idx_mcp_api_keys_user ON mcp_api_keys(user_id);
```

- **形态**：`kbm_` + 32 字节随机 hex（64 字符）。**按域隔离**（表在域库，密钥只在所属域有效）——用户跨域需各域建钥；理由：用户体系本身按域分库，跨域单钥需要全局库，引入新拓扑，收益低。
- **存储**：只存 sha256，明文仅创建响应返回一次；`key_prefix` 供 UI 列表识别。

**管理 API**（mining，`/api/kb/users/me/mcp-keys`，登录态）：

| 端点 | 说明 |
|---|---|
| `GET /api/kb/users/me/mcp-keys?domain=` | 列本人的钥（id/name/key_prefix/status/created_at/last_used_at，无 hash） |
| `POST /api/kb/users/me/mcp-keys` `{name}` | 建钥 → 返回**明文一次**；每人每域上限 5 把 |
| `DELETE /api/kb/users/me/mcp-keys/{id}` | 吊销（status=revoked；不物理删，留审计） |

**校验 API**（mining，internal-only，走 `X-Internal-Auth`，供 MCP 调用）：

`POST /api/kb/auth/mcp-key-verify` `{domain, key}` → 200 `{username, display_name, key_id}`（命中且 active，顺带更新 last_used_at，节流 60s）/ 401。选 mining 承接的理由：域→库路由（domain_registry）在 mining 侧现成；mcp_server 保持零 DB 依赖；校验结果可进 IdentityCache 同款缓存。

### 3.2 KB 库级默认检索范式（新列 + 双栈读写）

**DDL**（`databases/kb/schemas/009_kb_default_paradigm.sql`）：

```sql
ALTER TABLE knowledge_bases ADD COLUMN IF NOT EXISTS default_paradigm_id TEXT;
```

跨库无 FK（范式在控制库），应用层校验。

**写路径**（mining `PATCH /api/kb/{kb_id}` 增加 `default_paradigm_id` 字段）：
- 值非空时校验：调 serving `GET /api/v1/paradigm/{id}`（已发布 active、servable=assemble 终点、同域）——不满足 → 400 带原因；
- 置空 = 清除库级默认（回落领域默认）。

**读路径**（Java `GET /api/v1/paradigm/resolve` 增强查询参数 `kbIds`）：
- 请求带单个 kbId 且该库有 default_paradigm_id → 返回 `{paradigmId, source: "library"}`；
- 该范式当前不可用（已归档/非 active）→ 跳过并降级下一层，响应附 `degraded: true, degradedFrom: "library"`（不炸、可观测）。

### 3.3 范式执行请求支持运行时 kbIds（Java）

- `RunArgs` 增加 `List<String> kbIds`；`ParadigmRequests.toRunArgs` 解析 body `kbIds`（数组，可空）；`POST /api/v1/paradigm/{id}/search` 与 inline run 两个入口都接。
- **注入语义**（ExecutionContext 增加 `requestKbIds`）：

```java
// ScopeResolveOperator（唯一改动点）
List<String> paramKbIds = params.getStringList("kbIds");
List<String> effective = !paramKbIds.isEmpty() ? paramKbIds : ctx.requestKbIds();
// effective 为空 → 域级 release（现状）；非空 → authorize 后 resolveKbScope（现状）
```

授权不变：`kbAccessService.authorize(domain, effective, ctx.username())`——注入的库不可读整单拒（现语义，匿名时仅 public）。

- **UI**（kb-ui 范式编辑器）：scope 节点 kb-picker 支持清空并显示"留空 = 检索时指定范围"提示；搜索页（SearchView 范式执行路径）可带库选择。

### 3.4 MCP 接线（身份 + 解析）

- server.py 每个 tool 读 `Authorization` 头（FastMCP 1.x 的 get_request_headers）→ 无 → 匿名（现状）；有 → 调 3.1 校验 API → 得 username → 全部 serving 调用附 `X-KB-User`。
- `search_knowledge` 工具参数增加 `kb_ids`（数组，可选；现有 `paradigm`/`scope` 参数保留但继续标 ignored——B 阶段工具族重构时一并清理）。
- client.py 路由升级为 §2.2 四层解析：显式 →（单库库级）→ 领域 → 官方默认；每层失败不盲落 legacy（仅第④层无官方默认时回落 legacy，维持现状，C 阶段删除）。
- **官方默认检索范式**：Java 侧 seeding 一个 `system-official-default` 范式（含 query_embed→fts→rrf→rerank→assemble 的最小可发表图，`is_default` 不占域默认槽，用专用 system 标记）——本批先落图与 seeding 逻辑，效果对齐 legacy 由 C 阶段的四能力算子化完成，本批**不**承诺检索质量对齐。

## 4. 安全设计

- 明文密钥只在创建响应出现一次；库中仅 sha256；日志永不记明文（prefix 可记）。
- 校验 API internal-only（`X-Internal-Auth`，与 P13 中间件同款防线）；MCP 与 mining 同容器/同网段。
- last_used_at 节流更新（60s），避免每次搜索一次写。
- 吊销即时生效：校验 API 每次实查 status（命中缓存仅缓存 username 映射 60s，revoked key 因 hash 未命中 active 行直接 401——**缓存键含 key_hash**，吊销后缓存自然失效，无绕过窗口）。
- MCP 匿名保留为过渡（仅 public）；是否最终强制鉴权 → C 阶段决定。
- 注入 kbIds 与图内 kbIds 一律过 KbAccessService（不可读整单 403，不泄露哪个库不可读——现状语义）。

## 5. 兼容性与风险

| 风险 | 缓解 |
|---|---|
| 已发布范式（kbIds 写死）行为变化 | 无：非空 kbIds 照旧，注入只在留空时生效（编译/绑定/执行三层语义已核实） |
| MCP 现有匿名调用方（如有脚本） | 无 Authorization 头 → 行为不变 |
| 官方默认范式检索质量低于 legacy | 本批仅 seeding 占位 + 路由可达；质量对齐在 C（四能力算子化），期间第④层回落 legacy 兜底 |
| kb_ui SearchView 仍走 legacy `/api/v1/search` | 本批不动 UI 检索入口（C 阶段切）；仅新增范式执行带 kbIds 的 API 能力 |
| 跨库 default_paradigm_id 悬挂（范式被删） | resolve 降级 + degraded 标记；PATCH 校验尽量挡住新悬挂 |
| Java mvn 383 项回归 | RunArgs/Controller 均为加字段不改语义；新增注入单测 |
