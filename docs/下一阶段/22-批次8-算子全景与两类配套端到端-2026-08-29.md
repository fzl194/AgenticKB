## 3. 两条配套的端到端

### 3.1 配套一：纯向量检索（兜底，朴素 RAG）

**挖掘范式：快速向量检索**（主线 + retrieval_unit_build + embedding，不走 enrich/discourse/contextualizer——**实施时校准：关闭问答卡生成，把"快"做实**）

```
端到端料流：
input_ingest → document_parse → segment_compile ──→ asset_persist → mining_finalize
                                        │
                       retrieval_unit_build（raw_text 1:1 + table_row 每表格行 + facets）
                                        │
                                  embedding（全部 unit 向量化）
                                        ↓
              资产：units + embeddings（无 LLM 生成内容，挖掘成本≈0 LLM）
```

**检索范式：纯向量检索**

```
request_input → query_embed → dense_vector(textKind=raw_text) → assemble
```

- 查询成本：0 LLM，1 次向量调用
- 吃的料：raw_text units + embeddings
- 定位：最低成本兜底 + **质量评估套件的基线对照组**

### 3.2 配套二：通用检索（主力，建库默认配套）

**挖掘范式：篇章增强检索**（主线 + 检索线全部 5 节点）

```
端到端料流（在配套一基础上增加）：
enrich(semantic_role 补全→facets)
discourse_line(篇章关系→上下文补写的输入)
contextual_retrieval_enrich(LLM 上下文补写→search_text)
retrieval_unit_build 全类型（+generated_question 问答卡）
embedding（全类型向量化）
```

**检索范式：通用检索（多路召回+路由）**

```
request_input
   ├→ route_signal(规则路由，0 LLM) ──────────────┐
   ├→ query_embed → dense_vector(textKind=all+facets) ─┤ 路1：语义+问答卡+表格行向量
   ├→ fts(facets 过滤) ────────────────────────────┤ 路2：精确 token+表格行+面包屑
   ├→ tree_navigate(章节树收窄) → 章内 dense ──────────┤ 路3：结构定位
   ↓                                                  ↓
weighted_rrf(权重 = 静态默认 × 路由信号覆盖)   ←────────┘
   → model_rerank → rerank_post(近重去重) → assemble(表格行→表头上下文重组)
```

- 查询成本：规则路由 0 LLM + rerank 模型 1 次；可选把 route_signal 换成 query_understanding（+1 LLM/查询，画布可改）
- 吃的料：**全部结构化产物**（对照表见 §5）
- 定位：默认配套，覆盖语义/精确/结构三类查询意图——**多路在一条 pipeline 内组合，不是一场景一 pipeline**

## 4. 范式匹配错了怎么处理（三层防线）

**场景**：库的挖掘范式产出的料 ⊄ 检索范式需要的料（如 minimal 库绑通用检索、fast 库绑树导航）。

| 层 | 机制 | 现状基础 |
|---|---|---|
| 1. 绑定时校验提示 | 检索范式编译期从图推导"所需能力"（dense→vector_ready；fts→lexical_ready；tree_navigate→section_path），对照该库 build.summary_json.paradigm_capabilities（批次4 已冻结）——**不满足则提示但不阻止** | 批次4 能力门禁机制直接复用 |
| 2. 运行时降级 | 通用检索三路天然冗余：某路无料→该路空候选+degraded 留痕（scope_resolve 的 degradedFrom 先例），其余路正常出结果；**三路全空→结构化错误提示"此库未产 X 资产，建议重挖或换范式"** | scope_resolve 降级留痕模式 |
| 3. 前端配套推荐 | 建库选挖掘范式时显示配套检索范式推荐；检索 tab 选范式时显示该库 readiness 匹配提示（批次4 readiness 四档已有） | readiness 面板已有 |

**失配不会 500/静默空转**：单路断=其余路兜底+留痕；全断=显式提示换法。

## 5. 结构化数据充分性对照（"改造的料到底用没用上"）

| 结构化产物 | 生产算子 | 消费算子（配套二） | 状态 |
|---|---|---|---|
| section_path 章节树 | segment_compile | **tree_navigate（新）**路3 | 本批打通 |
| structure_json 表格结构 | segment_compile | table_row units → dense(textKind=all)路1 + fts 路2 + **assemble 表头重组** | 本批打通 |
| block_type | segment_compile→facets_json | dense/fts 的 **facets 过滤参数**（SQL 已在，接线） | 本批打通 |
| semantic_role | enrich(LLM)→facets_json | facets 过滤（高级可选参数） | 本批打通 |
| generated_question 问答卡 | retrieval_unit_build(LLM) | dense textKind=question/all 路1 | 本批打通 |
| 上下文补写 | contextual_retrieval_enrich | search_text → fts+dense 语义增强 | 已通（正式编入默认图） |
| 章节面包屑 | retrieval_unit_build | search_text → fts | 已通 |
| **篇章关系** | discourse_line | **无直接消费**——间接价值=上下文补写的输入；直接消费（"相关段落扩展召回"类）列后续可选 | **诚实标注：暂无直接消费** |
| 图片描述 | image_caption(VLM) | — | 不在本批（OCR/图片线用户已拍板暂缓） |

结论：9 项结构化产物 **7 项本批打通消费、1 项间接消费（篇章关系）、1 项缓办（图片）**。核心断点（表格行向量通道、章节树、类型过滤）全部有明确修复路径，且多数是"接线"级改动（SQL 已备）而非新造轮子。
