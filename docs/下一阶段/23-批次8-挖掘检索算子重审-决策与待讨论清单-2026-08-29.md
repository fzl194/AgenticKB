## 1. 最终目标与讨论方式

用户的原始目标不是尽量使用现有算子，而是：

1. 摸清挖掘、检索两侧到底有哪些算子；
2. 判断哪些必要、哪些有条件有用、哪些应下线；
3. 参考工业界主流实现补齐真正缺失的能力；
4. 构建挖掘资产生产与检索消费成对闭环的范式；
5. 充分利用 ParseIR、章节、表格、代码、列表、证据定位等结构化数据；
6. 以真实业务检索质量、成本和延迟评估，而不是以“算子存在/执行成功”验收；
7. 讨论结论由用户逐项确认，全部确认后再形成一份可直接移交 Claude 详细开发的完整指南。

历史讨论约定是“先讨论、逐项确认”。当前产品级确认已经结束，详细实施需求已转入 24、25 号文档；代码实施仍需用户另行发起。

## 2. 已查实的当前实现事实

### 2.1 当前检索资产生产线

现有检索线主要为：

```text
enrich
→ discourse_line
→ contextual_retrieval_enrich
→ retrieval_unit_build
→ embedding
```

它接在新的 `document_parse → segment_compile` 后面，但后五个算子主要复用旧的 `DocumentContext/RawSegmentData` 管线，因此本质是“新结构化解析/分段 + 旧检索单元构建器”的兼容拼接。

### 2.2 五个旧算子的真实行为

| 算子 | 真实行为 | 已确认的问题 |
|---|---|---|
| `enrich` | LLM 补 `semantic_role`、文档类型、内容质量 | 消费端弱；v2 已预写 segment 后不会把 enrich 结果更新回原始段；失败可能被吞掉但仍声明成功能力 |
| `discourse_line` | LLM 滑窗抽取因果、对比、展开等段间修辞关系 | 不参与 contextualizer；普通检索收益闭环弱；成本高；失败/空关系也可能被记成功 |
| `contextual_retrieval_enrich` | 每段使用“文档前 2000 字 + 当前段前 500 字”生成定位描述 | 后半文档上下文失真；结果只进入 `search_text`，没有进入向量输入 |
| `retrieval_unit_build` | 同时生成 raw text、generated question、table row、entity card | 确定性投影、LLM 问题生成、实体资产混在一起；fast 也可能默认调用问题生成 LLM |
| `embedding` | 按 unit type 选择单元并嵌入 `unit.text` | 不嵌入 contextual `search_text`；模型、真实输入、哈希、维度留痕不足 |

### 2.3 结构化数据的关键断点

1. ParseIR 已包含表格单元格、表头、行列、证据定位、元素父子关系等丰富结构。
2. 新 segment compiler 能产生 `table_view=whole/row` 等结构段。
3. 兼容 projection 把 `table_row` 收敛成普通 `table` block type。
4. 旧 table-row builder 期待另一套 `columns:list + rows:list[dict]` 结构。
5. 因此新链路下 `tableRowUnit` 可能空转，行段只能退化成普通 raw-text unit。
6. `section_path/block_type/source_offsets` 已有生产和部分持久化，但检索端没有完整消费。
7. `generated_question` 默认门槛仅约 50 token，部分域包低至 30；生成结果主要做字符串长度校验，不能保证问题可由原文独立回答。

这些事实是后续重构的约束，不能在最终指南中被旧文档结论覆盖。

## 3. 工业界方法审视后的总判断

截至本轮调研，通用工业主线应收敛为：

```text
结构保真分段
→ typed retrieval units
→ BM25 + dense hybrid / RRF
→ rerank
→ 命中后 parent / neighbor / whole-document 扩展
```

需要吸收的工业能力不是“每种方法都造一个算子”，而是按独立成本、失败语义、产物和消费者划分：

| 工业方法 | 当前判断 | 后续落点 |
|---|---|---|
| Structure-aware chunking | 默认核心 | 强化 `segment_compile`，结构边界优先，token 上限兜底 |
| Parent-child / Small-to-Big | 默认核心候选 | 小单元召回，命中后返回父章节/较大块 |
| Sentence/segment window | 默认核心候选 | 命中后确定性扩前后段，不需要 LLM 修辞边 |
| Hybrid + RRF + rerank | 默认检索基线候选 | 检索侧配套范式，最终与挖掘资产一起确认 |
| Contextualized embeddings | 条件增强 | 作为 embedding 策略，不等同于当前 contextualizer |
| Late Chunking | 条件增强 | embedding 模型支持时实验，不调用生成式 LLM |
| Doc2Query / query expansion | 条件增强 | 必须资格门、答案证据校验、去重，并指回源单元 |
| Hierarchical summary / RAPTOR | 高级独立范式 | 大文档全局总结、多跳问题，不进入默认链 |
| GraphRAG | 高级独立范式 | 跨文档实体、多跳、全局主题；不等于段间 RST |
| Per-chunk LLM enrich/RST | 非默认 | 只有明确 query-time 消费器和消融增益才可恢复 |

主要外部依据见本文末尾 §10。

## 4. 已确认决策

### C1：实体/本体生产与消费链暂不上线

实体抽取、本体归纳及需要人工审核的链路暂不上线；代码和算子保留但不编入官方预置。前端实体图谱、本体版本、本体图谱菜单注释下线。该决策来自 21 号追加指令，继续有效。

### C2：通用默认挖掘线不包含生成式 LLM 算子

用户已确认通用默认生产线收敛方向：

```text
input_ingest
→ document_parse
→ segment_compile
→ retrieval_unit_project
→ embedding（按所配检索范式决定是否需要）
→ asset_persist
→ mining_finalize
```

其中：

- `enrich` 从通用正式算子集/预置范式下线；
- `discourse_line` 从通用正式算子集/预置范式下线；
- 当前形态的 `contextual_retrieval_enrich` 下线，不原样保留；
- 后续 C25 已确认当前仅为可清库测试环境：除明确要求保留的 entity/ontology 研究代码外，退役实现不保留迁移周期，直接删除；
- 若后续真实消融评估不能证明独立价值，则删除旧实现。

### C3：`retrieval_unit_build` 必须重构为确定性投影

已确认方向是 `retrieval_unit_build → retrieval_unit_project`：

- 只负责从 ParseIR/compiled segments 无损投影 typed retrieval units；
- 不调用问题生成 LLM；
- 不做 contextual LLM；
- 不生产 entity card；
- 不猜测 LLM semantic role；
- 不抽取修辞关系。

检索表示与原始证据分层、canonical target、结构扩展消费者已经在 C7 确认；具体字段、索引和迁移细节留待最终开发指南落实。

### C4：不新增独立 `document_profile_build` 挖掘算子

前一轮曾提出 `document_profile_build`，经用户追问后已修正：

- 文档 token、segment 数、section 数、结构比例等只是已有 ParseIR/segment 的确定性聚合；
- 它没有独立成本、独立失败语义或用户开关需求；
- 因此不应为了能力命名而增加新算子；
- 所需统计由 `segment_compile/asset_persist` 自动派生和持久化，作为 document metadata/profile，而不是画布节点。

### C5：查询路由不是逐文件遍历，也不属于当前挖掘算子清单

已向用户澄清并达成共同理解：

```text
一次知识库查询
→ BM25 / vector 在全库索引中统一召回 Top-K units
→ 得到少量候选文件
→ 读取候选文件已有结构元数据
→ 对不同候选决定返回全文、父章节、邻段、表格上下文等
```

知识库有 1000 个文件时，不会查询时把 1000 个文件逐一跑一遍路由。

入库时确实是同一挖掘范式按 document snapshot 分别执行，可并发/批处理；这不是为每个文件定制一条流程。

同一次检索中，不同文件最终可能返回不同粒度：

| 文件情况 | 可能的返回形式 |
|---|---|
| 小文件、全文在预算内 | 整个文件 |
| 中等结构文档 | 命中单元所属父章节 |
| 大文件或超大章节 | 命中单元 + 前后窗口 |
| 表格命中 | 表格行 + 表头 + caption |
| 代码命中 | 完整代码块 + 所属章节 |

搜索阶段仍统一召回细粒度资产；粒度变化发生在命中后的 evidence hydration/context assembly 阶段。

### C6：`document_route` 暂不作为已确认的新算子

`document_route` 是查询侧能力概念，不是挖掘算子。后续讨论检索范式时再决定：

- 是否需要独立路由算子；
- 是否由现有 `assemble`/context expansion 内部完成；
- 是否需要拆成 scope routing 与 evidence hydration 两个职责。

当前不得把 `document_route` 写进已定开发清单。

### C7：检索表示与原始证据分层，正式采用 `evidence_hydrate`

用户已确认以下闭环：

```text
原始内容资产（document/section/segment/table/code/list...）
→ retrieval_unit_project 生成可搜索表示
→ FTS / dense / fusion / rerank
→ evidence_hydrate 解析 canonical target 并补结构上下文
→ assemble 合并、去重、控制 token 预算
```

统一命名与职责：

- **取消 `document_route` 名称**，不得再用它指代召回后的内容展开；
- 新增/重构出的正式检索算子命名为 `evidence_hydrate`；
- `evidence_hydrate` 只处理 Top-N 候选，不遍历知识库文件；
- 它根据 `representation_type/target_type/target_id/source_refs` 读取真实原文；
- segment 命中可补父章节或邻段；table-row 命中补表头/caption；code/list 命中返回完整结构块；query alias 命中必须回到源证据；
- `assemble` 不再负责识别所有资产类型和数据库回读，只负责合并重叠内容、排序、预算和最终 evidence 输出；
- 后续已在 C19 确认本批不新增统一 `retrieval_route`：召回前路径由本地 Agent 通过 MCP 工具选择和显式参数决定，仍不得与 `evidence_hydrate` 混为一谈。

检索单元的最终语义也已确认：

- retrieval unit 是“可搜索表示”，不是原始内容真相；
- ParseIR/结构化资产/`asset_raw_segments` 是可追溯原始证据；
- `asset_persist` 负责真正入库，`retrieval_unit_project` 负责检索表示编译；
- 每个表示分别声明是否进入 lexical/FTS、是否进入 dense/embedding；
- 多种表示可以指向同一源证据，但必须共享 `canonical_evidence_id`；
- raw text、query alias、多向量等同源命中在融合阶段按 canonical evidence 合并，不能重复占候选位；
- hydrate 后还需合并父章节/邻窗产生的重叠区间，避免最终上下文重复。

### C8：embedding 采用“固定默认映射 + 算子参数可覆盖”的策略矩阵

用户已确认：embedding 不能是 pipeline 级单一 mode。正式模型为：

```text
retrieval_unit_project 产出不同 representation type 和能力事实
→ 一个 embedding 算子读取可配置 embedding policy
→ policy 为每类 unit 自动匹配不同 strategy
→ 每条 embedding 记录冻结实际采用的 strategy/profile/input hash
```

一个 pipeline 仍只有一个 embedding 节点，但该节点内部可同时执行：

```text
prose          → structural/contextualized/late_chunking
table_row      → structural
list_group     → structural
figure_caption → structural
code_block     → isolated 或用户配置的兼容策略
formula        → isolated 或用户配置的兼容策略
query_alias    → isolated
summary        → isolated
whole document / raw section → skip（默认）
```

配置原则：

1. 系统必须提供版本化、固定且可解释的默认策略矩阵；
2. 用户可以在 embedding 算子参数中按 representation type 覆盖 strategy；
3. 自动选择来自声明式 policy，不允许把 `if table then ...` 等规则散落硬编码在执行器；
4. policy rule 可以匹配 `representation_type/content_type/has_ordered_context/has_source_span` 等事实；
5. strategy 枚举为 `skip | isolated | structural | contextualized | late_chunking`；
6. contextualized/late-chunking 还必须通过 provider/model capability 校验；
7. 不满足必要资产或模型能力时不得静默换策略，除非 policy 明确配置 fallback；
8. 本批当前只有一个文本 embedding 模型，不含图片模型或代码专用模型；所有可向量化 unit 默认共享同一模型、维度和向量空间，只按 unit type 改变输入构造；
9. 本批不建设多模型、多 profile 的 query-embed 分路召回；不同模型/维度只能作为远期扩展边界，不进入当前参数面和正式范式；
10. 同一 canonical evidence 的多表示或多向量必须合并，不能重复占候选位。

embedding 与上游的正式契约：

- `retrieval_unit_project` 提供 `representation_type/content_text/structural_context/context_group_id/ordinal/source_span/dense_eligible/target/canonical_evidence_id`；
- embedding policy 基于这些字段路由并分组执行；
- FTS 与 dense 可以消费同一 retrieval unit，但各自受 lexical/dense eligibility 控制；
- 切换 embedding policy 不要求重新 parse/segment/project，只需按新签名重建 embedding 派生资产。

### C9：新增可选 `query_expansion_generate`，问题只是检索别名

用户已确认从旧 `retrieval_unit_build` 拆出独立可选挖掘算子 `query_expansion_generate`：

```text
retrieval_unit_project
→ query_expansion_generate（可选）
→ embedding（policy 可为 query_alias 选择 isolated 等策略）
→ asset_persist
```

正式语义：

- 输入是已经投影好的、通过资格门的 retrieval units，不直接遍历任意原始碎片；
- 输出 `representation_type=query_alias` 的检索表示；
- query alias 不是答案内容，`returnable=false`；
- 每条 alias 必须通过 `target_type/target_id/canonical_evidence_id` 指向原始证据；
- query alias 可以分别声明进入 lexical/FTS 和 dense/embedding；
- 命中后必须由 `evidence_hydrate` 返回源段、父块或结构化证据，不能返回问题文本本身；
- raw representation 与 query alias 命中同一 canonical evidence 时必须合并，不能重复占位或重复投票。

资格与质量规则：

1. 系统提供按 representation type 划分的固定默认 eligibility rules，用户可通过算子参数覆盖；
2. prose、table-row、list-group 等分别使用适合自身结构的规则，禁止只靠一个全局 token 阈值；
3. heading/navigation/TOC 默认永不生成；code/formula/figure-caption 默认关闭；
4. LLM prompt 必须允许返回 `SKIP`，不得强迫每个输入产生问题；
5. `SKIP`、LLM 失败、格式错误、证据校验失败必须分别留痕；
6. 每个生成项必须包含 `question + answer_span + source target`；
7. `answer_span` 必须能在允许的源证据范围内精确或归一化匹配，否则丢弃；
8. generation context 可以帮助理解，但不能扩大 answer evidence 的允许范围；
9. 默认 `maxAliasesPerTarget=1`，用户可配置；
10. 必须做单 target、文档内和 canonical evidence 三层去重；
11. 支持文档级数量/成本上限，不代表必须用满额度。

上线与失败边界：

- 不进入零 LLM 的官方基础生产线；
- 进入独立的 Query Expansion 增强范式或经业务验证的场景范式；
- 整体 LLM 不可用时基础 retrieval units 仍可发布，但 query expansion 必须标记 degraded；
- 发布摘要记录 eligible/generated/skipped/invalid/deduplicated/LLM failures/token/cost；
- 是否进入官方增强预置最终由真实业务问题集的 Recall、污染率和成本消融决定。

### C10：大小文档动态展开，新增可选结构层级摘要

用户已确认：全文、父章节、邻窗不是新的挖掘算子，而是 `evidence_hydrate` 的可配置展开策略。

正式规则：

- 不永久写死 small/medium/large 标签；
- 保存 document/section/segment 的客观 token、层级和 span 事实；
- 查询时结合本次上下文预算、查询范围、命中密度和父块大小决定返回粒度；
- 小文件仍建立 child retrieval representations，命中后全文 fits 才返回全文；
- 大文档局部事实仍走 child 召回 + parent/window，不需要先摘要或抽 LLM 修辞关系；
- table/code/list 等沿用 C7 的类型化 hydrate 策略；
- `evidence_hydrate` 的 expansion policy 必须有系统默认值并允许用户参数覆盖。

新增独立可选 LLM 挖掘算子 `hierarchical_summary_generate`：

```text
retrieval_unit_project
→ hierarchical_summary_generate（可选）
→ embedding（summary_alias 通常使用 isolated）
→ asset_persist
```

算子边界：

1. 只消费确定性的文档标题/章节层级，不重新切片；
2. 自底向上为达到配置门槛的 section/document 生成摘要；
3. 不对每个叶子段逐段总结；
4. 输出 `representation_type=summary_alias` 的派生检索表示；
5. summary alias 必须绑定 `target section/document + source target ids/source refs`；
6. 摘要不是 canonical 原始证据，默认引用必须回到源 segments；
7. 可以作为全局问答的派生上下文，但必须标记 derived 和完整 provenance；
8. source hash、prompt/model/version 构成幂等签名；
9. 文档局部变更只重建受影响 section 及其祖先摘要；
10. LLM 失败时基础检索资产仍可发布，summary capability 标记 degraded。

适用范围：全文总结、主题归纳、跨章节综合和长文档多步问题；不进入基础生产线。

### C13：保留并改造 FTS 与 dense，默认并行召回统一检索单元

8. 上述通道内 canonical 聚合属于 FTS/dense 统一输出契约，不新增独立去重算子；

### C14：融合层收敛为一个可选静态权重的 RRF

### C15：重排层保留专用模型，去重回归 canonical 与结构职责

用户已确认：

### C16：`evidence_hydrate` 按证据类型和预算物化内部证据

用户已确认：

1. `evidence_hydrate` 是正式独立检索算子，但不是最终 MCP 输出算子；它只负责把重排后的 Top-N retrieval hit 物化为内部 hydrated evidence；

3. 默认采用声明式、可版本化的 `auto` hydration policy，根据 target/representation type、文档结构、单条预算、总 token 预算和剩余候选动态选择返回粒度，不写死 small/medium/large 文件标签；

10. list item 默认回填列表标题和命中项，完整列表能装入预算时可整体返回；code block 回填标题路径、紧邻说明和完整代码块；formula 回填公式及紧邻定义/解释；

13. 实现必须对 Top-N 按 target type 批量读取，避免逐条 N+1 数据库查询，并在每次读取时继续校验 snapshot scope 和权限；

15. `assemble` 不再负责数据库回读、证据类型识别、graph/relation expansion；只消费 hydrated evidence，完成 source-span 合并、父子包含处理、整体预算、顺序、引用编号和最终输出投影。

### C18：结构化知识采用“搜索表示 + 直接查询 + 原始证据”三面并存

用户已确认不能把“充分利用结构化数据”退化为“所有内容都只变成 retrieval unit”。本批正式采用三面架构：

```text
ParseIR / canonical assets
  ├→ search projection：retrieval units + FTS/vector index，负责模糊发现和相关性排序
  ├→ structured projection：typed metadata/table/structure store，负责精确过滤、导航、排序和聚合
  └→ source projection：ParseIR/raw segments/source spans，负责准确原文、定位和引用

三路结果或引用
  → evidence_hydrate
  → assemble
```

已确认边界：

1. 所有适合“发现”的内容可以投影为多类型 retrieval unit，但 retrieval unit 不是结构化知识的唯一消费面；
2. document/section/list/code/formula/figure caption 等叙述性内容主要通过 typed retrieval unit 的 FTS+dense 发现；
3. KB、document、relative path、date、content/representation type、section ancestry 等 metadata 作为 FTS/dense 的精确 filter，不新增独立 `metadata_filter` 算子；
4. parent/container/ordinal/source span 等结构事实主要服务 filter、`structure_navigate`、`evidence_hydrate`、source-span merge 和引用，不需要全部变成可排名的搜索文档；
5. 具有稳定 schema 和可执行语义的资产必须同时保留直接结构化查询面；当前最明确的是 `TableAsset/TableCell`，未来真实存在并达到门槛的 KV/form 等也可接入；
6. 表格同时产生 `table/table_row` 搜索表示和 typed structured asset：前者用于模糊发现相关表/行，后者用于完整、严格的行列筛选、排序和聚合；
7. 数值范围、枚举条件、全量匹配、count/sum/min/max/avg 等不得用向量 Top-K 冒充完整结构化结果；
8. `asset_persist` 增强为可查询 structured asset 投影，不为此新增挖掘 LLM 算子；ParseIR 的 TableAsset 仍是 canonical truth；
9. 结构化查询只对通过质量门禁的资产开放，并冻结 `search_ready/structure_navigate_ready/structured_query_ready/aggregate_ready` 等能力事实；
10. 原生 Excel 等高置信表格可以进入 typed query；PDF 推断表格若表头、类型或单位置信不足，只保留 search ready，不能宣称可安全聚合；
11. explicit structured query 和 hybrid retrieval 是不同执行语义：
    - 明确结构条件可直接 `structured_query → hydrate`，不强制经过 RRF；
    - 结构条件 + residual text 时，先将条件作为 filter，再由 FTS/dense 排名；
    - 模糊问题先 hybrid 找到资产，再由 Agent 发起直接结构查询；
12. 结构化查询结果仍必须映射回 canonical evidence/source spans，经 hydrate 和 assemble 返回可引用证据。

各类结构的本批消费边界：

| 结构/资产 | 搜索表示 | 直接查询/过滤 | 结构导航/组装 |
|---|---|---|---|
| 文档、章节、段落 | FTS+dense | document/section filter | parent/children/sibling + hydrate |
| 文档 metadata | 可选进入 lexical text | 精确 filter/sort | 来源展示 |
| TableAsset/TableCell | table/table-row units | typed filter/sort/aggregate | caption/header/row/cell source |
| list/list item | typed units | 当前不做通用关系查询 | container/items/ordinal |
| code block | FTS+当前通用 embedding | 当前无代码专用查询 | 说明邻段+完整代码块 |
| formula | text/LaTeX 精确搜索 | 当前不做数学执行 | 定义/解释/source span |
| figure caption | caption text；当前无图片向量 | 当前无图片结构查询 | caption/mention/original ref |
| 显式脚注、caption、hyperlink、参见章节 | 可进入 lexical text | 按 ref 精确定位 | 确定性 references 导航 |
| LLM 修辞关系、entity/ontology graph | 本批不消费 | 本批不消费 | 不恢复 |

### C19：采用本地 Agent 驱动的渐进式结构检索闭环，服务端零 LLM 规划

用户已确认采用“方案一”：结构化查询和导航由用户本地 Agent 依据 MCP typed tools 自主规划；服务端不新增自然语言转 SQL/DSL 的 LLM `query_plan`，避免额外模型负担。

正式闭环：

```text
本地 Agent 输入自然语言
  → search_knowledge 模糊发现
  → 结果按需返回 evidence/document/structure ref
  → inspect_knowledge 查看真实 schema、可用关系和操作
  → navigate_structure 或 query_structured_asset 传显式参数
  → 服务端校验并返回统一 evidence/结构化错误
  → Agent 根据结果或错误继续收窄、下钻、换参数
  → get_evidence/get_document 获取准确原文或更多文件内容
```

服务端算子边界：

1. 新增确定性 `structure_navigate`：输入已有 `structure_ref + relation + depth/limit`，查询 parent/children/previous/next/ancestors/descendants/container membership/caption/footnote/explicit references；
2. 新增确定性 `structured_query`：输入 `asset_ref + schema-bound DSL`，对 query-ready table 及未来 typed asset 执行 filter/select/sort/pagination/allowlisted aggregation；
3. `structure_navigate` 与已否决的 `tree_navigate` 不同：前者在命中后按明确 ref 导航，后者在召回前根据 query 猜章节并硬过滤；本批不新增 `tree_navigate`，legacy `TreeNavigator` 随固定链退役；
4. 不恢复 `discourse_line` 或段关系版 `graph_expand`；可导航“篇章关系”仅指确定性的 parent/child、previous/next、contains、same container/table/list、caption-of、footnote-of、hyperlink/参见章节；
5. `structured_query` 不接受任意 SQL、数据库表名或内部列名，只接受版本化 DSL 和白名单操作符，如 `eq/ne/lt/lte/gt/gte/in/contains/is_null/order_by/count/sum/min/max/avg/limit`；
6. MCP/Agent 显式传入的 scope/filter/predicate 是 hard constraint；服务端不从自然语言偷偷推导 hard filter；
7. `search_knowledge` 增加显式 filters：`within/document_refs/section_refs/asset_types/evidence_types/include_descendants/relative_path_prefix/date_range` 等，并共同下推到 FTS/dense；
8. 所有调用都必须使用不透明 ref，服务端每次重新鉴权、验证 snapshot/build/current scope、类型、操作符、limit 和复杂度；
9. 本批不建设多轮服务端 reasoning loop；Agent 的工具调用序列就是查询规划和反馈闭环。

MCP 能力发现契约：

1. MCP 工具描述公开六类稳定能力：`search_knowledge/get_evidence/get_document/inspect_knowledge/navigate_structure/query_structured_asset`；
2. `search_knowledge` 保持极简 evidence schema，只在命中资产确实具有可操作结构时额外返回不透明 `structure_ref`；普通证据不得为了统一形状填充无意义空字段；
3. `inspect_knowledge(structure_ref)` 是动态能力发现入口：
   - table 返回真实字段名、类型、单位、asset ref、允许的 filter/sort/aggregate；
   - section/list/document node 返回 title/path、node ref、允许的 parent/children/sibling/descendant/reference 关系；
   - 不 query-ready 的资产返回明确 capability 状态和可用 fallback；
4. `navigate_structure`、`query_structured_asset`、`get_evidence` 继续尽量返回与 `search_knowledge` 相同的 `evidence[] + has_more` 公共形状，避免 Agent 学习多套证据协议；聚合操作可额外返回 `result`，但必须带可追溯来源；
5. table 命中后的典型流程为 `search → inspect schema → structured query → evidence/get exact`；section 命中后的典型流程为 `search → inspect relations → navigate parent/children/previous/next → get exact`；
6. Agent 可以将前一轮返回的 document/section/structure ref 作为下一轮 `search_knowledge.filters.within`，在局部范围继续 FTS+dense，从而支持“模糊找到 → 精确收窄 → 再模糊搜索”的循环；
7. 不把动态 schema、列全集或关系明细塞进每条初始搜索结果；由 `structure_ref → inspect_knowledge` 按需披露，控制默认 token 和认知负担。

结构化错误也属于反馈协议，至少包含：

| 错误码 | 必须反馈给 Agent 的修正信息 |
|---|---|
| `unknown_field` | 当前真实 `available_fields` |
| `type_mismatch` | 字段、expected/received type、可接受格式 |
| `unsupported_operation` | 当前资产允许的 operations |
| `structured_query_unavailable` | readiness 原因和 `search_knowledge` fallback ref/filter |
| `result_too_large` | estimate/limit/pagination 或增加 predicate 的建议 |
| `out_of_scope` | 不区分不存在、越权、版本失效，防止资源探测 |

所有 direct structure 能力必须有上限、分页、超时、审计和 trace；失败不得静默回退成一个看似完整的向量 Top-K 答案。

### C20：现有 `query_understanding` 退出正式体系，不建设替代算子

用户已确认现有 `query_understanding` 直接删除，产品目录和官方预置不再呈现；本批也不重写“轻量版”查询理解算子。

原因和职责归属：

1. 当前实现是 LLM-first，`useLlm` 参数只是 advisory 且执行时未读取；提示词、实体表、意图枚举和规则高度绑定云核心网，不是通用知识库能力；

3. keyword 分词、大小写、词干和同义词属于 FTS index/search analyzer，不能由一套与索引不一致的手写 Jieba/停用词结果替代；

7. API 请求边界仍执行空白清理、长度上限、非法控制字符处理、编码校验和原始 query 留存，但这些是输入安全与规范化，不拆成可编排算子；

- 清理 `entity_exact`、旧 router、旧 assemble/rerank 等对 `QUERY_UNDERSTANDING` slot 的依赖后，删除该 slot/type、提示词和正式 manifest；

- analyzer、同义词和拼写纠正应分别在其真实执行层设计，不能再次打包成一个万能“查询理解”。

### C22：`collect` 退出算子体系，评测直接消费目标节点输出

用户已确认 `collect` 没有独立业务职责，直接从产品、代码、算子目录、官方生产范式和评测范式中删除。

正式边界：

1. 当前 `collect` 只对单个 `CANDIDATE_LIST` 执行 `subList(0, maxItems)` 后原样返回；它不负责多路汇聚、融合、去重、排序、hydrate、assemble、分页或指标计算；
2. 多路 FTS/dense 候选仍由 `rrf` 的 `CANDIDATE_LIST_MULTI` 输入融合；不得把 `collect` 改成直接拼接列表，以免绕过 canonical 去重和通道级排名语义；
3. 范式引擎已经支持将任意节点的已声明输出 slot 作为 graph output，评测范式应直接输出 `fts.candidates`、`dense.candidates`、`rrf.candidates` 或 `model_rerank.candidates`；
4. `collect.maxItems` 拆回真实责任方：召回算子的 `top_k`、RRF 输出上限、rerank 输入/输出上限、`evidence_hydrate.input_top_n`、assemble token budget，以及 evaluation harness 的 `eval_at_k`；

7. `CANDIDATE_LIST_MULTI` 保留，它是融合算子的多输入槽类型，与 `collect` 生命周期无关；
8. MCP 分页和继续检索不属于 `collect`；后续 C23 已确认 `search_knowledge` 本批不做传统分页或 continuation cursor。

### C23：保留并整体重写 `assemble`，作为纯确定性最终证据投影

用户已确认 `assemble` 有真实独立职责，保留算子名称，但现有 `ContextAssembler/ContextPack` 形态不能沿用。新 `assemble` 是生产检索范式唯一的最终证据投影算子，不是检索、hydrate 或推理算子。

正式链路：

```text
FTS + dense
→ RRF
→ model_rerank（可选）
→ evidence_hydrate
→ assemble
→ search_knowledge EvidenceResponse
```

新算子契约：

| 项目 | 已确认要求 |
|---|---|
| 输入 | 已授权、已完成类型物化的 `hydrated_evidence[]`，以及上游已知省略状态 |
| 隐式请求上下文 | 原始 query、响应预算和隔离的 debug 权限 |
| 输出 | 新 `EVIDENCE_RESPONSE`，公开形状为 `query + evidence[] + has_more` |
| 核心参数 | `max_evidence`、`max_total_tokens`；具体默认值留到字段定稿和评测 |
| 幂等性 | 相同输入、相同 policy/version 必须产生相同顺序与输出 |
| 外部读取 | 禁止数据库、索引、文件或网络读取 |
| LLM | 禁止 |

保留职责：

1. 按 `canonical_evidence_id`、确定性 parent/container 关系和 source span 合并同源表示、邻窗重叠、父子包含及完全重复证据；
2. 继承 RRF/model rerank 的上游顺序；合并时保留最高排名位置，不自行计算相关性或执行文本相似度重排；
3. 执行最终 evidence 数量和总 token 预算，只允许结构边界或安全文本边界截断，不做关键词抽句式“智能压缩”；
4. 将内部 target/type 投影为 `paragraph|section|document|table|list|code|formula|figure_caption` 等稳定内容类型；
5. 输出授权后的知识库名、文件名、库内相对路径、章节、页码和 opaque evidence/document ref；服务器物理路径和内部 ID 永不公开；
6. 仅对真实具有可操作结构的证据额外输出 `structure_ref`，普通证据不填空占位；
7. 按最终数组顺序形成引用顺序，数字 score、score chain、channel contribution 和内部命中表示默认只留 trace/debug；
8. 记录输入数、合并数、预算淘汰数、截断数和输出数等内部可观测指标。

删除职责和旧契约：

1. 输入从 `candidates + QUERY_UNDERSTANDING + scope` 改为 hydrated evidence；删除对 `QueryUnderstanding`、旧 router 和 `scope` slot 的依赖；
2. 删除回库读取原段/文档来源、source drill-down、graph/RST expansion、relation 查询、evidence role 分类、冲突检测、suggestions 和意图驱动裁剪；
3. 删除 `relationExpansion/maxExpanded` 等旧参数；parent/window/table header 等物化已经属于 `evidence_hydrate`；
4. 旧公开 `ContextPack/ContextItem` 的 `items/relations/sources/evidenceGroups/issues/suggestions` 不再作为正式 MCP 响应；迁移到 `EVIDENCE_RESPONSE` 后删除 `CONTEXT_PACK` 正式 slot/type 和仅服务旧形状的代码；
5. `assemble` 不吞掉系统性契约错误；空检索结果可以合法返回 `evidence=[]/has_more=false`，单条 canonical 缺失或越权应在 hydrate 阶段丢弃并内部留痕。

公开 evidence 延续 C17 已确认 schema：`ref/type/content/source/truncated`，source 含授权后的 `knowledge_base/file_name/relative_path/document_ref/section/page`；正常响应不暴露内部点、边、segment/unit/canonical ID 或多层分组。

`truncated` 与 `has_more` 语义严格分离：

- `evidence[i].truncated=true`：该条内容未完整装入响应，Agent 应调用 `get_evidence(ref)`；
- `has_more=true`：流水线明确知道仍有其他有效 hydrated evidence 因最终条数/token 预算未输出；
- 顶层 `has_more` 不因单条内容截断而自动为 true，也不得仅因某召回通道返回满 `top_k` 就猜测为 true。

分页和继续检索边界：

1. 本批 `search_knowledge` 不增加 `offset/page/next_cursor`；相关性搜索不是稳定列表枚举，RRF/rerank 和索引更新会使机械 page 2 语义不稳；
2. `has_more` 是信息充分性信号，不是“下一页句柄”；Agent 应根据当前 evidence 使用更明确 query、`filters.within`、asset/evidence type 或结构工具再次检索；
3. `get_evidence` 按 ref 精确取证；`get_document` 按 document/section 渐进读取；`list_documents`、`structured_query` 和大规模 `structure_navigate` 可按其稳定排序语义单独分页；
4. 未来只有真实业务证明需要遍历相关性结果时才考虑短期 opaque cursor，且必须绑定 identity、KB scope、snapshot/build、query、filters、paradigm/ranking policy 和位置，禁止裸数字 offset。

### C24：冷启动库收敛为 4 套挖掘范式、2 套检索范式

用户已确认 P7 不再逐套确认字段和参数细节，正式采用“4 mining presets + 2 retrieval presets + 多对一配套”的最小骨架；具体 schema、默认数值和 UI 文案由最终实施指南在既定边界内定稿。

| 挖掘范式 | 配套检索范式 | 定位 | 默认状态 |
|---|---|---|---|
| 轻量关键词资产 | 关键词证据检索 | 无 embedding 的低资源、精确术语和故障兜底 | 正式可选 |
| 标准混合检索资产 | 标准混合证据检索 | FTS+dense 的通用主线 | **建库和检索默认配套** |
| 问题别名增强资产 | 标准混合证据检索 | 索引期生成带 answer span/source target 的 query alias | 实验增强 |
| 长文档全局增强资产 | 标准混合证据检索 | 索引期生成结构层级 summary alias | 实验增强 |

四套挖掘骨架：

```text
轻量关键词资产：
input_ingest → document_parse → segment_compile
→ retrieval_unit_project → asset_persist → mining_finalize

标准混合检索资产：
input_ingest → document_parse → segment_compile
→ retrieval_unit_project → embedding → asset_persist → mining_finalize

问题别名增强资产：
标准混合主线 + query_expansion_generate
→ 对 alias 执行既定 embedding policy → asset_persist

长文档全局增强资产：
标准混合主线 + hierarchical_summary_generate
→ 对 summary alias 执行既定 project/embedding policy → asset_persist
```

两套检索骨架：

```text
关键词证据检索：
scope_resolve → fts → evidence_hydrate → assemble

标准混合证据检索：
scope_resolve + query_embed
→ (fts || dense_vector) → rrf
→ model_rerank（可选且失败保持 RRF 顺序）
→ evidence_hydrate → assemble
```

组合边界：

1. query alias 和 summary alias 都是标准 FTS/dense 的 eligible representation，命中后统一回到 canonical evidence，因此两个增强挖掘范式复用标准混合检索，不复制检索图；
2. structured metadata/table/parent/container/source span 等确定性资产由所有适用挖掘范式共同生产和持久化，不另建“表格挖掘范式”；
3. small-to-big 是 `evidence_hydrate.auto` 的通用返回策略；表格严格查询、结构导航分别是 Agent 调用 `query_structured_asset`、`navigate_structure` 的通用能力，均不是独立检索范式；
4. 纯向量、dense+rerank 等只允许作为内部消融/评测图，不作为正式生产预置；
5. GraphRAG/entity graph、query understanding、HyDE、multi-query、contextual 专用链和全文返回专用链均不初始化正式预置；
6. 不建立 query alias × summary alias 等组合预置；高级用户可定制 graph，但官方冷启动库不承担排列组合；
7. 两个离线 LLM 增强范式必须显式标识成本、degraded 发布语义和实验状态，只有通过 P8 真实评测门槛后才可晋级为正式推荐；
8. 实施方可在最终指南中确定 manifest ID、参数默认值、readiness requires/provides、fallback 和展示文案，但不得改变 4+2 数量、默认配套、生成式 LLM 边界或新增未经确认的官方预置。

## 5. 已确认的设计原则

1. **不是为了使用现有算子而设计范式。** 没有稳定业务增益的算子允许下线。
2. **内容类型不自动等于算子。** table、code、list 优先作为 unit type/facet/结构契约。
3. **只有独立成本、独立失败语义、独立资产和明确消费者才拆算子。**
4. **挖掘与检索必须成对设计。** 每个资产必须说明生产者、持久化事实、消费算子和验收指标。
5. **默认链优先确定性、低成本、普适能力。** LLM 离线增强必须以真实业务查询消融实验晋级。
6. **大文档以确定性结构层级为主导，不以 LLM 修辞关系为主导。**
7. **小粒度用于召回，大粒度用于返回。** 返回粒度按候选文件结构和上下文预算动态决定。
8. **不写死 small/medium/large。** 文档大小是相对于模型上下文预算、查询范围和任务类型的运行时判断。
9. **能力成功以真实资产和质量衡量。** 不能仅因图中存在算子或 handler 返回 SUCCESS 就宣布 capability。
10. **统一搜索负责发现，直接结构查询负责严格约束。** Top-K 相似结果不得冒充完整结构化结果。
11. **结构能力采用渐进披露。** 初始 MCP 结果保持极简，Agent 通过 opaque ref 和 inspect/navigate/query 工具按需展开。
12. **检索运行时零生成式 LLM。** 服务端检索只提供确定性搜索、结构能力、embedding 和专用 rerank；推理、改写和多轮规划由本地 Agent 承担。
13. **最终输出是证据投影，不是新的检索阶段。** `assemble` 不回库、不推理、不重排，只做确定性合并、预算和公开协议映射。
14. **官方范式按能力差异收敛，不按资产类型排列组合。** 增强资产优先复用标准检索链，small-to-big 和结构工具是通用能力而非新范式。
15. **测试环境采用 clean break。** 退役能力直接删代码、清数据、重建新资产，不把生产兼容成本带入当前批次。

## 6. 已完成确认的议题（历史讨论清单）

以下顺序是后续对话的默认议程。每项由用户确认后，回填本文“已确认决策”。

### P1：`retrieval_unit_project` 的单元类型和结构关系（已转入 24 号实施文档）

已确认：

- 原始内容资产与检索表示分层；
- `retrieval_unit_project` 只编译可搜索表示，`asset_persist` 负责入库；
- 不是所有原始内容都成为 retrieval unit，也不是所有 unit 都同时做 FTS 和 embedding；
- `segment_compile` 负责结构真相；project 通过 target/source refs 映射；
- parent/container/ordinal 表达确定性层级和邻接，不新增 LLM 关系算子；
- 召回后由 `evidence_hydrate` 按类型读取原文并扩展，再由 `assemble` 合并预算；
- 多检索表示按 `canonical_evidence_id` 去重。

留到最终字段设计时落实：

- document / section / child 是否都要成为可检索 unit；
- table whole / table row 的一一投影；
- code block、list group、figure caption 是否独立 unit type；
- parent-child、previous-next、same-section、same-table、same-list 的具体字段和索引；
- 哪些字段进入 lexical text、embedding text、facets、source refs；
- 小文件的 document unit 与 child unit 是否同时生产。

### P2：embedding 算子重构（已转入 24 号实施文档）

已确认：

- 保留一个 embedding 算子；
- pipeline 选择一套 embedding policy，而不是全局单选 mode；
- policy 按 retrieval unit 类型/能力自动选择不同 strategy；
- 系统提供固定默认映射，用户可以通过算子参数定制覆盖；
- `skip | isolated | structural | contextualized | late_chunking` 是 per-unit/per-group strategy；
- 默认零 LLM，当前 per-chunk LLM contextualizer 不恢复；
- 真实 provider/model/version/dimension/strategy/input hash/coverage 必须冻结；
- 当前单一文本 embedding 模型，所有 unit 共用一个向量空间，query 每次只向量化一次；
- 多模型、多 profile 分路召回不在本批实施范围。

留到最终字段设计时落实：

- policy schema、规则优先级和默认矩阵版本；
- structural context 字段的最大长度与格式；
- 同一 source unit 多个 `text_kind/vector_kind` 的物理约束；
- 覆盖率、重跑回填、partial retry 和 readiness 的具体阈值；
- provider capability 的注册与编译期校验接口。

### P3：问题生成/query expansion（已转入 24 号实施文档）

已确认：

- 正式命名为 `query_expansion_generate`；
- 从 `retrieval_unit_build` 拆出，成为独立可选 LLM 算子；
- 产物是 `query_alias` 检索表示，不是可返回证据；
- eligibility 按 unit 类型提供固定默认规则并允许用户覆盖；
- 默认每 target 最多一个 alias；
- LLM 可正常返回 SKIP；
- 每个 alias 必须携带可验证 `answer_span` 并绑定 canonical source target；
- FTS/dense 命中 alias 后由 `evidence_hydrate` 返回源证据；
- 不进入零 LLM 基础线，只进入可选 Query Expansion 增强范式。

留到最终字段设计时落实：

- 默认 eligibility 数值、各类型阈值和可配置 schema；
- child/parent/section 作为 source target 的精确选择规则；
- answer-span 归一化匹配算法；
- 去重阈值、文档级成本上限和幂等签名；
- prompt/model/version 及发布统计字段；
- 真实业务问题集上的晋级门槛。

### P4：大小文档与长文档高级资产（已转入 24、25 号实施文档）

已确认：

- 全文/父块/邻窗由 `evidence_hydrate` expansion policy 负责，不新增对应挖掘算子；
- 不写死小/中/大文档分类，按运行时预算和结构事实动态判断；
- 小文件仍建立 child 检索表示；
- 大文档局部问题不需要 summary/discourse；
- 新增可选 `hierarchical_summary_generate`；
- 摘要是带完整 source refs 的 `summary_alias`，不是 canonical 原始证据；
- 层级摘要只进入长文档全局增强范式；
- 真正 RAPTOR 暂不建设，不得用结构摘要冒充。

留到最终字段设计时落实：

- expansion policy schema、默认预算和命中密度规则；
- summary eligibility、层级、输入/输出 token 默认值；
- summary source refs、derived context 和发布统计字段；
- 查询意图识别及 long-context/RAG fallback 由 P6 检索侧讨论落实。

### P5：GraphRAG、实体图和篇章研究线边界（已确认）

已确认：

- 本批不建设 GraphRAG，未来统一规划；
- 实体/本体代码保留，但产品不呈现、不进预置、不供新正式范式使用；
- `discourse_line` 与当前段关系版 `graph_expand` 成对退役并在 clean break 中直接删除；

- `assemble` 删除隐藏 relation expansion；
- 可追溯的原文显式引用关系可继续存储。

### P6：检索侧配套算子（已转入 25 号实施文档）

已确认：

- FTS 与 dense 默认并行；融合收敛为一个支持可选静态权重的 RRF；
- 保留专用 `model_rerank`，`llm_rerank` 仅留实验代码且产品不呈现，`score_rerank` / `rerank_post` 不进入正式能力；
- 去重与融合围绕 canonical evidence 进行，删除隐藏的文本相似度去重；
- parent/neighbor/whole-document、table header/code/list 等上下文由 `evidence_hydrate` 确定性回填；
- 不新增召回前猜章节并硬过滤的 `tree_navigate`，legacy `TreeNavigator` 随固定链退役；
- 新增命中后、基于明确 `structure_ref` 的确定性 `structure_navigate`；
- 新增基于 `asset_ref + schema-bound DSL` 的确定性 `structured_query`；
- 本批不新增服务端 LLM `query_plan` 或自然语言转 SQL/DSL；由本地 Agent 调用显式 MCP 工具完成“模糊发现 → 能力探查 → 结构导航/直接查询 → 错误反馈修正”；
- 不新增统一 `retrieval_route` 算子：本地 Agent 通过工具选择和显式参数决定路径，服务端各算子只校验、执行和返回能力/错误事实；
- `assemble` 只做最终合并、预算、排序与 MCP 输出投影，不承担路线规划和数据库读取。
- 现有 LLM-first、领域硬编码的 `query_understanding` 直接删除，不建设替代算子；基础清洗归 API，语言分析归 FTS analyzer，规划归本地 Agent。
- 本批检索运行时禁止生成式 LLM；`multi_query`、HyDE、`llm_rerank` 及相关提示词/模板/manifest 直接删除；本地 Agent 通过多轮 `search_knowledge` 承担改写和拆解。
- `collect` 直接删除；评测范式直接输出被测节点的 candidates，截断参数回归真实阶段或 evaluation harness，多路融合仍只由 RRF 负责。
- `assemble` 保留名称但整体重写为纯确定性最终投影：输入 hydrated evidence，输出 `EVIDENCE_RESPONSE`；旧 ContextPack、回库、图关系、意图分类和 suggestions 全部退出。
- `search_knowledge` 本批不做传统分页/cursor；`has_more` 只表示已知其他证据因最终预算未输出，Agent 通过收窄、改写、下钻和结构工具继续取证。

### P7：挖掘×检索冷启动范式库（骨架已确认，实施细节交最终指南）

已确认：

- 初始化 4 套挖掘范式、2 套检索范式，多对一配套；
- 标准混合资产 × 标准混合证据检索是建库和检索默认；

- 不再要求用户逐项确认每套链路的数值和字段，最终指南按 C24 固定边界给出实施级契约。

### P8：真实质量评估和算子晋级制度（本批取消为产品议题）
