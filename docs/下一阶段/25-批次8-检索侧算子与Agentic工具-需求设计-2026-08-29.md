## 1. 原始需求与最终判断

用户的核心问题是：既然文档已经解析出大量结构化信息，检索是否仍只应把所有东西转成检索单元做向量/关键词 Top-K？最终结论是三条消费路径并存：

```text
模糊发现：FTS + dense → RRF → optional rerank
证据物化：candidate → canonical target → parent/window/table/whole-document
精确操作：明确 structure_ref/asset_ref → navigate / schema-bound structured query
```

本地 Agent 承担问题拆解、改写、工具选择和多轮反馈；服务端不再调用生成式 LLM 猜意图、生成查询、HyDE、LLM 重排或 NL-to-SQL。这样既利用用户本地 Agent 的推理能力，也避免检索服务的 LLM 延迟和成本。

本批目标：

1. 只保留范式执行链，彻底删除固定 SearchService 九步链；
2. 以全库索引统一召回，不遍历 1000 个文件逐一“路由”；
3. 以 canonical evidence 聚合多种搜索表示，命中后才读取少量候选的结构和原文；
4. 将返回协议压缩为 Agent 易理解的 evidence 列表，不暴露点、边、切片 ID 和 score chain；
5. 通过 MCP 渐进披露结构能力，让 Agent 从模糊发现闭环到精确导航/查询；
6. 初始化 2 套检索预置，与挖掘侧 4 套资产预置多对一配套。

本批不做：GraphRAG、召回前文档逐一 routing、服务端 query planning/NL-to-SQL、传统 search pagination/cursor、正式质量晋级平台。

## 2. 当前代码事实与必须移除的双链路

### 2.1 当前正式算子目录

`agent_serving_java/.../serving/operator/operators` 当前有 19 个算子：

- input/query：`request_input/query_understanding/query_embed/multi_query/hyde`；
- scope/retrieve：`scope_resolve/dense_vector/fts/entity_exact/entity_graph/graph_expand`；
- fuse：`identity/rrf/weighted_rrf`；
- rerank：`llm_rerank/model_rerank/score_rerank`；
- output：`collect/assemble`。

### 2.2 现有官方图仍是旧目标

`operator/paradigm/ParadigmService.java` 的 `OFFICIAL_DEFAULT_GRAPH` 当前为：

```text
query_embed + scope_resolve
→ dense_vector || fts
→ weighted_rrf
→ model_rerank
→ assemble(relationExpansion=true)
→ contextPack
```

`ParadigmGraphs.isServable()` 也把 output slot 是否为 `contextPack` 当作可服务判断。这与本批确定的 `HYDRATED_EVIDENCE_LIST → EVIDENCE_RESPONSE` 不一致，必须整体更新。

### 2.3 范式外仍有固定链

旧 `SearchService` 及其协作者还包含 query understanding、TreeNavigator、multi-query、HyDE/语义缓存、召回、图扩展、ContextAssembler 等隐藏步骤。它会造成“画布图不是实际运行链”。本批必须删除固定链及其路由/回落，所有 `search_knowledge` 只运行已发布范式。

### 2.4 现有 MCP 暴露了内部实现

当前 `mcp_server/server.py` 提供 `search_knowledge/get_segment_fulltext/list_knowledge_bases/list_documents/get_document/upload_document`。`get_segment_fulltext` 要求 Agent 传回 `type + id + paradigm_id`，搜索响应包含 `_retrieval` 和 ContextPack 相关结构。用户已经明确：正常 Agent 不应看到内部 retrieval unit/raw segment ID、边、分数组和复杂包结构。

## 3. 目标检索数据流

### 3.1 标准混合检索

```text
API 边界校验 query / explicit scope / explicit filters
              │
        scope_resolve       query_embed（一次）
              │                 │
              ├──── fts ║ dense_vector ────┤
              │          并行               │
              └──────────→ rrf ←────────────┘
                              │
                    model_rerank（可选 Top-N）
                              │
                      evidence_hydrate
                              │
                          assemble
                              │
                      EVIDENCE_RESPONSE
```

索引先把结果收敛到 Top-K representation/canonical evidence，`evidence_hydrate` 才批量读取少量候选文件的源和结构。绝不按文件数执行检索流程。

### 3.2 结构化渐进闭环

```text
Agent: search_knowledge（模糊找）
  → evidence 中获得 actionable structure_ref / source document_ref
  → inspect_knowledge（看真实能力、schema、可导航关系）
  → navigate_structure 或 query_structured_asset
  → 根据 typed error 修正字段/关系/范围
  → 必要时再次 search_knowledge / get_evidence / get_document
```

服务端只校验和执行明确参数，不从自然语言偷偷推断 hard filter、结构字段或 SQL。

## 5. 核心中间契约

### 5.1 `RetrievalCandidate`

现有 candidate 应 clean-break 收敛为内部对象：

| 字段 | 说明 |
|---|---|
| `representation_ref/type` | 命中的搜索表示，仅内部使用 |
| `canonical_evidence_id` | 跨 raw/query alias/summary/multi-view 的融合键 |
| `target_type/target_ref` | hydrate 的 canonical target |
| `source_refs` | 文档、section、segment/asset/span 引用 |
| `channel_id` | `fts` 或 `dense` 等稳定通道标识 |
| `channel_rank/channel_score` | 供融合/调试，正常 MCP 不暴露 |
| `ranking_text` | reranker 的有界输入，不等于最终 evidence content |
| `facets/capability_facts` | 已持久化的过滤和可展开事实 |

同一通道应先按 `canonical_evidence_id` 聚合，保留最佳 rank/score 和命中 representation refs，再进入 RRF；否则 query alias 与 raw text 会给同一证据重复投票。

### 5.2 `HydratedEvidence`

`evidence_hydrate` 输出内部 `HYDRATED_EVIDENCE_LIST`：

- canonical evidence id；
- evidence type；
- exact source spans 与有序内容片段；
- source projection（KB/file/path/document/section/page）；
- expansion mode/reason；
- optional actionable structure/asset refs；
- derived/source-backed 标记；
- token/character estimate；
- internal provenance/debug（仅 debug 侧通道）。

它可以带内部 ID 供 assemble 使用，但 assemble 必须映射为 opaque public ref 并剥离实现细节。

### 5.3 `EvidenceResponse`

正常 `search_knowledge` 唯一公开响应：

```json
{
  "query": "用户原问题",
  "evidence": [
    {
      "ref": "ev_opaque",
      "type": "prose",
      "content": "可直接给 Agent 阅读的证据内容",
      "source": {
        "knowledge_base": "知识库名称",
        "file_name": "文件名",
        "relative_path": "可选/库内路径",
        "document_ref": "doc_opaque",
        "section": "可选/章节路径或标题",
        "page": 12
      },
      "truncated": false,
      "structure_ref": "st_opaque_optional"
    }
  ],
  "has_more": false
}
```

硬约束：

- 不暴露 retrieval unit/raw segment/数据库 UUID、点边、关系图、score、score chain、rank、evidence group、范式内部节点；
- `structure_ref` 仅在确实可导航或可 inspect 时返回；
- `type` 可扩展为 `prose|section|document|table|table_row|list|code|formula|figure_caption|derived_summary`；
- `truncated=true` 表示可用 `get_evidence(ref)` 取准确完整内容；
- `has_more=true` 只表示 assemble 已知还有候选因条数/token 预算未输出，不表示传统分页；
- debug 信息进入显式授权的独立诊断响应/日志，不污染正常 evidence schema。

## 6. 逐算子需求

### 6.1 API entry input（取代 `request_input`）

API 边界负责：query trim、空值/长度/编码校验、explicit scope/filter schema 校验、身份解析和 request id。`ParadigmExecutor` 已支持 `entryInputs={query:...}`，因此删除只复制 query 的 `request_input` 节点。entry input 是图外输入契约，不是用户可拖拽算子。

### 6.2 `scope_resolve`

**输入：**调用者身份、domain、已开放 KB、请求明确给出的 `within/filters`、范式可选固定 `kbIds`。  
**输出：**`ActiveScope`，含 authorized KB、active build/snapshot refs、规范化 hard filters。  
**规则：**

1. 先授权求交，再解析活动 Build/快照；
2. 图内固定 KB 只用于专属范式；通用官方范式保持空，由请求/库级默认/官方默认确定范式和范围；
3. `document_refs/section_refs/structure_ref/relative_path_prefix/date_range/asset_types/evidence_types/include_descendants` 等显式参数是 hard constraints；
4. 不从 query 猜文档、章节、日期或实体，也不逐文档执行；
5. ref 不在授权范围返回 `out_of_scope`，不存在/过期 ref 返回稳定 typed error；不得泄漏其是否属于其他用户。

### 6.3 `query_embed`

每次请求只对归一化后的原 query 调用一次当前文本 embedding 模型。必须校验 provider/model/version/dimension 与活动 Build 的 embedding profile 相容；不相容明确失败或让调用方选择 lexical preset，不能循环为每种 knowledge representation 生成不同 query vector。

可观测记录 model/version/dim/latency/error，不记录敏感 query 全文到普通日志。它不是生成式 LLM 算子。

### 6.4 `fts`

**输入：**query + ActiveScope。  
**输出：**channel_id=`fts` 的候选。  
**要求：**

- 只检索 `lexical_eligible=true` 的 representation；
- 对中文/英文等使用确定性 analyzer，分词/同义词归索引分析器而非 query understanding；
- scope 和 filters 在 Top-K 之前下推；
- tsvector/trigram/LIKE 的 fallback 行为必须可观测且不能绕过相同授权/filter；
- 同通道按 canonical evidence 聚合后取 `topK`；
- query alias 命中保留 representation provenance，但候选 target 指向源证据；
- 空结果是正常结果，存储/权限错误不是空结果；
- 中文等 CJK 查询必须先经**与索引侧同源同版本**的分词器（默认 jieba）分词再构造 tsquery；分词器版本与活动 Build manifest 不一致时显式失败（契约见 24 号 §5.8）。

### 6.5 `dense_vector`

**输入：**一次 query vector + ActiveScope。  
**输出：**channel_id=`dense` 的候选。  
**改造：**删除 `textKind=raw_text|question|both` 及 `OperatorEmbeddingMapper` 对旧 `unit_type/text_kind` 的特殊映射；统一检索活动 Build 中 `dense_eligible=true`、维度/profile 相容的 embeddings。representation type、asset type、document/section 等都作为确定性 filter。

同一 canonical evidence 可能有 raw/query alias/summary 等多个 vector；通道内先聚合再 Top-K，不能重复占位。无向量能力的 scope 应返回明确 capability diagnostic；关键词预置不调用本算子。

### 6.6 `rrf`

收敛 `rrf/weighted_rrf/identity` 后唯一融合算子。

```text
score(canonical) = Σ channel_weight[channel_id] / (k + rank_in_channel)
```

- 默认 `k=60`、所有 channel weight=1.0；参数可静态覆盖；
- channel_id 由上游固定声明，不从任意 metadata 字符串猜；
- 输入按 canonical evidence 对齐，输出保留各通道最佳命中 provenance 供内部 debug；
- equal score 使用稳定 tie-break（最佳 rank、canonical key）；
- 不做文本相似度去重、结构扩展、阈值过滤或 DB 查询；
- 单通道评测可直接消费 fts/dense 输出，不需要 identity。

### 6.7 `model_rerank`

只对融合后的有限 Top-N（默认不超过 50，最终返回通常 ≤10）调用专用 reranker。`ranking_text` 按类型有界构造：prose 用标题路径+正文，table row 用 caption/header/row，code 用路径+代码，alias 必须补源证据摘要而不是只排问题文本。

输出只改变候选顺序/专用 score；不得改变 canonical target、filters 或 source refs。超时、服务不可用、返回数量/identity 不合法时，原样保留 RRF 顺序并记录 degraded，绝不调用 `llm_rerank` fallback。

### 6.8 `evidence_hydrate`

这是“搜索表示命中后如何变成真实证据”的唯一主链算子，不是 document route。

**输入：**Top-N candidates + ActiveScope + expansion options + evidence/token 预算。  
**输出：**`HYDRATED_EVIDENCE_LIST`。  
**实现约束：**

1. 批量解析 candidate 的 canonical target/source refs，按 document/table/structure 分组查询，禁止 N+1；
2. 只读 Top-N 涉及的资产，不遍历 KB 文档，不递归无界图；
3. query/summary alias 必须回到 source target；summary 如作为 derived context 输出也必须附完整 source refs；
4. options：`mode=auto|exact|window|parent|whole_document`，另有有界 `windowRadius/maxParentTokens/maxDocumentTokens`；
5. `auto` 使用客观事实和本次预算：全文 fits 才 whole document；父章节 fits 则 parent；否则 exact/window；不持久化 small/medium/large 标签；
6. 类型化展开：

| 命中类型 | 默认 hydrate |
|---|---|
| prose | exact + 同 section 有界邻窗；父 section fits 时可返回 parent |
| section/document | 对应 section；整个 document fits 且请求允许时返回全文 |
| table_row | caption + headers + hit row；保留 cell/source refs |
| table | 有界整表；过大时返回 caption/header/命中区域并 `truncated` |
| list | 完整 list container 或有界分组 |
| code | 完整 code block + section path |
| formula | 完整公式 + 有界相邻说明 |
| figure_caption | 原始 caption + 明确 mention；无图片向量推理 |

7. 只依据 parent/container/ordinal/caption/footnote/explicit reference 等确定性结构；不读旧 RST relation；
8. 证据读取失败按候选留痕并跳过；授权/存储系统性失败必须失败，不能伪装为空；
9. 生成稳定 opaque evidence/document/structure/asset refs，ref 需绑定授权范围和不可变快照，防篡改/不可枚举；
10. hydrate 不做最终条数截断、公开协议投影或 rerank。

### 6.9 `assemble`

保留名称但删除当前 `ContextAssembler` 混合职责。

**输入：**`HYDRATED_EVIDENCE_LIST`。  
**输出：**`EVIDENCE_RESPONSE`。  
**唯一职责：**

- 先按 canonical evidence 合并，再按 source span 重叠和父子包含去重；
- 保持 rerank/RRF 的证据顺序；同一证据的扩展片段按源 ordinal 排列；
- 执行最终 `maxEvidence/maxOutputTokens` 预算，设置 item `truncated` 与顶层 `has_more`；
- 投影 §5.3 的公开字段并剥离内部信息；
- 生成/转交 opaque refs 和授权后的来源名。

**禁止：**DB/网络读取、LLM、query intent、字符相似度压缩、关系/图扩展、冲突分析、suggestions、evidence roles/groups、二次重排。旧 `ContextPack/CONTEXT_PACK`、相关 SlotType、可服务判断、controller DTO 和 MCP parser 直接删除。

### 6.10 `structure_navigate`

确定性后端算子，由 `navigate_structure` MCP tool 调用，不加入搜索主图。

**输入：**authorized `structure_ref`、relation、depth/limit/cursor。  
**白名单关系：**`parent|children|previous|next|ancestors|descendants|container|caption|footnotes|references`。  
**输出：**稳定顺序的结构节点摘要、public refs、source projection、可继续关系和 cursor。

默认 depth=1；descendants/ancestors 有严格上限。`references` 仅跟随原文显式可追溯边。不得根据 query 猜章节、把导航结果作为隐藏 hard filter，或复用 legacy `TreeNavigator` 的实体/标题推断逻辑。

### 6.11 `structured_query`

确定性后端算子，由 `query_structured_asset` MCP tool 调用，不加入模糊搜索主图。

**输入：**authorized `asset_ref` + schema-bound DSL。  
**允许操作：**

- filter：`eq/ne/lt/lte/gt/gte/in/contains/is_null`；
- projection：`select`；
- stable sort：`order_by`；
- pagination：bounded `limit + cursor`；
- aggregate：`count/sum/min/max/avg`，仅字段 capability 允许时。

示例：

```json
{
  "asset_ref": "asset_opaque",
  "query": {
    "select": ["型号", "最大功耗"],
    "where": [{"field": "最大功耗", "op": "lte", "value": 100}],
    "order_by": [{"field": "最大功耗", "direction": "asc"}],
    "limit": 20
  }
}
```

字段名、类型、enum、可过滤/排序/聚合能力来自 `inspect_knowledge`，不是内部列名。禁止 arbitrary SQL、内部 table name、表达式执行、join 任意资产、自然语言转 DSL。表格 quality/readiness 不足时返回 `structured_query_unavailable`，Agent 可退回 search/get evidence。

### 6.12 `query_understanding`

直接删除 operator、`QueryUnderstandingEngine`、领域 prompt/profile 依赖、DTO、测试、固定链和 assemble/evidence-role 消费。API 只做基础输入校验，FTS analyzer 做语言分析，Agent 负责意图与范围；不得留下规则版替代算子或 runtime intent 隐藏分流。

### 6.13 `multi_query`

直接删除 operator、`MultiQueryExpander`、LLM prompt、固定链调用和无消费者的 `STRING_LIST` 输出用法。本地 Agent 可显式多次调用 search；服务端不暗中扩写，也不把失败回落为原 query 后宣称执行成功。

### 6.14 `hyde`

直接删除假设文档生成和 `embedHyDE` 检索入口、参数、测试与 preset。query 只由 `query_embed` 使用当前文本模型向量化一次；不保留 HyDE fallback。

### 6.15 `entity_exact`

确定性源码可随实体研究线保留，但从正式 component/catalog、API、UI、seed 和范式 compiler 可用集合隔离。它当前依赖 `QueryUnderstanding.entities`，而该上游已删除；本批不得通过简单字符串猜实体重新接线。

### 6.16 `entity_graph`

源码随 GraphRAG 研究保留，正式隐藏且不消费生产图表。删除官方范式和运行时注册；不得以多跳代码存在就声明 GraphRAG ready，未来启用需重新设计生产与查询闭环。

### 6.17 `graph_expand`

直接删除 operator、BFS 段关系 mapper/retriever、preset、测试和 assemble 内隐藏关系扩展，与挖掘 `discourse_line` 成对退役。确定性 parent/window/table expansion 只能由 `evidence_hydrate` 实现。

### 6.18 `identity`

直接删除直通算子和测试。单通道范式/评测图直接把 FTS 或 dense 的 candidates slot 声明为 output；不得为画布连线方便保留一个无独立语义节点。

### 6.19 `weighted_rrf`

将 `weights` 参数、校验和测试合并到唯一 `rrf` 后删除 operator type、类、注册和旧 graph JSON。旧 manifest 不迁移；静态权重缺省等于 1.0。

### 6.20 `llm_rerank`

直接删除 operator、生成式模板、`LlmReranker` bean、测试和所有 fallback。专用 `model_rerank` 失败时保留 RRF 顺序，绝不转调本能力。

### 6.21 `score_rerank`

直接删除按已有 score 再排序/threshold 的算子。RRF/model rerank 各自定义顺序；召回阈值必须归属明确召回参数或 evaluation harness，不新建 `rerank_post`。

### 6.22 `collect`

直接删除 operator、`maxItems` 参数、servable/evaluation 特判和 preset 节点。评测 harness 直接读取被测节点 output 并自行应用 `eval_at_k`；MCP 的预算与 `has_more` 由 assemble 负责。

## 7. 显式 filters 与 Agent 控制

### 7.1 `search_knowledge` 输入

```json
{
  "query": "...",
  "kb_names": ["可选"],
  "within": {
    "document_refs": ["doc_..."],
    "section_refs": ["st_..."],
    "structure_ref": "st_...",
    "include_descendants": true
  },
  "filters": {
    "relative_path_prefix": "规范/接入网",
    "asset_types": ["table"],
    "evidence_types": ["table_row", "prose"],
    "date_range": {"from": "2026-01-01", "to": "2026-12-31"}
  },
  "expansion": {"mode": "auto"},
  "top_k": 20,
  "debug": false
}
```

具体字段可拆为 Pydantic/Java DTO，但语义必须一致。Agent 明确传入的 constraints 是 hard filters，并在 FTS/dense 之前下推；服务端不能根据 query 自动增加 hard filters。未传表示宽检索，Agent 从结果和 inspect 反馈后再收窄。

### 7.2 Typed errors

所有结构工具使用稳定错误码和可操作 details：

| code | 语义/Agent 下一步 |
|---|---|
| `unknown_field` | 字段不存在；返回允许字段摘要或提示 inspect |
| `type_mismatch` | value 与字段类型不符；返回 expected type |
| `unsupported_operation` | 字段不支持该 filter/sort/aggregate |
| `structured_query_unavailable` | 资产未通过 readiness；退回 evidence 或换资产 |
| `result_too_large` | 缩小范围、增加 filter 或使用 cursor |
| `out_of_scope` | ref 不在当前授权范围；不泄漏真实归属 |
| `invalid_ref/expired_ref` | ref 非法或所绑定快照不再可读；重新搜索/列文档 |

错误反馈是 Agent 闭环的一部分，不能统一返回 500 或空数组。

## 8. MCP 工具设计

### 8.1 正式取证工具族

| MCP 工具 | 作用 | 后端能力 | 返回原则 |
|---|---|---|---|
| `search_knowledge` | 模糊发现并返回可读证据 | 检索范式主图 | 极简 EvidenceResponse |
| `get_evidence(ref)` | 取某条证据的完整/更大粒度原文 | authorized ref resolver + hydrate | 不再要求 type/id/paradigm_id |
| `get_document(document_ref)` | 获取准确文件内容/结构化章节 | source projection reader | 可有 token/页范围和稳定分页 |
| `inspect_knowledge(ref)` | 看 document/structure/asset 的能力、schema、关系 | readiness/schema registry | 渐进披露，不吐内部 DDL |
| `navigate_structure` | 沿明确结构关系导航 | `structure_navigate` | public refs + stable cursor |
| `query_structured_asset` | 对表格等 ready asset 过滤/排序/聚合 | `structured_query` | typed rows/aggregate + schema ref |

`get_segment_fulltext` 被 `get_evidence` 取代并直接删除。`get_document` clean-break 改为 `document_ref` 主键，而不是要求 Agent 同时记住 kb name + internal document id。

工具数量由 6 扩至 9：`MCP_TOOL_NAMES` 开关白名单、开放库与描述编辑体系（批次7 交付）同步扩展。

### 8.2 保留的管理/浏览工具

`list_knowledge_bases/list_documents/upload_document` 继续保留，它们不属于检索算子：

- list 返回 public KB/document refs，分页使用稳定 order/cursor 或已有有界列表语义；
- upload 仍不自动挖掘，并受编辑权限和大小/MIME 校验；
- 工具开关/描述可编辑机制保留；关闭某工具时 initialize 指令不得继续暗示可用（**已知限制**：fastmcp 3.4.7 的 initialize instructions 注入在中间件路径外不生效——批次7 S5b；tools/list 动态清单与描述替换已生效。8c 波次升级 fastmcp 收口，升级前该要求降级为“工具清单动态化已生效、instructions 注入随升级收口”）；
- list/get/search/navigate/query 均复用用户级 MCP key 和开放 KB 授权。

### 8.3 Agent 如何知道结构能力

1. `search_knowledge` 的 evidence 只在可操作时给 `structure_ref`；
2. `inspect_knowledge(evidence.ref|document_ref|structure_ref|asset_ref)` 返回 `capabilities`，如 `can_navigate/can_query_structured/can_aggregate`；
3. inspect 同时返回允许关系、asset refs、字段 display name/type/operations；
4. tool description 明确建议“先 search，看到 ref 后 inspect，再 navigate/query”；
5. structured errors 回传修正信息，使 Agent 可以反馈式重试；
6. 不把完整 schema 和关系图塞进每次 search 响应，避免把 Agent 搞晕。

## 10. 安全、性能与可观测

### 10.1 安全

- 任何 public ref 在解析后再次校验用户开放 KB、active snapshot/build 和对象类型；
- FTS、dense、hydrate、navigate、structured query 的授权条件必须一致；
- structured DSL 只编译白名单字段和参数化 SQL，禁止字符串拼接列/操作符；
- `out_of_scope` 不泄漏对象是否存在或属于哪个 KB；
- debug 仅对有权限的显式请求开放，且不返回 secret、连接信息或其他 KB metadata；
- query、文件内容和 refs 的日志按敏感数据策略截断/哈希。

### 10.2 性能预算

- FTS/dense 并行；filters 在各自 Top-K 前下推；
- canonical aggregation 在通道内完成，RRF 输入不带大量重复 alias；
- rerank 限定 Top-N，失败不重试生成式 LLM；
- hydrate 按 target 批量查询，禁止 candidate N+1；
- assemble 纯内存确定性处理；
- navigate/structured query 都有 depth/limit/result-size 上限；
- search 无 offset/cursor，Agent 通过收窄和下钻控制结果面。

### 10.3 可观测

内部 trace 至少记录：scope 数量、过滤条件摘要、各通道 raw/canonical 数量、RRF 输入输出、rerank 是否降级、hydrate mode/批次数/缺失 ref、assemble 去重/截断/has_more、各阶段延迟。正常 MCP 响应不含这些 trace。

## 13. 验收标准

### 13.1 算子和范式

- 正式 catalog 只出现保留/新增算子；旧 11 个删除算子不可创建、发布或执行；研究实体算子不可见；
- 两套官方图可编译、执行并输出 `EVIDENCE_RESPONSE`；servable 判定不再依赖 ContextPack；
- 同一 query 只调用一次 embedding；FTS/dense 默认并行且 filters 完全一致；
- raw/query alias/summary alias 命中同一 canonical evidence 只占一个融合位；
- model rerank 失败时顺序等于 RRF，不触发 LLM fallback；
- hydrate 不出现全库扫描/N+1，assemble 不访问数据库。

### 13.2 内容和结构

- 小文件在预算内可返回全文；大文件局部命中按 parent/window 返回；不同候选文件可有不同粒度；
- table row 返回表头/caption/准确 source，code/list/formula 保持完整结构；
- get_evidence 能从 opaque ref 取完整准确原文；get_document 不要求内部 document id；
- inspect 能告诉 Agent 可导航关系和 structured schema；structured query 的 filter/sort/aggregate 结果正确；
- 无 structured readiness 的资产明确报错并可退回搜索路径。

### 13.3 MCP 与安全

- 正常 search 响应严格只有 `query/evidence/has_more` 顶层字段和 §5.3 evidence 字段；
- 不出现内部 UUID、raw segment/retrieval unit type+id、边、score chain、groups；
- search 无 offset/page/cursor；`truncated/has_more` 语义有契约测试；
- 所有 ref 工具对未开放 KB、过期/伪造 ref、跨用户 ref 均拒绝且不泄漏；
- structured DSL 的未知字段、类型错、非法操作、超量结果均返回 typed error；SQL 注入用例必须失败。

### 13.4 最小真实语料 smoke/eval

使用至少包含短小文件、长标题树文档、跨页表格、代码/列表/公式的真实样本，验证关键词与标准混合链均非明显退化；记录 Recall/空结果/重复率、引用解析成功率、structured query 正确率、P50/P95 延迟和 rerank/hydrate 降级。这里是开发验收，不建设 P8 正式晋级制度。
