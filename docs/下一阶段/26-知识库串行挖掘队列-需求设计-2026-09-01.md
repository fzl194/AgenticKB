# 知识库串行挖掘队列需求设计

- 日期：2026-09-01
- 状态：需求已确认，可进入详细开发
- 范围：知识库挖掘任务提交、域内串行调度、启动恢复、前端状态反馈
- 核心原则：不扩大实现范围；不做真正并行；复用现有 `mining_runs` 和 `queued` 状态

---

## 1. CAPABILITY：能力定义

具备知识库写权限的用户，可以在同一知识域下为不同知识库连续提交挖掘任务。系统始终只实际执行该知识域中的一个任务，其余任务可靠落库并显示“排队中”；当前任务结束后自动执行下一项。一个知识库在已有未结束任务时不得再次创建覆盖性任务，用户应看到明确、友好的当前状态提示。

本能力解决的是“提交体验和串行调度”，不是提升实际挖掘并行度。

---

## 2. 背景与当前问题

当前系统已经具备：

- `mining_runs.status = queued` 状态；
- KB 任务列表和任务详情；
- 前端“排队中”中文状态与 3 秒轮询；
- 每个知识域一次只执行一个 Run 的进程锁和数据库租约；
- Run 失败、取消、重启恢复等基础状态机。

但当前提交路径存在产品断点：

1. `POST /api/kb/{kb_id}/mine` 在发现同域已有任务后，直接返回 HTTP 409。
2. 第二个知识库不会生成 `queued` Run，因此前端无法展示“排队中”。
3. 用户只能看到报错，无法确认任务是否已经被系统接收。
4. 多用户同时使用时，只要知识库属于同一知识域，也会互相收到 409。
5. 当前启动恢复会把无租约的 `queued` Run 一并改为 `interrupted`，不符合持久队列语义。

因此当前行为是“域内拒绝第二个任务”，而不是“域内串行排队”。

---

## 3. 用户故事

### 3.1 不同知识库连续提交

作为有写权限的用户，当知识库 A 正在挖掘时，我仍可以提交知识库 B。系统应接受 B，并在任务列表中显示“排队中”，待 A 结束后自动开始 B。

### 3.2 多用户连续提交

作为用户甲和用户乙，只要各自对目标知识库具有写权限，就可以分别提交知识库 A、B。任务按照提交顺序串行执行，不因提交人不同而拒绝。

### 3.3 同一知识库防重复

作为用户，当目标知识库已经处于排队、挖掘或待处理状态时，再次点击挖掘不会创建第二个任务，也不会覆盖已有任务；系统应提示该知识库当前正在挖掘或已经排队。

### 3.4 失败后队列继续

作为用户，即使前一个知识库任务失败，后续已经排队的知识库仍应自动开始，不需要人工重新提交。

### 3.5 重启后队列不丢

作为运维人员，服务重启后，尚未开始的排队任务仍保持排队，正在执行但因重启中断的任务按既有恢复机制优先恢复，随后继续处理队列。

---

## 4. 固定业务规则

### 4.1 调度粒度

- 一个知识域同一时刻最多实际执行一个挖掘 Run。
- 不同知识域沿用现有隔离，可以各自执行一个 Run。
- 不增加全系统级串行锁。
- 不增加并行 Run 数量配置。

### 4.2 知识库任务唯一性

同一知识库最多存在一个“未结束任务”。未结束状态固定为：

- `queued`
- `running`
- `awaiting_review`
- `interrupted`

终态固定为：

- `completed`
- `failed`
- `cancelled`

只有不存在未结束任务时，才能为该知识库创建新 Run。

说明：虽然正式产品当前不启用 GraphRAG 人审流程，`awaiting_review` 仍属于现有状态机，必须纳入防重复集合；`interrupted` 可能被恢复，也不能与新任务交叉覆盖。

### 4.3 排队顺序

- 同一知识域按 Run 入库时间升序执行，先提交先执行。
- 时间相同时以 Run ID 做稳定排序。
- 不提供优先级、插队、置顶、拖动排序或管理员调序。
- 不展示预计等待时间。
- 本批不要求展示精确队列位次。

### 4.4 用户与权限

- 沿用现有知识库权限：owner、editor、site admin 可以触发；viewer 不可以。
- 调度顺序不因用户角色不同而变化。
- 不建立“每用户独立队列”。
- Run 继续以 `kb_id` 作为可见性和授权边界。
- 建议把提交用户 ID、用户名写入现有 `metadata_json`，只用于审计，不新增用户调度策略。

### 4.5 失败隔离

- 一个 Run 失败，只结束该 Run。
- 调度器必须继续认领下一条 `queued` Run。
- 单个任务的异常不得使整个知识域队列永久停止。
- 无法把异常 Run 标为终态时应记录错误日志，并由现有租约恢复机制接管。

## 5. 用户可见行为

### 5.1 提交其他知识库

知识库 A 正在运行时提交知识库 B：

- API 返回 HTTP 202；
- B 创建一条 `queued` Run；
- 前端提示“挖掘任务已加入队列”；
- B 的任务列表显示“排队中”；
- A 结束后，B 自动变为“运行中”。

### 5.2 重复提交同一知识库

同一知识库已有未结束 Run 时：

- 不创建新 Run；
- API 返回 HTTP 409；
- 错误码统一为 `kb_mining_busy`；
- 响应 `details` 包含已有 `run_id` 和 `status`；
- 前端按状态展示：
  - `queued`：该知识库已在排队中；
  - `running`：该知识库正在挖掘；
  - `awaiting_review`：该知识库存在待处理的挖掘任务；
  - `interrupted`：该知识库存在待恢复的挖掘任务。

不新增四套错误码，避免扩大前后端契约。

### 5.3 按钮行为

- 知识库详情页已加载到本库 `queued/running` Run 时，挖掘按钮应禁用。
- 按钮文字可分别显示“排队中”或“挖掘中”。
- 列表页、批量挖掘入口无法预知最新状态时，允许发起请求；若后端返回 `kb_mining_busy`，必须显示上述友好提示。
- 不为了按钮状态新增独立轮询接口，继续复用 `GET /api/kb/{kb_id}/runs`。

### 5.4 任务展示

- 继续使用现有状态徽章、进度展示和 3 秒轮询。
- `queued` 不展示伪进度，不把等待时间算作挖掘耗时。
- 本批不增加队列管理页面。
- 本批不增加跨知识库总队列页面。

## 6. 状态与调度流程

```text
用户提交知识库 B
  ↓
校验权限、知识库、文档和挖掘范式
  ↓
查询本 KB 是否已有未结束 Run
  ├─ 有 → 409 kb_mining_busy，不创建新行
  └─ 无 → INSERT mining_runs(status=queued, kb_id=B)
                 ↓
             返回 HTTP 202
                 ↓
             幂等唤醒域调度器
                 ↓
域内已有 running/有效租约？
  ├─ 有 → 调度器退出；现有执行者结束后继续取队列
  └─ 无 → 取最早 queued Run 并按现有租约协议认领
                 ↓
             queued → running
                 ↓
          执行原有完整挖掘 Workflow
                 ↓
 completed / failed / cancelled / awaiting_review
                 ↓
          调度器继续取下一条 queued Run
```

### 6.1 调度器约束

- 每个知识域只有一个轻量调度循环。
- 调度器只负责“找下一条和调用现有 run/resume”，不实现新的挖掘执行器。
- 调度器的唤醒必须幂等，多次调用不能创建多个实际执行者。
- 数据库 `claim_run` 和租约继续作为跨线程、跨实例的最终执行权护栏。
- 某实例发现执行权已被其他实例认领时，应退出本地调度循环，不忙等。
- 实际持有执行权的调度循环在任务结束后继续取下一条。

### 6.2 候选任务选择

调度器按以下顺序处理：

1. 本域需要恢复且无有效租约的 `interrupted` Run；
2. 本域最早的 `queued` Run。

同一时刻仍只执行一个。恢复旧 Run 优先，避免后提交任务先覆盖旧任务的结果。

## 7. 启动恢复要求

当前 `recover_startup_runs` 会把无有效租约的 `queued/running` 都改为 `interrupted`。本需求必须调整为：

- `queued`：保持 `queued`，不得写 `finished_at`；
- 无有效租约的 `running`：改为 `interrupted`，保留既有恢复语义；
- 有有效租约的 `running`：视为其他实例仍在执行，不接管；
- 启动扫描完成后，对存在 `queued/interrupted` 的知识域幂等调用调度器；
- 租约到期补扫不直接并行恢复多个 Run，只负责标记并唤醒域调度器；
- 重启后不能出现多个恢复协程同时运行同一知识域任务。

不新建恢复队列表，不引入消息中间件。

## 8. 数据与接口契约

### 8.1 复用表

继续复用 `mining_runs`：

- `id`：任务身份；
- `domain`：域内串行调度范围；
- `kb_id`：同库防重复和授权范围；
- `status`：`queued/running/...`；
- `started_at`：当前实现中的提交排序时间，本批不另加 `queued_at`；
- `worker_id/lease_until/heartbeat_at`：现有执行租约；
- `metadata_json`：保留 `publish/force_redo/signature/document_ids`，增加提交人审计字段即可。

### 8.2 数据库并发兜底

必须增加部分唯一索引，防止两个用户同时请求时都通过应用层查询：

```sql
CREATE UNIQUE INDEX ...
ON mining_runs(kb_id)
WHERE kb_id IS NOT NULL
  AND status IN ('queued', 'running', 'awaiting_review', 'interrupted');
```

应用层先查询用于返回友好信息；数据库索引负责最终竞态兜底。唯一冲突需要转换为 `kb_mining_busy`，不能直接暴露数据库错误。

### 8.3 提交接口

接口保持不变：

```http
POST /api/kb/{kb_id}/mine
```

成功响应保持现有结构，`status` 固定返回 `queued`。不增加队列位次字段。

同库繁忙响应：

```json
{
  "detail": {
    "code": "kb_mining_busy",
    "message": "该知识库正在挖掘或已在排队，请完成后再试",
    "details": {
      "run_id": "...",
      "status": "running"
    }
  }
}
```

### 8.4 查询接口

以下接口结构不变：

- `GET /api/kb/{kb_id}/runs`
- `GET /api/runs/{run_id}`
- `GET /api/runs/{run_id}/progress`
- `GET /api/runs/{run_id}/stages`
- `GET /api/runs/{run_id}/documents`

## 10. 明确非目标

本需求严格不包含：

- 不支持同域多个 Run 真正并行执行；
- 不支持同一知识库多个 Run 同时存在；
- 不修改 staging 表，不增加 `run_id` 资产隔离；
- 不修改挖掘算子、挖掘范式或检索范式；
- 不修改向量化、LLM 调用、切片和资产晋升逻辑；
- 不新增 Redis、Celery、Kafka、RabbitMQ 或独立 Worker 服务；
- 不增加队列优先级、队列位次、ETA、暂停队列、手工调序；
- 不做跨知识域全局限流；
- 不修复或重构增量挖掘判定；
- 不把本需求扩展为通用任务中心。

## 11. 验收标准

### 11.1 核心场景

1. 同域知识库 A 正在运行时提交知识库 B：B 返回 202，任务为 queued。
2. A 完成后，B 无需人工操作自动进入 running。
3. A 失败后，B 仍自动进入 running。
4. A 运行时再次提交 A：返回 409 `kb_mining_busy`，数据库没有第二条 A 的未结束 Run。
5. 两个用户同时提交同一个 KB：最多一个请求成功创建 Run，另一个收到友好 409。
6. 两个用户提交不同 KB：两个请求都成功，先提交者运行，后提交者排队。
7. 不同知识域各有任务时，沿用现有能力，可各执行一个。

### 11.2 重启恢复

1. A running、B queued 时重启服务：B 仍为 queued。
2. A 被标 interrupted 并按现有节点事件恢复，不重新创建 Run。
3. A 恢复完成后 B 自动运行。
4. 重启恢复期间同一知识域始终最多一个有效执行租约。

### 11.3 前端

1. queued 状态显示“排队中”并持续轮询。
2. running 状态显示“运行中/挖掘中”。
3. 本库 queued/running 时详情页挖掘按钮不可重复触发。
4. 列表页或批量入口遇到同库繁忙时显示中文提示，不显示裸 409 或英文域锁信息。
5. 任务从 queued 变为 running 后页面能在下一轮轮询中更新。

## 12. 测试要求

### 12.1 后端单元测试

- 调度器按时间 FIFO 选择 queued Run；
- 调度器每次只执行一个 Run；
- 任务 completed/failed/cancelled 后继续下一项；
- claim 失败时本地调度器退出，不忙等；
- 同库状态映射到统一 `kb_mining_busy`；
- 提交用户审计写入 metadata。

### 12.2 PostgreSQL 集成测试

- 部分唯一索引阻止同 KB 两条未结束 Run；
- 不同 KB 可以同时存在 queued Run；
- queued Run 不妨碍当前 running Run 的租约；
- 同域只有一个有效 worker lease；
- 两请求竞态下只有一个同 KB Run 创建成功。

### 12.3 启动恢复测试

- queued 不被改成 interrupted；
- 失效租约的 running 被标 interrupted；
- 恢复任务和普通 queued 任务串行；
- 租约补扫只唤醒调度器。

### 12.4 前端测试

- queued/running 按钮禁用和中文文案；
- `kb_mining_busy` 的四种现有状态提示；
- queued 轮询保持，终态停止；
- 异库成功提交提示“已加入队列”。

## 13. 代码核查：新增 5 个文件后再次整库挖掘

### 13.1 用户问题

一个知识库原有 5 个文件已经挖掘完成，之后再上传 5 个新文件；不选择强制重挖、不切换挖掘范式，再次点击整库挖掘，旧 5 个文件是否自动跳过？

### 13.2 当前代码结论

**当前正式 KB 对象存储执行路径不会在 Run 文档分类阶段把旧 5 个文件直接判为 `SKIP`。**

代码行为是：

1. 整库挖掘未传 `document_ids` 时，worker 会读取该 KB 的全部当前文档，因此本例会取到 10 个文件。
2. 提交时 `preflight_manifest=None`，没有提前冻结 `REUSED` 判定。
3. `_prepare_document_states` 在 KB 对象输入分支中，只要已有 `existing_doc`，就直接设 `lifecycle_action = "UPDATE"`，没有调用基于内容哈希的 `decide_document_lifecycle_action`。
4. `force_redo=False` 只意味着不会主动清除旧快照派生资产，不会把这里的 UPDATE 改成 SKIP。
5. 底层解析 Run、Parse IR、Snapshot Commit 具有指纹幂等复用能力，因此旧文件可能复用已有解析结果或快照；但它们仍进入 Workflow，后续切片编译、检索投影、问题生成、摘要、Embedding、persist 等节点仍可能执行。

因此当前实际语义是“底层部分复用”，不是“旧文件零成本跳过，只挖新 5 个文件”。

### 13.3 与本需求的关系

- 这是独立的增量挖掘问题。
- 本串行排队需求不得顺手修改该逻辑，避免扩大工作量和测试面。
- 串行排队完成后，系统只改变 Run 的等待与启动顺序，不改变一个 Run 内哪些文件被挖掘。
- 后续若修复，应单独建立“KB 对象输入增量 SKIP”需求，并验证旧文档不会重复触发 LLM 和 Embedding。
