# 第一部分：挖掘侧复审

## 1.1 原始需求基线

挖掘侧原始目标不是继续叠加 LLM enrich 或篇章关系，而是建立以下资产生产线：

```text
文件输入
→ 解析为结构化事实
→ 按内容类型编译结构保真切片
→ 投影 document/section/prose/table/table_row/list/code 等检索表示
→ 可选生成 query/summary alias
→ 按 representation 类型选择 embedding 策略
→ 原子持久化源证据面、搜索表示面、结构化面
→ 按真实 readiness 校验并发布 Build
```

固定产品决策：

1. `enrich/discourse_line/contextual_retrieval_enrich` 退出正式生产链；
2. 本批不建设 GraphRAG；实体、本体、图代码可保留研究，但不进入正式 catalog、预置、readiness、API/UI 产品能力；
3. 表格、代码、列表、结构导航是标准资产契约，不是单独范式；
4. embedding 策略按 representation 类型选择，可由算子参数覆盖；
5. `asset_persist` 应是唯一真正入库者；
6. `mining_finalize` 必须根据实际资产 readiness 发布，不能以节点 SUCCESS 代替能力成立；
7. 两个 LLM 增强算子是可选实验能力，失败只能降级增强能力，不能破坏基础搜索资产。

## 1.4 B8-R02：表格结构化闭环仍然错误

### Claude 已修复

这些修复只能保证 `table_row` 类型不被压成 `table`，并没有保证同一张表的 identity 和 cells 正确。

### 当前缺陷 A：compiler 没有传播稳定 `table_ref`

真实 compiler 产出的 whole 和 row metadata 没有 `table_ref`：

- `knowledge_mining/mining/segment_compiler/compiler.py:448-501`

`structure_projection` 因此回落到每个 segment 自己的 `tbl:{segment_index}`：

- `knowledge_mining/mining/retrieval_projection/structure_projection.py:101-132`

同一张表会变成：

```text
whole → tbl:10
row 1 → tbl:11
row 2 → tbl:12
row 3 → tbl:13
```

### 当前缺陷 B：caption 导致第一列确定性丢失

compiler 把 caption 拼在首列前：

```text
[表 3-1 告警对照] 告警码=A-101；原因=风扇停转
```

`_row_cells` 只接受列名与 header 严格相等，因此首列名被解析成 `[表 3-1 告警对照] 告警码` 并被丢弃：

- `knowledge_mining/mining/segment_compiler/compiler.py:484-488`
- `knowledge_mining/mining/retrieval_projection/structure_projection.py:30-47`

### 当前缺陷 C：row target 格式与检索侧不一致

projector 的 row target 没有稳定地包含 `{table_ref}:{row_index}`：

- `knowledge_mining/mining/retrieval_projection/projector.py:122-143`

检索侧却按以下格式解析：

```text
{document_ref}#table_row:{table_ref}:{row_index}
```

- `agent_serving_java/src/main/java/com/coremasterkb/serving/operator/operators/output/TargetRefFormat.java:8-13`

结果是 table representation、table row representation、structured asset 使用三套不同 identity，命中行后无法可靠回到对应整表和行号。

### 当前缺陷 D：从文本反推 cell

当前先把 `TableCell` 串成 `列=值；列=值`，后面再拆回来。值中包含 `；`、重复列名、合并单元格时均会错误。

### 必须修改

1. 从 ParseIR `TableAsset.table_id/TableCell` 直接向 segment metadata 或结构投影传递稳定事实；
2. whole、所有 rows、table node、structured asset、cells、representation container 必须共享同一 `table_ref`；
3. row target 必须显式包含真实 row index；
4. caption 与 cell 分字段保存，禁止从展示字符串反解析结构化 cell；
5. `row_count` 使用真实数据行数，不使用 `max(row_index)+1`；
6. 重复表头需确定性消歧，不能被 JSON pivot 静默覆盖。

### 验收条件

- 从真实 `TableAsset` 编译，不得手工构造带 `table_ref` 的 `CompiledSegment`；
- 一张 N 行 M 列数据表严格形成一个 table asset 和 `N×M` 数据 cells；
- 有/无 caption、值含 `；`/`=`、重复列名、跨页表格均不丢 cell；
- table row 搜索命中后 hydrate 能准确得到表头、命中行和对应 table asset；
- `query_structured_asset` 能在同一资产上查询多行并正确聚合。

## 1.5 B8-R03：`asset_persist` 仍非唯一写入者

### 原始需求

project/embedding 应只生产中间结果；`asset_persist` 应完成完整校验后一次性切换源证据、搜索表示、向量、结构化资产和 readiness。

### 当前实现

最终表仍在多个阶段被直接修改：

- project 阶段直接删除、重写 units：
  - `knowledge_mining/mining/retrieval_projection/repositories_pg.py:189-224`
- embedding 阶段直接删除、重写 vectors：
  - `knowledge_mining/mining/retrieval_projection/repositories_pg.py:319-337`
- persist 阶段再次删除、重写 units/structure/tables/readiness：
  - `knowledge_mining/mining/retrieval_projection/repositories_pg.py:414-438`

v2 派生表只按 `snapshot_id` 标识，没有 `run_id/build_id/asset_version/staging_version`。如果 snapshot 已被活动 Build 引用，新 run 的 project/embedding 提交会立即改变线上读到的资产，即使新 run 最终失败或未发布。

### 必须保持的架构不变量

1. 未发布 run 绝不能改变活动 Build 的任何读结果；
2. persist 任一步失败不得留下可被活动 Build 读取的半成品；
3. readiness 与其描述的资产版本必须原子一致；
4. source、units、vectors、structure、typed assets 应能指向同一不可变派生版本。

### 可选实现方向

- 方案 A：按 `asset_version/run_id` 写 staging，Build 发布时原子绑定版本；
- 方案 B：所有派生资产写不可变 version 表，Build selection 指向具体版本；
- 方案 C：临时 staging schema/table，persist 完成后事务内切换活动版本。

具体方案可由 Claude 设计，但不能继续把活动 snapshot 对应的最终表当作暂存区。

### 验收条件

- 活动 Build 引用 snapshot X 时，新 run 对 X 重挖，在发布前检索结果完全不变；
- project、embedding、persist 任一点注入失败，活动 Build 仍读取旧资产；
- 成功发布后所有资产面同时切到新版本；
- 并发处理相同 snapshot 不发生最后写入者覆盖。

# 第二部分：检索侧复审

## 2.1 原始需求基线

检索侧原始目标是：

```text
Agent 先模糊检索
→ 返回少量类型化 EvidenceResponse 和 opaque refs
→ Agent inspect 能力/结构/schema
→ 再通过 public refs 收窄搜索、结构导航或结构化查询
→ 形成无服务端 LLM 的 Agentic 反馈闭环
```

固定产品决策：

1. 检索侧本批不承担生成式 LLM query understanding；
2. 一个 query 只调用一次当前文本 embedding 模型；
3. FTS/dense 在 Top-K 前使用完全一致的授权范围和 hard filters；
4. alias 命中必须回到源证据，不把生成问题当答案；
5. 输出极简 EvidenceResponse，不暴露内部 unit ID、图点边和内部数据库 ID；
6. public ref 必须 opaque、授权绑定、可稳定解析；
7. structured query 使用 schema-bound DSL，不做 NL-to-SQL；
8. 实体/GraphRAG 不进入正式检索目录或产品能力。

- `structure_ref`
- `include_descendants`
- `relative_path_prefix`
- `date_range`

当前只是改成明确 400。明确拒绝比静默忽略正确，但不能算原始需求完成。若决定延期，必须由用户明确修改需求范围，不能由 28 号报告单方面列为“不阻塞”。

### 必须修改

1. 请求 DTO 对每个 filter 做数组/对象/布尔/日期格式校验；
2. ref 列表只接受非空字符串和正确 public ref kind；
3. evidence/asset types 使用明确 enum；
4. 设置数组长度、filter 数量上限；
5. 实现原始 filter，或形成经用户确认的延期决策。

### 验收条件

- 错误类型返回 typed 400，不得退化为宽检索；
- FTS/dense 对同一请求使用完全相同的 filter；
- `document_refs` 不接受 `st_`，`section_refs` 不接受 `doc_`；
- 所有显式约束均在 Top-K 前生效。

## 2.5 `query_embed` 复审

已完成：

- 一个 query 只 embed 一次；

- query vector dimension 不兼容时明确失败。

## 2.6 B8-R08：public ref 反查仍不可扩展

当前 public ref 是 HMAC 短哈希，服务通过枚举授权 snapshot 内部候选重新编码匹配：

- 活动候选上限 200,000；
- 历史候选上限 50,000；
- `agent_serving_java/src/main/java/com/coremasterkb/serving/structure/StructureRefService.java:34-37`

Claude 增加了稳定排序并把 unit `target_ref` 加入候选，解决了结果抖动和部分 `st_` 无法解析，但没有解决规模问题。

超过 cap 后：

- 排序范围之外的合法 ref 会稳定地解析失败；
- 每个 filter ref 都可能重新扫描候选；
- 复杂度接近 `O(ref 数 × 候选数)`。

对于 1000 文件知识库，representation 数超过 20 万是正常场景。

### 必须修改

建议二选一：

- persist 时建立 `opaque_hash → snapshot/internal_ref/ref_kind` 反向索引，并按授权 snapshot 查询；
- 改为携带加密/签名 payload 的可验证 token，避免全候选枚举。

无论采用哪种方式，仍必须绑定 domain/KB/active snapshot 授权，不能仅凭 token 解码越权读取。

### 验收条件

- 单 KB 超过 20 万 refs 时，任意合法活动 ref 均可解析；
- 解析复杂度不随候选总数线性增长；
- 过期、越权、不存在保持稳定 typed error，且不泄漏其他用户资产；
- 多 ref filter 不重复扫描完整候选集。

## 2.7 B8-R09：alias rerank 仍没有回到源证据文本

需求要求：alias 命中时，reranker 应使用“生成问题 + 有界源证据文本/摘要”，不能只排列问题本身。

当前 query alias 的 `content_text` 明确是生成问题：

- `knowledge_mining/mining/retrieval_projection/query_expansion.py:68-83`

`ChannelAggregator` 使用最佳命中 representation 的 `structural_context + content_text` 构造 ranking text：

- `agent_serving_java/src/main/java/com/coremasterkb/serving/operator/operators/retrieve/ChannelAggregator.java:47-55`
- `agent_serving_java/src/main/java/com/coremasterkb/serving/operator/operators/retrieve/ChannelAggregator.java:68-81`

如果最佳命中是 alias，reranker 收到的仍主要是生成问题。代码注释称 alias content 已是源证据摘要，与实际写入契约相反。

### 必须修改

- rerank 前批量读取 alias 的 canonical source representation；或
- 持久化经过约束的 source ranking text，并保持 source refs/provenance；
- 禁止 N+1 回源。

### 验收条件

- alias 为最佳召回行时，reranker 输入包含源证据正文；
- alias 不是最终可返回证据；
- reranker 失败仍原样保留 RRF 顺序；
- query/summary alias 与源 evidence 不重复占位。

## 2.8 `evidence_hydrate` 与 `assemble`

### 已完成度较高

`evidence_hydrate` 已实现：

`assemble` 已实现：

### 当前依赖性风险

因此两个算子自身完成度较高，但不能脱离上游资产契约宣称端到端完成。

## 2.9 inspect、navigate、structured query

### `inspect_knowledge`

Claude 已让 document/普通 structure 分支优先读取冻结 readiness，但：

- evidence 分支和 asset 分支仍有现场推断；
- 同一 snapshot 从不同 ref inspect 时，capabilities 可能不一致；
- readiness 表缺失时 SQL 异常不一定能进入 legacy fallback。

要求所有 ref kind 使用同一冻结 snapshot readiness/schema 事实源。

### `navigate_structure`

主关系、深度、limit、游标和授权基本完成。边界问题：

- footnotes/references 查询只取 `limit`，没有 `limit+1`/offset，超过 limit 时可能错误返回 `has_more=false`；
- previous/next 受固定 sibling 扫描上限影响。

### `query_structured_asset`

字段白名单、操作符白名单、参数绑定、数值能力和 readiness 检查基本完成，但：

- 只拒绝 `limit>200`，不拒绝 `limit<=0`；
- `limit=0` 会形成空页和不前进 cursor；
- 负数可能下沉成数据库错误；
- where 数量和 `in` 数组没有上限；
- Controller 对错误形态的 where/order_by 可能静默当成空条件。

验收必须覆盖 `limit=0/-1/201`、超大 where/in、错误 JSON 形态及稳定 typed error。
