# 知识库生命周期、挖掘运行与前端问题：Codex 审查整改清单

> 日期：2026-08-31  
> 审查基线：`f25d15d`  
> 用户复现输入：知识库删除重建、多用户同名、挖掘实体阶段、PostgreSQL deadlock、旧默认范式、前端系统性问题  
> 审查方式：只读代码审查、跨端契约核对、定向测试与前端构建；本次未修改业务代码。

## 0. CAPABILITY：整改后必须具备的能力

整改完成后，系统应满足以下用户结果：

1. 用户删除知识库后，可以恢复或使用原名称重新创建，不会进入“既不能恢复也不能重建”的死状态；
2. 不同用户的私有知识库可以使用相同显示名称，所有授权和机器调用仍以稳定 KB ID/ref 为准；
3. 每次挖掘任务只展示本次冻结 workflow 中真实存在的算子、节点状态和进度，不再显示写死的实体、本体和旧篇章阶段；
4. 多文档、多 worker、多进程同时挖掘时，业务热路径不执行 DDL，不发生关系级 AccessExclusiveLock 升级死锁；
5. 新建知识库默认绑定当前正式默认挖掘范式 `system-hybrid-assets`，存量旧绑定得到迁移；
6. 前端能正确展示真实状态、错误、空数据、范式绑定和异步请求结果，不把服务故障伪装成“没有数据”；
7. 最新 M3 问题生成和层级摘要接线遵守 staging/发布原子性，并能区分业务 SKIP 与 LLM 故障。

## 1. 固定约束与不变量

### 1.1 已确认的产品规则

- 知识库的稳定身份是 `kb_id`，显示名称不是机器身份；
- 软删除必须有明确恢复或重新创建语义，不能永久占用名称却不提供恢复入口；

- 多用户隔离必须依赖授权和 KB ID，不得依赖名称全局唯一来间接维持安全。

### 1.2 本轮非目标

- 不要求本轮重新设计全部 UI 视觉样式；
- 不要求一次性清理所有 legacy 源码；
- 不把纯格式、命名或性能微优化作为验收阻塞；
- public ref 20 万候选扩展性、GraphRAG、完整自然语言结构化查询不在本整改单展开；
- 本文聚焦已复现或代码上可确定推出的功能问题。

# 第一部分：知识库生命周期与多用户隔离

## 3. KB-01：删除后同名重建失败

### 3.1 当前数据库契约

`knowledge_bases` 使用全域、全生命周期唯一约束：

```sql
UNIQUE (domain, name)
```

证据：

- `databases/kb/schemas/002_knowledge_bases.sql:4-18`

删除只做软删：

```sql
UPDATE knowledge_bases
SET status='deleted', deleted_at=..., updated_at=...
WHERE id=...
```

证据：

- `knowledge_mining/mining/kb/db.py:707-717`

删除后的行仍参加唯一约束，故相同 domain/name 永久冲突。创建服务捕获 `UniqueViolation` 并返回 409：

- `knowledge_mining/mining/kb/services/kb_service.py:55-68`

系统没有知识库 restore API；前端又提示“不可在 UI 撤销”。因此形成不可恢复死状态。

### 3.2 必须确定的生命周期

建议采用以下产品语义：

- 删除后历史 KB 保留，默认列表和授权读路径不可见；
- owner/admin 可以从回收站恢复；
- 若不恢复，也允许创建新的 active KB 使用相同显示名称；
- 新 KB 使用新 ID，不继承旧 KB 的成员、MCP 授权、文档或 Build；
- 恢复旧 KB 时，如果 owner 下已有同名 active KB，返回明确 `kb_name_conflict`，要求改名或删除新 KB。

### 3.3 数据模型建议

删除原约束：

```sql
UNIQUE (domain, name)
```

改为 active、owner 范围的规范化唯一索引，例如：

```sql
CREATE UNIQUE INDEX ...
ON knowledge_bases(owner_id, domain, lower(btrim(name)))
WHERE status='active';
```

是否使用 `lower()` 需与最终大小写产品规则一致，但前后端和数据库必须采用同一规范。

### 3.4 接口要求

- `POST /api/kb`：只与当前 owner 的 active 同名库冲突；
- `POST /api/kb/{id}/restore`：恢复已删除 KB；
- `GET /api/kb/deleted`：owner/admin 的回收站列表；
- 创建/重命名/恢复冲突统一返回：

```json
{
  "detail": {
    "code": "kb_name_conflict",
    "message": "当前用户在该知识域已有同名活动知识库"
  }
}
```

### 3.5 验收用例

- 创建 `test` → 删除 → 再创建 `test` 成功；
- 创建 `test` → 删除 → restore 成功；
- 删除后创建新 `test` → 再恢复旧 `test` 返回稳定冲突；
- 删除 KB 不会让历史文档、Build、审计记录串到新 KB；
- 软删 KB 不再出现在普通列表、检索范围和 MCP 开放库中。

## 4. KB-02：不同用户同名知识库

### 4.1 当前事实

当前唯一键没有 `owner_id`，因此同一 domain 下不同用户也不能同名。

当前权限读取本身主要以 KB ID、owner/member/public 为边界：

- `knowledge_mining/mining/kb/db.py:366-436`
- `knowledge_mining/mining/kb/services/kb_service.py:132-144`

没有发现“允许同名后自然导致越权”的必要条件。真正需要调整的是名称解析接口。

### 4.2 安全影响

全局名称唯一当前会产生：

1. 不可见 private KB 名称可通过创建请求的 409 被探测；
2. 任意用户可以抢占全域常用名称，阻止其他用户创建；
3. 显示名称被错误当成租户级身份。

### 4.3 MCP 与名称歧义

MCP 当前仍支持 `kb_names → kb_id`：

- `mcp_server/identity.py:208-234`
- 内部使用字典 `{normalized_name: id}`，重名会被后一个覆盖。

整改要求：

- MCP 和机器 API 优先使用 `kb_id` 或 opaque `kb_ref`；
- `list_knowledge_bases` 返回 ID/ref + name；
- 名称仅作为用户输入便利项；同一用户可见范围内出现重名时必须返回 `ambiguous_kb_name`，列出候选 ID/ref，不能静默选一个；
- 所有实际授权仍按 KB ID 求交。

### 4.4 验收用例

- 用户 A、B 可各自在同一 domain 创建 private `test`；
- A 看不到 B 的 private `test`；
- public/member 场景下名称重复时 UI 显示 owner 或附加标识；
- MCP 以 KB ID/ref 可准确选择；纯名称歧义返回 typed error；
- 创建同名请求不泄漏其他用户 private KB 是否存在。

## 5. KB-03：创建、重命名、恢复错误语义统一

创建已捕获 `UniqueViolation → Duplicate → 409`，但更新没有：

# 第三部分：PostgreSQL deadlock 与资产并发

## 9. DB-01：业务热路径并发 DDL

### 9.1 最高置信根因

`PgRepresentationStore/PgEmbeddingStore/PgAssetWriter` 各自继承 `_PgSchemaBound`：

- `knowledge_mining/mining/retrieval_projection/repositories_pg.py:134-154`

每个实例都有独立、无锁的：

```python
self._schema_ready = False
```

首次业务调用会执行全部 `ASSET_SCHEMA_V2_STATEMENTS`，包含：

- final/staging `CREATE TABLE`；
- `CREATE INDEX`；
- `ALTER TABLE asset_retrieval_units_v2`。

`DocumentExecutor` 多线程并行处理文档。多个线程可以同时看到 `_schema_ready=False`，在不同连接上重放同一批 DDL；三个不同 store 又会各跑一次。

### 9.2 为什么会出现 AccessExclusiveLock deadlock

psycopg 默认 `autocommit=false`。业务连接上的首条 DDL 会开启隐式事务，前面 CREATE/INDEX 获得的锁持续到事务结束；随后同一事务执行 ALTER TABLE 请求 AccessExclusiveLock。

两个连接可能形成：

```text
A、B 均已持有 relation 的较低级锁
→ A 请求 AccessExclusive，等待 B
→ B 请求 AccessExclusive，等待 A
→ deadlock detected
```

这与用户错误中的 `AccessExclusiveLock on relation ...` 一致。

捕获 `DuplicateTable/DuplicateObject` 也不能修复已 aborted 的 PostgreSQL 事务；没有 savepoint 时 Python 层吞异常后连接仍不可继续正常使用。

### 9.3 为什么正式 schema ensure 没避免

DomainPoolManager 的启动 schema ensure 有进程内单飞锁：

- `knowledge_mining/mining/api/domain_pools.py:69-85`

但 retrieval v2/staging DDL 没加入 `domain_schema_paths()`，所以启动迁移不会创建这些表，repository 仍必须在首个业务请求中动态执行。

### 9.4 必须修改

1. 将 retrieval v2/staging DDL 落为正式 migration SQL；
2. 加入 `domain_schema_paths()`；
3. 创建连接池、启动 worker 前完成 migration；
4. 删除 repository 业务热路径 `_ensure_schema()`；
5. runtime 只做轻量 schema version/assertion，不做 ALTER/CREATE；
6. migration 使用 PostgreSQL advisory lock，保证跨进程单飞；
7. schema migration 失败应阻止服务 ready，不能在文档算子里降级；
8. deadlock retry 只能包围完整、幂等事务。

### 9.5 验收用例

- 空库启动时由 migration 创建全部 final/staging 表；
- 4/8 worker 同时挖掘首批文档不执行任何 DDL；
- 两个服务实例同时启动，只有一个迁移执行者；
- repository 源码和 SQL trace 中不存在热路径 CREATE/ALTER；
- 发生 DeadlockDetected 时记录 run/node/snapshot/operator，并安全重试完整事务或明确失败。

## 10. DB-02：同 snapshot 并发和锁序

### 10.1 staging 没有 run/version

staging 表仅按 `snapshot_id` 保存和删除：

- `knowledge_mining/mining/retrieval_projection/schema.py:162-249`
- `knowledge_mining/mining/retrieval_projection/repositories_pg.py`

两个 run 处理同一 snapshot 时可能：

- 后一个删除前一个 staging；
- finalize 读取另一个 run 的 readiness；
- 一个 run 晋升另一个 run 的资产；
- 晋升清理另一个仍执行中的 staging。

要求引入 `run_id/asset_version`，Build 绑定不可变资产版本。

### 10.2 raw segment 与 force-redo 锁序

segment replace：

```text
element links → raw segments
```

- `knowledge_mining/mining/segment_compiler/repositories_pg.py:57-65`

force-redo 清理涉及 units/relations/segments，顺序与 segment writer 不一致；raw segment 删除还可能通过 FK cascade 访问 relations/mentions。多进程并发时存在锁序交叉。

要求：

- 同 snapshot 编译/清理/晋升使用数据库 snapshot advisory lock；
- 所有路径使用统一表顺序；
- force-redo 不直接清活动资产；
