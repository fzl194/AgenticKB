## 0. 执行结论

项目已经越过“基础文档 RAG”的早期阶段：现有代码具备知识库管理、文档快照、结构化解析、切片编译、检索表示、表格结构资产、向量、Build、挖掘/检索 DAG、EvidenceResponse、结构导航、结构化查询和用户级 MCP。当前正式链路也已经将不成熟的实体、本体和旧段关系图从产品面隔离。

下一步不应原样恢复“开放式实体抽取 → 本体归纳 → 全库落图”，也不应另起一套 GraphRAG 服务。建议以现有资产和发布机制为底座，先上线 **Knowledge Compilation Graph（知识编译图，KCG）v0.1**：

```text
原始文档与快照
  → 确定性结构图（文档 / 章节 / 表格 / 证据）
  → 可追溯编译产物（Wiki 页 / 摘要 / 主题页）
  → Build 级不可变知识图与覆盖报告
  → UI 浏览 + 现有混合检索 + MCP 三工具消费
```

首版的图是**证据图、结构图和编译血缘图**，不是“自动认定业务事实的实体图”。它能最快形成用户可见能力，同时保留向受约束 Claim/Entity 图、Temporal Context Graph 和 Agentic Search 演进的接口。

上线前有三个 P0 门禁：

1. 控制面当前把 `GET /api/v1/system/*` 作为免 token 配置读取面，raw YAML 和解析后的 JSON 都可能返回完整 secret-bearing 配置；Nginx 又对外代理整个 control plane，IP whitelist 默认关闭。必须封禁全部 secret-bearing config 读面，并拆分“服务身份最小授权读取”和“前端字段 allowlist 脱敏 DTO”。
2. 多个 Git 跟踪配置与本地 skip-worktree 配置含 LLM、数据库、对象存储、JWT/internal auth 等明文凭据，Git 历史中也已有同类暴露。必须先外置、部署新凭据并完成全量轮换。
3. 建立一条可复现的 CI 测试入口，明确纯单测与 PostgreSQL 验收测试的环境边界；不能继续依赖“从不同工作目录运行会得到不同结果”的隐式约定。

### 2.2 正式挖掘和检索的当前口径

正式挖掘 catalog 不是旧文档所说的 16/19 算子或 FULL Pipeline，而是：

```text
input_ingest → document_parse → segment_compile
             → retrieval_unit_project
             → [query_expansion_generate | hierarchical_summary_generate]
             → [embedding]
             → asset_persist → mining_finalize
```

- `query_expansion_generate`、`hierarchical_summary_generate` 为可降级实验增强；
- 默认 `system-hybrid-assets` 不包含生成式 LLM 节点；
- `entity_extract/entity_resolve/entity_relation_extract/entity_review_gate/ontology_induction/ontology_review_gate/graph_write` 集中声明在 `workflow/operators/research.py`，不注册到正式 catalog；
- 检索正式算子只有 8 个，实体精确/实体图源码仍有研究残留，但没有 `@Component`，不进入正式 registry；
- 官方检索预置是 `system-lexical-retrieval` 与 `system-hybrid-retrieval`。

### 2.4 当前真实缺口

1. **没有 Build 级知识编译图。** `asset_structure_nodes/edges` 是单 Snapshot 的文档结构投影，不是跨文档、包含编译产物和依赖血缘的 KB 图。
2. **没有正式 Wiki/Artifact 产品。** `hierarchical_summary_generate` 主要产生非 returnable 的 summary alias，用于搜索增强；它不是可浏览、可版本化、逐段引用的 Wiki 页。
3. **没有统一编译资产信封。** 现有检索表示、表格资产、历史实体资产各有结构，缺少通用的 `artifact type + build + source dependency + provenance + ACL + quality` 契约。
4. **没有依赖闭包失效。** 文档变化可以重挖，但“某 Wiki 页/主题页由哪些 Snapshot/Span 支持、变化后哪些派生物必须重编”尚无正式模型。
5. **没有覆盖率门禁。** 系统能检查检索 readiness，但不能回答“哪些文档/章节没有被知识图或 Wiki 覆盖、为什么跳过”。
6. **没有正式效果评测线。** 26 号验收也把问题集、新老对比列为后续项。当前有大量契约测试，但缺 50–100 条真实任务题的持续回归。
7. **没有服务端 Agentic Search runtime。** 当前设计有意把复杂规划放在调用方 Agent；这是合理边界，但缺少可观测的受限多步检索会话和 Knowledge Gap 反馈对象。
8. **安全门禁未满足。** 模型配置跟踪文件仍含明文密钥；派生 Wiki/摘要的 ACL 继承与跨源泄露策略也尚未定义。
9. **当前 staging 并不适合未来并行编译。** v2 staging 的关键主键仍以 `snapshot_id/representation_id` 为主，没有 `run_id/workflow_version`；当前依靠“同 KB 单开放 Run + 每域串行”规避互踩。KCG 新表必须直接使用 `build_id/run_id` 隔离，不复制这个技术债。
10. **删除/撤回机械仍不完整。** 文档 withdraw 仍有未接发布路径；KCG 必须以新 Build 的依赖闭包失效为准，不能依赖旧 withdraw 行为自动正确。
11. **KB 没有单一活动 Build。** 当前一次检索 scope 可能组合多个文档各自最新的 validated Build；`build_id` 又到 finalize 的 `assemble_build()` 才生成。这与“Build-scoped 全库知识图”直接冲突，是 KCG M1 前必须解决的基础架构问题。
12. **Global runtime 没有 ArtifactBag fan-in。** GlobalExecutor 当前只拿 capability 并集；KCG global handler 必须通过冻结的 `CompilationInputManifest` repository 读取完整输入，不能假设 DocumentState 自动汇总。

## 3. 本体、实体和 GraphRAG 为什么暂停

暂停不是因为“图没有价值”，而是当时只有局部代码，没有可上线闭环：

1. 默认域没有 active ontology 时，全线被 `has_ontology`/applicability 守卫跳过；
2. `ontology_induction` 没有形成可用生产实现；
3. 跨文档实体聚合、关系抽取、证据绑定和图写入链不完整；
4. 实体/本体两道人审会让通用整库挖掘进入阻塞态；
5. 查询消费依赖旧 `query_understanding`、`graph_expand` 和固定链，这些已在 clean break 中删除；
6. 没有社区摘要、Wiki、graph readiness、来源删除传播和真实评测闭环。

## 4. 工业界实现给出的方向

### 4.1 已形成共识的部分

1. **原始证据必须保留。** 图、Wiki、摘要都是可重建派生物，不能替代原文。Graphiti 把 Episode 作为派生事实的 ground truth；KAG 强调图与原文块互索引。[Graphiti 官方仓库](https://github.com/getzep/graphiti)；[OpenSPG/KAG 官方仓库](https://github.com/OpenSPG/KAG)
2. **图与关键词/向量互补。** LightRAG、Graphiti、KAG 都采用混合检索，而不是只保留图。[LightRAG 官方仓库](https://github.com/HKUDS/LightRAG)
3. **确定性结构优先于 LLM 猜测。** DeepWiki 的可用产品形态是分层 Wiki、架构图、源链接和检索的组合，并允许人工 steering；Sourcegraph 对代码使用精确索引、符号/引用关系和搜索，而不是只做 LLM 摘要。[DeepWiki 官方文档](https://docs.devin.ai/work-with-devin/deepwiki)；[Sourcegraph MCP](https://sourcegraph.com/mcp)
4. **多粒度预编译摘要适合全局问题。** Microsoft GraphRAG 的实体/关系/社区报告和 Local/Global/DRIFT 查询证明了这类资产的价值；但其官方仓库当前已明确处于 maintenance mode，不能把该项目本身当成未来平台底座。[GraphRAG 索引架构](https://microsoft.github.io/graphrag/index/architecture/)；[GraphRAG 官方仓库](https://github.com/microsoft/graphrag)
5. **Agentic 检索应按复杂度触发。** 两步 RAG 更可控、低延迟；Agentic RAG 灵活但延迟可变。简单查询继续走固定混合检索，只有多约束、多跳任务进入有限循环。[LangChain Retrieval 官方文档](https://docs.langchain.com/oss/python/deepagents/retrieval)
6. **本体成熟后的价值不只在检索。** Palantir 把对象/关系与动作、函数和动态权限共同建模，说明本体最终要连接业务对象、规则、能力和治理，而非只为生成三元组。[Palantir Ontology 官方文档](https://www.palantir.com/docs/foundry/ontology/overview)

### 4.2 成熟度边界

| 能力 | 当前成熟度 | 本项目取舍 |
|---|---|---|
| Document/Section/Chunk 结构图 | 成熟 | v0.1 直接上线 |
| BM25 + Vector + Rerank | 成熟 | 继续作为默认搜索主路 |
| 带 source span 的摘要/Wiki | 条件成熟 | v0.1 做，必须强制引用与覆盖检查 |
| 社区检测与全局摘要 | 条件成熟、成本高 | v0.2 评测后决定 |
| 明确 schema 下的实体/关系抽取 | 条件成熟 | v0.3 按具体场景启用 |
| 开放式全库本体发现 | 不成熟 | 不进近期产品 |
| 自动实体全局融合 | 风险高 | 需要主数据/别名规则/人工复核 |
| Temporal Context Graph | 对 Agent Memory 有价值 | v0.4 之后，先建立版本/有效期合同 |
| 任意 Text-to-Cypher | 风险高 | 不建设；使用白名单导航/DSL |
| 所有查询都 Agent loop | 成本/延迟不可控 | 禁止；按复杂度路由且有预算 |

### 4.3 对本项目最重要的反例

- 自动 Wiki 会漏覆盖。DeepWiki 官方专门提供页面清单和 repo notes 解决大型仓库关键目录被跳过的问题。因此首版必须有 Coverage Manifest，不能只展示生成成功。
- 图化会丢信息。HippoRAG 2 等工作说明图对多跳和联想检索有价值，但原文 passage 仍不可缺。图扩展只能补充现有混合检索，不能替代它。[HippoRAG 2](https://arxiv.org/abs/2502.14802)
- 图索引和全局查询成本高。GraphRAG 的 Global Search 是 map-reduce 类过程，应预编译并按需使用，不能成为每次查询默认路径。[GraphRAG Query Engine](https://microsoft.github.io/graphrag/query/overview/)
- LLM 生成的“事实”不是事实。任何 Claim/关系必须区分 `observed / inferred / generated_summary` 并能回到原始 span。
- 跨权限摘要可能泄露。派生物不能只继承创建者权限，必须从全部来源做 ACL 交集或按权限域分别编译。

## 5. CAPABILITY：知识编译图 v0.1

面向知识库所有者、领域专家和通过 MCP 接入的 Agent，系统先建立 KB 单一活动 Build，再把该 Build 的完整有效 Snapshot 集编译为不可变、可浏览、可追溯的知识图；来源变化时只重编受影响依赖闭包，并在同一事务中切换 Build 与知识图。M1 用户可从确定性图进入原文证据并在节点范围内调用现有搜索；M2 增加带引用 Wiki；M3 才让 Artifact 正式进入 FTS/向量检索。MCP 全程保持三工具。

## 6. CONSTRAINTS：固定规则与不变量

### 6.1 资产与真相边界

1. 原始 Document Snapshot 和 Evidence Span 是真相源；图、主题、摘要和 Wiki 都是派生物。
2. 每个生成 artifact 的每个段落至少有一个可解析 source span；无来源内容不得进入 published 状态。
3. `observed`、`derived_deterministic`、`generated_summary`、`inferred_candidate` 必须显式区分。
4. 图节点/边不能只保存自由文本；必须声明 `kind`、来源、生成方式、build、schema version 和 ACL scope。
5. 目标态的 current 查询只读 `kb_active_builds` 指向的一个 validated KB Build；这是 KCG 的前置改造，不是当前 HEAD 已有事实。

### 6.2 架构边界

1. v0.1 使用现有 PostgreSQL 和 Java/Python 服务，不引入 Neo4j/FalkorDB/专用图服务。
2. 图编译是现有挖掘 Workflow 的 global node，不新建平行任务系统。
3. 默认搜索仍是 FTS + dense + RRF + optional rerank；图不是召回唯一入口。
4. MCP 继续保持三件套，不新增 `browse_graph`/`get_wiki` 等工具；通过 opaque artifact ref 扩展 `get_knowledge`。
5. v0.1 不恢复旧 research entity/ontology operators，不复活旧 `graph_expand` 或固定 SearchService。

### 6.3 安全与权限

1. 图、artifact、引用和搜索结果都必须复用 KB 授权，且在 ref 解析后再次检查当前活动 Build 与用户 scope。
2. 多来源 artifact 的可见权限取来源权限交集；若来源来自不同 ACL 域，必须拆分编译或拒绝发布。
3. 失效、伪造、跨用户、跨 KB、跨 Build ref 统一返回 typed error，不泄露对象是否存在。
4. 日志不记录原始密钥、完整正文、模型输入或可还原敏感内容；query 和 ref 按策略截断/哈希。
5. 所有 LLM/API 密钥来自环境变量或 Secret Manager，启动时校验，不得进入 YAML、镜像层、前端包和 Git 历史。
6. LLM task、prompt、raw output、Provider error body 和 query log 都视为敏感数据；默认不得无限期明文保存，读取必须按 caller + KB + snapshot 做授权。
7. 私有知识发送外部模型前必须经过 egress policy；部署需要支持“禁止外部模型/仅本地模型/允许指定 Provider”的 KB 或系统策略。
8. `caller/domain/kb_id/snapshot_id/actor` 必须由已认证服务身份和服务端授权上下文固化，不信任请求 body 自报；task/result/attempt/retry/cancel/stats 使用同一 ACL。
9. 普通用户、前端 admin JWT 和通用共享 token 都不得读取 secret value；内部服务使用独立 workload identity，并按 namespace 最小授权。
10. Java KCG 读面只接受网关验证后注入的身份上下文或独立服务身份，不能信任客户端可直传的 `X-KB-User/X-KB-Role`；backend 直连与伪造身份头必须被拒绝。
11. 配置 PUT/热更新接口服务端拒绝 literal secret，只接受 secret reference/环境变量占位；否则运行时会把秘密重新写回 YAML。

## 7. IMPLEMENTATION CONTRACT

### 7.1 角色与产品面

| 角色 | 可见能力 |
|---|---|
| KB owner/editor | 选择知识编译预置、发起编译、查看覆盖/错误、浏览图和 Wiki、重编 |
| KB viewer | 浏览当前活动 Build 的图/Wiki/证据，不可修改编译 Profile |
| 领域专家 | 对未来 Claim/Entity 候选审核；v0.1 仅查看引用与标记问题 |
| MCP Agent | `search_knowledge` 发现证据，`get_knowledge` 读取 evidence/document/structure/artifact，不能修改图 |
| 运维人员 | 查看编译耗时、LLM 成本、失败阶段、覆盖和失效队列，不查看无权正文 |

KB 详情页新增“知识图”页签，内部包含：

1. 左侧 Wiki/主题树；
2. 中央图画布，可切换文档/章节/主题/Artifact 层；
3. 右侧节点详情、引用、来源版本、覆盖状态和相关证据；
4. 顶部 Build、编译时间、Profile、覆盖率、degraded 原因；
5. “在此范围搜索”动作，将 `document_refs/section_refs` 传给现有搜索接口。

图/Wiki 的 title、label、Markdown、HTML、链接、代码块和 LLM 输出全部是不可信内容。服务端必须先做结构 schema 校验与规范化；HTML 默认禁用或使用严格 allowlist；URL 只允许安全 scheme；前端禁止直接渲染未清洗 HTML，并启用 CSP、外链 `noopener/noreferrer`。sanitization 失败的候选不得发布，编译模型不拥有网络或工具调用权限，源文档中的 prompt injection 只作为数据处理。

### 7.2 状态机

```text
draft profile
  → queued
  → compiling
  → validating
  → validated

compiling ──可恢复错误──> degraded_candidate ──修复/重试──> validating
compiling ──不可恢复错误──> failed
validated  ──仅由 finalize 原子切换 KB active pointer──> active
旧 active ──新 Build 激活──> historical
```

约束：

- `degraded_candidate` 不得替换 KB active pointer；
- 没有 coverage manifest、存在 unresolved source ref 或 ACL 冲突时不得 validated；
- 删除来源或权限收紧后，旧 Build 可留作历史审计，但依赖内容必须立即 fail closed，不能等待重编；
- 同一 KB 同时只有一个未结束挖掘/编译 Run，沿用现有唯一约束与 FIFO。

### 7.3 v0.1 图模型

#### 节点

| kind | 来源 | 是否 LLM 生成 | v0.1 |
|---|---|---:|---:|
| `kb_root` | KB/Build | 否 | 必须 |
| `document` | Document Snapshot | 否 | 必须 |
| `section` | structure node | 否 | 必须 |
| `evidence` | raw segment / table row / code block | 否 | 必须 |
| `table_asset` | typed asset | 否 | 必须 |
| `wiki_page` | 编译 Artifact | 是 | M2 |
| `topic` | 标题/标签聚合或 LLM 候选 | 可选 | M2；需标 provenance |
| `community` | 图聚类 | 是 | v0.2 |
| `claim/entity` | schema 约束抽取 | 是/混合 | v0.3 |
| `episode/temporal_fact` | 交互或业务事件 | 混合 | v0.4 |

#### 边

v0.1 正式边：

- `CONTAINS`：KB→Document、Document→Section、Section→Evidence；
- `NEXT` / `PREVIOUS`：同级结构顺序；
- `PARENT_OF`：标题/结构层级；
- `LINKS_TO`：原文显式链接或明确文档引用；
- `DERIVED_FROM`：M2 的 Artifact→Source；
- `ABOUT`：M2 的 Artifact/Section→Topic。

Artifact 段落到 Evidence Span 的支持关系以 `asset_compiled_artifact_sources` 为唯一事实源，不伪装成图边；否则必须先将 paragraph 建成正式节点。跨 Build 的版本关系使用 `asset_builds.parent_build_id` 或独立 artifact lineage 表，不放入只允许同 Build 端点的当前图。

不允许将 LLM 自由生成的业务关系伪装为确定性边。候选关系如果被实验性生成，只能以 `inferred_candidate` 存在且不进入默认图导航。

### 7.4 KB Active Build 前置与数据模型

KCG 不能直接建立在当前“每文档选择各自最新 validated Build”的 scope 上。M1 前先冻结以下目标态：

1. Run 提交时预分配 `candidate_build_id`，写入 `mining_runs`；`assemble_build()` 接受该 ID，不再到 finalize 才随机生成；
2. global 阶段前生成不可变 `CompilationInputManifest`：父 active Build 的完整 Snapshot 集 + 本 Run 的 new/update/remove 决策；
3. candidate Build 包含整个 KB 的 effective document/snapshot 集，不只是本 Run 被重新处理的文档；
4. 变更 Snapshot 只读本 Run staging，复用 Snapshot 只读父 active Build 对应 final；不在 manifest 的资产禁止读取；
5. finalize 在同一事务中完成 KCG promote、Build validated 和 `kb_active_builds` 指针切换；失败保持旧指针；
6. Java serving 的 scope/ref/检索 mapper 只从该 KB 单一 active Build 解析 Snapshot，不再逐文档选不同 Build；
7. 来源软删或权限收紧时即使新编译未完成，旧 artifact/node/ref 也立即 fail closed，并持久化 invalidation 事件进入同 KB 队列。

建议新增：

```text
kb_active_builds
  kb_id PK, active_build_id, previous_build_id, activated_at, revision

asset_compilation_input_manifests
  build_id PK, run_id, kb_id, parent_build_id,
  effective_snapshot_set_hash, profile_version, created_at

asset_compilation_input_items
  build_id, run_id, kb_id, document_id, document_snapshot_id,
  source_state(new_staging|reused_final|removed), dependency_hash

asset_compiled_artifacts
  build_id, run_id, kb_id, acl_scope, security_label,
  artifact_ref_key, artifact_type, title,
  body_json, content_hash, provenance_json, quality_json,
  compilation_status, schema_version

asset_compiled_artifact_sources
  build_id, run_id, kb_id, acl_scope,
  artifact_ref_key, paragraph_key,
  document_snapshot_id, target_ref, source_span_json, support_kind

asset_knowledge_graph_nodes
  build_id, run_id, kb_id, acl_scope, security_label,
  node_ref_key, node_kind, label,
  source_ref_key, artifact_ref_key, properties_json, provenance_kind

asset_knowledge_graph_edges
  build_id, run_id, kb_id, acl_scope,
  edge_ref_key, relation,
  from_node_ref_key, to_node_ref_key, provenance_json

asset_compilation_coverage
  build_id, run_id, kb_id, acl_scope,
  document_snapshot_id, expected_units, compiled_units,
  omitted_units, omission_reasons_json, dependency_hash

asset_compilation_coverage_items
  build_id, run_id, kb_id, document_snapshot_id,
  source_kind, source_ref_key, eligibility,
  status(compiled|reused|excluded|failed), reason_code,
  artifact_ref_key, node_ref_key
```

设计规则：

- 所有表先有 `_staging` 同构表，由 `mining_finalize` 原子晋升；
- `(build_id, ref_key)` 唯一；ref_key 为内部逻辑键，外部只发 HMAC opaque ref；
- staging 的唯一键和所有清理/晋升操作都必须包含 `build_id/run_id`，不得只按 snapshot 删除；
- 节点和边使用同 `kb_id + build_id` 的复合外键；edge 两端不得跨 KB/Build；artifact source 只能引用该 Build 已选入的 Snapshot；
- v0.1 禁止跨 ACL 合成，由数据库约束可表达的部分与发布 validator 双重执行；权限收窄条件必须在 SQL 查询前下推，不得查询后过滤；
- coverage 分母区分“全部文档 / eligible 文档 / eligible source units”；Profile 排除项记录 `excluded_by_profile`，`minimumDocumentCoverage=1.0` 只针对 eligible 分母；
- artifact body 使用结构化段落数组，每段单独绑定 sources，不保存不可核查的大段 Markdown blob；
- `dependency_hash` 至少覆盖来源 Snapshot hash、Profile version、prompt/model、编译器版本和上游 artifact hash；
- unchanged dependency closure 可以从父 Build 复用，LLM 只重算受影响节点；
- v0.1 不使用图数据库专属特性，1–3 hop 用有界 SQL/内存邻接，所有 depth/limit 有硬上限。

删除与权限变化的即时失效采用 fail-closed 双保险：查询把 artifact source dependency 与当前未删除、同 KB、仍授权的 Document 联查；删除/ACL 事务同时写 tombstone/invalidation。若同 KB 已有 Run，事件必须合并进持久队列而不是丢弃。

### 7.5 Workflow 影响

M1 新增确定性 global operator：

```text
knowledge_graph_compile@1
zone: global
input: finalizeInput: FINALIZE_INPUT
output: finalizeInput: FINALIZE_INPUT
requires: assets_persisted
provides: compilation_graph_candidate
error_policy: FAIL_FAST
```

`structure_ready` 不是当前静态 capability，改为 handler 内对 candidate manifest 全量 readiness 的运行时门禁。当前 NodeDef 不能按 preset 覆盖 error policy，因此 v0.1 不承诺“同一算子正式 FAIL_FAST/实验 FALLBACK”。

推荐首版预置：`system-knowledge-graph-assets`：

```text
input_ingest → document_parse → segment_compile
             → retrieval_unit_project → embedding
             → asset_persist
             → knowledge_graph_compile
             → mining_finalize
```

实现要求：

1. `asset_persist → knowledge_graph_compile → mining_finalize` 使用同一个 `FINALIZE_INPUT` slot；catalog、options、handler registry、compiler、manifest 与 UI editor 同批更新；
2. global handler 通过 `CompilationInputRepository.resolve(run_id)` 读取冻结 manifest，不依赖当前不存在的 DocumentState/ArtifactBag fan-in；
3. 变更 Snapshot 读本 Run staging；复用 Snapshot 读父 active Build 对应 final；禁止读取 manifest 外资产；
4. M1 只生成 deterministic graph，不调用 LLM；
5. manifest 冻结 Compilation Profile、compiler version 和 graph schema version；
6. 每 Run、KB、用户和 Provider 都有 token/cost hard cap、触发频率和并发上限；达到上限返回稳定错误并保持旧 active Build，不得仅记录后继续执行。

M2 另增 `knowledge_artifact_generate@1` global operator，放在 graph compile 之后、finalize 之前，生成 Wiki/Topic 与逐段 citation；其固定策略为 FAIL_FAST，实验性缺图/缺 Wiki 是否允许发布由独立 preset/Profile 的 finalize 质量门禁决定，不在 NodeDef 动态改 error policy。

预置分开：

- `system-knowledge-graph-assets`：M1，仅 deterministic graph；
- `system-knowledge-wiki-assets`：M2，在 M1 之上增加 `knowledge_artifact_generate`。

### 7.6 Compilation Profile v0.1

为最快上线，Profile 先作为 workflow node 参数和冻结 manifest 的一部分，不立即建设独立 Profile 管理产品。字段至少包括：

```json
{
  "schemaVersion": "kcg-profile-1",
  "sourcePolicy": {
    "includeMimeTypes": ["text/markdown", "application/pdf"],
    "excludePaths": [],
    "authorityRules": []
  },
  "graphPolicy": {
    "deterministicRelations": ["contains", "parent_of", "next", "links_to"],
    "maxNavigationDepth": 3
  },
  "artifactPolicy": {
    "generateWiki": false,
    "generateTopics": false,
    "maxSourcesPerParagraph": 8,
    "requireSourceForEveryParagraph": true
  },
  "coveragePolicy": {
    "failOnSilentOmission": true,
    "minimumDocumentCoverage": 1.0
  }
}
```

这是需求合同示例，不是最终 JSON Schema；字段命名在实现前由架构评审冻结。

### 7.7 REST 与 MCP 接口

服务归属必须先冻结，避免 Python/Java 分别复制 ACL 与 active-scope 选择逻辑：

- mining：编译提交、dry-run、coverage、失败诊断；
- Java serving：current graph、artifact、ref、neighbors/navigation；
- MCP：只转发 Java internal read；
- `kb_active_builds` 与 effective snapshot manifest 是唯一 scope 真相源，Python/Java 不得各自定义“当前”。

逻辑接口如下；实现时按现有 Nginx 代理前缀落到对应服务：

```text
Java serving:
GET /api/v1/knowledge-graph
  ?kb_id=...&kinds=document,section,evidence,table_asset&limit=...&cursor=...

GET /api/v1/knowledge-graph/{node_ref}

GET /api/v1/knowledge-graph/{node_ref}/neighbors
  ?relations=contains,parent_of,next,links_to&depth=1&limit=...

GET /api/v1/knowledge-artifacts/{artifact_ref}

Mining:
GET /api/kb/{kb_id}/knowledge-compilation/coverage
POST /api/kb/{kb_id}/knowledge-compilation/dry-run
```

统一错误码：

- `compilation_not_ready`
- `artifact_out_of_scope`
- `artifact_ref_expired`
- `coverage_incomplete`
- `source_ref_unresolvable`
- `graph_query_too_broad`

MCP 保持三件套：

- M1/M2 的 `search_knowledge` 协议不加入整图和内部 ID，默认仍返回原始证据；Artifact 到 M3 完成 representation 投影后才承诺可检索；
- 新增 opaque `art_` ref，`get_knowledge(ref=art_...)` 返回 Wiki/Artifact 的结构化段落和逐段来源；
- `get_knowledge(kb_name=...)` 的浏览结果可附 `knowledge_graph_root_ref` 与 compilation status；
- `get_knowledge(ref=st_..., relation=...)` 继续负责确定性结构导航；
- Agent 若引用 Artifact 结论，最终答案仍应落到 Artifact 的原始 evidence refs。

`art_` 不直接复用现有 Snapshot-scoped ref resolver。新增 `ArtifactRefCodec/ArtifactRefService`，HMAC 输入绑定类型域、domain、kb_id、active_build_id、artifact_ref_key 和 key version；不同 ref 类型域分隔，恒定时间比较，生产缺 key fail closed，支持双密钥轮换，日志只记录 ref 哈希。source 表保存稳定内部身份（snapshot + canonical evidence/segment/element/span），响应时再编码 `ev_/st_`，不持久化 opaque ref。

伪造、无权、跨用户、跨 KB 统一返回 `artifact_out_of_scope`；只有当前用户仍有该 KB 权限且命中其历史 Build 时才返回 `artifact_ref_expired`，避免存在性泄漏。

### 7.8 增量编译与删除传播

1. Source Snapshot 变化后计算依赖闭包：`source → evidence/structure → artifact paragraph → artifact/page/topic → graph edge`；
2. 仅闭包内对象重编，其他 artifact 从父 Build 复用；
3. 来源删除后，新 Build 不复制依赖该来源的孤儿 artifact；
4. 多来源 artifact 删除一个来源后必须重新验证，不得只删引用保留原结论；
5. prompt/model/profile/编译器版本变化视作影响所有对应产物的依赖变化；
6. 旧 Build 保留审计，当前接口只解析 active Build；
7. 提供 dry-run：列出将新增/复用/重编/失效的节点和预计 LLM 调用量。
8. KB/文档删除、ACL 撤销或保留期到期时，依赖闭包同时覆盖 prompt/raw output/attempt/error body、编译缓存、query log、导出文件和备份；按策略 purge、crypto-shred 或只保留不可恢复聚合统计。

### 7.9 Readiness 与质量门禁

新增 `knowledge_graph` readiness，至少包含：

```text
deterministic_structure_ready
artifact_sources_resolvable
coverage_complete
acl_consistent
graph_integrity_valid
artifact_generation_ready/degraded
```

发布门禁：

- 图中无悬空 node/edge；
- artifact 每段 source ref 可解析；
- 所有选入 Build 的文档出现在 coverage manifest；
- 被排除的内容必须有稳定 reason code；
- 同一来源不得同时出现在两个活动版本；
- ACL 交集为空的跨源 artifact 拒绝发布；
- 编译失败不影响旧活动 Build 可读。

### 7.10 可观测与预算

每次编译记录：

- source/document/section/evidence/node/edge/artifact 数量；
- 新增、复用、重编、失效数量；
- coverage 与 omission reason；
- LLM calls、token、缓存命中、模型、失败/降级；
- graph validation、citation validation、ACL validation；
- 各阶段耗时、队列等待、Build 激活结果。

查询记录：direct/hybrid/graph-assisted/agentic mode、scope、hop、引用解析、延迟和无结果原因。正常用户响应不暴露内部 trace、score chain 或内部 UUID。

建议性能预算（待基线压测后冻结）：

- KB 图首屏使用分页/分层，禁止一次返回全图；
- 单次邻接导航最大 depth=3、limit=200；
- 不含 LLM 的图/Artifact 读取 P95 目标 ≤ 800ms；
- 简单 search 不触发图遍历和额外 LLM；
- 增量编译的 LLM 调用仅发生在 dependency closure 内。
- 最大文档数、节点数、边数、artifact body、source 数和单 Run token/cost 都有服务端硬限制；viewer/MCP 不得触发重编，dry-run 不得执行完整 LLM 编译。

## 8. MVP 需求分批

### M0：上线门禁与事实源收口

| ID | 需求 | 验收 |
|---|---|---|
| P0-SEC-00 | 封禁全部 secret-bearing config 读面 | `/api/v1/system/{service}`、`/{service}/raw` 及聚合完整配置端点均不对用户/公网开放；独立 workload identity 按 namespace 读取；前端只收字段 allowlist 脱敏 DTO |
| P0-SEC-01 | 从 Git 跟踪配置撤出全部凭据 | LLM/embedding/rerank/DB/MinIO/JWT/internal auth 均改专用变量或 Secret Store；HEAD/镜像/同步包无明文 secret |
| P0-SEC-02 | 完成全量凭据轮换 | 先部署新凭据并健康检查，再吊销历史值；供应商日志/账单和异常 IP 已核查 |
| P0-SEC-03 | Secret 启动校验 | JWT/internal/workload/ref/encryption key 缺失必须 fail closed；只有明确可选 Provider 缺 key 时可禁用该能力并 degraded；禁止硬编码/临时 boot key |
| P0-SEC-04 | LLM 审计数据授权与保留 | caller 由认证上下文派生；task/result/attempt/retry/cancel/stats 按 caller+KB 授权；raw prompt/output 加密或关闭，设 TTL；错误/日志脱敏；备份与删除传播有策略 |
| P0-SEC-05 | Secret scanning | CI 扫当前树和 Git history，阻止非占位 key/password/secret 进入跟踪配置 |
| P0-SEC-06 | 配置写面阻断 literal secret | JSON/YAML PUT、热更新、同步接口只接受 secret reference/占位符；literal secret 返回 typed 4xx 且不落盘 |
| P0-CI-01 | 统一测试入口 | 根目录一条命令可跑纯单测；PostgreSQL 验收独立 profile |
| P0-DOC-01 | 建 CURRENT 文档索引 | README、mining、serving、MCP 不再互相冲突 |

### 建议节奏

在 1 个熟悉仓库的开发者等价投入、无新增基础设施的前提下，经过 Build/scope 复审后的粗估为：

- M0：3–5 个工作日，安全轮换窗口取决于外部凭据协调；
- M0-B：5–7 个工作日；
- M1：5–7 个工作日，可形成第一版“知识图”；
- M2：5–7 个工作日，可形成“自动 Wiki + 引用”；
- M3：5–7 个工作日完成 Artifact 投影、检索联动、评测和灰度。

这是需求拆分的粗估，不是排期承诺；PostgreSQL 验收环境、LLM 可用性和 UI 交互复杂度会影响实际时间。最快正确上线不应跳过 M0-B，否则知识图与当前检索会看到不同 Snapshot 集。完成 M0/M0-B 后，先独立交付 M1，再让 M2/M3 迭代。

## 9. 后续演进路线

### v0.2：多粒度知识合成

- 基于图连通和主题相似度生成跨文档专题页；
- 只对高价值范围做社区检测/Community Brief；
- 引入 compile → evaluate → refine，但精炼只能生成新候选 Build；
- 建 artifact 手工锁定/页面规划，避免自动聚类漏关键内容。

### v0.3：受约束 Claim/Entity 图

- 每个场景先定义窄 schema、golden set、别名/主键规则和审核策略；
- 实体抽取与 entity resolution 分开评测；
- Claim 必须带主体、谓词、客体/值、适用版本、时间、置信度和 source span；
- 只有 `observed + validated` 进入正式图导航；candidate 不影响默认搜索；
- 不恢复旧研究算子，按新的 Artifact/Build/Readiness 合同重写生产链。

首个候选场景应选择只读、可人工核验、对象边界明确的任务，例如“核心网变更前检查包”，而不是先做全领域通用本体。

### v0.4：Agentic Search 与 Knowledge Gap

- 简单问题保持 direct/hybrid；
- 复杂任务允许最多 2 轮、每轮 2–4 个子查询；
- 明确 time/token/tool budget、停止原因和 fallback；
- 新增 `Knowledge Gap`：无证据、版本冲突、未解析对象、无权限、工具失败；
- Agent 只能创建候选知识/缺口，不能直接修改活动 Build。

### v0.5：Temporal Context Graph 与受控能力

- 引入 Episode、valid time、ingestion time、supersedes/conflicts；
- 连接配置快照、Inventory/CMDB、KPI 等动态只读数据；
- 再引入 Runbook、Rule、Tool Contract、审批和动作；
- 高风险动作始终要求最小权限、幂等、审批、回滚和完整审计。

## 10. NON-GOALS：本轮明确不做

1. 不建设大而全的领域本体；
2. 不把 LLM 三元组直接认定为业务事实；
3. 不自动做跨全库实体融合；
4. 不引入 Neo4j 作为 v0.1 前置；
5. 不恢复旧 `graph_expand`、固定 SearchService 或 ContextPack；
6. 不用生成 Wiki 替代原文证据；
7. 不新增 MCP 工具数量；
8. 不建设任意 NL-to-SQL/NL-to-Cypher；
9. 不让所有查询进入 Agent loop；
10. 不在本轮让 Agent 调用生产变更接口。

## 11. 验收与测试合同

### 11.1 必须的测试层

- 单元：hash、dependency closure、node/edge projection、citation validator、ACL intersection、ref codec；
- 集成：staging/promote、Build activation、删除传播、跨 Build ref、SQL depth/limit；
- API：权限、分页、typed errors、旧 Build 过期、coverage；
- MCP：三工具清单不变、`art_` 分流、跨用户/跨 KB 拒绝；
- UI：空态、degraded、Build 切换、来源跳转、异步旧响应隔离；
- E2E：上传 → 挖掘 → 图编译 → validated Build → 图/Wiki → search → get evidence；
- 安全：伪造 ref、SQL 注入、XSS Markdown、ACL 混源摘要、跨 KB cache、LLM task 越权、日志泄露、密钥扫描、raw config 匿名访问；
- 回归：变更/删除一个来源后，旧 artifact 不再出现在 current Build。

新增/修改代码按 TDD 先红后绿；改动范围覆盖率目标至少 80%，并保留真实 PostgreSQL 验收。

安全测试还必须覆盖 owner/editor/viewer/non-member/site-admin × private/public KB 的创建、编译、读取、邻接、发布、导出、ref 解引用矩阵；匿名、直连 backend、伪造身份头均拒绝；权限撤销/public→private 后旧 ref、缓存和已打开页面立即失效；不存在对象与无权对象返回同等 status/body；edge 跨 KB/Build 的数据库约束；cursor/relation/depth/filter 篡改；跨用户/跨 ACL cache 污染。

### 11.2 产品级完成定义

- 用户能在一个真实 KB 中看到有用的文档/章节/主题/Wiki 图，而非仅开发者 JSON；
- 每个生成段落能回到原文具体位置；
- 来源修改/删除后当前图一致更新；
- 未授权用户不能通过图、摘要、ref 或错误信息推断不可见内容；
- 简单搜索性能不因 KCG 明显退化；
- 50–100 条真实问题集能区分解析、编译、检索和生成问题；
- 旧活动 Build 在新编译失败时继续可用。

## 12. OPEN QUESTIONS：实施前需要拍板

M1 前必须拍板的架构决策：

1. **KB 是否正式切为单一 active Build？** 建议是；否则 KCG 需要另建 compilation revision 生命周期，检索与图会有两个“当前”定义。
2. **candidate Build 何时创建？** 建议 Run 提交时预分配 ID，global compile 和 finalize 全程复用。
3. **完整 Snapshot 集如何冻结？** 建议父 active Build + 本 Run new/update/remove 生成 `CompilationInputManifest`，并作为 coverage 分母。
4. **Serving 如何解析当前 scope？** 建议 Java 只读 `kb_active_builds`，不再逐文档挑不同 Build。
5. **删除/权限变化如何即时失效？** 建议查询依赖联查 + 同事务 tombstone/invalidation 双保险。

M2 产品决策：

6. **首个 Wiki 的页面规划范围？** 建议 KB 总览 + 每文档页 + 标题层级主题页，不做自动社区页。
7. **M2 编译失败策略？** 建议保留旧 active Build，新的 candidate 整体不激活；不要发布半引用 Wiki。
8. **是否允许多 ACL 来源合成？** 建议 v0.1/M2 禁止，先按同一 KB/同一授权域编译。
9. **首个业务评测场景？** 建议在现有核心网语料中选择一个只读、可人工核验的变更前检查/规范查证任务。

已有推荐默认：M1 先独立上线纯确定性图、PostgreSQL 存图、MCP 三件套不变、Artifact 到 M3 才可检索、开放式实体/本体继续 research、简单检索不走 Agent loop。
