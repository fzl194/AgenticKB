## 0. 结论

当前项目已经上线“文档级结构编译 + 结构感知 RAG”的主体，不应继续把下一步定义成“重新提取结构”或“再建一套 Document/Section/Table 图”。

下一阶段的核心是建立一条生产者—消费者合同：

```text
Parse IR 已有结构事实
  → 高保真、可热读的 Source/Typed 投影
  → 完整 KB Build 原子发布
  → FTS/向量/结构导航/精确查询共同消费
  → UI/MCP 可从证据回到页、区域、单元格和结构节点
  → 真实题集验证“结构确实改善任务”
```

任何结构字段只有同时满足以下条件才算“生产能力”：

1. 正式 Workflow 可达；
2. 有版本化输入输出合同；
3. 进入 staging，并由 finalize 原子晋升；
4. Readiness 来自实际数据而不是算子成功；
5. Java Serving 有正式消费者；
6. UI 或 MCP 有用户入口；
7. 有端到端验收和回滚。

已失效的备选关键路径（第一阶段不得执行；当前顺序见34号）：

```text
SEC-0 安全止血 ───────────────┐
                              ├→ G1 KB Active Build
G0 当前事实收口 ──────────────┘
                                → G2 精确证据闭环
                                  → G3 结构/表格消费与确定性知识图
                                    → G4 图范围检索与评测
                                      → G5 Wiki/Topic Artifact
```

SEC-0 与 G0 可以并行，但二者必须同时完成，G1 才能激活生产 Build。

## 1. 当前生产基线

### 1.1 已经上线的挖掘能力

正式生产链：

```text
POST /api/kb/{kb_id}/mine
→ 冻结已发布 Workflow Manifest
→ domain FIFO
→ input_ingest
→ document_parse
→ segment_compile
→ retrieval_unit_project
→ [query_expansion_generate | hierarchical_summary_generate]
→ [embedding]
→ asset_persist
→ mining_finalize
→ staging 晋升 final + validated Build
```

当前 Parse IR 已表达：Container、Element、EvidenceSpan、Parse Relation、Table/Figure/Formula Asset、parser/model/quality/provenance。默认 hybrid 进一步生成 document/section/prose/table/table_row/list/code/formula/figure_caption 检索表示，标题路径参与 FTS/embedding，结构节点和表格 cells 进入正式表。

因此 v1 不扩 Parse IR schema、不重写 parser、不全量重新解析历史语料。

### 1.2 已经上线的消费能力

正式搜索：

```text
scope + query_embed
→ FTS || dense
→ RRF
→ model_rerank
→ evidence_hydrate
→ EvidenceResponse
```

生产消费已覆盖：

- 标题路径参与 lexical/dense/rerank；
- section 命中后可水合父章节；
- segment 可扩展邻段、父章节或整文；
- table/table_row 参加双路召回并可水合整表；
- MCP `get_knowledge` 可 inspect、navigate、query table；
- 前端可查看快照、大纲、元素、切片和表格。

### 1.3 当前真正的断点

1. 结构化预览读取当前 revision 最新 READY Parse Snapshot；检索读取每个文档各自最新 validated Build，二者可能不是同一版本。
2. KB 没有单一 active Build；选择性挖掘后一次检索可能组合多个 Build。
3. Parse IR 的 bbox/page/A1/XPath/OOXML 等 EvidenceSpan 已生成，但线上不能解析；EvidenceResponse 的 page 当前实际为空。
4. `asset_segment_element_links`、v2 `source_refs_json/provenance_json` 已落库但没有正式 Serving 消费。
5. Parse Relation 只有 caption 被间接使用；structure final 只产 parent/order，footnote/reference 导航通常为空。
6. `semantic_role/table_kind` 可在解析结果中看到，但不进入正式 v2 filter/routing。
7. Table 已有精确查询；Figure/Formula 主要仍是文本/caption 检索，没有 typed asset 读取。
8. 浏览器不消费 `structure_ref`；结构导航和 table DSL 基本只对 Agent 可用。
9. 当前存在 document `structure_ref`、文档分页首段、公开类型往返、legacy retrieval-unit UI 等生产协议缺陷。

## 2. CAPABILITY

KB owner 完成一次挖掘后，系统发布一个可回滚的完整 KB Build。该 Build 冻结当前文档 Snapshot 集，以及每个 Snapshot 的结构、typed asset、检索表示和精确来源。用户或 Agent 可以搜索、按章节范围检索、沿结构关系导航、精确查询表格、读取图片/公式实际可得内容，并从任何返回结果回到原始页、区域、元素或单元格。失败的新 Build 不改变当前线上版本。

## 3. 固定约束

1. Parse IR JSON 是解析真相源；新表是热读投影，不是第二套 parser。
2. 图节点不复制正文；正文继续来自 raw segment、Parse IR 或对象存储。
3. Parse 事实归 Snapshot；所有可变的结构/检索/typed 投影归不可变 `projection_revision_id`。Build membership 必须同时绑定 Snapshot 与 Projection Revision。
4. 新 rich asset 使用 `run_id + projection_revision_id + snapshot_id` 隔离 staging，只有 finalize 能晋升；现有 v2 派生资产也必须进入 projection revision，历史 Build 才能完整回滚。
5. 一次单 KB current 查询只读一个 active Build；多 KB 查询每库恰好一个 active Build，并记录 build vector。
6. FTS/dense 的 ACL、Build、document/section filter 在 Top-K 前下推。
7. Alias/Summary 只帮助召回，最终证据仍来自 returnable source。
8. MCP 保持 `search_knowledge/get_knowledge/upload_document` 三件套。
9. 不恢复 entity/ontology research operator，不恢复旧 `graph_expand`，不引入图数据库。
10. 缺少 locator/type 是 `unknown/unavailable + reason`，禁止模型或规则伪造。
11. 每个 readiness 必须有对应生产行、正式消费者和 E2E 用例。

## 4. 端到端资产合同

### 4.1 Source Fact Projection

灰度期新增 `protected/unique` 文档算子；不得立即加入旧 Workflow schema 的全局 fixed 集：

```text
source_fact_project@1
slot: documents: DOCUMENT_BATCH → documents: DOCUMENT_BATCH
input: MiningDocumentBundle(snapshot_ref, parse_ir_ref, projection_revision_id)
reads: immutable Parse IR + compiled segment links
output: source_fact_projection_ref + counts + readiness fragment
provides: source_facts
error_policy: SKIP_DOCUMENT
edit_policy: protected during canary; fixed only in Workflow schema 2.1
unique: true
```

Bundle 只携带引用和计数，不内嵌大数组。

热读事实：

```text
SourceContainerFact
  snapshot/container/type/order/parent/name/page/sheet/slide/
  geometry/text-layer/language/quality/provenance

SourceElementFact
  snapshot/element/type/order/parent/style/confidence/metadata

EvidenceSpanFact
  snapshot/span/element/page/container/text-range/
  source-locator/visual-region/native-ref/raw-text-hash/ocr-confidence

ParseRelationFact
  snapshot/from-element/to-element/relation/confidence/method/provenance

SegmentEvidenceLink
  snapshot/segment/element/span/char-range/link-order
```

建议新增 final/staging 表：

- `asset_source_containers[_staging]`
- `asset_source_elements[_staging]`
- `asset_evidence_spans[_staging]`
- `asset_parse_relations[_staging]`
- `asset_segment_evidence_links[_staging]`
- 必要时 `asset_element_container_links[_staging]`

同 Snapshot 的 element/span/relation/link 使用复合 FK；不得从 lossy raw segment 反推 locator。

`asset_source_elements` 只保存热读身份、类型、层级、定位和 provenance，不复制完整正文。`asset_segment_evidence_links` 可通过扩展现有 `asset_segment_element_links` 或增加其规范化 span child table实现；两者不能同时成为 canonical writer，旧表只能作为兼容面。

### 4.2 Typed Asset Projection

灰度期新增 `protected/unique` 文档算子：

```text
typed_asset_project@1
slot: documents: DOCUMENT_BATCH → documents: DOCUMENT_BATCH
input: MiningDocumentBundle + source_facts + projection_revision_id
reads: Parse IR Table/Figure/Formula Asset
output: typed_asset_projection_ref + counts + readiness fragment
provides: typed_assets
error_policy: SKIP_DOCUMENT
edit_policy: protected during canary; fixed only in Workflow schema 2.1
unique: true
```

v1 类型：

```text
table   → 完整结构与精确查询
figure  → caption/region/binary ref/mention，实际可得才发布
formula → raw/plain/LaTeX/MathML/provenance，实际可得才发布
```

Table 需要保留：

- row/column 数；
- header regions；
- row/column span；
- caption/footnote/continuation；
- raw/display/normalized value；
- value type、formula、cached value；
- cell source span、confidence、projection version。

rich typed 表是线上查询投影，Parse IR 仍是可重建权威源。当前 `asset_structured_assets/asset_table_cells` 保留为兼容投影；兼容行只能由 rich typed 投影在同一 asset-persist 事务派生，不能由两套 repository 独立双写。

至少冻结以下表及其 `_staging` 同构表：

- `asset_typed_tables`
- `asset_typed_table_columns`
- `asset_typed_table_cells`
- `asset_figure_assets`
- `asset_formula_assets`

每张 staging 表必须包含 `run_id + projection_revision_id + snapshot_id`；final 表按 `projection_revision_id + snapshot_id + local_key` 唯一，并使用 Source Element/Span 复合 FK。

### 4.3 Retrieval Representation v2.2

不重写 FTS/dense，只补齐正式消费字段：

```text
section_ref
parent_ref
source_refs_json
provenance_json
semantic_role
table_kind
tokenizer/profile compatibility
```

Recall 热行与 Hydration 重行分开：

- Recall 只读排序、过滤、target、canonical 和轻量结构字段；
- Hydrate Top-N 才批量读取正文、source refs 和 provenance；
- 禁止在召回 SQL 拉大 JSON；
- alias 继承源 representation 的 section/source/parent。

### 4.4 EvidenceResponse additive contract

保持顶层 `query/evidence/has_more`，Evidence 增量增加：

```json
{
  "ref": "ev_...",
  "type": "table",
  "content": "...",
  "source": {
    "knowledge_base": "...",
    "file_name": "...",
    "document_ref": "doc_...",
    "section": "...",
    "locations": [
      {
        "page": 12,
        "container_type": "page",
        "bbox": [0.1, 0.2, 0.8, 0.3],
        "native_ref": {"sheet": "参数", "cell": "C18"},
        "char_range": [120, 186],
        "quote_hash": "..."
      }
    ],
    "locations_truncated": false
  },
  "fragments": [
    {
      "index": 0,
      "kind": "exact|window|section|row|header",
      "text": "...",
      "evidence_char_range": [0, 38],
      "locations": [{"page": 12, "bbox": [0.1, 0.2, 0.8, 0.3]}]
    }
  ],
  "structure_ref": "st_...",
  "capabilities": {
    "can_navigate": true,
    "can_query_structured": true,
    "can_read_typed_asset": true
  }
}
```

普通响应不暴露内部 UUID、storage key、score chain 或原始 provenance JSON。

兼容规则：`content` 继续保留为 fragments 的确定性拼接，旧客户端无需修改；新客户端以 `fragments[].locations` 做逐片段定位，禁止把 flat locations 误认为支持整段 content。每条 evidence 最多 32 个 location、每 fragment 最多 8 个，超限分别标记 truncated。

### 4.5 KB Build / Release contract

当前域级 Release 不允许发布 KB Build，因此新增 KB 级激活账本：

```text
asset_kb_releases
  kb_id, channel, build_id, status,
  activated_at, deactivated_at, actor

UNIQUE(kb_id, channel) WHERE status='active'
```

同时新增派生资产版本边界：

```text
asset_projection_revisions
  id, snapshot_id, workflow_graph_hash,
  parse_ir_schema_version, source_projection_version,
  structure_projection_version, typed_projection_version,
  retrieval_schema_version, compiler_version,
  tokenizer_version, embedding_profile_hash,
  status, created_by_run_id

asset_build_projection_memberships
  build_id, document_id, snapshot_id, projection_revision_id,
  selection_status, reason

asset_public_refs[_staging]
  ref_digest, ref_kind, kb_id, build_id,
  projection_revision_id, snapshot_id, internal_ref, key_version
```

现有 retrieval/embedding/structure/table/readiness final 表逐步增加 `projection_revision_id`，Serving 必须通过 Build membership 选择对应 revision，禁止仅按 snapshot 读取“最新投影”。

Build 必须包含完整 closure：

```text
parent active Build 的未变化 memberships
+ 本 Run NEW/UPDATE/RESTORE
- DELETE/WITHDRAW
= candidate Build 完整 Snapshot 集
```

validate 后在同一事务中晋升资产、标记 Build validated、退役旧 KB Release、激活新 Release。失败时旧 active Build 完全不变。重新激活同一不可变 Build 时，该 Build 所属旧 ref 可以重新有效；Build 非 active 期间返回 expired。

单条 `ev_/doc_/st_` 只绑定所属 `kb_id + build_id + projection_revision_id + snapshot_id + internal_ref + ref_kind`；query cache、query log 和整次响应 trace 才绑定完整多 KB `buildByKb` vector，避免无关 KB 更新导致单条 ref 失效。

当前 ref resolver 的全 scope 候选枚举不得承接扩容后的 section/span/typed/graph refs。G1 将 public ref 改为索引/O(1) 解析：先查 `ref_digest`，再校验 owning KB current Build、ACL、kind 和 key version；支持密钥轮换，候选 cap 不得把有效 ref 误判为 invalid。

candidate Build ID 必须在文档投影前预分配。Public ref 在 internal ref 已冻结后写入同 Run/Revision staging；finalize 校验 registry 覆盖率，将 ref registry 与资产同事务晋升，最后才激活 KB Release。禁止出现 Build 已 active 但其 refs 尚未可解析的窗口。

`ref_digest` 唯一且碰撞时拒绝晋升；搜索热路径只读 registry，不能懒写补行。GC、Build 回滚和 HMAC key rotation 都必须维护 registry 生命周期。

## 5. Readiness 合同

Projection Revision / Snapshot 级新增：

```text
source_grounding_ready
container_projection_ready
lineage_complete
explicit_relation_projection_ready
locator_coverage + reason counts
typed_table_ready
cell_source_coverage
typed_value_coverage
formula_preservation
figure_asset_ready/partial
formula_asset_ready/partial
```

Build/KB 级新增：

```text
effective_snapshot_manifest_ready
document_coverage
structure_coverage
source_resolve_rate
typed_asset_coverage
graph_integrity_ready
```

Readiness fragment 单独落 `asset_projection_readiness_fragments`，以 `run_id + projection_revision_id + snapshot_id + producer` 唯一。`asset_persist` 是唯一合并者，生成最终 revision-bound Snapshot readiness；前置算子不得直接写随后会被覆盖的 readiness 行。

统一晋升接口：

```text
promote_projection_assets(run_id, projection_revision_id, snapshot_ids)
```

所有 staging SELECT/DELETE 都带 run/revision。晋升顺序固定为 containers → elements → spans → relations/lineage → typed assets → compatibility faces → retrieval/embedding/structure → readiness → public ref registry → Build membership/manifest → KB Release。任一步失败整事务回滚；恢复/GC 也按 run/revision 清理。

门禁：

- dangling element/span/relation/cell 阻断；
- 有表却静默漏数据 cell 阻断；
- parser 不提供 bbox 可 degraded，但必须有 reason；
- Figure 无原图不得把 caption 冒充完整 Figure；
- Alias 有命中但不能回 source 时阻断；
- 新 Build degraded 不替换旧 active Build。

## 6. SEC-0：上线安全硬门禁

优先级：P0；建议 3–5 个工作日，可与 G0 并行。

1. 封禁 `/api/v1/system/{service}`、`/{service}/raw` 及其他 secret-bearing 配置读面；前端只读字段 allowlist 脱敏 DTO。
2. 内部服务使用独立 workload identity 和 namespace 最小授权；不能使用普通用户 JWT 读取 secret。
3. 将 LLM/embedding/rerank/DB/MinIO/JWT/internal/ref/encryption secret 全部外置；部署新值并健康检查后吊销历史值。
4. 配置 PUT/热更新拒绝 literal secret，只接受环境变量占位、Secret Store ref 或 write-only secret 流程。
5. LLM task/result/attempt/retry/cancel/stats 按可信 caller + KB + Snapshot 授权；raw prompt/output 关闭或加密并设 TTL。
6. CI 扫描当前树、Git history、镜像和同步包；非占位 secret 阻断发布。
7. JWT/internal/ref/encryption key 缺失必须 fail closed；只有可选 Provider 缺 key 时可禁用能力并 degraded。

验收：匿名/普通用户不能读取完整配置；旧凭据已失效；缺核心认证 secret 不能启动；配置写接口不能重新把明文 secret 写回 YAML；日志、错误和配置 diff 不回显 secret。

## 7. G0：生产事实与协议收口

优先级：P0；建议 3–5 个工作日。

### 挖掘/Build

1. 冻结 stable section identity v2 合同，扫描重复标题/分隔符冲突并产出迁移清单；G0 不生成尚无 element identity 输入的新 ref。
2. `parse-result` 明确 `view=current_serving|latest_revision`；G0 的 current_serving 表示该文档当前进入线上 mosaic scope 的 Snapshot，并返回 `scope_mode=legacy_mosaic`，不得冒充尚不存在的 KB active Build。
3. 跑一次只读 coverage probe：统计各 parser 的 Container/Span/Relation/Typed Asset 实际覆盖，不改 Parse IR schema。

### 检索/MCP

1. 修 document representation `#document` 与真实 document node ref 不一致；搜索返回的 `st_` 必须可直接 inspect/navigate。
2. 修 `get_document` 空 cursor 导致 `segment_index=0` 丢失；改为版本化 keyset cursor，起点 `-1`。
3. 公开 evidence type 可原样回传 filter；内部映射 `list→list_group`、`code→code_block`。
4. `footnotes/references` 仅在真实边存在时披露，不宣传空能力。

### 前端

1. 结构化预览、正式知识、搜索结果同屏显示 Snapshot 与 `scope_mode`，并明确 latest revision 是否已进入 current serving；G1 后再显示统一 Build。
2. 文档检索单元改读 v2，不再读 legacy `asset_retrieval_units`。
3. 表格提示改为当前 `get_knowledge(ref=st_, query=...)`。
4. Run trace fallback 不再渲染已退出生产的实体/本体/graph_write。

### 验收

- Preview、search、get evidence 对 `current_serving` 使用同一文档 Snapshot；
- 重复标题/ref 冲突可被完整检测并进入迁移清单；新 identity 到 G2 source facts 上线后生效；
- document `st_` 可 children/descendants；
- 0/1/199/200/201 条及稀疏 ordinal 分页不漏不重；
- Evidence type filter 往返一致；
- 旧路径有兼容或稳定 expired error。

## 8. 第二阶段候选：G1 KB 原子 Active Build（第一阶段不执行）

旧方案优先级：P0；建议 7–10 个工作日。该“G2/G3强依赖”判断已被34号的单文档知识版本方案替代，仅在第二阶段讨论知识库级统一版本时重新评审。

### 挖掘/Build

1. 引入 `asset_kb_releases` 和完整 Build closure。
2. 引入 `asset_projection_revisions` 与 Build Projection Membership；将现有 retrieval/embedding/structure/table/readiness 纳入 revision 选择，禁止同 Snapshot 覆盖历史 Build 的派生资产。
3. 从当前 per-document latest mosaic 和现有 v2 行生成 synthetic baseline Build/Projection Revision；先 shadow 对比，不直接全库激活。
4. 新 Run 以上一个 KB active Build 为 parent，复制未变化 membership，替换变化，剔除删除。
