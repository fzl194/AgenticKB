# 结构化知识业务演进路线与第一阶段需求

> 日期：2026-09-03  
> 当前代码基线：`master@0d55a8c`  
> 文档定位：业务需求事实源  
> 本轮讨论范围：第一阶段“文档级结构化知识消费闭环”  
> 关联材料：33 号保留此前技术调研与备选方案；第一阶段的实施拆解必须重新服从本文件，不得沿用其中“KB Active Build 是第一阶段前置”的旧顺序。

## 0. 核心决定

当前系统已经能够从文档中提取章节、段落、表格、字段、列表、代码、图片说明、来源标记等结构化信息，并将其中一部分用于搜索和 Agent 工具。

下一步不继续追求“抽取更多”，先解决：

> 用户能否真正利用这些结构完成查找、理解、精确查询和原文核验。

第一阶段完成后的标准用户路径是：

```text
打开文档或发起搜索
→ 找到具体证据
→ 看清所属章节和内容类型
→ 沿父子/前后章节继续阅读
→ 必要时限定在本节或子节内搜索
→ 对表格做精确筛选和统计
→ 回到原文页、段落或单元格核验
```

这一阶段是文档级能力，不做知识库级全景图、跨文档 Wiki、实体、本体或自主 Agent。

## 1. 整体业务演进路线

| 阶段 | 业务问题 | 核心结果 |
|---|---|---|
| 准备工作 | 当前功能有断链、旧提示和来源入口错误 | 现有能力可靠可用 |
| 第一阶段 | 结构已经抽取，但普通用户不能连续消费 | 搜索→结构→表格→原文的文档级闭环 |
| 第二阶段 | 用户只能逐篇理解文档 | 知识库级结构视图和完整度 |
| 第三阶段 | 系统主要交付原始资料 | 带逐段来源的 Wiki、专题和主题页 |
| 第四阶段 | 缺少业务对象、关系和规则 | 面向具体任务的受约束实体/关系知识 |
| 第五阶段 | 知识建设与真实任务脱节 | Agent 主动取证和知识缺口闭环 |

后续阶段暂不展开。本轮只讨论第一阶段。

## 2. 第一阶段 CAPABILITY

领域工程师打开一份已经加工的专业文档后，可以快速理解文档结构，在整篇或指定章节范围内找到答案，对表格做精确查询，并从任何搜索结果或查询结果回到真实原文位置。知识库维护者能够判断这份文档哪些结构可用、哪些不可用以及原因。网页用户和 Agent 对同一证据看到相同内容和来源。

## 3. 当前生产能力是什么

### 3.1 已经能够完成

#### 文档结构化展示

用户打开文档后，可以看到：

- 当前文件和加工状态；
- 解析质量；
- 文档大纲；
- 章节层级；
- 结构元素；
- 切片及其章节路径；
- 表格字段和前若干行；
- 检索单元；
- 解析警告。

生产证据：[KbDocPreviewView.vue](../../kb-ui/src/views/kb/KbDocPreviewView.vue)、[read_service.py](../../knowledge_mining/mining/snapshot_store/read_service.py)。

#### 结构参与搜索

当前搜索不是只使用扁平文本：

- 标题和祖先章节会作为上下文参与搜索；
- 默认模式会建立文档、章节、段落、整表和表格行等不同搜索入口；
- 表格行会带字段名，例如“告警码=A101；原因=风扇停转”；
- 命中小段后可以返回相邻内容、父章节或整篇文档；
- 搜索同时使用关键词和语义匹配，并进行排序。

生产证据：[templates.py](../../knowledge_mining/mining/workflow/templates.py)、[projector.py](../../knowledge_mining/mining/retrieval_projection/projector.py)、[ParadigmService.java](../../agent_serving_java/src/main/java/com/coremasterkb/serving/operator/paradigm/ParadigmService.java)。

#### Agent 结构导航和表格查询

Agent 当前已经可以通过现有知识工具：

- 读取证据或整篇文档文本；
- 查看章节的父级、子级、祖先和后代；
- 查看有顺序编号的前后内容；当前章节本身没有可靠顺序编号，尚不能稳定支持“上一节/下一节”；
- 查看表格字段；
- 对表格筛选、排序；
- 执行计数、求和、平均、最小和最大值。

生产证据：[server.py](../../mcp_server/server.py)、[StructureNavigateService.java](../../agent_serving_java/src/main/java/com/coremasterkb/serving/structure/StructureNavigateService.java)、[StructuredQueryService.java](../../agent_serving_java/src/main/java/com/coremasterkb/serving/structure/StructuredQueryService.java)。

### 3.2 当前用户路径在哪里断开

| 用户动作 | 网页当前状态 | Agent 当前状态 | 主要问题 |
|---|---|---|---|
| 搜索并看到证据 | 可用 | 可用 | 用户看不到正在使用的文档版本 |
| 看来源 | 只显示文件名和章节文字 | 可继续读取 | 文件名、章节和结构入口不可点击；精确位置缺失 |
| 展开证据 | 只能展开更多文本 | 可取段落/章节/整文 | “查看完整”不是打开原件 |
| 看文档大纲 | 文档页可看 | 可导航 | 搜索结果不能进入大纲；网页大纲不可操作 |
| 父子/前后导航 | 不可用 | 部分可用 | 网页没有入口；部分关系只存在名称，没有实际数据 |
| 本章节搜索 | 不可用 | 只能命中章节本身 | 不能真正搜索章节内全部正文和表格 |
| 表格查看 | 只能预览部分行 | 可查询 | 网页不能筛选、排序和统计 |
| 回到原文 | 可以独立打开文档 | 只能回文本 | 搜索结果不能跳页、段落、区域或单元格 |
| 质量与缺失 | 有警告和数量 | 有部分能力说明 | 没有“为什么不可定位/不可查询”的完整说明 |

### 3.3 已经产生但尚未被消费的信息

- 页码、页面区域、字符范围、Excel 单元格、HTML 路径等来源定位；
- 切片与原始元素之间的对应关系；
- 内容来源和加工方式记录；
- 脚注、引用、延续等文档内部关系；
- 内容属于定义、约束、示例、结论等类型；
- 表格的字段类型、公式、合并单元格和单元格来源；
- 图片原件、区域和正文提及；
- 公式的原始结构。

其中表格消费最成熟，章节次之；图片、公式和精确来源仍明显不足。

### 3.4 当前明确缺陷

这些属于准备工作，不是新产品能力：

1. 部分“查看结构”引用能够生成，但打开后找不到真实节点；
2. Agent 分页读取整篇文档时可能漏掉第一段；
3. 搜索结果的内容类型不能全部原样用于再次筛选；
4. 文档页“检索单元”仍读取旧数据来源；
5. 表格页面仍提示已经合并删除的旧工具名；
6. 历史任务的降级页面仍可能展示已退出产品的实体、本体阶段；
7. 结构化预览可能展示最新加工结果，而搜索仍使用上一可用结果，页面没有清楚说明。

## 4. 工业级实现是什么

### 4.1 保留结构，而不是只生成文本切片

Google 和 Azure 的文档布局能力都会识别标题、段落、列表、表格、图片等元素，并保留文档层级和位置信息。Google还会把祖先标题加入切片，避免内容脱离章节后失去语义；Azure可以输出图片和位置元数据。[Google Agent Search 文档解析](https://docs.cloud.google.com/generative-ai-app-builder/docs/parse-chunk-documents)、[Google Document AI Layout Parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk)、[Azure Document Layout Skill](https://learn.microsoft.com/en-us/azure/search/cognitive-search-skill-document-intelligence-layout)

对本项目的判断：这一部分我们已经完成主体，不需要另换解析平台。

### 4.2 小内容负责命中，大章节负责回答

AWS Bedrock 的层级切分先用较小子块提高命中精度，再用父块替换或扩展结果，提供更完整上下文。Google也采用按布局切分并附带祖先标题的方式。[AWS Hierarchical Chunking](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)、[Google Layout-aware Chunking](https://docs.cloud.google.com/generative-ai-app-builder/docs/parse-chunk-documents)

Anthropic 的 Contextual Retrieval 同样强调，孤立切片会丢失文档、时间和主题背景，因此在关键词和向量索引前给切片补充上下文，并配合重排。[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)

对本项目的判断：当前标题路径、章节表示和父章节扩展已经符合这一模式，下一步重点是让用户看见“命中内容”和“展开上下文”的区别。

### 4.3 引用必须落到具体内容位置

Google Document AI 通过文本锚点和页面区域把段落、表格单元格关联回原文；Azure保留字符范围、页码和多边形位置；AWS的引用同时携带答案片段、引用内容、来源位置和文档信息。[Google Document AI Response](https://docs.cloud.google.com/document-ai/docs/handle-response)、[Azure Analyze Document Response](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0)、[AWS Retrieve and Generate](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-generate.html)

对本项目的判断：我们底层已经保存了一部分位置身份，但没有形成用户可用的精确引用，这是第一阶段最大的差距。

### 4.4 工业搜索支持前置过滤；章节后代是本项目的设计选择

外部事实是：AWS、Azure 等工业搜索系统支持在召回前使用结构化元数据过滤，并区分字段是否可搜索、可返回、可过滤和可排序。[AWS RetrievalFilter](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_RetrievalFilter.html)、[Azure Search Index Fields](https://learn.microsoft.com/en-us/azure/search/search-how-to-create-search-index)

“当前章节及全部子章节”的具体语义不是这些产品直接提供的统一标准，而是本项目基于已有章节树做出的产品设计：章节和祖先路径必须成为明确范围，搜索前先收窄，不能交给模型猜。

对本项目的判断：现有“章节范围”只匹配章节摘要本身，不能稳定覆盖章节下全部正文、列表、代码和表格，需要补成真正的范围搜索。

### 4.5 表格抽取已经成熟；双轨消费是本项目的工程选择

Google、Azure、AWS Textract 和 Docling 都保留表格行列、表头、合并单元格、单元格位置等结构。[Azure Layout Tables](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)、[Amazon Textract Tables](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html)、[Docling Document Model](https://docling-project.github.io/docling/concepts/docling_document/)

基于这些事实，本项目采用“双轨消费”：把表格转成带字段名的文本用于模糊发现，同时使用真实行、列和类型完成精确筛选、排序和统计。这是本项目架构推论，不是外部产品文档的直接结论。

对本项目的判断：Agent 的受控表格查询方向是正确的，第一阶段应把它产品化到网页；不需要先做自由自然语言转数据库查询。

### 4.6 方向性工业实现采用渐进式查看

成熟体验通常不是先给用户一张巨大关系图，而是：

```text
搜索摘要
→ 命中证据
→ 所属章节/表格
→ 原始位置
→ 必要时继续限定范围查询
```

Azure Agentic Retrieval 返回引用标识和执行记录；Google建议先显示搜索结果，再加载带引用答案。这说明来源和过程可见比默认大图更重要。[Azure Knowledge Base Retrieval](https://learn.microsoft.com/en-ie/azure/search/agentic-retrieval-how-to-retrieve)、[Google Vertex AI Search Answer](https://cloud.google.com/generative-ai-app-builder/docs/answer)

其中 Azure Agentic Retrieval 部分接口以及 Google 的 Gemini layout enhancement 仍含 preview 能力，只作为产品方向参考，不采用其预览字段、稳定性或服务承诺作为本项目验收依据；通用 layout parsing 与预览增强分开判断。

## 5. 第一阶段业务需求

### P0-1 当前知识版本可信

- 文档页同时显示“当前可搜索版本”和“最新上传版本”；
- 默认结构、搜索和 Agent 读取当前可搜索版本；
- 用户可以查看最新上传版本，但页面必须明确它是否已经可搜索；
- 新版本失败时继续使用上一可用版本，并显示失败原因；
- 第一阶段按单篇文档保证一致，不要求建设知识库整体发布版本。
- 同一篇文档的结构、搜索内容、来源位置和表格结果作为一个不可拆分的“文档知识版本”生效；新加工不得原地覆盖历史版本。
- 第一阶段允许增加后台版本隔离能力，但不向用户提供知识库级统一发布、整体回滚或跨文档版本功能。

### P0-2 文档结构工作台

- 普通用户默认看到原文、大纲、表格和来源；
- 切片、检索单元、处理指纹等放入“高级信息”；
- 大纲节点可点击；
- 支持父章节、子章节、上一节、下一节；为此必须先给同级章节建立稳定顺序，不能沿用标题文本作为唯一身份；
- 内容类型只展示真实存在的能力；
- 没有脚注/引用关系时不显示对应操作。

### P0-3 文档内范围搜索

- 支持整篇文档搜索；
- 支持仅当前章节；
- 支持当前章节及全部子章节；
- 范围是强约束，不能混入范围外结果；
- 超大章节无法展开时明确提示缩小范围，不能退回整篇搜索；
- 结果保留真正命中的小段，同时可展开父章节上下文。

### P0-4 精确来源定位

- 每条可引用结果至少提供一种真实位置：页码、章节、行号、字符范围、Sheet+Cell 或格式原生位置；
- 搜索返回多个片段时，每个片段分别绑定自己的来源，不能用一组来源笼统支持整段内容；
- PDF 第一批支持跳页；Markdown/文本支持段落或字符范围；表格支持行/单元格；
- DOCX/PPTX/XLSX 暂无在线原件定位时，显示位置说明并提供下载；
- 不能高亮时不显示“精确定位”按钮；
- 摘要和问题别名命中后，必须返回原始证据位置。
- 明确三个来源等级：L1=文档+章节，L2=页/行/字符范围，L3=区域/单元格；所有可引用原文片段至少达到 L1，只有解析器确实提供更精确位置的格式才进入 L2/L3 分母。
- 统一字符索引和坐标口径，明确字符单位、页码起点、原始坐标/归一化坐标、旋转方向和位置描述版本；中文、emoji、旋转页和跨页表格必须验证不偏移。

### P0-5 表格精确消费

- 表格详情展示表名、章节、字段、行数和可用状态；
- 网页提供可视化选列、筛选、排序和基础统计；
- 不要求用户编写查询语言；
- 数字、文本、日期按真实类型检查；
- 字段错误、类型错误和结果过大给出可修正提示；
- 查询失败不能自动退化为模糊搜索；
- 结果可以回到对应表格、行和单元格。

### P0-6 搜索结果成为结构入口

- 来源文件名可点击进入文档；
- 章节可点击进入大纲对应位置；
- 有结构能力时显示“查看结构”；
- 表格证据显示“查看表格/精确查询”；
- “查看完整”明确区分查看更多文本和打开原始文件；
- 用户从搜索进入结构后可以继续限定范围搜索，不必重新选择文档。
- 来源链接必须由服务端在当前权限下解析并打开文档，不能要求浏览器拼接或持有内部文档编号。

### P0-7 网页与 Agent 一致

- 网页和 Agent 对同一证据返回相同正文、章节、来源位置和可用操作；
- 前端与 Agent 共用同一份结构和表格能力，不各自实现不同规则；
- Agent 继续使用现有三个知识工具，不增加工具名称；
- 页面不再提示已经删除的旧工具名称。

### P0-8 状态和异常可理解

必须区分：

- 未加工；
- 处理中；
- 当前可用；
- 最新版本尚未可用；
- 部分能力可用；
- 当前范围无命中；
- 来源位置不可用；
- 表格不可精确查询；
- 无权限；
- 系统错误。

每种状态都给出下一步操作，不能用空白页面或“暂无数据”代替错误。

### P1-1 质量与覆盖

知识库维护者可以看到：

- 大纲是否完整；
- 表格是否完整；
- 有多少证据可以精确定位；
- 哪些位置只能定位到章节；
- 哪些结构关系无法使用；
- 哪些表格字段无法识别类型；
- 对应原因和建议动作。

第一阶段只提供反馈和重新加工入口，不提供在线编辑解析结果。

### P1-2 引用复制与深链接

- 支持复制“文档名 + 章节 + 位置 + 证据文本”；
- 深链接固定到相同文档内容和位置；
- 内容已更新或权限已撤销时明确提示；
- 不自动把历史链接静默跳到另一段新内容。

## 6. 用户旅程

### 6.1 条款和步骤查证

```text
搜索“升级失败后如何回退”
→ 显示命中段和所属“回退流程”章节
→ 打开章节，查看前置条件、步骤和后续检查
→ 查看上一节/下一节
→ 点击来源进入原文页
```

### 6.2 表格查询

```text
搜索“A101”
→ 命中告警表对应行
→ 打开完整表格
→ 筛选告警码=A101
→ 查看原因和处理方法
→ 点击回到原始表格单元格
```

### 6.3 文档版本变化

```text
文档已上传新版本，但尚未加工完成
→ 页面显示“当前可搜索版本”和“最新上传版本”
→ 普通用户继续使用当前可搜索版本
→ 新版本可用后，结构、搜索和 Agent 读取同时切到新文档版本
```

## 7. 验收标准

### 必须通过的用户验收

1. 搜索结果可以进入正确文档和章节；
2. 大纲支持父子和前后导航；
3. 当前章节搜索不返回章节外结果；
4. 包含子章节搜索能命中其中的正文、列表、代码和表格；
5. PDF 至少跳到正确页；Markdown/文本定位到正确段落或范围；Excel 表格给出正确 Sheet/Cell；
6. 不支持在线高亮的格式只显示真实位置描述和下载入口；
7. 表格筛选、排序、计数、求和、平均、最小和最大值与人工结果一致；
8. 非法字段和类型给出可修正错误，不自动放宽查询；
9. 同一证据在网页和 Agent 中的正文、章节和位置一致；
10. 新文档版本未完成时，不影响上一可用版本；
11. 权限撤销后，旧链接、来源定位和 Agent 读取立即不可用；
12. 没有实际关系时，不展示脚注、引用等虚假入口。

### 发布指标

- `来源可解析率 = 能成功解析位置的已返回原文片段 / 按该格式声明可定位的已返回原文片段`，目标 ≥99%；未声明精确定位能力的格式不混入分母，但必须有原因；
- `来源位置准确率 = 人工标注样本中位置正确的片段 / 已解析样本`，PDF页、文本范围、表格Cell分开统计；每类至少抽检100个位置（不足则全量），准确率均须 ≥99%，跨文档/跨章节/跨表格的严重错绑为0；
- 章节范围越界率 = 0；
- 已接受为“可精确查询”的表格，其查询执行黄金用例正确率 = 100%；表格抽取单元格/类型准确率单独统计，不能与查询执行混为一个指标；
- 文档版本混读 = 0；
- 权限越界 = 0；
- 在固定代码、配置、数据规模、并发和冷热缓存条件下，分别记录普通搜索、完整混合搜索、来源读取、章节导航和表格查询的 P50/P95/P99；相对当前基线增幅目标 ≤15%，并在A0基线后补充绝对上限；
- 首批至少 50 条真实题，来源正确通过不少于 48 条（≥96%）；分别记录文档正确、章节正确、位置正确和证据是否支持结论；
- 无证据问题不得给出伪造来源。

### 业务价值指标

- `来源打开成功率 = 成功打开预期文档位置的次数 / 点击查看来源次数`；
- `可核验证据时间 = 从提交问题到用户首次确认正确来源的时长`，取中位数和P90；
- `章节查证任务完成率 = 在限定时间内找到正确结论和来源的任务数 / 章节任务总数`；
- `表格任务完成率 = 正确完成筛选/排序/统计并找到来源的任务数 / 表格任务总数`；
- `回退/放弃率 = 已开始结构化查证后退回无范围搜索或放弃的任务数 / 任务总数`；
- “定位错误、表格错误、内容缺失”反馈分别统计，不合并掩盖问题。

A0 使用同一批用户、同一组文档和至少50个任务记录当前基线。A4 放量门禁建议为：来源打开成功率 ≥99%；总体任务完成率达到85%或相对基线提升至少15个百分点；可核验证据中位时间相对基线降低至少30%；表格任务完成率 ≥95%；回退/放弃率相对基线下降至少20%；严重来源错绑、权限越界和章节范围越界均为0。任一安全硬门禁失败则停止放量；业务指标未达标则保留小范围试用并继续改进，不扩大到全部知识库。

## 8. 第一阶段分批

### A0：当前断点修复

建议 3–5 个工作日。

- 修复结构入口、文档分页、内容类型筛选和旧数据读取问题；
- 统一搜索、结构化预览和 Agent 的当前文档版本；
- 清理旧工具提示和实体/本体降级展示；
- 建立当前效果和速度基线。

用户结果：现有功能不再断链或误导。

### A1：搜索到原文

建议 7–10 个工作日。

- 将现有页码、区域、字符范围、Sheet/Cell 等来源信息整理为可在线读取、可随文档知识版本生效的来源记录；
- 对历史已有结构化结果采用受控重放，不重新调用解析模型，也不原地改写当前版本；
- 搜索结果的文件、章节和结构入口可点击；
- 每个返回片段有独立来源；
- PDF 页、Markdown/文本范围、表格行/单元格可定位；
- 不支持在线定位的格式显示真实位置和下载入口；
- 网页与 Agent 使用相同来源。

用户结果：找到内容后可以立即核查。

### A2：章节导航和范围搜索

建议 7–10 个工作日。

- 为章节建立不会因同名标题冲突的稳定身份和同级顺序，并补齐已有文档；
- 让每条可搜索内容明确归属章节，章节及子章节范围在搜索前生效；
- 大纲成为可操作入口；
- 支持父子、前后和章节上下文；
- 支持整篇、本节、本节及子节搜索；
- 搜索结果保留命中小段，同时允许展开父章节。

用户结果：可以沿文档结构完成长文查证。

### A3：表格精确消费

建议 7–10 个工作日。

- 将已经解析出的字段类型、原始值、规范值、公式、合并单元格和单元格来源完整保存为可查询结果；
- 现有字符串表格查询保持兼容，切换前完成历史数据补齐和结果对照；
- 网页表格详情；
- 可视化筛选、排序、选列和聚合；
- 类型校验与可修正错误；
- 查询结果回表格行和单元格；
- 与 Agent 表格查询结果一致。

用户结果：表格从“可搜索文本”变成“可直接查询的知识”。

### A4：质量、题集与灰度

建议 3–5 个工作日。

- 结构和来源覆盖报告；
- 50 条真实题；
- 权限、版本、速度和异常回归；
- 先选择三份代表性文档灰度，再扩大范围。

建议试点：

1. 一份长 PDF 规范；
2. 一份 Markdown/HTML 手册；
3. 一份含复杂表格的 Excel 或 Word 文档。

单个熟悉项目的开发者完成完整第一阶段预计 6–8 周；A0+A1 最小可见版本约 2–3 周。两人可并行进行前端交互、历史补齐和题集准备，预计 4–6 周完成完整灰度。以上为当前范围估算，不是交付承诺。

## 9. 非目标

- 不做知识库级全景图和跨文档关系；
- 不做 Wiki、主题页和自动长文合成；
- 不恢复实体、本体、Claim 或开放式三元组；
- 不引入图数据库；
- 不做任意自然语言表格查询或自动生成数据库语句；
- 不做自主多轮 Agent 检索；
- 不默认启用 OCR/VLM；
- 不承诺 DOCX/PPTX/XLSX 原件内像素级高亮；
- 不在线编辑解析元素、表格和切片；
- 不执行公式；
- 不改变当前默认混合搜索主路。

## 10. 开放决策

1. 第一批定位格式：建议 PDF 页、Markdown/文本范围、Excel 结构化表格 Cell。
2. 表格精确查询是否为 P0：建议是，它是现有结构化能力最容易被用户感知的价值。
3. 切片/检索单元是否默认展示：建议放入高级信息，普通用户默认不看。
4. 文档默认视图：建议默认当前可搜索版本，最新上传版本为显式切换。
5. 来源深链接：建议固定原文版本；过期时提示，不自动跳到新内容。
6. 试点文档：建议长 PDF、Markdown/HTML、复杂 Excel/Word 各一份。
7. 反馈入口：建议提供“定位错误、表格错误、内容缺失”三个分类；在线修订后置。
