# 场景级知识制品：产业 Agent 知识编译体系与演进方向

> 版本：V2.1
>
> 日期：2026-09-08
>
> 文档定位：在《产业知识底座技术架构与演进方案》（35号）基础上，进一步明确产业知识底座从“知识检索”走向“知识制品”的下一步方向。本文件不调整35号总纲，不展开数据库、接口和实施细节。

## 一、核心判断

一份产品文档下面可能有几十个HTML，每个HTML都在描述一种硬件，页面结构基本相同。

如果只使用RAG，Agent需要先搜索相关页面，再逐页读取和整理；如果使用GraphRAG，可以进一步找到型号、部件和特性之间的关系，但Agent仍然需要在每次任务中重新汇总规格、统一单位并进行比较。

面向产业Agent，更合适的做法是提前完成这部分重复工作：把几十个HTML中的硬件规格统一抽取、由领域专家校准并整理成一张可查询的规格表。Agent需要筛选或比较硬件时，直接使用这张表；遇到缺失、冲突或需要核验的内容，再回到原始文档。

这张规格表就是一种“知识制品”。

> 知识制品，是把Agent在执行任务前反复进行的查找、整理、对齐、判断和准备工作提前完成，形成可以反复使用、能够由人校准、可以回到原始依据的知识成果。

产业知识底座下一步应从“帮助Agent找资料”，演进到“提前为Agent准备可以直接使用的知识”。

这不是用一个新平台替代RAG或GraphRAG，而是在现有知识底座之上增加一层面向任务的知识成果：

```text
原始资料和数据：保存事实，负责核验
RAG和GraphRAG：负责发现证据、理解关系和处理未知问题
知识制品：负责把高频任务需要的知识提前准备好
业务Agent：使用制品完成任务，必要时回到原始资料
```

下一阶段建议聚焦四件事：

1. 选择少量高价值任务，验证“提前编译知识”是否真正优于运行时临时整理；
2. 建设可复用的知识编译能力，而不是为每个场景手工开发一套系统；
3. 建立从原始来源、机器编译、人工校准到Agent使用的完整治理链路；
4. 保留未知任务的处理能力，根据真实使用持续决定下一步编译什么。

## 二、与RAG、GraphRAG的关系

RAG、GraphRAG和知识制品解决的是不同层次的问题。

| 能力 | 主要解决什么 | Agent拿到什么 |
|---|---|---|
| RAG | 从大量资料中找到可能相关的内容 | 原始片段和出处 |
| GraphRAG | 找到对象、关系和跨文档线索 | 关系网络、关联内容和摘要 |
| 知识制品 | 提前完成某类任务反复需要的知识整理 | 可直接查询、判断或使用的知识成果 |

GraphRAG本身也会提前抽取实体、关系和社区摘要，因此它已经包含知识加工。但它通常围绕一套通用图结构组织语料，不能自然覆盖所有产业任务需要的结果形态。例如，配置规则、硬件规格表、方案选择条件、作业流程和检查器都不只是“图中的节点和边”。[Microsoft GraphRAG](https://github.com/microsoft/graphrag/blob/main/docs/index/default_dataflow.md)

知识制品也不是预先生成最终答案。它提前准备的是完成任务所需的知识结构和方法，Agent仍需结合当前用户要求、实时状态和权限作出最终判断。

因此，三者不是替代关系：

- 简单查证继续使用RAG；
- 关系分析和多跳问题可以使用GraphRAG；
- 高频、稳定、整理成本高且结果可验证的任务，优先建设知识制品；
- 实时库存、运行状态、工单进度等动态信息，继续通过数据库、API或工具实时获取；
- 没有知识制品覆盖的问题，仍然回到原始资料和Agent临时分析。

## 三、外部产品、规范与研究出现的共同信号

当前还没有形成统一的“知识制品平台”标准，但产品实践、开放规范和近期研究正在出现相近信号：把更多知识整理工作从Agent运行时前移到知识建设阶段，并让整理后的知识持续积累和复用。

### 1. Pinecone Nexus：围绕工作任务准备知识

Pinecone Nexus提出Knowledge Engine和Context Compiler。它不是只对资料做统一切片，而是先明确某个Agent要完成什么工作、需要什么结果，再把同一批企业资料整理成适合该工作的知识成果。相同来源面向销售、财务或合规Agent，可以形成不同的知识形态。[Pinecone Knowledge Engine](https://www.pinecone.io/learn/how-knowledge-engines-work/)

它带来的关键启示是：

> 知识建设不再只围绕“资料是什么”，还要围绕“Agent要完成什么任务”。

但Nexus当前仍需要领域人员先给出明确工作目标和代表性评价任务，并没有解决自动发现企业全部业务场景的问题。

### 2. LLM Wiki：原始资料之上需要持续维护的知识层

Karpathy提出的LLM Wiki保留不可变原始资料，同时由LLM持续维护主题、对象、比较、矛盾和交叉链接。查询过程中形成的有价值结论也可以沉淀下来，而不是消失在一次对话中。[Karpathy LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

它提出了一种设计思想：原始资料和Agent之间不应只有一次性检索，还可以建立一层持续更新、不断积累的派生知识。

### 3. Google OKF：机器生成的知识必须可判断是否可信

Google Open Knowledge Format关注知识包如何被人和Agent共同理解，并为来源、生成与验证主体、陈旧时间和生命周期提供了可选的表达机制。它不负责怎样编译知识，除基础类型外也没有强制所有知识采用这些字段。本项目在此基础上进一步要求：正式知识制品必须具备来源、验证、版本和有效性等治理信息。[Google OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md?plain=1)

### 4. WikiSkill：使用经验可以改进方法，但不能直接改写事实

WikiSkill把Agent执行轨迹、持续积累的经验知识和正式Skill分开管理：先从成功与失败中总结模式，再提出Skill修改，只有通过独立评价才采用。它表明Agent经验可以用于提出Skill改进，但修改需要经过独立评价。[WikiSkill](https://arxiv.org/abs/2608.27454)

论文采用三层结构：原始执行轨迹保持不变，Wiki持续记录成功策略、失败模式和历次修改结果，正式Skill只保留经过验证、真正能提升任务效果的方法。作者在五个Benchmark、五种模型上报告：按五个Benchmark平均后，WikiSkill相对每种模型下最强的竞争方法提升3.3至12.0个百分点，并发现经过演进的Skill可以跨模型复用。

论文的边界也很清楚：实验预先具备训练、验证和测试任务，并且直接把全部Skill提供给Agent，没有解决产业环境中“大量Skill怎样被准确发现和触发”的问题。因此，本项目借鉴的是“经验积累—提出修改—独立验证—通过后采用”的机制，而不是让Agent自行修改正式知识。

本项目进一步规定：经验只用于改进“编译什么、怎样编译、怎样使用”，产品事实只能由授权来源和验证流程更新。

### 5. LLM-Wiki论文：检索仍然存在，但检索对象发生变化

《Retrieval as Reasoning》提出的LLM-Wiki，不再把原始文档切片作为Agent唯一的检索对象，而是先将资料编译成带主题、事实、来源和双向链接的Wiki页面。运行时Agent通过搜索页面、读取页面、沿链接继续查找并判断证据是否充分来完成任务。[Retrieval as Reasoning via LLM-Wiki](https://arxiv.org/abs/2605.25480)

该论文还设计了Error Book：将编译过程中反复出现的断链、引用错误、无依据内容和跨页面矛盾记录下来，用确定性检查和模型复核持续修正。作者在其多跳问答和AuthTrace测试中报告，LLM-Wiki优于所比较的GraphRAG、LightRAG等方法，跨文档问题上的提升更加明显；该结果不能直接外推为所有产业语料都更优。

但论文也显示，经过整理的Wiki可能遗漏单篇文档中的局部细节。因此，本项目不能只保留编译后的知识，必须始终保留从制品回到原始资料的核验链路。

### 6. EVAPORATE与DocETL：知识编译不是一次“大模型总结”

EVAPORATE研究如何把大量半结构化文档转成可查询表格。它比较了两条路径：让LLM逐份抽取，或者让LLM先识别字段和规律，再生成可以批量运行的抽取代码。论文发现，代码路径更适合大规模重复格式，但单一代码可能不可靠，因此又通过生成多个候选函数、过滤低质量结果和综合判断提高稳定性。作者在16组、每组1万份文档的实验设置中报告，相比逐文档调用LLM，改进后的代码方案平均减少约110倍的LLM处理Token。[EVAPORATE](https://arxiv.org/abs/2304.09433)

DocETL进一步把文档加工表达成可组合步骤，例如抽取、过滤、归并和汇总，再由Agent尝试拆分任务、改写处理流程，并使用评价样本比较不同方案。作者在四类复杂文档任务上报告，自动优化后的流程相对精心设计的基线准确度提升25%至80%。[DocETL](https://arxiv.org/abs/2410.12189)

这两项工作带来的启示是：知识编译器应能组合代码、模型和校验方法，并根据资料特点和任务效果选择方案；不能把所有制品都交给一个通用总结Prompt生成。

### 7. WiCER与SRA：知识编译和知识使用都需要校准

WiCER专门研究“提前编译会不会丢信息”。作者发现，直接把原始资料压缩成Wiki可能过度概括并丢失关键事实；通过用诊断问题检查遗漏、定位丢失内容并再次编译，一至两轮可以恢复大部分损失质量。[WiCER](https://arxiv.org/abs/2605.07068)

Skill Retrieval Augmentation则研究大量Skill怎样被Agent使用。SRA-Bench包含5400个测试实例，并使用包含26262个Skill的外部Skill语料库。结果显示，即使正确Skill已经被找出来，Agent仍可能不知道是否应该加载、何时加载。这说明“找到制品”不等于“正确使用制品”，使用条件、适用范围和调用说明也必须经过验证。[Skill Retrieval Augmentation](https://arxiv.org/abs/2604.24594)

两项研究分别提示了两个风险：编译时可能漏掉重要知识，使用时可能选错知识制品。它们直接支持“编译和使用都需要评价”；领域专家校准和原文回查则是本项目针对产业知识风险进一步增加的治理要求。

这些方向共同指向一条路线：

```text
保留原始事实
→ 根据具体用途提前整理
→ 形成可持续使用的知识成果
→ 带着来源、版本和适用范围交给Agent
→ 根据真实使用和评价持续更新
```

本项目在此基础上的进一步判断是：产业知识成果不能只有Wiki页面或知识图，而应允许形成任务真正需要的多种知识制品。

## 四、除了表格，知识制品还可以是什么

知识制品不只是把资料重新写成一份文档。可以按照Agent拿到知识后要做什么，将其分为四类。

### 1. 帮助Agent看懂

将分散信息整理成一个完整对象或专题。

典型制品包括：

- **对象卡**：一个硬件、一条命令、一个配置对象或一个网元的完整档案；
- **专题知识页**：把多份资料中关于同一特性或方案的内容汇总起来；
- **版本差异说明**：说明不同版本新增、修改和废弃了什么。

例如，关于一块板卡的信息可能分散在规格、安装、维护和兼容性文档中。对象卡可以提前将这些内容组织在一起，并保留每项信息的原始出处。它可以理解为面向一个具体业务对象形成的完整档案。

### 2. 帮助Agent查清关系

将原本隐含在多份资料中的对应、依赖和影响关系提前连接起来。

典型制品包括：

- **对照表**：产品别名、版本映射、命令与特性对应关系；
- **关系地图**：谁依赖谁、谁引用谁、修改一项配置会影响什么；
- **对象目录**：一个领域中有哪些对象，以及怎样找到它们。

例如，云核心网的业务方案、特性、命令和核查规则可以提前关联。Agent生成配置时不再从大量文档中临时寻找每一层关系，而是沿已经整理好的知识逐层使用。

### 3. 帮助Agent作出判断

把文档中的条件、限制和专家判断整理成可直接检查的依据。

典型制品包括：

- **规则包**：哪些配置可以重复创建、哪些会覆盖、哪些组合不允许；
- **决策指南**：在什么条件下选择哪个产品或方案，哪些候选需要排除；
- **检查器**：自动检查输入是否满足规格、基线或配置约束。

IP配置建模中的 `createInstance`、`ifRepeat` 和 `reference` 就属于这一类。产品手册和历史配置模型被提前整理成行为知识，AST建模Agent可以直接用它们判断，而不是只根据CLI语法猜测。

### 4. 帮助Agent完成任务

把完成工作所需的步骤、材料和输出形式提前准备好。

典型制品包括：

- **作业流程**：任务步骤、前置条件、检查点和异常处理；
- **标准模板**：配置方案、评估报告、物料清单和核查报告模板；
- **专业能力包**：将说明、参考资料、模板和经过验证的小工具组合为Skill；
- **场景知识包**：为一个完整业务场景组合对象、关系、规则、流程和模板。

例如，ODN数字化方案不仅需要查产品资料，还需要规划依据、设计约束、方案模板和检查清单。把这些内容组合成场景知识包，Agent拿到的是一套完成工作的专业资料，而不是一组搜索结果。

### 5. 同一份资料可以形成不同制品

仍以硬件文档为例，同一批HTML可以根据任务形成不同成果：

| 任务 | 可以提前形成的知识制品 |
|---|---|
| 查询某个型号的完整信息 | 硬件对象卡 |
| 筛选和比较多种型号 | 硬件规格表 |
| 判断是否满足环境和安装条件 | 适配规则包或检查器 |
| 进行产品选型 | 候选对比和决策指南 |
| 形成站点方案 | 物料清单、方案模板和场景知识包 |
| 指导安装和验收 | 作业流程和检查清单 |

所以，知识编译的重点不是把所有资料都转成表格，而是根据任务选择最合适的知识形态。

## 五、产业知识如何编译并交给Agent

结合上述外部信号，本项目建议采用“目标和评价驱动的知识编译”，而不是先人工设计完所有场景和所有制品。领域人员仍需明确业务任务、预期结果、关键知识边界和评价标准；平台不要求领域人员预先设计底层技术实现，而是由领域人员与知识编译器共同形成候选制品，再通过真实任务验证和优化。

完整流程可以概括为七步。

```text
1. 明确Agent要完成的工作
        ↓
2. 提供少量代表任务和预期结果
        ↓
3. 选择相关资料和已有知识
        ↓
4. 组合抽取、归一、关联、总结、规则化和代码生成等能力
        ↓
5. 形成一种或多种候选知识制品
        ↓
6. 使用真实任务和领域专家共同验收，通过后再正式提供给Agent
        ↓
7. 根据资料变化和使用反馈持续更新
```

### 1. 先明确工作，不先规定技术形态

首先明确Agent服务谁、要完成什么工作、最终需要什么结果。例如：“根据环境条件筛选硬件并给出有依据的对比”，而不是先决定“建设一个硬件知识图谱”。

### 2. 用代表任务定义方向，不穷举所有问题

领域人员提供少量有代表性的问题、正确结果或验收标准。这些任务用于告诉知识编译器什么信息最重要，也用于验证编译结果是否有效。

任务样例不需要覆盖所有用户表达，只要覆盖主要目标、关键边界和高风险错误。

### 3. 领域人员与知识编译器共同形成制品

领域人员负责确认关键字段、规则、边界和制品用途；知识编译器负责降低资料加工和反复试验的成本。它不是一个大模型总结提示词，而是一组可组合能力：

```text
读取和解析
→ 发现重复结构
→ 抽取字段和对象
→ 统一名称、单位和版本
→ 建立对应和依赖
→ 整理规则、流程和模板
→ 必要时生成可复用的小程序
→ 校验来源和结果
```

面对同构HTML，可以生成抽取代码并形成规格表；面对分散的配置约束，可以整理成规则包；面对跨文档流程，可以形成作业流程和Skill；面对方案知识，可以组合成决策指南和场景知识包。

EVAPORATE的研究已经展示了两条可借鉴路径：让LLM逐文档抽取，或者让LLM先识别结构并生成可复用抽取代码；后者更适合大量格式相似的资料，但仍需要多样本验证和错误检查。[EVAPORATE](https://arxiv.org/abs/2304.09433)

### 4. 用任务评价和专家验收选择制品

对于同一任务，可以同时尝试不同知识形态。例如，产品选型可以只用规格表，也可以增加适配规则或决策指南。平台可以提出候选方案，但不能无人审核地决定最终形态；领域专家需要结合真实任务，判断哪种方式更准确、更完整、更快、更稳定。

Pinecone Nexus将这类思路概括为：给出数据、任务要求和评价集，由编译器生成并不断改进适合该任务的知识结构。具体产品实现仍在演进，但“任务与评价驱动编译”值得作为本项目的核心方向。

### 5. Agent优先使用制品，必要时回到原文

知识制品适合处理已经覆盖的高频任务，原始知识底座继续处理以下情况：

- 制品没有覆盖的新问题；
- 信息缺失或发生冲突；
- 用户需要查看原始依据；
- 产品版本超出制品适用范围；
- 需要获取实时业务状态。

因此，最终运行方式不是“只用知识制品”，而是“制品优先、原文托底、实时工具补充”。

## 六、知识治理：机器负责加工，人负责校准

知识编译不能成为一个看不见过程的黑盒。机器可以批量读取资料、发现结构、生成表格、整理关系和提出规则，但什么内容可以成为正式知识、适用于什么范围、发生冲突时相信谁，必须由明确的责任人和治理流程负责。

知识治理的目标不是增加审批环节，而是保证每一条正式知识都能回答四个问题：

1. 来自哪里；
2. 经过了什么整理；
3. 谁检查和修改过；
4. 当前是否仍然有效。

### 1. 知识来源链路必须完整

正式知识必须有可信链路，但不能把所有内容都假设为来自产品文档。产业知识制品可以同时包含来源事实和专家知识，两者采用不同链路。

来源事实的链路是：

```text
来源系统
→ 原始文档或数据版本
→ 具体章节、表格、字段或记录
→ 机器抽取和整理结果
→ 人工来源校正
→ 正式来源事实
→ Agent任务中的具体使用结果
```

专家知识的链路是：

```text
领域专家
→ 判断依据、适用范围和例外
→ 审核确认
→ 正式专家知识
→ Agent任务中的具体使用结果
```

例如，硬件规格表中的“工作温度”不能只有一个数值，还需要知道它来自哪一版产品手册、哪个HTML、哪个字段，以及是否经过单位换算或人工修正。Agent给出选型建议时，也应能够从建议回到规格表，再回到产品手册。

对于跨多份资料形成的规则或结论，还需要说明使用了哪些来源、怎样合并、是否存在冲突。来源链路不是文档末尾的一组参考链接，而是知识内容与原始依据之间的直接对应关系。

一个制品可以同时包含三类内容，但必须逐项区分：

- **来源事实**：能够回到产品手册、数据记录或其他授权来源；
- **专家校准**：领域专家对机器抽取、归一和关联结果的修正；
- **专家判断**：没有直接来源原文，由责任专家确认的经验、规则或例外。

### 2. 编译出的知识必须允许人修改

机器生成的制品首先是草稿，不应因为“编译成功”就自动成为正式知识。领域专家应能够直接修改：

- 表格中的字段和值；
- 对象卡中的属性和说明；
- 关系地图中的关系；
- 规则包中的条件、结论和例外；
- 决策指南中的选择条件；
- 作业流程中的步骤和检查点；
- 模板、专题页和Skill中的专业内容。

人工修改不能覆盖或篡改原始资料，而是形成一条有记录的校准结果。系统需要保留“机器原始结果、人工修改内容、修改人、修改理由、时间和适用范围”，使知识可以追溯、复核和回退。

专家判断可以成为正式知识，但要标明责任人、判断依据、确认状态、适用范围和复核时间，不能伪装成产品手册中的原始事实。

### 3. 人和机器的分工

| 参与方 | 主要职责 |
|---|---|
| 知识编译器 | 批量读取、抽取、归一、关联、生成候选制品并执行自动检查 |
| 领域专家 | 确认关键字段、术语、规则、例外、适用范围和业务价值 |
| 知识审核人 | 复核高风险修改、来源冲突和正式发布内容 |
| 平台团队 | 提供通用编译、编辑、版本、权限、评价和回源能力 |
| 业务Agent使用者 | 反馈遗漏、错误、过期内容和新的重复任务 |

核心原则是：机器扩大知识加工规模，人保证产业知识的正确方向和最终质量。

### 4. 从机器草稿到正式知识

```text
机器编译草稿
→ 自动检查完整性和来源
→ 领域专家查看、修改和补充
→ 真实任务验证
→ 必要的专业审核
→ 正式发布给Agent
→ 使用反馈进入下一轮校准
```

不同风险的制品可以采用不同的人审强度。普通专题页和低风险目录可以自动生成后抽样检查；配置规则、选型条件、生产配置和高风险方案必须由领域专家逐项确认。人的参与不是固定地审核所有内容，而是根据风险和机器可信度进行分级。

### 5. 资料变化后，人工校准不能丢

产品文档更新后，系统需要识别哪些表格、对象、关系、规则和场景知识包受到影响，并重新编译相关部分。但重新编译不能简单覆盖人工修改。

新的机器结果应与上一版人工校准内容进行比较：

- 来源事实和专家校准需要随对应来源重新核验；
- 来源已经更新、原有校准不再适用时，提示专家重新确认；
- 独立专家判断按照自身适用范围和复核时间单独确认，不因机器重编自动删除；
- 新来源与专家知识冲突时，进入人工处理；
- 原始来源被删除或权限收紧时，相关知识立即停止对无权Agent使用。

这样才能同时避免两种问题：机器重编把专家知识冲掉，或者人工修改长期不更新而变成过期知识。

### 6. 知识治理贯穿整个生命周期

知识治理不是发布前的一次检查，而是贯穿来源接入、机器编译、人工校准、任务验证、正式使用、来源更新和知识退役的全过程。

最终需要形成两个闭环：

```text
来源变化
→ 找到受影响知识
→ 重新编译和人工复核
→ 发布新版本

使用反馈
→ 提出疑似错误、遗漏、新任务或编译方法改进
→ 授权来源核验或专家判断签署
→ 人机共同形成制品新版本
→ 验证后发布新版本
```

使用反馈本身不能修改事实字段。事实内容只有在授权来源完成核验，或者被明确标为专家知识并由责任专家签署后，才能进入正式新版本。

## 七、场景无法穷举，怎样持续演进

平台不需要提前列出所有产业场景，也不应一开始建设完整的行业任务树。

更现实的方式是：

> 有限快路径 + 长尾慢路径 + 使用中发现 + 验证后升格。

### 1. 已知高价值任务走快路径

先选择少量高频、稳定、重复整理成本高、结果容易验证的任务，提前编译正式知识制品。

### 2. 未知和低频任务走慢路径

没有制品覆盖时，Agent继续通过RAG、GraphRAG、原始文档和实时工具完成任务。这样，知识制品建设不需要以“覆盖全部问题”为前提。

### 3. 从真实使用中发现下一批机会

观察Agent在哪些任务中反复进行相同工作，例如：

- 总是读取相同的一组资料；
- 总是在抽取和对齐相同字段；
- 总是在编写相似的临时代码；
- 总是在做相同的关联、比较或检查；
- 总是在同一个位置失败或请求人工补查。

这些信号说明某类知识整理可能值得提前完成。

资料本身也可以提供线索。例如，大量同构HTML、重复参数表和统一格式的方案文档，即使还没有明确场景，也可以先被识别为“有加工价值的知识机会”。但只有与真实业务任务结合并证明有价值后，才正式建设。

### 4. 重复需求经过验证后再升格

当一类任务同时满足以下条件时，再将其升格为正式制品：

- 有明确业务价值；
- 多次出现或单次失败代价较高；
- 来源和判断逻辑相对稳定；
- 当前运行时整理成本较高；
- 结果能够评价和核验。

使用经验只能提出“下一步应该编译什么、现有制品怎样改进”。它不能自动修改产品事实，也不能绕过领域审核直接发布。

### 5. 哪些内容不适合提前编译

- 偶发且一次性的任务；
- 来源和规则频繁变化的内容；
- 必须读取实时状态才能判断的问题；
- 缺少明确验收标准的主观任务；
- 数据权限无法稳定界定的跨域内容。

这些任务继续通过检索、工具和人工协同完成，避免为了追求“制品数量”建设大量过期或无人使用的知识。

## 八、在现有产业中的落点

### 1. 站点

首个试点建议选择硬件规格矩阵。它能够最直观地验证：同一批资料经过提前编译后，是否可以减少Agent逐页阅读和临时汇总，并提高筛选、比较和回源效率。

在此基础上，可继续形成：

- PAV评估所需的指标、规则和基线；
- ODN数字化场景的规划依据、方案模板和检查清单；
- 离网电站场景的产品目录、选择条件、设计流程和方案模板。

### 2. IP

IP已经形成19000+配置对象，并在AST建模中使用产品手册和历史模型补全行为语义。下一步可以把这些资产进一步组织为：

- 配置对象完整档案；
- 创建、重复和覆盖规则；
- 配置对象之间的引用关系；
- AST建模使用的专业能力包。

这不是重新建设一套IP知识库，而是把现有知识从“可检索”进一步变成“可判断、可建模”。

### 3. 云核心网

云核心网已经具备命令图谱、特性图谱、业务方案和核查规则。下一步不是继续增加图节点，而是面向配置生成，将这些知识组合成APN、DPI、UELogo等场景知识包。

Agent拿到的不只是命令搜索结果，而是：业务目标涉及哪些特性、需要哪些命令、受哪些规则限制、如何生成和核查配置，以及每项依据来自哪里。

### 4. 政企

政企仍处于起步阶段，不宜先假设一套统一知识模型。应从第一个明确、可验证的业务任务开始，再决定需要对象卡、规则包、流程、模板还是场景知识包。

四个产业方向共同体现同一个原则：底层平台和编译能力可以复用，但最终知识形态由任务决定。

## 九、下一步演进建议

下一阶段不建议先建设一个大而全的“知识制品平台”，而应分三步推进。

### 第一阶段：证明价值

以站点硬件规格矩阵为试点，打通从原始资料、机器编译、人工校准到知识制品发布、Agent使用、原文核验和增量更新的完整闭环。

重点验证：

- 信息是否更准确、完整；
- Agent是否减少逐文档读取和临时汇总；
- 任务时延和Token是否下降；
- 结果是否能够稳定回到原始依据；
- 领域专家是否能够直接修改并保留校准记录；
- 产品文档变化后，维护成本是否可控。

### 第二阶段：形成通用知识编译方法

在IP或云核心网选择一个需要组合多种制品的任务，验证对象、关系、规则、流程和Skill能否协同工作。

这一阶段要沉淀的不是某个产业的专用代码，而是可复用的知识编译能力：怎样从资料发现结构、怎样选择制品形态、怎样让专家校准、怎样评价结果、怎样随来源变化更新。

### 第三阶段：形成持续演进机制

接入真实任务反馈，发现重复知识整理、高成本路径和常见失败。经过业务验证后，将其中稳定、可复用的部分编译成下一批制品，并持续改进现有流程和Skill。

最终形成：

```text
通用知识底座
  + 可组合的知识编译能力
  + 面向任务的知识制品
  + 原始检索和实时工具托底
  + 真实使用驱动的持续演进
```

## 十、建议领导决策事项

1. 是否认可“场景级知识制品”作为35号之后的主要演进方向；
2. 是否确定站点硬件规格矩阵为首个价值验证试点；
3. 是否明确由产业团队负责业务任务和领域验收，平台团队负责通用编译能力；
4. 是否明确正式知识制品必须支持领域专家查看、修改、校准和追溯；
5. 是否以任务准确性、完整性、效率、可核验性和维护成本作为试点评价标准。

## 十一、需要坚持的边界

1. 不把知识制品理解为RAG或GraphRAG的替代品；
2. 不要求提前穷举全部产业场景和用户问题；
3. 不把所有知识都提前编译，只处理高价值、稳定、可验证的重复任务；
4. 不把知识制品等同于摘要、Wiki、知识图或预生成答案；
5. 不让Agent使用经验未经验证直接改写产品事实；
6. 不脱离原始资料、版本和权限建设派生知识；
7. 不让机器重编静默覆盖人工校准结果；
8. 不先建设大平台，再寻找业务价值；
9. 不用制品数量衡量成效，最终看产业任务是否做得更好。

## 十三、总结

产业知识底座的下一步，不是继续堆叠更多切片、向量和图节点，而是把已有知识加工能力组织成一座“知识工厂”。

这座知识工厂不需要提前知道所有产业场景。它先围绕少量高价值任务，把分散资料编译成Agent可以直接使用的知识制品；没有覆盖的任务继续依靠RAG、GraphRAG和实时工具；真实使用再告诉平台下一步值得编译什么。

最终形成的不是一个静态知识库，而是一套能够持续把原始知识转化为产业Agent生产力的知识编译体系。
