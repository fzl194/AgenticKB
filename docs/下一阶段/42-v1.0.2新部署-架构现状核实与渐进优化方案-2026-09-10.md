# v1.0.2 新部署：架构现状核实与渐进优化方案

日期：2026-09-10。状态：只读审计完成，整改建议待作为后续开发范围采用；本文不代表业务代码已修复或运行环境已验收。

## 1. 能力目标与审计边界

面向全新部署 v1.0.2 的知识库用户，在保留已有解析、挖掘、检索和 A0–A4 成果的基础上，让文件整理、知识更新、结构阅读、搜索和来源核验遵守一致的数据契约。优化成功的标准是用户动作可靠、状态能解释、开发者能沿一条主链定位问题。

用户确认：不存在需要兼容的旧版本部署或旧业务数据；网关和场景表格由其他负责人推进；Agent 模块另行研究。不能以“可能有旧数据”为理由设立迁移工程，也不能把存在旧字段等同为新系统默认走旧路径。

## 2. 已核实的正式主链

```text
用户 / KB 权限
  → 逻辑目录与 Document 身份（PostgreSQL）
  → 当前原文件对象（MinIO；PostgreSQL 登记对象位置/hash）
  → KB 挖掘 Run 冻结对象与修订信息
  → 解析为 Parse IR，形成 Snapshot
  → 从 Snapshot 编译切片、结构、表格、检索表示与向量
  → Build 校验与有效文档选择
  → Java 检索、结构读取、网页和 MCP 消费
```

### 2.1 新部署默认走对象存储，用户纠正成立

| 用户动作 | 现行路径 | 结论 |
|---|---|---|
| 普通上传 | `kb/deps.py` 注入对象存储；`DocumentService.upload_stream` → 对象登记 → `KbDB.insert_document_from_storage` | 新行有对象 ID/hash/revision，`storage_path` 为 NULL |
| 归档上传 | 临时目录解压，成员走对象上传 | 临时文件是执行资源，不是持久化原文件地址 |
| KB 挖掘 | `jobs/run.py::_kb_object_documents` 读取对象身份 | 不靠扫描上传目录发现文件 |
| 下载 | `DocumentService.download_object` 对象优先 | 新对象文档正常不进入本地下载回退 |
| 删除 | `DocumentService.delete` 软删 | 保留对象与历史快照，不能把删文档等同为物理删字节 |

证据：[对象上传](../../knowledge_mining/mining/kb/services/document_service.py:198)、[新文档登记](../../knowledge_mining/mining/kb/db.py:1238)、[对象挖掘输入](../../knowledge_mining/mining/jobs/run.py:303)。

`storage_path` 仍出现在代码中，但其含义必须逐调用点核对。临时解压、解析器临时文件可以保留；用户文件目录对本地业务磁盘的依赖不应保留。无需旧数据迁移，但仍需处理正式可达的错误路径。

### 2.2 已有能力，不应重复建设

- A0 默认 `current_serving`，显式支持 `latest_revision`；网页已能显示两种知识视图及版本提示。证据：`kb/routes/documents.py:71`、`kb-ui/src/views/kb/KbDocPreviewView.vue:103`。
- `update_failed` 已表达更新失败但旧知识仍可用；不是所有失败都等于整库不可搜。
- Python 当前文档读取、主 readiness 与 Java 当前范围大体采用相同规则：先取每文档最新 validated/published Build selection，再过滤 active 与软删。
- `assemble_build` 已支持 carry-forward、增量合并和删除选择，不是每次只记录本 Run 文件。Java mapper 部分注释落后于实现。
- 派生资产已有 staging → final 的事务晋升；但需注意其保护范围，见 O2。
- A2–A4 已实现章节身份/范围过滤、类型化表格、公共结构 REST、质量面板和评测框架；网页和 MCP 复用结构服务与授权逻辑。正在修复的细节属于该分支验收范围。

### 2.3 前次讨论需纠正的说法

1. 不能说新系统“需要先迁移 storage_path 旧文件”。本次范围没有旧数据。
2. 不能说各读取入口完全没有一致版本规则。已有规则，问题在少数查询与写入路径未遵守。
3. 不能因有 Snapshot/Build/Release 就立即增加 KB 发布系统。当前每文档增量选择可保留，跨文档正式发布是后续需求。
4. 不能把底层原件指针替换能力等同为已交付的“上传新版本”产品操作。当前正式 KB 路由没有独立替换内容入口；活跃同名上传冲突，软删同名重传才有 revive 路径。
5. 不能只凭 Snapshot 有 compiler 字段，就断言正式挖掘链已正确隔离所有加工版本；O2 已复现反例。

## 3. 应保留的架构约束

| 固定约束 | 对实现与用户体验的要求 |
|---|---|
| PostgreSQL 管业务事实，MinIO 管字节 | 目录改名/移动不搬原文件字节；对象地址不承担用户文件树 |
| Document ID 是稳定身份 | 改名/移动不改变所属知识身份、原对象和内容修订号 |
| Snapshot 是知识版本根 | 不新建独立 ParseResult/SegmentSet 版本体系；加工变化复用已有快照隔离机制 |
| 文件当前态与当前可搜索知识可以不同 | 用户明确知道正在看哪一种；证据回源固定对应来源，不误用最新文件下载 |
| 当前可搜索文档集合按同一合同解析 | 知识读取、统计、质量与搜索使用同一有效集合；管理列表仍保留未就绪文档，并准确标示状态 |
| 部分成功继续可用 | 不因一篇失败而使整库成功知识不可读 |
| 权限与服务可用性分别判断 | 无权/不存在可以隐藏存在性；数据库故障不能伪装成无权 |

ADR D4 不建设完整文档历史版本管理；补“替换当前文件”不等于增加版本列表/回滚产品。若未来跨文档制品归属超出 ADR D10 的单 Snapshot 子资产模型，应在该需求启动时更新 ADR，本轮不暗中改变。

## 4. 已证实的不一致与渐进优化

### O1：对象上传与磁盘式文件移动冲突【优先级 P1，已复现】

**用户触发：** 新上传文件后移动到另一个目录。

新文档 `storage_path=NULL`，但 `FolderService.move_document` 仍无条件 `shutil.move(doc['storage_path'], ...)`。目录改名/移动也操作本地目录，`_relocate_docs` 还把对象文档写回非空本地路径。

证据：`kb/services/folder_service.py:136,152,180,211`；正式路由 `kb/routes/documents.py:389`。A2–A4 没有修改这些函数。

**实测：** 生产 FolderService + 假数据库 + 临时目录，跨目录移动返回 `TypeError: rename: src should be string, bytes or os.PathLike, not NoneType`；单独执行目录重定位确认写回非空 storage_path。

**优化：** 保留目录 UI 和当前数据结构；逻辑目录改名/移动放在一个数据库事务内完成，不创建、搬动持久业务磁盘目录，不改变 storage_object_id/hash/revision。先不强制切换全部 folder_id/path 存储方式。

**身份配套：** 当前改名仅改 document_name，移动却修改 document_key；上传也使用路径生成 key。先盘点当前结构/ref 消费，统一稳定 Document ID 与展示位置的职责，不能直接全库重命名 key。没有旧部署不代表同一新部署内已经发出的引用可以随意失效。

**验收：** 对象上传 → 移动文件 → 改名父目录 → 下载 → 挖掘 → 回源；无原文件本地镜像仍能完成；失败事务不留下半改目录；对象/hash/revision不变。

### O2：正式重切链可改写同一快照的正式正文【优先级 P1，已复现核心行为】

**用户触发：** 对相同内容换切片策略重新挖掘。

`parse_operator/service.py:667` 提交快照未传 compiler fingerprint；`workflow/new_chain_services.py:257` 的 SegmentCompileFacade 对传入 snapshot 调普通 compile。`segment_compiler/service.py:97` 在编译指纹变化时调用 replace_for_snapshot；`segment_compiler/repositories_pg.py:59` 删除重写正式 raw segments/element links。

**定向复现：** 生产 `build_new_chain_services` + FakeObjectStore + 内存仓储；同一 Markdown 分别 whole/rows 编译：

```text
same_snapshot = True
compiler_fingerprints_differ = True
snapshot_compiler_fingerprint = None
segments_changed = True
segment_counts = [2, 3]
```

Java `EvidenceSourceV2Mapper.xml:81,101,132` 根据 snapshot 与 ordinal 读取正式正文；因此结合实际 PG 写法，可以判断有未完成构建的新正文与旧结构混读的风险。该跨数据库并发窗口未在真实 PG 中实测，不能将内存复现表述为生产事故。

派生表 staging 事务不能保护提前改写的 raw。A2–A4 没有修改上述关键链路。

**优化：** 优先接通已有 `SnapshotRecompileService` 或在正式编译前确定包含编译指纹的新快照，并将身份贯穿 bundle、持久化、Build 和检索；不再增加一种版本实体。不同模型/增强/投影配置是否都影响派生资产身份，作为同一契约的后续覆盖项逐项核实，不能未经检查宣布全部已隔离。

**验收：** 旧知识正在被读时改变切片策略，新结果与旧结果隔离；构建前/构建失败后旧正文和旧结构一致；成功才切换；另一篇共享旧快照的文档不受影响。

### O3：共享快照的来源关联缺少文档绑定【优先级 P1，SQL 已证实】

`KbDB.get_current_serving_snapshot` 在选择文档快照后，JOIN links 只限定 snapshot，随后按 linked_at 取最新一条，没有限定 link.document_id。两篇文档共享快照时，可取到另一篇的来源修订号/对象信息。

证据：`kb/db.py:1031`；`snapshot_store/read_service.py:294,376` 消费该信息。A2–A4 相同。

**影响边界：** 已证明版本与来源元数据可能错绑。`in_sync` 当前比较 snapshot ID，不能声称错 link 必然改变同步判断；正式当前文件下载读取本篇 Document 的对象并验证权限，未证明此处造成下载越权。

**优化：** 来源至少按 `(document_id, snapshot_id)` 绑定。对同一文档同内容多次修订再评估是否需要固定精确 link/revision；仅加 document 限制不自动解决所有历史 occurrence 语义。

**验收：** 两篇同内容文档、不同来源修订，各自显示和引用自己的来源；分别删除/恢复时不串联。

### O4：资产总览与搜索的当前文档范围不同【优先级 P2，SQL 已证实】

`KbDB._CURRENT_SNAPSHOT_CTE` 没有 JOIN 文档表，不过滤文档软删；用于 `stats_assets` 和检索类型统计。Java 搜索、主 readiness、A4 quality 已排除软删。

证据：`kb/db.py:633,680,711`；`AssetBuildDocumentSnapshotMapper.xml:37`。A2–A4 保留此差异。

**用户表现：** 删除文档后搜索已排除，资产总览仍可能计入切片/向量。不是“代码重复必然错误”，而是具体过滤条件不同。

**优化：** 先补齐现有查询，再定义共享的 current membership 查询或数据库视图及跨语言样例；授权仍在各入口执行，视图不替代 ACL。不要求为统一 SQL 新建网络服务。

**验收：** 删除、恢复、removed、更新失败时，涉及当前可搜索知识的详情/统计/质量/搜索采用一致有效文档集合；管理列表可以包含未挖掘或首次失败文档，但不能把它们标成可搜索。另明确统计是按文档累计还是去重物理资产，不能把两种指标混用。

### O5：源文件更新有底层模型，缺正式用户动作【优先级 P2，产品闭环缺口】

正式 KB 路由有上传、元数据修改、移动、删除和恢复，未发现独立 replace-content 入口。活跃同名文件上传返回冲突；只有软删同名重传使用 revive。此前“用户直接替换原文件”的描述超出了已交付入口。

证据：`kb/routes/documents.py`、`kb/services/document_service.py:226`、`kb/db.py:1335`、`file_management/__init__.py`。

**优化建议：** 增加明确的“替换当前文件”动作，复用现有对象上传和 revision 并发保护；原文更新成功后保持旧知识可用，直到重新挖掘成功。不要求用户先删后传，不新增历史版本列表/回滚体系。同名上传继续是冲突还是允许明确选择替换，需要冻结为产品规则，禁止静默覆盖。

**验收：** 替换 → 显示待更新 → 挖掘失败仍可搜旧知识 → 重试成功切换；并发替换能检测冲突；原件下载与证据回源标识清楚。

### O6：质量原因和异常原因需要按事实说明【优先级 P2】

- A4 `KbQualityPanel.vue:19,39,80` 将部分缺口直接解释为旧版本/回填，对全新部署不可靠。实际应区分不适用、未加工、生成失败、资料本身缺失，依据后端事实给操作建议。
- master `StructureRefService.java:127` 对活动范围读取的数据库异常转成 out_of_scope，历史读取异常也按无历史处理。用户会把服务故障误解为无权或引用无效。
- 最新原文件下载和当前可搜索知识读取各有用途，不能为了“统一”强制都打开最新文件。保留双入口，明确名称；证据回源必须保留版本约束。

**优化：** 复用既有 typed error 与能力报告，保留权限隐藏存在性边界，同时把服务故障作为可重试异常；前端文案使用真实原因和普通用户能执行的操作。

### O7：大归档异步任务恢复能力是明确限制【后续按规模安排】

`kb/services/archive_tasks.py` 使用进程内有界注册表，代码明确重启会丢任务；与持久化挖掘 Run 的恢复能力不同。这是已有取舍，不是所有 Run 都需要重建。

若真实上传规模要求跨重启恢复，再增加持久化接收任务与成员幂等进度；不要仅因已有 upload_sessions/operations 表就假定现成可接，也不优先引入通用工作流系统。

## 5. 目标结构：保留主链，只明确责任

| 责任 | 继续使用的载体 | 这次优化 |
|---|---|---|
| 谁能管理哪些资料 | KB / member / Document | 沿用权限，目录操作只改业务位置 |
| 当前上传文件 | Document 对象指针与 revision | 提供明确替换动作，不新增文件历史版本产品 |
| 一版知识结果 | Snapshot / Parse IR / 编译指纹 | 接通已有版本隔离，避免重切覆盖正在使用的数据 |
| 当前可用知识 | 现有 Build selection | 统一查询合同、来源绑定及删除规则 |
| 如何加工 | Mining Run / parse attempts / LLM tasks | 保持分层执行日志，不另建总任务系统 |
| 如何读取 | Java 检索与结构服务、Python 原件/解析读取 | 明确最新文件和证据来源区别，统一异常与用户用语 |

不因类或表多就合并；不为了方便编译而削弱来源或权限。对 unused/legacy 路径按可达性逐个退役，禁止先做全仓删除工程。

## 6. 分批实施与完成条件

### 批次 C0：以新部署路径修复实际断点

范围：O1 文件/目录操作，O3 文档来源绑定，O4 统计范围。三组定向修改分别验收，互不等待大版本设计。

交付：对象文档能可靠整理；共享快照不会串来源；删除后当前知识统计与搜索范围一致，管理列表状态准确。测试首先使用新上传对象文档，而非人工构造磁盘文件。

### 批次 C1：接通已有 Snapshot 编译隔离

范围：O2；先写能够复现正式调用链的测试，再调整快照创建/编译组合点；覆盖共享快照和失败窗口。

交付：新加工不影响旧可用知识。只恢复既有 ADR D5 的承诺，不新建知识版本层。需与 A2–A4 的 section identity、typed cells、IR 持久化修复共同验证。

### 批次 C2：把状态变成用户能理解的操作闭环

范围：O5 明确替换动作，O6 质量与错误解释；复用已经存在的 current/latest 双视图、A4 质量面板。

交付：用户清楚当前下载什么、搜索什么、为什么还没更新、失败后怎么办。替换当前内容不扩展成历史版本管理。

### 后续演进门槛

完成以上后，再以真实跨文档制品需求判断是否扩展 KB 发布清单、依赖失效与整体切换。40 号 F 的业务目标仍有价值，但不把完整 Release 改造作为修好文档级主链的先决条件。
