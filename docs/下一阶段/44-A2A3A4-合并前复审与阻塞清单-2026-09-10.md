## 3. 优先修复的主流程阻塞

### R1 [P1] 分页计数按数字下标读取 dict_row，阻断文件列表刷新

位置：[kb/db.py:1411](D:/mywork/AgenticKB/.claude/worktrees/a2-a3-a4/knowledge_mining/mining/kb/db.py:1411)。

`count_documents_in_kb` 使用 `int(row[0])`，实际连接使用 dict_row，`COUNT(*)` 返回类似 `{"count": 3}`。`/documents/count` 因此抛出 KeyError。前端 `KbFileManager.vue:355` 将列表和计数放在同一个 Promise.all，计数失败时不会把已取得的文件写入列表。

**修法与验收：** 使用明确 SQL 列别名和字典键；测试 count API 的真实 row 形状，并测试首次打开文件列表和翻页。不能只 mock 前端 total 为数字。

### R2 [P1] 子章节递归 CTE 多一个右括号，FTS/dense 查询语法错误

位置：[AssetRetrievalUnitV2Mapper.xml:111](D:/mywork/AgenticKB/.claude/worktrees/a2-a3-a4/agent_serving_java/src/main/resources/mapper/AssetRetrievalUnitV2Mapper.xml:111)。

`sectionClosureCte` 的 `WITH RECURSIVE sec(...) AS (...)` 后又输出一个 `)`。开启 descendants 且章节范围非空时，FTS 拼出 `WITH ... (...) ) SELECT`；dense 内层子查询也被提前关闭。XML 文档本身合法，所以字符串/XML 测试仍可通过。

**修法与验收：** 删除多余括号；实际执行 FTS 与 dense 的 descendants SQL，包含父子章节、两个快照同 ref、空结果和闭包限制。只检查 SQL 字符串包含 snapshot_id 不足以验收。

### R3 [P1] 表格排序翻页丢失排序条件，结果会漏行或重复

位置：[TbTableQueryPanel.vue:200](D:/mywork/AgenticKB/.claude/worktrees/a2-a3-a4/kb-ui/src/components/kb/TbTableQueryPanel.vue:200)。

`buildSpec(nextCursor)` 把 order_by 放在无 cursor 分支；第二页只有 offset cursor。后端 cursor 不保存排序，第二页回到默认物理行号顺序，再追加到已排序的第一页。修改筛选框后直接点下一页也会混用新条件与旧 offset。

**修法与验收：** 保存已执行的查询规格，后续页保持筛选、排序、选列一致；编辑条件后重置分页。用超过两页、物理顺序与业务排序相反的表格检查无漏行/重复。

### R4 [P1] XLSX 解析输出变化但身份未升级，重挖可继续复用无类型旧 IR

位置：[native_xlsx.py:46](D:/mywork/AgenticKB/.claude/worktrees/a2-a3-a4/knowledge_mining/mining/parse_adapters/native/native_xlsx.py:46)、同文件 normalizer 版本约 524 行。

parser 仍为 `2.0.0`、normalizer 仍为 `native-xlsx@2`，与 master 相同。同一 Excel 输入在 master 得到 cell 类型/规范值为空，在新分支得到 number/text 等事实，但 ParseIdentity 相同。

已存在快照会在同指纹提交时复用旧 snapshot 及旧 IR 对象；A3 持久化/回填按 snapshot 读取 IR，因此仅重挖不保证取得新类型事实。这是本分支改变解析语义引入的失效问题，不是旧部署迁移工程。

**修法与验收：** 升级相应解析/归一身份，加入“先使用 master 解析同一 XLSX，再用新解析器处理”的用例，验证新 snapshot/IR、typed cells 和最终查询一致。

### R5 [P1] 父子标题进入同一切片时，大纲锚点会指错章节

位置：[section_identity.py:102](D:/mywork/AgenticKB/.claude/worktrees/a2-a3-a4/knowledge_mining/mining/retrieval_projection/section_identity.py:102)。

每层新建 SectionIdentity 都使用 `opener.element_ids[0]`。真实编译器可以输出 heading_chain=(Parent, Child)、element_ids=(parent, child, body) 的单个切片；投影却把父、子章节都绑定 element_id=parent。

`list_section_anchors` 把 element_id 映射成单个 ref，两个锚相互覆盖，父章节可能指向子章节，子标题没有自己的锚。有兄弟子节时，点击父章节范围搜索可能只搜索一个子节。

**修法与验收：** 从真实 IR heading 元素/层级取得相应元素身份，无法判定时不要伪造首元素绑定。测试父子标题合并入切片、同父两个子节及各大纲锚的搜索范围。这不同于文档中已说明的连续同名标题折叠边界。
