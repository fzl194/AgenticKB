# 产业知识底座、本体与 Agent：用“图书馆和工厂”讲清楚

> 版本：通俗逐步版 V1.0  
> 日期：2026-09-14  
> 阅读方式：不必一次读完。每一节只回答一个问题。读到觉得“这就是我现在关心的事”时，再读下一节。

这份文档把产业知识底座想成一座“图书馆加工厂”。这样可以先把大多数术语放到一边，先弄清楚一件最重要的事：**我们到底想让 Agent 做什么，它凭什么能做对。**

本文基于40、41号方案、当前代码和公开资料。代码核查与公开资料访问截至2026-09-14；没有运行生产服务、查询生产数据库或访问内网产业系统。文中“已经有”“正在建设”“建议做”是三种不同意思，不能混在一起。

## 第1讲：我们现在有一座什么样的“图书馆”？

现在的产业知识底座，已经很像一座认真整理过的专业图书馆。

它能把PDF、网页和表格放进来；把一本大书按章节、段落、表格拆开；记住每句话原来在哪；让人或Agent按关键词和意思去找资料；还会保留版本和权限。

这很重要。假如没有这座图书馆，后面谈本体、图谱、规则，都会变成没有出处的猜测。

但图书馆的强项是：**帮人找到书。** 它还不能自动替人完成下面这件事：

> 根据资料、现场情况和业务规则，给出一个真的可用、没有违反硬条件的方案。

这就是当前“知识做得越来越细，但离垂直业务落地仍很远”的根源。

当前正式代码也支持这个判断：默认加工链路是“解析资料 → 切成可搜索内容 → 生成检索表示 → 入库发布”。实体、本体和图谱相关加工目前明确留在研究隔离区，不是正式产品链的一部分。[正式算子目录](D:/mywork/AgenticKB/knowledge_mining/mining/workflow/operators/catalog.py:16) [研究隔离说明](D:/mywork/AgenticKB/knowledge_mining/mining/workflow/operators/research.py:3)

## 第2讲：RAG到底像什么？它为什么还不够？

RAG可以理解成一个很擅长找资料的图书管理员。

你问：“这个站点能不能选设备甲？”它会从几百份资料里找出设备甲的说明书、温度限制、安装条件、历史方案和相关表格。它找得越准，Agent越少漏看材料。

可是，拿到资料以后，还要有人把事情做完：

1. 设备甲“支持室外”是不是还有温度条件？
2. 现场温度到底是多少？这个数据是今天的还是两年前的？
3. 需要的散热部件有没有库存？
4. 某个规则是否只适用于旧版本？
5. 少了一个关键条件时，应该说“无法判断”，还是假装给出答案？

RAG并不天然负责这些问题。它像图书管理员，不是现场工程师、规则检查器或业务系统。

所以，RAG不是没价值，而是它只解决了完整链路中的第一步：**把可能有用的依据找到。**

## 第3讲：从“找到资料”到“把事情做对”，中间少了什么？

还是用选设备举例。

资料可能写着：“设备甲适合室外使用；环境超过40℃时，必须加装散热组件。”现场系统告诉我们：“当前站点最高温度45℃；仓库没有对应散热组件。”

如果Agent只读到第一句话，它会说“设备甲适合”。这不是它没有资料，而是它没有把资料、现场事实和规则一起检查。

要让结果可信，系统至少要能把下面四件事分开：

| 事情 | 通俗说法 | 谁应主要负责 |
|---|---|---|
| 找依据 | 找到相关手册、表格、历史记录 | 知识底座与RAG |
| 知道在说谁 | 分清型号、实际设备、站点和版本 | 业务对象模型／本体 |
| 算和检查 | 温度是否超限、条件是否满足 | 规则和检查器 |
| 读真实现场 | 库存、工单、运行状态到底是什么 | 业务系统 |

Agent很适合做的是：听懂人的需求、补问缺少的信息、提出候选方案、把经过检查的结果解释给人。

程序和业务系统更适合做的是：精确计算、检查硬规则、管理权限、读当前状态、记录操作结果。

## 第4讲：本体、知识图谱、LLM Wiki、知识制品，分别是什么？

它们不是四种谁替代谁的“更高级技术”。把它们放进同一座工厂，就容易理解了。

| 名字 | 像什么 | 主要用途 |
|---|---|---|
| 术语表 | 词典 | 统一叫法，例如“板卡”和英文缩写是不是一回事 |
| 本体 | 图纸和词典规则 | 规定这个行业有哪些东西、字段分别是什么意思、哪些东西能发生什么关系 |
| 知识图谱 | 带关系的台账 | 记录“哪台设备装在哪个站点、用了什么版本、关联哪些资料” |
| LLM Wiki | 持续整理的业务百科 | 把多份资料解释成容易阅读的主题页、对象页和对比页 |
| 知识制品 | 已经备好的工具箱 | 面向一个具体用途交付的规格表、规则包、计算器、模板或Wiki页 |
| RAG | 图书管理员 | 找到上述材料或原始资料 |

一个例子：本体说“设备型号”“实际设备”“站点”是三种不同东西，“部署在”是它们之间的一种关系；图谱记录“设备P-101部署在站点A”；Wiki解释这个型号常用于什么场景；规格矩阵让人直接筛选几十个型号；规则包检查45℃时是否合格。

这些东西可以互相引用，但不需要都存成一张大图，也不需要都做成同一种数据格式。

## 第5讲：为什么“抽到概念名字”通常帮不了太多业务忙？

因为业务真正关心的往往不是“文档中有没有出现泵这个词”，而是“这台泵现在能不能做某件事”。

| 层次 | 示例 | 为什么不能混 |
|---|---|---|
| 概念 | 泵 | 只是一个类别名称 |
| 型号 | 某厂家型号P | 是一类产品，不等于现场那一台 |
| 版本 | 型号P的R2版本 | 同型号不同版本可能能力不同 |
| 实际对象 | 某工厂里的P-101 | 需要稳定编号和来源系统主键 |
| 当前状态 | P-101今天的运行温度、故障和工单 | 会变化，必须从业务系统读取 |
| 规则 | 高于40℃需要散热组件 | 要写清输入、例外和适用版本 |
| 操作 | 为P-101创建检修申请 | 需要权限、前置检查和操作回执 |

现在研究代码中的实体模型，主要以“领域、类型、规范名”来合并名称，默认也是concept层；虽然留了attributes_json字段，但还没有正式的业务属性定义、单位、有效时间和业务主键映射。[实体schema](D:/mywork/AgenticKB/databases/ontology/schemas/001_ontology_concept_postgresql.sql:61)

因此，它现在更像“从资料中找出重要名词”，还不是“把业务世界中的对象建好台账”。这不是一个小细节，而是从知识检索走到业务判断的分界线。

## 第6讲：为什么有了本体，Agent也不会自动稳定？

本体能让大家对“设备”“版本”“站点”“兼容”有统一说法。它能大幅减少歧义，这很有价值。

但本体本身不是警察，也不是计算器，更不是业务执行系统。

举例说，在图纸上写“每台设备必须有版本号”，不等于系统会拒绝没有版本号的表单；写“设备甲可以连接模块乙”，不等于此时此刻的设备甲一定能安装模块乙。

正式本体标准也说明了这个边界。OWL适合描述领域知识，但它不负责把缺失字段自动判错；在它的规则里，“没有记录”也可能只是“暂时不知道”。[W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

如果希望系统真的检查“字段是否缺失、数值是否越界、两个条件是否冲突”，还要使用检查机制。SHACL是图数据的一种标准选择；不使用图也可以用数据库约束、JSON Schema或代码检查器完成同样职责。[W3C SHACL](https://www.w3.org/TR/shacl/)

所以，不要相信这句话：“有了本体，垂直Agent就稳定了。”

更准确的话是：**本体让数据、规则和工具能说同一种业务语言；稳定性还要靠可执行规则、当前状态、受控操作和结果验证。**

## 第7讲：关系图里有一条线，为什么还不能当真？

如果两个人经常出现在同一篇新闻里，我们只能说他们“可能有关联”，不能直接说他们一定是合作伙伴。

知识图谱也一样。当前研究代码会先把同一段文字中的实体两两配对，只要两个类型允许连接，就产出关系候选；随后再用“经常一起出现”的统计量过滤候选。[关系候选构造](D:/mywork/AgenticKB/knowledge_mining/mining/stages/entity_relations/__init__.py:134) [共现过滤](D:/mywork/AgenticKB/knowledge_mining/mining/stages/graph_write/__init__.py:202)

这对于发现“值得人工看一看”的关系很有帮助，但不能直接证明设备甲真的兼容模块乙、配置A真的依赖配置B，或特性C真的禁止和特性D同时开启。

因此要永远分清三句话：

1. 类型上允许这样连。
2. 文本里经常一起出现。
3. 这个具体业务事实已经被证实。

只有第三句话，才可以作为严肃业务判断的依据。

## 第8讲：什么叫“规则有两种”？

规则至少有两种，不能混着叫。

第一种是“给人看的经验”。例如：“高温环境下优先考虑带散热的方案。”它很有用，但不同人可能理解不同。

第二种是“系统必须执行的条件”。例如：“环境温度大于40℃，且设备版本属于R2之前，则散热组件字段不能为空；缺失时返回‘无法判断’，不能返回‘通过’。”

第二种规则需要明确：需要哪些输入、输入单位是什么、适用于哪些型号和版本、有什么例外、缺少信息时怎么回答、根据哪份资料或哪位专家确认、由哪个检查程序执行。

网络行业的YANG模型就是一个直观例子：它不仅描述字段，也允许用must条件声明什么数据才算有效。[IETF RFC 7950](https://www.rfc-editor.org/rfc/rfc7950.html)

下一阶段真正值得建设的，是把高价值、稳定、可以说明清楚的规则，从“Agent读到的一段话”变成“每次都会经过的检查”。

## 第9讲：Agent怎样才算“稳定”？

稳定不是每次回答措辞都一样。

稳定是：面对相同的业务事实和要求，它都能交付一个符合验收条件的结果；不满足条件时，不会把“不知道”伪装成“可以”。

一个比较健康的流程是：

```text
人提出需求
  → Agent理解需求，收集必要信息
  → 从知识底座找到依据和已发布制品
  → 从业务系统读取当前状态
  → Agent提出候选方案或判断
  → 规则/计算/专业验证器检查
  → 通过：交付带依据的结果
  → 不通过或信息不足：说明失败原因、需要补什么
```

如果未来要执行真实操作，还要多两步：执行前再次检查状态和权限；执行后读取业务系统回执，确认目标真的达成。Agent说“我完成了”不能当作完成证据。

这也是为什么生产环境的Agent通常需要和工作流、规则、人工审批一起用。Camunda公开文档将非确定性的Agent工作放进带确定性规则和人工节点的流程中；这是一种职责分工，不是让流程引擎代替Agent。[Camunda Agentic Orchestration](https://docs.camunda.io/docs/components/agentic-orchestration/agentic-orchestration-overview/)

## 第10讲：有没有证据说明“给够资料也不一定做对”？

有，而且这件事很关键。

τ-Knowledge论文把Agent放进一个模拟银行业务环境：有约700篇相互关联的知识文档，Agent既要找政策和工具说明，又要完成可验证的数据库状态变化。

论文中，最佳检索设置的单次任务成功率是25.52%；即使把完成任务必须的正确文档直接给Agent，最佳受测设置也只有39.69%。这两个最佳数字来自不同模型，不能当作同一模型的提升或下降。它们也不能代表所有模型、所有行业或真实银行。

但它说明了一件足够重要的事：**正确知识在眼前，不等于Agent会正确理解、安排步骤、调用工具和处理当前状态。** [τ-Knowledge原论文](https://arxiv.org/html/2603.04370v1)

另一个很好的思路叫“生成—检查—修正”：Agent先给候选，外部检查器找出违反条件的地方，再让Agent修改。可靠性来自检查器实际覆盖的规则，而不是来自“让Agent多反思一次”。[LLM-Modulo论文](https://arxiv.org/html/2402.01817v3)

## 第11讲：工业界做得比较深的地方是什么？

公开资料里，真正走得比较深的工业系统，通常不是只有文档搜索或只有图谱。

- Palantir把真实数据映射成对象、属性和关系，同时提供动作、函数、权限和提交检查。它所说的Ontology，更像“业务对象世界加受控操作”，不只是传统意义上的本体。[Ontology概览](https://www.palantir.com/docs/foundry/ontology/overview) [Action Types](https://www.palantir.com/docs/foundry/action-types/overview)
- Cognite把工业资产、实际设备、文件、活动和时间序列连接起来。重点是把资料挂到具体业务对象和观测状态上，而不是只做术语集合。[Cognite Core Data Model](https://docs.cognite.com/cdf/dm/dm_reference/dm_core_data_model)
- Airbus Skywise把飞行、工程和运营数据放到同一个行业数据平台中，为运维和运行决策服务。它提醒我们：工业知识不只来自说明书，还来自业务系统和实时数据。[Skywise Core](https://www.skywise.com/en/digital-platform/skywise-core)
- Batfish会根据网络配置模型检查变更后网络会怎样工作。它提醒我们：如果某件事能由领域验证器检查，就不要只让另一个大模型来判断。[Batfish变更验证示例](https://batfish.readthedocs.io/en/latest/notebooks/linked/introduction-to-forwarding-change-validation.html)

这些材料证明的是：真实对象、状态、规则、操作和验证需要结合。它们不是“只要建本体就成功”的公开对照实验，也不是对本项目收益的承诺。

## 第12讲：我们到底该建设一张大而全的行业图吗？

我不建议一开始建设一张覆盖所有行业、所有对象的大图。那很容易变成一张漂亮但没人用的“知识世界地图”。

更好的方法是，先选一件真实而小的事。例如：

> 给定站点条件和产品资料，判断候选设备是否合格，并说明不合格或无法判断的原因。

然后反过来问：要做对这件事，系统必须认识谁、知道什么、检查什么？

可能得到的最小清单是：

1. 设备型号、版本和站点的稳定标识；
2. 温度、功耗、容量等字段的含义和单位；
3. 每个字段来自哪份资料，何时有效；
4. 高温、库存、兼容性等规则；
5. 哪些状态要从实时系统读取；
6. 什么结果算通过、不通过或无法判断。

这套最小清单就是这个任务需要的“小本体加小规则包加小制品”。做成以后，再去另一个领域试用，才知道哪些东西真的应该成为跨行业的共用能力。

经典本体工程也主张先写“这个知识系统必须回答什么问题”，再决定要建多大模型，而不是先收集几百个类别名称。[Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)

## 第13讲：跨行业时，什么应该共用，什么不能强行共用？

可以共用的是“做事的方法和接口”：怎么记录来源、版本、权限和审核；怎么定义稳定对象ID；怎么说明字段的单位、时间和适用条件；怎么发布规则、运行检查和记录结果；怎么评价一个任务是否真的做得更好；怎么在资料变化后找到受影响的制品和规则。

不应该强行共用的是每个行业的业务内容：什么是设备、订单、网元或风险事件；哪些字段最重要；哪些规则必须严格执行；哪些例外需要专家裁决；哪个系统才是实时状态的权威来源。

可以把它理解成：所有工厂都可以共用质量管理办法，但每家工厂的产品图纸、原料和验收标准仍然不同。

## 第14讲：未来架构中，谁对什么负责？

不需要立刻新增三套大平台，但责任要分清。

| 部分 | 它像什么 | 应负责什么 |
|---|---|---|
| 知识与语义底座 | 图书馆加图纸库 | 来源、对象定义、可查询事实、规则和方法的版本管理 |
| Agent任务运行系统 | 项目经理 | 把任务、知识和状态放在一起；让Agent提出候选；驱动检查和记录过程 |
| 业务系统 | 现场和台账 | 提供真实身份、当前状态、受控操作和操作回执 |
| 行业专家团队 | 总工程师 | 定义行业对象、关键规则、例外和验收标准 |

现有的三个知识MCP工具可以继续用来“找知识、读知识、上传资料”。但业务查询、计算和操作应该有自己的清楚接口；不能因为知识服务只准备了三个工具，就把整个行业Agent限制成只能有三个工具。

网关负责把工具接进来、把身份正确传递出去、记录调用情况。它不应该替业务系统判断行业规则，也不应替下游服务决定知识版本是否适用。

## 第15讲：下一阶段最该先承诺什么？

不建议一上来承诺“自动完成业务操作”。更合适的第一步是：

> Agent能交付一个经过明确规则检查的判断或方案；如果材料或状态不足，它能明确说出为什么无法判断、还缺什么。

这一步已经比“回答一段看起来合理的话”强很多，但不要求马上写入生产系统。

可以按下面四个小关口推进：

1. **先看现在会怎么错。** 收集真实任务、人工正确答案和失败案例。
2. **再建最小业务模型。** 先完成少量真实对象、事实和关键规则，不追求全行业。
3. **让结果必须过检查。** Agent给方案，检查器给通过、不通过或信息不足；每个结果都能回到依据。
4. **换一个行业试。** 看哪些部分真的可以共用，再决定是否平台化。

评价时不要只看文档数、切片数、节点数或制品数。更该看：关键业务结果对不对，有没有违反硬规则，是否能识别“信息不足”，重复运行是否仍然正确，人工要改多少，花多少时间和成本，资料更新后能不能找到并更新受影响的内容。

## 第16讲：如何判断接下来该多投RAG，还是多投规则和执行？

不要靠感觉，拿同一批任务做一个小实验。

| 比较方式 | 给Agent什么 | 能看出什么 |
|---|---|---|
| A | 现有RAG和原始资料 | 今天的真实基线 |
| B | 同一资料整理出的Wiki或专题页 | 提前整理是否减少重复阅读 |
| C | 结构化事实，例如型号、版本、条件 | 是否减少字段和归一错误 |
| D | 事实加规则检查器 | 是否真的减少硬规则违规 |
| E | D再加任务步骤、状态重检和结果验收 | 多步任务和实时状态是不是主要难点 |
| 诊断对照 | 直接给正确必要知识 | 分清“没找到”还是“不会用” |

如果直接把正确知识给Agent，它还是常常错，下一步就应该先补规则、任务步骤和验证。

如果给正确知识后它做得很好，但现实检索时做得差，下一步就应该继续改善资料接入、知识编译和检索。

这比争论“本体、图谱还是Wiki谁更先进”更有用，因为它会告诉我们：**真正卡住业务的地方在哪里。**

## 最后，用一句话记住这份文档

RAG让Agent更容易找到资料；本体让资料、对象和规则说同一种业务语言；知识制品把高频工作提前做好；但Agent能否稳定落地，最后取决于是否把**真实状态、可执行规则、受控操作和结果验证**接成闭环。
