# 50 · 删除体系与快照生命周期设计（2026-09-16 定稿）

## 一、背景与决策

内网实测暴露删除体系三问题：软删无恢复入口却挡名字（"删了又回来"）、文件夹
"仅叶子"规则在深树下不可用、换范式的旧快照知识永久僵尸化。经真库调查
（全表依赖图 + 挖掘产物生死追踪）与用户多轮对齐，定稿：

1. **软删全面退役**——用户可见层面全部直接硬删，防误删靠确认门槛
   （整库=输入库全名，GitHub 风格），不靠"可恢复"；
2. **一条统一硬删管线**，三入口复用（整库 / 文件夹级联 / 文档批量，
   一张网 source 删除 = N 个文档批量）；
3. **共享资产引用计数回收**——快照（域级指纹共享）与 MinIO 对象（sha 去重）
   归零才动，隔壁库一根毫毛不少；
4. **快照废弃轨道**——DEPRECATED → 留 7 天（切回范式不必重花 LLM 钱）→
   物理回收；指纹命中复活 READY。

## 二、数据模型（用户理解版）

```
用户 → 知识库 → 文档行(PG) ──storage_object──→ MinIO 原件
                    │ link 表(多对多)
                    ▼
              快照(域级共享：同内容跨库同一行) ──parse_ir──→ MinIO IR 对象
                    │
                    ├── 段落/检索单元/向量/表格/结构/定位（全部挂 snapshot_id）
                    └── Build 选片行（历史累积；"当前"= 最新 validated Build 的 active 选择）
```

铁律：**知识产物只跟快照走**——快照被回收则全删；快照共享则谁也不动。
删除顺序（FK 反向）：引用行 → 历史轨 → 文档行（CASCADE links+选片）→
快照（独占判定）→ 对象（引用清点）。

## 三、统一硬删管线（`kb/services/purge_service.py`）

### purge_documents(kb_id, doc_ids)
1. 归属校验（软删文档也接受——存量清理）；收集快照集合（删行前取）与源对象
2. `kb_document_refs`（跨库引用行）→ `mining_run_documents` → parse_runs/attempts
   → upload_sessions / file_audit_events（随文档陪葬）
3. 文档行删除（CASCADE 带走 snapshot_links + build 选片行）
4. 快照回收：逐个查剩余 links + build 选片引用；**独占才删**（v2 八族 +
   staging 孪生手动按 snapshot_id 删；v1/段落/本体证据随快照行 CASCADE）
5. 对象回收：源对象 + 被回收快照的 IR 对象，软列清点归零才删 MinIO 字节
   （`object_store.delete`，失败仅告警不阻断）+ 登记行

### purge_kb(kb_id)
先删 KB 自有 Build（KB Build 恒不进 release，无 RESTRICT 风险）与
mining_runs → purge_documents（全量）→ 引用行/配额/上传会话/onenet_imports →
库行（成员/文件夹/开放库随 CASCADE）。**软删态库同样接受**（存量善后）。

### purge_folder(kb_id, path)
树下全部文档走 purge_documents → 目录子树删除。`folder_delete_preview`
供确认框计数（子文件夹数 + 文档数）。

## 四、快照废弃轨道

- **标记**（`deprecate_superseded_snapshots`，每日后台 + 管理员手动）：
  READY 且非任何活文档的当前 serving 快照（serving 规则与
  `kb/db.get_current_serving_snapshot` 及 Java `AssetBuildDocumentSnapshotMapper`
  逐语义对齐——三处修改必须同步）且 created_at 早于 1 小时（避开在途 Run）
  → `lifecycle_status='DEPRECATED' + deprecated_at`（017 迁移新增列）。
- **回收**（`reclaim_deprecated_snapshots`，废弃满 7 天）：stale links/选片行
  销账 → v2 八族 + 快照行删除 → IR 对象引用清点回收。
  7 天缓冲 = 切错范式想切回来不必重花 LLM 钱。
- **复活**（snapshot_store 指纹命中分支）：命中行若 DEPRECATED → 回 READY、
  清 deprecated_at（同指纹即同内容，重挖纯浪费）。
- 每日 GC 任务挂 mining lifespan（启动即跑一轮清存量，之后 24h 一轮，
  失败只记日志）；管理员手动端点 `POST /api/kb/snapshots/gc`。

## 五、路由面（软删退役）

| 端点 | 语义 |
|---|---|
| `DELETE /api/kb/{id}`（body confirm_name） | 整库硬删；名字不符 422；软删态库可删（善后） |
| `GET /api/kb?include_deleted=1` | site-admin 已删库清单（存量善后入口） |
| `GET .../folders/{id}/delete-preview` | 级联删除预览计数 |
| `DELETE .../folders/{id}` | 级联硬删（"仅叶子"退役） |
| `DELETE .../documents/{id}` | 单文档硬删（管线） |
| `POST .../documents/purge` | 批量硬删（≤5000/次） |
| `DELETE /api/onenet/imports/{id}` | source 删除切统一管线（全量含软删态） |
| `POST /api/kb/snapshots/gc` | GC 手动触发（admin） |

restore 端点保留（软删时代存量救济），新删除不再产生软删态。

## 六、前端

- KB 删除（列表卡片菜单 + 设置面板）：输入库全名确认，文案全部
  "永久删除/不可恢复"口径；管理员"已删除的知识库"折叠区 + 彻底删除。
- 文件夹删除：预览计数确认（"X 个子文件夹、Y 篇文档（含全部挖掘内容）"）。
- 文件删除/批量删除：硬删口径；批量走 purge 端点（替代逐个循环）。

## 七、验收

- 单元：`test_purge_routes.py` 14 条（确认门槛/权限/管线调用契约）；
- **真库 E2E**（`test_purge_e2e_real_pg.py`，默认跳过需 DSN）：
  ①共享快照两库删一留一（快照/IR 对象保住、邻居逐表无损；两库全删后回收）
  ②文件夹级联（兄弟目录不动）③GC 轨道（僵尸标记→未满期不回收→满期回收，
  serving 快照与 v2 行无损）。
- 本轮真库 E2E 抓出 3 处代码列名错误（snapshot_id→document_snapshot_id、
  byte_size→size、v2 无 document_ref 列）——正是 fake 单测拦不住的漂移面。

## 八、已知边界

- 本体实体/关系为域级聚合，随快照 CASCADE 的只有 evidence/mentions 子行；
  实体计数器（mention_count/document_count）不重算（实体本体线未上线，留待）。
- storage_operations（outbox）与 LLM 任务面（独立库）不参与回收。
- 1.1.5 之前软删的文档：随所属库/文件夹/单删硬删时一并清理（管线不过滤
  deleted_at）。

## 九、双路审查整改（2026-09-16）

code-reviewer（3H/3M/8L）+ security-reviewer（0C/1H/5M/7L）整改记录：

**已修**：①每日 GC 循环 asyncio 未导入（首轮后 NameError 静默死亡）；②GC 回收
满期复核 serving（DEPRECATED 期间又成为 serving → 跳过+复活 READY，绝不删
正在服务的知识；真库 E2E 增该用例）；③前端批量删除的文件夹壳清理改预览
门控（documents>0 不删——级联语义下旧壳清理会顺带删未勾选文档）；④文件夹
级联 >50 文档要求 body.confirm_name==文件夹名（editor 不可裸调摧毁整树）；
⑤purge 三入口加在途 Run 门禁（kb_busy 409）；⑥两处权限异常漏捕（500→
404/403 反探测约定）；⑦GC serving CTE 对齐 db.py「先取最新再滤 active」
语义 + b.id DESC 决胜；⑧批量 purge 入参解析期收紧（元素 64 字符/总量 5000）；
⑨对象回收先删字节后删行（失败可重试）；⑩快照行删除带 NOT EXISTS 引用守卫；
⑪复活 SELECT 加 FOR UPDATE；⑫purge 日志带 actor；⑬002 两个 trigger 补
DROP IF EXISTS（DDL 真幂等，双进程重放不炸）。

**设计修正**：GC 回收守卫**不做**「活文档 link」检查——links 是 append-only
血缘（文档用过的快照永远挂着），按它判一切历史快照均不可回收；「还有用」
由 serving 集判定，切回范式走指纹命中复活。

**遗留（记录不修）**：大库 purge 内联 HTTP 请求（管线幂等可重跑，后台任务化
为后续工作项）；对象孤儿（快照行删后、对象回收前崩溃）无 GC 兜底；本体实体
计数器不重算；审计事件随文档陪葬（追责链让位于「删干净」产品语义，actor
已固化进日志）。

## 十、删除任务化（二期，2026-09-16 内网反馈驱动）

内网实测：数万文档的库同步硬删跑几十分钟，请求被网关 300s 掐断、库行最后
才删导致"刷新还在"，用户全程无感知；LLM 清理几十万行单请求贴 axios 290s
超时直接失败。二期四件套：

1. **禁用态**（`deleting`，013 迁移）：确认后秒级置位——读写全退
   （Python `is_visible` 与 Java `KnowledgeBaseMapper` 均滤 `status='active'`，
   借力现有过滤链，Java 零改动）、成员侧即刻不可见；重复删除幂等返回
   既有任务。
2. **后台任务 + 进度**：`kb_purge_tasks` 表落 phase（prepare/documents/
   snapshots/objects/finalize）与计数；`DELETE` 改 202 秒回任务 id；
   `GET /api/kb/purge-tasks`（admin 全域/库主自己发起）；前端"删除中的
   知识库"卡片 + 快照阶段百分比 + 5s 轮询；startup 恢复 queued/running
   任务（管线幂等）。
3. **管线批量化**：快照/对象回收从逐个循环（2 万文档 ≈ 64 万条语句）
   改集合判定 + 2000/块批删 + MinIO 并发(8)——语句量 O(块数×表数) ≈ 200 条。
4. **一张网连带清理**（用户定稿）：删公共库时 onenet_imports + toc 缓存 +
   拉取工作区一并清。**LLM**：预算 240s→90s + model_calls created_at 索引
   （005）+ 前端自动续跑循环（累计进度，单请求远低于超时）。

坑：kbs 路由 `GET /purge-tasks` 字面量必须注册在 `GET /{kb_id}` 之前
（FastAPI 按注册序匹配——安全审查 L-6 的地雷真炸过一次）。
