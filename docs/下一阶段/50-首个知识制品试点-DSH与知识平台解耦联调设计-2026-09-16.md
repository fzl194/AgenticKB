# 首个知识制品试点：DSH 与知识平台解耦联调设计

> 版本：V1.0（首个场景实施设计）  
> 日期：2026-09-16  
> 目的：先用一张可回源的规格表打通“独立 DeepSeek Harness + 知识平台 + 固定 MCP + 人工审查”的完整闭环。本文不要求开发 DSH 插件、改造 DSH 源码，或先完成全部知识制品类型。
>
> 前置依据：[48号总纲](48-产业知识底座-统一知识资产体系与本体知识制品协同演进总纲-2026-09-14.md)、[49号全景架构](49-产业知识底座-端到端全景架构与知识生命周期-2026-09-15.md)、[DSH内网部署与表格试点](../deployment/deepseek-harness-intranet-pilot.md)。

## 一、先把边界说清楚

把整个系统看成“资料管理员”和“一名外部整理助手”的合作。

- **知识平台是资料管理员。** 它保存知识库、来源权限、制品定义、草稿、发布版、任务记录和审计记录。它是唯一能决定“能看什么、成果写到哪里、能不能发布”的系统。
- **DSH 是外部整理助手。** 它运行独立模型，进行多轮思考、调用工具、必要时运行 Python 整理临时数据。它不知道数据库结构，也没有平台数据库写权限。
- **固定 MCP 是受理窗口。** DSH 永远连接同一个 MCP 地址和同一组工具。每次能拿到什么资料、能提交到哪个草稿，由平台签发的短期任务票据决定。

因此，解耦不是“两个系统完全不通信”。真正的解耦是：**DSH 可以替换，制品定义和资料不丢；知识平台可以更换模型，权限、版本和发布规则不改变。**

```text
知识负责人
    │ 在平台创建制品、选资料、审查和发布
    ▼
知识平台 ── 原生会话接口 ──► 独立 DSH 服务 ──► 独立内网 LLM
    ▲                                  │
    │ 保存过程、草稿、版本              │ 固定 MCP 工具调用
    │                                  ▼
    └────────────── 知识平台 MCP 服务 ◄┘
                 校验票据，只读资料，只写绑定草稿
```

`llm_service`不在这条链路中。它继续只服务现有挖掘 Pipeline 的单次模型调用；DSH 直接调用单独配置的内网 OpenAI 兼容模型。

## 二、第一场景只做什么

首个场景固定为：**从 3–5 份已在平台内、来源清楚的产品资料中，制作一张“产品规格矩阵”草稿。**

不要先选扫描件、跨权限资料、实时运行数据或几百条复杂规则。先选择人工也能在半天内核对的资料，让问题出在系统接缝时能快速定位。

### 1. 本次任务的输入

在平台创建制品时，负责人填写和选择下面内容：

| 输入类别 | 首个试点的最小内容 | 为什么必须由平台保管 |
|---|---|---|
| 制品身份 | 名称、负责人、制品类型=`specification_table` | 确保草稿、会话和发布版都属于同一制品 |
| 业务目标 | 例如“比较这些产品的能力，支持专业问答与方案准备” | Agent知道为什么整理，专家也能据此审查 |
| 资料范围 | 3–5 份指定文档；必要时限定章节或表格 | Agent不能因为搜索方便而读到全库资料 |
| 字段定义 | 先限定 5 个左右字段，如型号、产品版本、关键规格、单位、来源 | 输出可检查，减少模型自由发挥 |
| 对象规则 | 一行代表什么；同名型号如何处理；单位如何保留 | 防止把不同版本或不同对象混成一行 |
| 人工样例 | 至少一行已人工确认的示例，或一条正确/错误对照 | 让Agent按真实标准整理，不只靠抽象提示词 |
| 试用问题 | 3–5 个代表问题，例如“哪些型号满足条件 X？” | 发布前有明确的检验题，不只看表格是否好看 |

> 修订（51号批次3，2026-09-18）：制品身份不再包含 domain——制品与知识域解耦，归属由「负责人」表达，资料边界由下方「资料范围」（文档/库粒度）表达。

输入应保存为“制品定义修订”和“本次制作输入快照”。资料内容不必一次塞进 DSH 的第一条消息；Agent 先取得资料清单，再按需分段搜索、读取和回原文。

### 2. 本次任务的正式输出

Agent 的聊天文字、容器中的 Excel、临时 JSON 都不是正式输出。正式输出只能是平台收到并校验成功的一次或多次 `submit_creation_result`。

首期提交结果至少包含：

```json
{
  "submission_id": "agent生成的稳定UUID",
  "based_on_draft_revision": 3,
  "kind": "specification_table_batch",
  "rows": [
    {
      "object_key": "型号或平台定义的对象标识",
      "values": {
        "model": "…",
        "product_version": "…",
        "key_specification": "…",
        "unit": "…"
      },
      "evidence": [
        {
          "document_id": "…",
          "snapshot_id": "…",
          "anchor": "章节/表格/段落定位",
          "quoted_value": "支持该字段的原始值"
        }
      ]
    }
  ],
  "unresolved_items": [
    {
      "reason": "两份资料的容量口径不同",
      "affected_object_key": "…",
      "evidence": ["…"]
    }
  ],
  "summary": "本批处理范围、缺失项和建议"
}
```

平台不要求 Agent 传完整原文；`document_id`、`snapshot_id`、`anchor`和摘录足以让平台核验并在页面打开正确位置。平台校验这些证据是否真的在本次允许资料范围内，不能信任 Agent 自报的来源。

平台成功写入后返回：`submission_id`、新的草稿修订、已接受行数、冲突/拒绝项。只有拿到这个回执，Agent 才能说“成果已交付”。

### 3. 人工在何处介入

首期只要求人做三次有价值的判断：

1. **启动前**：确认资料范围、字段和一行样例；
2. **处理中**：只回答会改变字段含义、对象边界或资料范围的关键歧义；
3. **提交后**：核对关键行及来源，用代表问题试用，再决定发布。

不要求人逐行陪着 Agent，也不允许 Agent 因没有人工确认而把冲突静默抹平。

## 三、DSH 到底接收什么，平台到底接收什么

这两边使用不同的接口，各自只承担一类责任。

### 1. 平台 → DSH：只控制会话，不传业务资料全文

平台是 DSH 的客户端。它使用 DSH 固定版本的原生会话接口完成认证、建会话、发送消息、取消、事件跟随和历史补读。

平台第一次启动制作实例时做下面的事：

```text
创建制品草稿和输入快照
  → 创建 creation_instance
  → 签发短期 task_ticket
  → 调 DSH session/create，记录 harness_session_id
  → 调 DSH session/prompt，发送启动指令和 task_ticket
  → 跟随 DSH 事件并保存可见过程
```

启动消息只需要告诉 Agent：

```text
你正在制作制品 abc。
先调用 get_creation_context，取得本次工作定义和资料清单。
只使用当前任务票据允许的材料；遇到关键歧义列入 unresolved_items。
不要把聊天回复作为最终成果；完成一批内容后调用 submit_creation_result。
```

任务票据必须以最小权限、短有效期的方式附给 Agent，因为固定 MCP 工具调用需要它。它不是平台管理员密钥；平台页面、普通日志和发布成果都必须脱敏。任务取消、资料范围收缩、权限撤销或草稿定义发生不兼容变化时，平台立即使它失效。

DSH 原生 POST 接口不是通用的`/chat/completions`。平台需要按其原生 Cookie 认证、RPC 请求体、`sessionId`、`requestId`和事件/历史协议实现一个平台侧适配器；重复发送同一条消息时必须复用同一个`requestId`。这部分属于平台代码，不要求 DSH 增加任何代码。[DSH 会话与连接说明](https://github.com/deepseek-ai/deepseek-harness/tree/dsh-v0.1.5-rc.2/packages/client/connection)

### 2. DSH → 平台：只通过固定 MCP 取资料和提交草稿

DSH 运行时只需要配置：内网模型地址与凭据、固定 MCP 地址、固定 MCP 的服务身份、工作目录与安全限制。它不保存制品业务定义，也不保存平台数据库连接。

| DSH 调的固定 MCP 工具 | 传入什么 | 平台返回/执行什么 |
|---|---|---|
| `get_creation_context` | `task_ticket`、可选分页游标 | 本次制品目标、字段定义、资料清单、样例、当前草稿摘要、待确认项、输出结构 |
| `search_knowledge` | `task_ticket`、查询、筛选和分页 | 只在本任务允许范围内检索证据和被授权的已发布制品 |
| `get_knowledge` | `task_ticket`、文档/章节/表格/制品引用 | 只读取允许内容，并返回可回原文的定位信息 |
| `submit_creation_result` | `task_ticket`、提交ID、草稿修订、结构化结果 | 校验后写入绑定草稿，或返回结构/来源/并发冲突错误 |

MCP 服务端每次调用都校验：服务身份、票据签名、制品与实例绑定、票据有效期、输入快照、当前权限、资源范围、草稿修订和输出 schema。

换句话说，**DSH 不知道“全库在哪”，只知道问窗口要这次允许的材料；DSH 不知道“数据库在哪”，只知道把结果交回窗口。**

### 3. DSH → 平台的另一条回流：过程上下文

成果通过 MCP 回来；过程通过 DSH 原生事件和历史接口回来。这两条不能混为一条。

| 回流内容 | 取得方式 | 平台用来做什么 |
|---|---|---|
| 用户消息、Agent可见回复 | 会话事件 + 历史补读 | 制品页面展示多轮对话 |
| 工具开始、工具结果、错误 | 会话事件 + 历史补读 | 展示进度、诊断失败、审计工具使用 |
| 会话状态、取消、完成 | 原生会话控制与事件 | 更新制作实例状态，处理超时/恢复 |
| 正式草稿内容 | `submit_creation_result`回执 | 修改制品草稿，触发来源和修订记录 |

平台必须保存事件位置、去重键和最后一次成功补读位置。实时 WebSocket 断开后，用历史接口补齐；不能因为最终聊天回复出现，就假定前面的工具过程和结果都已保存。

## 四、平台需要新增什么，不需要新增什么

### 1. 首期必须新增的八项能力

| 平台能力 | 最小实现 | 为什么与 DSH 解耦 |
|---|---|---|
| 制品与草稿 | 表格制品、字段定义、草稿行、人工编辑、发布修订 | 内容仍在平台，换 Agent 不丢 |
| 来源关系 | 每个字段/行保存到文档快照和锚点的引用 | Agent不能伪造“有出处” |
| 制作实例 | `creation_instance`绑定制品、输入快照、草稿修订和状态 | Agent会话只是它的一个外部执行记录 |
| 任务票据 | 短期、可撤销、绑定范围与输出结构 | 固定 MCP 无需因任务动态变更 |
| 制作 MCP 工具 | 上述四个工具及其服务端范围校验 | DSH 只使用标准工具，不接数据库 |
| DSH 适配器 | 创建会话、发消息、取消、订阅/补读历史、会话映射 | 以后可替换为别的 Agent 适配器 |
| 过程投影与页面 | 对话、工具活动、问题、回执、草稿差异 | 人不需要进入 DSH 后台 |
| 试用与发布 | 代表问题、人工结论、发布/回退、反馈 | 发布权始终不在 Agent 手里 |

### 2. 首期明确不做的事

- 不开发 DSH 插件、回调服务、业务 Prompt 包或自定义 Agent 框架；
- 不向 DSH 交付平台数据库账号、对象存储管理员凭据或全库 Token；
- 不让 DSH 直接写平台数据库、文件存储或发布正式制品；
- 不为每个制品改变 MCP 地址、工具清单或重新部署 Harness；
- 不先建全行业本体、规则引擎、复杂多 Agent 调度或自动审批；
- 不把 DSH 容器目录中的文件当作正式知识资产。

### 3. 平台内建议的最小边界

第一期可以在现有应用中实现，但代码上最好清楚分为四个模块：

```text
knowledge-product
  ├─ 制品、草稿、发布、来源、试用和反馈
agent-creation
  ├─ 制作实例、任务票据、状态机、提交幂等与并发控制
harness-adapter
  ├─ DSH认证、建会话、发消息、取消、事件跟随和历史补读
creation-mcp
  └─ 制作上下文、受限检索/读取、成果提交、审计与权限校验
```

这四个模块可以同进程、同数据库部署。它们是责任边界，不是立即拆成四个微服务。

## 五、首个试点的接口合同

下面的接口名是平台内部/对前端的建议，不要求与当前 REST 路由同名；MCP 工具名则是后续需要稳定支持的业务合同。

### 1. 平台内部的制作流程接口

| 动作 | 平台内部接口示意 | 结果 |
|---|---|---|
| 创建草稿 | `POST /knowledge-products` | 制品 ID、草稿修订、资料范围和字段定义 |
| 启动制作 | `POST /knowledge-products/{id}/creation-instances` | 实例 ID；平台随后创建 DSH 会话，不把票据交给前端 |
| 发送人类补充 | `POST /creation-instances/{id}/messages` | 写入平台过程记录后转发 DSH 同一会话 |
| 查看过程 | `GET /creation-instances/{id}/events` | 已投影的对话、工具活动、状态与回执 |
| 人工编辑草稿 | `PATCH /knowledge-products/{id}/draft` | 新草稿修订；必要时使旧票据失效 |
| 取消制作 | `POST /creation-instances/{id}/cancel` | 平台撤销票据、停止本地队列、再调用 DSH cancel |
| 试用/发布 | `POST /knowledge-products/{id}/trials`、`/publish` | 保存评价后发布固定修订 |

前端始终调用平台，不直接访问 DSH。这样 DSH 的认证 Cookie、启动 token、内部会话 ID、任务票据不会暴露给浏览器。

### 2. `get_creation_context` 的最小返回

首次不返回全部原文，只返回“这次该做什么”和“可读材料在哪里”。大文档用后续`get_knowledge`按需读取。

```json
{
  "creation_instance_id": "ci_123",
  "product": {
    "id": "kp_abc",
    "type": "specification_table",
    "purpose": "比较产品能力，用于专业问答与方案准备",
    "draft_revision": 3
  },
  "output_contract": {
    "required_fields": ["model", "product_version", "key_specification", "unit"],
    "row_identity_rule": "同一型号和产品版本为同一行",
    "source_required": true
  },
  "inputs": [
    {"document_id": "doc_a", "snapshot_id": "snap_7", "allowed_sections": ["2", "3.1"]}
  ],
  "examples": ["一条人工确认的行或校验案例"],
  "human_decisions": ["容量以额定值为准；不同口径必须列为待确认"],
  "next_action": "先读样例文档，提交不超过十行的第一批结果"
}
```

它不返回其他制品草稿、未选文档列表、平台密钥或无权来源。平台发现当前草稿修订已经变化时，返回明确的“需刷新上下文”结果，而不是让 Agent 按旧定义静默提交。

### 3. `submit_creation_result` 的校验规则

| 校验 | 失败时怎么办 |
|---|---|
| 票据仍有效、实例仍在运行、提交目标匹配 | 拒绝，不写入任何内容 |
| `submission_id`是否已处理 | 返回原回执，保证网络重试不重复写 |
| `based_on_draft_revision`是否当前 | 返回冲突与新的草稿摘要，要求Agent重新读取 |
| 是否符合表格字段和对象规则 | 返回哪些字段不合格 |
| 每个关键值是否有有效来源 | 返回无来源或越权来源的具体行 |
| 人工是否已修改同一行 | 返回待合并差异，不覆盖人工结果 |

成功时平台原子保存：草稿内容、来源关系、提交回执、制作过程引用和新的草稿修订。它们必须一起成功或一起失败，不能出现“页面看到了一行，但没有来源记录”的半成品。

## 六、怎样拿着 DSH 逐步测试，而不是一上来做大联调

测试顺序是从“容器是否能跑”走到“知识制品是否真的可制作”。每一步都有明确输入、输出和失败归属。

| 阶段 | 给 DSH 的输入 | 期待输出 | 这一步验证什么 | 失败通常归谁 |
|---|---|---|---|---|
| T0：独立运行 | 一条非敏感普通消息 | 模型回复 | 容器、内网模型、基础会话 | DSH部署/模型网关 |
| T1：工具连通 | 要求调用固定 MCP 的只读测试工具 | 一次成功工具调用和后续回复 | 固定 MCP 配置、模型工具调用能力 | DSH配置/MCP连通/模型能力 |
| T2：平台范围 | 平台创建测试实例；有效和无效票据各一次 | 有效票据得到限定上下文；无效/越权票据被拒绝 | 制作工具、票据和资料范围 | 平台 MCP 权限实现 |
| T3：单批制作 | 平台启动会话，要求从一份样例资料做 1–3 行 | `submit_creation_result`成功回执；草稿有来源 | DSH会话控制、MCP读取、成果回写 | 平台适配/工具合同/输出校验 |
| T4：多轮协作 | 人修改一个字段含义后继续同一实例 | Agent刷新上下文，提交新草稿修订 | 多轮会话、修订与人工协作 | 平台状态机/前端/适配器 |
| T5：真实小试点 | 3–5份资料、完整字段与代表问题 | 可试用的表格草稿，人工可核验 | 端到端知识制品价值 | 逐项归因，不把问题都算给模型 |
| T6：异常恢复 | 取消、重复提交、权限撤销、DSH重启 | 不越权、不重复写、可补读过程 | 稳定性与治理闭环 | 平台状态/部署/适配器 |

### T0 和 T1：可以先由你直接操作 DSH

这两步的目的只是验证 DSH、内网模型和固定 MCP。可以在 DSH 自带界面中做，但只能使用非敏感测试资料。

建议的 T1 提示词：

```text
调用已注册的知识 MCP，只读取测试资料。
先搜索“测试产品A”，再读取命中的一小段内容。
说明你调用了哪个工具；不要尝试写入或访问其他资料。
```

看到“调用工具 → 得到内容 → 基于内容回复”即可通过。只看到模型口头说“我查到了”，不能算通过。

### T2 以后必须由平台发起

从 T2 开始，不建议手工复制任务票据到 DSH 页面长期测试。正确方式是：平台创建测试制品和制作实例，平台把短期票据发给 DSH 会话，并把过程投影回平台页面。

原因很简单：手工复制无法验证票据怎样签发、取消、脱敏、绑定草稿修订，以及平台怎样拿回过程和成果。T2以后，DSH 页面只作为排障观察工具，不是业务操作入口。

### 每阶段应保留的证据

| 阶段 | 平台应保存的证据 |
|---|---|
| T0/T1 | DSH版本、模型ID、会话创建结果、工具调用成功/失败摘要；不保存敏感token |
| T2 | 制作实例、输入快照、票据签发/拒绝审计、允许/拒绝范围样例 |
| T3/T4 | DSH会话映射、消息与事件位置、工具调用、提交回执、草稿修订、人工修改 |
| T5 | 代表问题、人工正确结果、表格来源核验、补查次数、发布结论 |
| T6 | 取消/重启/重复请求记录、最终草稿状态、是否发生越权或重复写 |

## 七、第一轮的验收线

“DSH 能聊天”不等于“知识制品可制作”。首轮至少同时满足下面四组条件。

### 1. 输入没有串

- abc只选了三份文档时，搜索、列表、统计、正文、章节、表格、下载和来源跳转都不能泄露未选资料；
- 票据缺失、过期、取消，或 abc 票据改成 xyz 制品 ID 时，必须拒绝；
- 资料或字段定义变更后，旧票据不能按旧范围继续提交。

### 2. 过程看得见、接得回来

- 平台能创建 DSH 会话、发起第二轮消息、取消会话；
- 人在制品页面能看到可见对话、工具活动、待确认问题和提交回执；
- 断线后平台能通过原生历史接口补读，事件重试不会重复显示或重复写内容。

### 3. 成果没有绕路

- 聊天最终回复、工作目录文件、Agent附件都不能直接变成正式草稿；
- 只有`submit_creation_result`成功后，表格行和来源关系才出现；
- 重复提交幂等；迟到提交、越权提交、结构错误、来源错误和覆盖人工修改均被拒绝或转为待合并。

### 4. 业务上确实有价值

- 每个抽查字段能打开对应原文；
- 冲突和缺失没有被伪装成确定值；
- 代表问题用这张表的结果不低于人工整理/现有检索基线，并记录人工补查量；
- 通过试用后，网页和 MCP 都能读到同一个发布修订。

## 八、运行安全和恢复的最低要求

DSH 官方明确标注为开发者预览，能够执行模型生成的代码和命令，不能作为唯一安全控制。因此首个试点必须把它当作受控的外部执行环境，而不是可信业务服务。[官方安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-rc.2/SAFETY.md)

- DSH 单独容器、非 root、只挂专用工作卷和会话卷；不挂平台数据库目录、Docker socket、宿主根目录或管理员密钥；
- 模型网关和固定 MCP 是它仅需访问的网络目的地；出站限制由宿主或公司网络实施；
- 首期每个信任范围只运行一个活动制作任务，不把互不信任用户混在同一容器和工作卷；
- 平台拥有任务取消与票据撤销权。调 DSH 的`cancel`后仍必须撤销票据，防止队列中的迟到工具调用写回；
- DSH重启后可从持久化会话历史继续，但无法恢复正在运行的 Python 进程。平台先按提交 ID 和草稿修订核对真实结果，再决定是否重发消息。

## 九、按什么顺序开始实施

1. 部署独立 DSH 容器，配置独立内网模型，完成 T0；
2. 固定注册一个测试知识 MCP，完成 T1，确认内网模型真的支持工具调用；
3. 平台先实现最小表格草稿、资料选择和一份测试制品；
4. 实现`creation_instance`、任务票据、`get_creation_context`和受限搜索/读取，完成 T2；
5. 实现`submit_creation_result`及来源/修订/幂等校验；
6. 实现平台侧 DSH 适配器：会话创建、消息、多轮、事件/历史和取消，完成 T3/T4；
7. 接入制品详情页，再做 T5 真实小试点；
8. 最后补 T6 异常与恢复测试，再决定是否把模式复制到 Wiki、本体或规则。

第一轮结束时，应该得到三样可审查的成果：一张带逐字段来源的表格制品草稿/发布版、一套可复跑的接口与异常测试记录、以及一个可替换 DSH 的平台侧适配边界。没有其中任何一项，都不能说已经打通“Agent 制作知识制品”。
