# 52 · 数据库收敛最终决策与实施部署步骤

> 日期：2026-09-18
> 基线：`worktree-batch3-closure@4242b59`
> 实施分支：`codex/database-convergence-v2`
> 目标：保留历史业务数据，把当前启动链从 72 张表收敛为 52 张正式表，并清理 1 张不在启动链内的历史缓存表；增加 1 张必要的迁移账本表后，目标物理表数为 53。

## 1. 最终结论

1. 当前 default 与全部 domain 已指向同一个物理 PostgreSQL 数据库。本次不是多库合并，而是将唯一旧库完整克隆为一个新库。
2. 宿主机不安装 Python，不更换镜像。迁移代码放入 `knowledge_mining/`，随现有代码增量包同步，再由当前容器中的 Python 执行。
3. `deploy-sync.sh pack/apply` 的用户入口和增量包格式保持不变；只在 apply 的“同步代码”和“重启服务”之间加入迁移计划、执行、验证和配置切换。
4. 新库先完整复制旧库，再只在新库执行数据转换和结构收敛。旧库保持不变并作为回滚副本。
5. 业务服务启动时不再执行 CREATE/ALTER/DROP，不再全量重放历史 SQL。服务只校验数据库 schema 版本，不满足即拒绝 Ready。
6. 新建空库直接使用当前 bootstrap，不创建任何已退役表。存量库通过版本化 migrations 跨版本升级。
7. 普通纯代码版本不动数据库；只要 manifest 出现新的结构迁移，就从当前生产库克隆新目标、迁移并切换。禁止在正在营业的生产库逐条提交 destructive migration，旧库始终是完整回滚点。

## 2. 表数量口径

| 口径 | 数量 | 说明 |
|---|---:|---|
| 51 号批次 3 最新启动表 | 72 | 已含 `user_domains`、`mcp_keys`、`mcp_key_open_kbs`、`kb_purge_tasks`；已摘除旧 MCP 两表 |
| 直接升级的 pre-51 基线 | 48 张保留表 + 退役/兼容表 | 不要求部署 51，但必须是 51 前一版的完整启动结构，不承诺任意古老或残缺库自动跨越 |
| 本次退役 | 21 | 启动链内 20 张 + 历史残留 `serving_query_cache`；代码、DDL、测试和存量数据面同步退役 |
| 正式业务/运行表 | 52 | 新库 bootstrap 的产品目标 |
| 迁移账本 | 1 | `cmkb_schema_migrations`，防重复、支持跨版本和校验码 |
| 最终物理表 | 53 | 52 张正式表 + 1 张必要基础设施表 |

`cmkb_schema_migrations` 不是产品功能表，不接受业务字段扩张。建议字段：

- `migration_id`：全局唯一、带领域前缀，例如 `core/20260918_convergence_v1`；
- `checksum`：迁移文件内容校验码；
- `app_version`：发布版本；
- `applied_at`：成功提交时间；
- `details_json`：源/目标库与校验摘要，不保存密码。

## 4. 不能删除的核心数据

以下数据迁移前后必须保持业务等价：

- 用户、用户域绑定、知识库、成员、目录和文档；
- `asset_storage_objects` 及其 MinIO object key；
- 文档快照、文档—快照 link、原始段落；
- 每个 KB 当前最新有效完整 Build 与选片；
- v2 final/staging 八族及来源定位；
- 当前 Build 的来源 Run、必要的最新 Run 和事件链；
- Workflow、MCP 多钥匙、一张网、删除任务；
- LLM 运行时和 Java 检索范式表。

MinIO 字节不随 PostgreSQL 克隆重复复制，也不因退役表 DROP 被删除。迁移只验证数据库引用与对象抽样 HEAD。

## 6. 增量同步接入

用户命令不变：

```bash
bash deploy-sync.sh pack
bash deploy-sync.sh apply sync-YYYYMMDD-HHMMSS.tar.gz
```

首次从旧部署脚本进入 52 号版本时，内网必须先用本分支的 `deploy-sync.sh`
替换旧脚本（脚本本身不需要 Python或新镜像）。原因是旧 apply 不认识数据库迁移钩子。
从这一次开始，`deploy-sync.sh` 会随增量包携带，并只在整次发布健康检查成功后
同 inode 自更新；后续仍只需原来的 pack/apply 命令。

apply 内部流程改为：

```text
校验并解包
→ 按现有规则同步 knowledge_mining/databases/Java jar/前端
→ 容器内执行 database_upgrade plan
→ 无待办迁移：沿用现有重启逻辑
→ 有待办迁移：保存旧代码快照并暂停写入服务
→ database_upgrade apply
→ database_upgrade verify
→ 成功后原子切配置
→ control → llm_service → mining → serving → mcp 顺序启动
→ 业务冒烟
```

容器内命令由 `deploy-sync.sh` 自动执行：

```bash
docker compose exec -T app python -m knowledge_mining.mining.maintenance.database_upgrade plan
docker compose exec -T app python -m knowledge_mining.mining.maintenance.database_upgrade apply
docker compose exec -T app python -m knowledge_mining.mining.maintenance.database_upgrade verify
```

普通增量包仍不得携带 `main_control_service/config/` 或 `.env`。只有数据库迁移器在全部验证成功后，才可修改内网现有数据库地址。

## 7. 本次新库迁移步骤

### 7.1 预检

1. 读取 `database.yaml.default` 和全部 domain 连接，规范化 host/port/dbname/user 后去重。
2. 必须确认只有一个源物理数据库；发现多个源库立即失败，不自动合并。
3. 检查目标库名称、磁盘空间、PostgreSQL 权限和 `pg_trgm`/`vector` 扩展。
4. 检查 queued/running 的 Mining、Purge 和 LLM 任务；有活动写任务默认停止迁移。
5. 获取固定 PostgreSQL advisory lock，防止两个部署同时迁移。
6. `CREATE DATABASE` 使用部署时临时注入的 `CMKB_MIGRATION_PG_USER` / `CMKB_MIGRATION_PG_PASSWORD`；不得把 CREATEDB 权限授给长期业务账号，也不得把管理员密码写入 YAML 或日志。

### 7.2 暂停写入与克隆

1. 按 `mcp → serving → mining → llm_service` 暂停服务；control/nginx 可保留维护页。
2. 等待并确认源库业务连接归零。
3. 同实例使用 `CREATE DATABASE <target> WITH TEMPLATE <source>` 完整克隆。
4. 目标库已存在时一律不复用、不覆盖：显式目标直接失败；自动目标改用新的 UTC 时间后缀重新克隆。失败目标库保留供排查，避免把陈旧副本误切为生产。

### 7.3 目标库转换

1. 创建迁移账本并登记 legacy 基线。
2. 按 manifest 顺序执行未登记迁移；每步在事务中写业务变更和账本。
3. 回填 `user_domains`，非 admin 活跃用户零绑定数必须为 0。
4. 回填 MCP 新表：pre-51 源逐旧 `key_hash` 迁移；已部署 51 的源按旧钥匙所属用户核对覆盖，新表中的轮换 hash、吊销状态和工具范围以线上现状为准，不得被冻结旧表反向覆盖。
5. 验证所有保留表后，按 FK 依赖顺序 `DROP TABLE ... RESTRICT` 退役 21 张表。
6. 删除只服务于退役能力的列、索引、CHECK、Java/Python 查询契约。
7. 用 `pg_get_indexdef` 校验真实索引定义；同名错误索引必须显式 DROP/CREATE。

### 7.4 验收

1. 保留表逐表行数与主键集合一致；大表使用分块 checksum。
2. 每个 KB 当前 serving 文档—快照集合与源库一致。
3. 当前快照的 v2 units/readiness/source locators 完整；需要向量的 embeddings 完整。
4. FK、NOT NULL、CHECK、唯一索引和部分唯一索引与 bootstrap 一致。
5. MinIO 登记数量一致，并抽样检查对象存在。
6. 目标物理表精确为 53，21 张退役表全部不存在。
7. 对目标重复执行 apply/verify，必须成为无副作用 no-op。

`plan` 在停服务和克隆前输出 `bridge_preflight` 四项计数（信息性，按裁定兜底迁移，不阻断）：

- `cross_domain_keys`：跨 domain 旧钥匙数——迁移时取开放库最多的 domain，并列取字典序第一（51 号原裁定）；
- `zero_binding_users`：推不出 domain 的普通用户数——自动绑定默认 domain（`domain_registry.yaml` 未配置 `default_domain` 时取第一个启用 domain），apply 输出 `fallback_domain_binds` 计数；
- `retired_tool_config_keys`：含退役工具名的旧配置数——按改名映射归并、剔除无法映射的名字；
- `discarded_open_grants`：指向失活/已删除 KB 或跨 domain 被丢弃的旧授权数——丢弃但逐条进入 apply 输出的 `dropped_grants` 留档。

（2026-09-21 裁定修订：以上四项由「非 0 拒绝」改为「兜底迁移+输出留档」——内网单 domain 场景下拒绝语义会阻断唯一升级路径。真正损坏的状态仍拒绝，见 §8.10。）

### 7.5 配置切换

1. 把当前配置备份到权限受限的迁移备份目录。
2. 原子修改 `database.yaml.default.dbname` 为目标库。
3. 删除各 domain 重复的 inline `database` 块，让它们统一回落 default。
4. 保留顶层 `default_domain` 和全部业务配置；不得复用会丢顶层字段的保存方法。
5. 日志不得输出数据库密码或完整 DSN。

### 7.6 启动与回滚

1. 依次启动 control、llm_service、mining、serving、mcp。
2. 完成上传、覆盖、挖掘（含 SKIP/部分失败）、FTS、向量、结构、来源回溯、MCP、删除任务冒烟。
3. 失败时恢复配置备份并重启回旧库；目标库保留用于排查，不自动覆盖。
4. 旧库改为只读并至少保留 30 天；删除旧库必须是独立人工动作。

## 8. 幂等与多版本跨度

1. 发布过的 migration ID 和文件内容不可修改。
2. 已登记且 checksum 一致：跳过；checksum 不一致：失败并人工处理。
3. 数据回填按业务唯一键 UPSERT，或采用“先比对、再插入”的可重入逻辑。
4. 数据库没有账本时，先按精确表名集合识别受支持的 pre-51/51 基线；缺表或出现未声明的历史表都在克隆前停止，禁止猜版本。
5. 对已纳入 manifest 的后续版本，可按依赖顺序执行所有缺失迁移；不要求逐版本部署应用代码。当前首次收敛只承诺“完整 pre-51 或 51 → 52”单跳，不承诺任意古老版本。
6. 大版本可以重新生成 current bootstrap，但旧 migrations 只能归档，不能改写；支持范围外的未知旧库必须走显式 bridge。
7. 52 自带 pre-51 bridge：源库必须具备 51 前一版的 48 张完整保留表，但不要求先部署51。bridge 只在克隆目标执行，补建并回填 `user_domains`、`mcp_keys`、`mcp_key_open_kbs`、`kb_purge_tasks`，随后继续52索引修复和退役迁移。
8. 旧 MCP 钥匙若同时开放多个 domain，按“开放库最多的 domain，并列取字典序第一”选域，其余授权丢弃并进 `dropped_grants` 留档（2026-09-21 裁定修订：由“停止并要求显式处理”改为兜底迁移，内网单 domain 场景拒绝语义会阻断唯一升级路径）。
9. 52 上线后删除 `backfill_user_domains.py`、`backfill_mcp_keys.py`、`drop_legacy_mcp_tables.py`，运维只保留 `database_upgrade plan/apply/verify` 一个入口。
10. 旧表只存在一半、新 MCP 表只存在一半、或 51 回填漏掉了某个旧钥匙所属用户，均视为损坏的半升级状态并拒绝自动猜测。
11. MCP 对外权限只允许 `search_knowledge`、`get_knowledge`、`upload_document`：历史读取别名归并为 `get_knowledge`；剔除退役名后映射为空的配置按 51 号原裁定记 `NULL=全部开放`（2026-09-21 裁定修订）；`open_tools` 结构损坏（非数组）、孤儿用户、重复 key_hash、未知 domain 仍然拒绝迁移。

## 9. 服务启动新契约

Mining、LLM 和 Java 的启动 DDL 初始化器全部退出生产启动路径，替换为 schema contract 检查：

- 数据库版本低于应用要求：服务启动失败，提示运行 `deploy-sync.sh apply`；
- 数据库版本高于应用支持：旧应用拒绝启动，防止误回滚代码；
- 表、扩展或关键索引缺失：拒绝 Ready；
- 检查只读，不做任何 DDL；
- Java 初始化异常不得再吞掉后继续启动；
- LLM 不得再清理其他服务的长连接。

测试环境可显式调用 bootstrap fixture 建库；生产 repository 和业务热路径禁止发 DDL。

## 10. 表与代码一一对应的退役门禁

每张退役表必须同时满足：

1. Python 无生产 SQL 读写；
2. Java mapper 无表名引用；
3. MCP/LLM 无直接或间接消费；
4. 新 bootstrap 不创建；
5. 存量 migration 显式 DROP RESTRICT；
6. reset/export/统计/测试夹具已更新；
7. 新旧数据库业务等价测试通过；
8. 静态测试断言启动链和生产代码不再出现表名。

不能只删 SQL 文件，也不能只删物理表。

## 11. 发布切分

### A. 兼容代码与迁移框架

- 引入账本、runner、plan/verify 和 schema contract；
- 引入 deploy-sync 条件迁移钩子；
- 保持旧库可运行；
- 测试先行，不 DROP 数据。

### B. 生产读写退役

- 删除 21 张表的 Python/Java/MCP 消费；
- 切换所有正式路径到保留表；
- 清理测试和辅助脚本；
- 服务仍可连接旧库中的多余表，但不使用它们。

### C. 新库收敛迁移

- 克隆、转换、严格验证、DROP、配置切换；
- 新库成为唯一写库；旧库只读保留。

### D. 启动 DDL 退役与 current bootstrap 定版

- Mining/LLM/Java 启动只验版本；
- 空库从 current bootstrap 初始化；
- 测试断言退役表不会复活。

## 12. NON-GOALS

- 本次不删除 MinIO 对象字节。
