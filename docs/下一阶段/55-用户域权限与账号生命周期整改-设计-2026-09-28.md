# 55—用户、域权限与账号生命周期整改设计

> 日期：2026-09-28  
> 状态：实现完成，自动化门禁通过；等待真实 PostgreSQL 与人工 UAT  
> 适用范围：用户管理、域管理员、知识库权限、MCP 钥匙、前端退出、增量部署脚本  
> 原则：在现有 `kb_users` / `user_domains` / `knowledge_bases` / `kb_members` / `mcp_keys` 模型上渐进修复，不另建认证、权限或导入平台。

## 1. CAPABILITY

本批让站点管理员、域管理员和普通用户在现有权限模型中获得完整且一致的账号生命周期：域管理员授权时安全设密，域管理员可发现并添加本域成员，站点管理员可清退和恢复用户，用户可删除已吊销的 MCP 钥匙，CSV/XLSX 可批量导入普通账号或域成员；同时补齐禁用、管理员降级、域解绑、MCP 验钥、退出竞态和部署脚本自更新中的一致性缺口。

本批不是重建一套用户中心。身份源仍是 `kb_users`，域角色仍在 `user_domains`，KB 局部角色仍由 `owner_id` / `kb_members` 表达，MCP 仍使用当前单用户、单域、多钥匙模型。

## 2. 已确认的现状

### 2.1 当前数据与权限分层

```text
kb_users
  ├─ site_role: member | admin
  ├─ status: active | disabled
  └─ password_hash

user_domains
  ├─ user_id
  ├─ domain
  └─ domain_role: member | admin

knowledge_bases
  └─ owner_id

kb_members
  └─ role: editor | viewer

mcp_keys
  ├─ user_id
  ├─ domain
  └─ status: active | revoked
```

权限从外到内为：

```text
站点角色 → 域角色/域绑定 → KB owner/member/public → 具体操作
```

除站点管理员外，`user_domains` 是 owner、KB member 和 public 可见性的共同外层边界。

### 2.2 可复用的现有实现

| 能力 | 现有实现 | 本批处理方式 |
|---|---|---|
| 用户 CRUD、密码、启停 | `UserService`、`routes/auth.py`、`KbDB` | 扩展，不平行新建 service |
| 域角色 | `user_domains.domain_role`、`set_domain_grants()` | 保留二值角色，只补原子设密授权 |
| 域管理员检查 | `can_manage_domain()`、`_require_domain_manager()` | 复用并补 active 不变量 |
| 域解绑清理 | `_unbind_domain_on_conn()` | 复用成员删除和 MCP 吊销逻辑 |
| KB 权限 | `is_visible()`、`can_write()`、`can_restore()` | 收口状态检查，不引入权限引擎 |
| KB 候选用户 | 现有 member candidate 查询模式 | 复用最小字段投影构造域候选搜索 |
| MCP 生命周期 | `McpKeyService`、revoke/rotate、owner 检查 | 增加删除记录，不新建 MCP 服务 |
| Excel 解析 | 项目已有 `openpyxl`，Python 有 `csv` | 建用户专用导入协调层，不建通用 ETL |
| 前端会话 | auth/domain stores、Axios 拦截器、`usePolling()` | 补退出代次和多标签同步 |
| 增量部署 | stage、备份、健康检查、自更新 | 只修复执行中覆盖自身 |

### 2.3 已确认缺口

1. `domain_admin_requires_password` 是正确的安全门槛，但前端未提供一体化设密授权。
2. 用户只有启用/禁用，没有清退、已删除列表和恢复能力。
3. 域管理员只能输入准确用户名，缺少可添加用户候选搜索。
4. 用户 CSV/XLSX 导入不存在。
5. 用户退出时旧页面 watcher/轮询可能在 token 清除后继续请求并显示 `unauthenticated`。
6. 多标签页退出不同步。
7. disabled 用户的 MCP Key 验证未完整检查用户状态。
8. 站点管理员降级可能产生无同域绑定的 KB owner。
9. 域用户逐项移除可能把 active 普通用户变为零域用户。
10. 用户拥有 KB 时解绑会被正确阻断，但系统没有 owner 转移入口。
11. disabled 用户可能通过直接 API 被加入 KB。
12. 非法 KB member role 可能下沉为数据库异常，而非稳定 4xx。
13. MCP 只有吊销，没有删除已吊销记录的入口。
14. `deploy-sync.sh` 在执行中同 inode 覆盖自身，跨版本时可能继续解析新版中间字节。
15. 用户创建把所有唯一约束冲突都映射成“用户名重复”，未区分理论上的 ID 碰撞。

## 3. CONSTRAINTS

### 3.1 固定业务规则

1. 站点管理员全域通行，不写 `user_domains`。
2. active 非站点管理员必须至少有一个有效域绑定。
3. 域管理员必须是密码账号；真实 SSO 上线前不得放宽。
4. 域管理员只能管理自己作为 `domain_role=admin` 的域。
5. 域管理员只能给当前域添加普通成员，不能授予域管理员、站点管理员或操作其他域。
6. disabled 是可恢复暂停：保留域、KB 关系和 MCP 配置，但所有 Web/API/MCP 实时访问必须拒绝。
7. deleted 是永久清退：权限、成员关系和 MCP 全部清除；数据库身份记录保留。
8. 用户名在删除后继续保留，不能被新身份复用。
9. 恢复 deleted 用户沿用原 ID，但不恢复旧域权限、KB 关系或 MCP Key。
10. 任何仍保留数据库行的 KB owner 在用户清退前必须先转移；active KB owner 在域解绑前必须先转移。
11. MCP 明文永不落库；轮换、吊销和删除都不能恢复旧明文。
12. 用户导入不接受外部 ID、密码或管理员角色。
13. 所有权限判断以数据库当前状态为准，不能因进程本地身份缓存导致禁用窗口。

### 3.2 安全边界

- 域候选搜索只返回 `id`、`username`、`display_name` 和当前域是否已绑定。
- 域管理员不可看到候选用户的密码状态、其他域、系统角色详情或 MCP 信息。
- 用户清退、恢复、站点角色变更和全局导入只允许站点管理员。
- MCP 删除只允许 Key 所有者；非本人统一按不存在处理。
- 导入文件限制 5 MB、5,000 行，仅支持 CSV/XLSX。
- 导入中的公式单元格不得作为用户名、显示名或域值执行/求值。
- 任何密码、JWT、MCP 明文不得进入导入文件、响应日志和错误报告。

### 3.3 一致性不变量

- active 非站点管理员：`count(user_domains) >= 1`。
- active owner/editor/viewer：必须存在 KB 所在域的 `user_domains`。
- `domain_role=admin`：用户必须有 `password_hash` 且状态可登录。
- MCP Key 生效：Key active、未删除、用户 active、用户仍具备 Key 对应域访问资格。
- owner 转移目标：active、非 deleted、同域绑定；不能转给跨域用户。
- 删除用户：不能是当前操作者，不能导致 active 站点管理员归零，不能仍拥有 active KB。

## 4. IMPLEMENTATION CONTRACT

### 4.1 用户状态模型

为保持对现有 `status IN ('active','disabled')` 的最大兼容，不新增第三个数据库 status 值。逻辑状态定义为：

| 逻辑状态 | 数据表示 | 是否登录 | 是否保留权限数据 |
|---|---|---:|---:|
| active | `status='active' AND deleted_at IS NULL` | 是 | 是 |
| disabled | `status='disabled' AND deleted_at IS NULL` | 否 | 是 |
| deleted | `status='disabled' AND deleted_at IS NOT NULL` | 否 | 否 |

新增最小字段：

```text
kb_users.deleted_at          TIMESTAMPTZ NULL
kb_users.deleted_by_user_id TEXT NULL
```

不为 `deleted_by_user_id` 增加 FK，避免删除/恢复历史产生循环约束；该字段仅用于审计展示。

#### 禁用

- 保留密码、域绑定、KB 成员关系和 MCP 配置。
- 所有实时身份校验和 MCP 验钥拒绝。
- 重新启用后原权限恢复。

#### 删除/清退

在一个业务事务中：

1. 锁定目标用户并重新校验操作者、self/last-admin 等守卫。
2. 若目标仍拥有 active KB，返回冲突和有界 KB 清单，不做部分修改。
3. 设置 `status='disabled'`，清空 `password_hash`，写 `deleted_at/deleted_by_user_id`。
4. 删除 `kb_members` 中该用户的成员边。
5. 删除全部 `user_domains`。
6. 将全部 active MCP Key 置为 revoked，并标记为删除记录。
7. 失效身份缓存。

deleted 用户默认不出现在用户列表；站点管理员可切换“已删除用户”。

#### 恢复

1. 仅站点管理员可恢复。
2. 清空 `deleted_at/deleted_by_user_id`，保留 `status='disabled'`。
3. 不恢复域、KB member、MCP Key 或密码。
4. 站点管理员重新分配至少一个域并按需设密后，才能启用。

### 4.2 用户身份和重复规则

- 用户 ID 继续由服务端 `uuid.uuid4().hex` 生成。
- API 和导入文件不允许调用方提供 ID。
- deleted 用户的 ID 和 username 永久保留。
- 创建相同 username 返回稳定的 `username_reserved`，提示恢复原用户。
- 恢复使用原 ID，不创建新记录。
- 真正新用户必须使用不同 username 和新 ID。
- ID 主键碰撞时有限重试生成；按约束名区分 username 冲突与 ID 冲突。

### 4.3 域管理员设密授权

复用现有域授权弹窗和 `set_domain_grants()`：

- 用户已有密码：按现有方式保存域角色。
- 用户无密码且新授权包含 `domain_role=admin`：同一弹窗出现初始密码字段。
- 后端在一个事务中完成密码哈希写入和域角色更新。
- 任一步失败不得留下“已设密码但未授权”或“已授权但无密码”的中间态。
- API 不返回密码，日志不得记录请求中的密码字段。

### 4.4 域用户候选和批量添加

新增当前域候选搜索，复用现有 KB member candidate 的最小投影模式：

```text
输入：domain、query、page/cursor、page_size
输出：id、username、display_name、already_in_domain
```

候选范围：

- active、非 deleted；
- `site_role='member'`；
- 可按 username/display_name 前缀或包含搜索；
- 不返回其他域或密码信息。

域管理员添加时角色固定为 member。重复添加应幂等，不提升角色。

### 4.5 KB owner 转移

在现有 `KbService` 中增加 owner 转移，不创建独立资源模型：

- 允许：站点管理员、当前域管理员、当前 owner。
- 目标必须 active、非 deleted、绑定 KB 所在域。
- 转移与必要的 member 边调整在一个事务中完成。
- 原 owner 是否保留为 editor 由调用方显式选择，默认不自动新增权限。
- 用户清退/域解绑的冲突响应应提供可跳转的 owned KB 列表。

### 4.6 站点管理员降级

管理员降级为 member 前：

1. 保留该账号已有的普通域绑定。
2. 收集其拥有的全部 retained KB 域，并自动补为普通域绑定，避免降级后产生无域绑定 owner。
3. 若已有绑定与 owned KB 域的并集为空，则自动绑定 registry 的默认域。
4. 在一个事务中先补齐上述域绑定，再写 `site_role='member'`；调用方无需先手工分配域。

这是有意的兼容行为：降级不会因缺 owned-domain 绑定而拒绝，但必须在同一事务内补齐，
不允许先降级、再依赖后台修复硬域边界。

### 4.7 域解绑和零域

- active 普通用户不能通过任何入口被解绑至零域。
- 若目标仍拥有该域 active KB，继续返回 `domain_has_owned_kbs`。
- 成功解绑继续复用现有逻辑：删除本域 KB member 边、吊销本域 MCP Key、删除域绑定。
- deleted 用户清退不受“至少一个域”限制，因为最终会删除全部绑定。

### 4.8 MCP 生命周期

保留现有状态，增加软隐藏字段：

```text
mcp_keys.status: active | revoked
mcp_keys.deleted_at TIMESTAMPTZ NULL
```

状态转换：

```text
active --rotate--> active（旧明文失效）
active --revoke--> revoked
revoked --delete--> revoked + deleted_at
```

规则：

- active Key 不提供“删除记录”，必须先吊销。
- revoked Key 显示“删除记录”。
- 删除后默认列表不显示，但数据库保留审计行。
- Key 校验必须显式要求 `m.deleted_at IS NULL`、`m.status='active'` 和 `u.status='active' AND u.deleted_at IS NULL`。
- 用户清退时所有 Key 原子吊销并标记删除。
- 删除后可创建同名 Key，新 Key 使用新 ID、新 hash 和新明文。

### 4.9 CSV/XLSX 导入

不建导入任务表、队列、临时文件库或通用映射引擎。

#### 站点管理员模板

```text
username,display_name,domain
zhangsan,张三,generic
zhangsan,张三,odn
lisi,李四,generic
```

规则：

- 新 username：创建普通用户并添加 member 域绑定。
- 已存在 active 普通用户：只补缺失的 member 域绑定。
- disabled、deleted、站点管理员：列为冲突，不自动改动。
- 不导入密码、site admin 或 domain admin。
- 同一用户多域使用多行，服务端归并后验证。

#### 域管理员模板

```text
username
zhangsan
lisi
```

- 只能绑定已有 active 普通用户到当前域。
- 不能创建账号、修改显示名、提升管理员或传入其他域。

#### 调用方式

采用同一专用端点的 `dry_run=true|false`，前端保留所选文件供确认后再次提交：

1. dry-run：解析、规范化、校验，零数据库写入。
2. 前端显示新增、补绑定、跳过和错误行。
3. apply：重新解析并重新校验，在一个事务中提交。

不保存服务端 preview token，不引入 staging 表。

### 4.10 退出生命周期

复用现有 auth/domain stores、轮询 composable 和 Axios 客户端：

- auth store 增加 `loggingOut` 和会话 generation。
- 退出开始即停止/失效轮询和后续状态写入。
- domain watcher 在无 token、无用户、空域或 `loggingOut` 时不发请求。
- 在途请求晚到时，generation 不匹配则丢弃结果；退出过程中的 401 不弹 toast。
- 跳转使用 `router.replace('/login')` 并等待完成。
- 监听 localStorage `storage` 事件，多标签同步清状态和停止轮询。
- 保持现有原则：登录期间普通代理 401 不自动摧毁整个会话；只有 `/auth/me` 明确 401 或跨标签 token 删除才退出。

本批不引入服务器端 JWT 黑名单或 session 存储。

### 4.11 部署脚本自更新

保留现有 pack/apply、stage、备份、数据库迁移和健康检查顺序。修改执行方式：

- apply 入口先把当前脚本复制到安全临时 worker，再由 worker 执行完整发布。
- 健康检查通过后，worker 同 inode 更新仓库中的 `deploy-sync.sh`。
- 正在执行的 Bash 不再读取被覆盖的原脚本。
- 更新后运行 `bash -n deploy-sync.sh` 和内容校验。
- 自更新失败不得反向标记已成功的数据库/服务操作；应给出明确的“业务发布成功、脚本更新失败”状态和恢复指令。

## 5. 权限矩阵

| 操作 | 站点管理员 | 当前域管理员 | KB owner | editor | viewer |
|---|---:|---:|---:|---:|---:|
| 管理全局用户 | 是 | 否 | 否 | 否 | 否 |
| 管理当前域普通成员 | 是 | 是 | 否 | 否 | 否 |
| 批量创建普通用户 | 是 | 否 | 否 | 否 | 否 |
| 批量添加当前域已有用户 | 是 | 是 | 否 | 否 | 否 |
| 查看当前域全部 active KB | 是 | 是 | 否 | 否 | 否 |
| 写 KB 内容 | 是 | 是 | 是 | 是 | 否 |
| 删除/恢复 KB | 是 | 是 | 是 | 否 | 否 |
| 转移 KB owner | 是 | 是 | 是 | 否 | 否 |
| 管理自己的 MCP Key | 是 | 是 | 是 | 是 | 是 |

Editor 是否继续管理 KB 成员是唯一尚未冻结的既有行为，见第 10 节。

## 6. 接口变更草案

接口命名在实施前可按现有路由风格微调，但不得改变权限边界。

| 方法与路径 | 调用者 | 语义 |
|---|---|---|
| `PUT /api/kb/admin/users/{id}/domain-grants` | 站点管理员 | 扩展现有接口；缺密码时可携带一次性初始密码并原子授权 |
| `GET /api/kb/domains/{domain}/user-candidates` | 站点/当前域管理员 | 最小字段候选搜索 |
| `POST /api/kb/{kb_id}/transfer-owner` | 站点/当前域管理员/owner | 同域 owner 转移 |
| `GET /api/kb/admin/users/{id}/deletion-preview` | 站点管理员 | 返回 owned KB、域、KB member、MCP 数量 |
| `DELETE /api/kb/admin/users/{id}` | 站点管理员 | 清退用户；请求含确认用户名 |
| `POST /api/kb/admin/users/{id}/restore` | 站点管理员 | 恢复为 disabled 空权限账号 |
| `GET /api/kb/admin/users?include_deleted=true` | 站点管理员 | 已删除用户列表 |
| `POST /api/kb/admin/users/import?dry_run=...` | 站点管理员 | 普通用户 CSV/XLSX 预检/导入 |
| `POST /api/kb/domains/{domain}/users/import?dry_run=...` | 当前域管理员 | 已有用户批量加入本域 |
| `DELETE /api/kb/users/me/mcp-keys/{key_id}` | Key owner | 仅删除已 revoked Key 的显示记录 |

### 稳定错误码

至少提供：

```text

user_deleted
user_not_active
last_active_admin
cannot_delete_self
user_owns_active_kbs
owner_target_not_domain_bound

cannot_manage_domain_admin
mcp_key_must_be_revoked_before_delete
invalid_member_role

```

前端必须映射为中文业务提示，不直接展示内部错误字符串。

## 7. 数据库迁移与兼容

### 7.1 最小迁移

新增：

```text
kb_users.deleted_at
kb_users.deleted_by_user_id
mcp_keys.deleted_at
```

并补充相关筛选索引；不重建用户表，不改变现有 PK/FK，不新增角色表。

### 7.2 迁移分类

上述均为 nullable 字段扩展，设计为 `online_expand`：

- 1.1.11 已在 `kb_db_converged` 时原库在线迁移；
- 不为本批轻量字段新增触发双库 rebase；
- 迁移幂等并带 checksum；
- 新增字段前先铺兼容读取，再启用写入。

### 7.3 回滚

- 新字段保留，不做破坏性回滚。
- old code 不认识 `deleted_at`，但 deleted 用户仍保持 `status='disabled'`，因此不会重新登录。
- revoked/deleted MCP 在 old code 下最多重新出现在列表，仍不能验钥。
- 若已发生用户清退，回滚到旧 UI 后禁止重新启用带 `deleted_at` 的用户；部署回滚手册必须明确这一点。

## 8. 可观测与运维

- 用户删除预检显示 owned KB 数、域数、KB member 数、active/revoked MCP 数。
- 导入结果记录请求操作者、文件摘要、总行数、成功/跳过/失败计数；不保存文件和敏感内容。
- 用户禁用、删除、恢复、角色变更、owner 转移和 MCP 删除写结构化审计日志。
- 日志不记录密码、JWT、MCP 明文或完整导入行。
- 数据库升级 `plan/apply/verify` 输出本批迁移 ID和 mode。

## 10. 已冻结的兼容决策

### Editor 是否管理 KB 成员

当前 Editor 因复用 `can_write()` 可以增删 KB 成员。这是既有行为，不属于确定的程序错误。本批保持该语义，不借生命周期整改改变现有授权；若后续要收口为“Editor 只管理内容”，应单独立项并做兼容评估。

本设计已无阻塞实施的产品问题。

## 11. NON-GOALS

本批明确不做：

- 新认证中心、SSO 接入或外部 IAM；
- JWT 黑名单、Redis session 或服务端 logout；
- 动态 RBAC 表、角色编辑器或通用权限引擎；
- 物理删除用户及用户名复用；
- 通用导入/ETL 平台、导入队列、staging 表或文件长期存储；
- MCP Key 恢复、明文找回或通用密钥管理服务；
- 通用事件溯源、审计微服务；
- 因本批 nullable 字段扩展触发离线双库重建；
- 改变 Editor 的成员管理语义。
