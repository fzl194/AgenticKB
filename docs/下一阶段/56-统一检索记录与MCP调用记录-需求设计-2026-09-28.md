# 56—统一检索记录与 MCP 调用记录需求设计

> 日期：2026-09-28  
> 状态：需求已定案，端到端增量实施中  
> 适用范围：Java Serving 检索记录、MCP Tool 调用记录、Mining 查询 API、前端首页/系统状态/知识库检索页面、数据库版本化迁移、`deploy-sync.sh` 增量发布  
> 依赖基线：55 号用户域权限与账号生命周期设计、52 号数据库收敛与版本化升级机制

## 0. ELI5 对齐：旧账本与新账本

把调用记录想成两本账本：

- 旧账本是 `serving_query_logs`。它记的东西太少，没有用户、MCP Key、Tool、真实来源和可靠的失败状态。已部署环境中的全部旧记录已被明确确认为无保留价值。
- 新账本是 `knowledge_access_records`。它从本能力上线后从零开始，统一记录网页检索、API 检索和 MCP 三个 Tool 的调用。

本次升级的做法是：

1. 先完整复制当前生产数据库到现有双库轮换目标；
2. 在目标库建一本空的新账本；
3. 不抄旧账，直接删除目标库中的旧账本；
4. 验证其他业务数据完整后，切换到新库并启动新代码；
5. 旧数据库仍按 52 号方案作为回滚副本暂时保留，不再承载新流量。

上线后的规则是：

> 后续版本升级可以给新账本加列、加索引或做有明确规则的数据迁移，但不得因为部署而 `DROP`、`TRUNCATE` 或全量 `DELETE` 新账本。

这条规则仅限制“版本部署”。未来若需要产品化的保留期、用户删除或合规清理，必须另行立项并明确范围，不得夹带在普通 `sync.sh` 升级中。

## 1. CAPABILITY

在当前知识库平台中新增左侧一级“检索记录”功能，以一条用户可感知的调用为一条记录，统一呈现：

- 知识库页面的实时检索；
- 普通 API 检索；
- MCP `search_knowledge`；
- MCP `get_knowledge`，包括证据读取、文档读取、结构导航、结构化查询和库/文档浏览；
- MCP `upload_document`，包括票据签发与最终上传结果的可关联留痕。

功能上线后，用户不再只能看到少量汇总图表，而是能从汇总下钻到单次调用，查明谁、从哪个入口、调了什么、针对哪些知识库、是否成功、是否零结果以及耗时多少。

## 2. 已确认的现状和问题

### 2.1 旧 Java 记录不可继续演进

`serving_query_logs` 当前只由 Java `QueryLogAspect` / `QueryLogService` 写入，存在以下已确认问题：

- 没有 `user_id`、`mcp_key_id`、`tool_name`和真实 `source`；
- `channel` 是发布通道，不是 Web/MCP/API 来源；
- `intent` 被固定写为 `evidence`，keywords/entities/scope/issues/relations 等字段基本为空；
- 失败调用与正常零结果都会落成 `result_has_result=false`；
- 没有请求目标 `kb_ids`，零结果时无法判定查过哪个库；
- 没有 MCP `get_knowledge` / `upload_document` 的统一记录；
- 日志写入失败仅 warning 后吞掉，不是可查询的完整业务记录。

产品裁定：已有旧记录不回填、不导出、不兼容展示，可在本能力切换版本中全量删除。

### 2.2 现有前端只有分散汇总

- 首页 `OpsPanel` 已包含 KPI、零结果原文、趋势和范式排行，体量过重；
- “设置 → 系统状态”内还有一份更完整的检索分析；
- 知识库“检索”Tab 只能做实时检索，没有历史记录；
- 不存在逐条记录、分页、筛选和单次调用详情。

### 2.3 部署基线

- 当前发布基线为 1.1.11；目标发布版本由实施时 `releases.json` 决定，不在需求文档中抢占版本号。
- 52 号收敛后，default 和全部 domain 指向同一物理 PostgreSQL；新表不引入独立日志库，`domain` 作为逻辑隔离与查询维度。
- 业务服务启动期只读校验 schema 版本，不允许启动时建表或修表。
- 数据库变更必须通过 `databases/migrations/manifest.yaml` 和 `database_upgrade plan/apply/verify` 执行。

## 3. CONSTRAINTS

### 3.1 固定产品规则

1. 左侧新增一级“检索记录”入口，作为唯一完整版记录页。
2. 首页保留瘦身的检索摘要，不保留原文清单和完整分析图。
3. “设置 → 系统状态”的检索使用分析整块迁出，该 Tab 只保留服务状态、重启与知识资产。
4. 知识库详情不再新增顶层 Tab；现有“检索”Tab 内增加“在线检索 / 检索记录”二级切换。
5. KB 内“检索记录”复用全局记录表组件，强制固定当前 `kb_id`，不复制数据、API 或统计口径。
6. MCP 接入页只增加“查看调用记录”深链，不再实现一套历史列表。
7. 旧 `serving_query_logs` 数据不迁移到新表；新页面从切换时刻开始计数。
8. 活跃数据库中的旧 `serving_query_logs` 必须被物理删除，后续空库 bootstrap 不得再创建它。
9. 新 `knowledge_access_records` 从切换上线后为必须保留表；未来版本的普通部署和 schema 升级不得清空该表。
10. 本能力不新增 Python、JavaScript 或 Java 依赖，不修改 `pyproject.toml`、`kb-ui/package.json`、`kb-ui/package-lock.json`、`agent_serving_java/pom.xml` 的依赖集合。
11. 部署必须使用现有 `deploy-sync.sh pack/apply`，不使用 `deploy-build.sh`，不重建或替换 Docker 镜像。
12. 权限只复用 55 号实施后的 `current_user`、用户域绑定、域管理与 KB 可见性逻辑；本文不新增角色、capability 或权限引擎。
13. `deploy-sync.sh` 是稳定的部署级基础设施；本需求只使用其现有 pack/apply 与数据库迁移钩子，不修改脚本的打包、同步、迁移、重启、健康检查或自更新逻辑。

### 3.2 数据不变量

- 一次用户可感知调用只记一条主记录，不因内部 HTTP 转发、范式执行或结果整形重复计数。
- 正常零结果与编译失败、权限失败、下游超时、服务异常必须是不同状态。
- `kb_ids` 记录请求目标范围，不允许从命中结果反推。
- 记录不存 MCP 明文、JWT、密码、Cookie、认证 Header、上传票据、文件字节或内部 stack；用户业务输入与检索证据快照按第 13 节规则留存。
- `mcp_key_id` 仅用于关联，不复制 Key 明文或 hash。
- 账号被禁用、清退，MCP Key 被轮换、吊销或删除显示记录时，已产生的调用记录不级联删除。
- 旧表 DROP 迁移只能精确指定 `serving_query_logs`，不得使用 `CASCADE`，不得命中新表。

## 4. IMPLEMENTATION CONTRACT

### 4.1 唯一新主表

新增单表 `knowledge_access_records`，不新增通用事件表、span 表、审计微服务或独立数据库。

建议最小字段合同：

| 字段 | 类型 | 要求 |
|---|---|---|
| `id` | TEXT PK | 入口产生的唯一调用 ID，下游复用，用于防重 |
| `occurred_at` | TIMESTAMPTZ | 调用开始时间，默认 `now()` |
| `completed_at` | TIMESTAMPTZ NULL | 调用最终完成时间；上传票据尚未 PUT 时可空 |
| `domain` | TEXT | 逻辑域，必填 |
| `actor_user_id` | TEXT NULL | 沿用 `kb_users.id`；不设 FK，避免历史记录被账号生命周期级联删除 |
| `actor_username` | TEXT NULL | 调用时用户名快照，便于账号清退后还原当时记录 |
| `source` | TEXT | `web` / `mcp` / `api` |
| `operation` | TEXT | `search` / `read` / `upload` |
| `tool_name` | TEXT NULL | MCP 对外 Tool 名；非 MCP 可空 |
| `mcp_key_id` | TEXT NULL | MCP Key 内部 ID；不存明文/hash |
| `kb_ids` | JSONB | 请求目标库 ID 数组，默认 `[]` |
| `query_text` | TEXT NULL | search 查询原文；read/upload 可空 |
| `paradigm_id` | TEXT NULL | 实际执行范式 |
| `paradigm_version` | INTEGER NULL | 实际执行版本 |
| `status` | TEXT | `pending` / `success` / `no_result` / `denied` / `invalid` / `timeout` / `failed` |
| `result_count` | INTEGER NULL | 结果数；不适用时为 NULL |
| `duration_ms` | INTEGER NULL | 入口视角总耗时 |
| `error_code` | TEXT NULL | 稳定错误码，不存 stack |
| `details_json` | JSONB | 非敏感摘要，默认 `{}` |

最小索引：

- `(domain, occurred_at DESC)`；
- `(actor_user_id, occurred_at DESC)`；
- `(source, tool_name, occurred_at DESC)`；
- `(status, occurred_at DESC)`；
- `kb_ids` GIN。

表的权威 DDL 建议放在 `databases/kb/schemas/015_knowledge_access_records.sql`，并显式注册到现有 `domain_schema_paths()` / `primary_schema_paths()` 空库 bootstrap 链。

### 4.2 记录边界

一条“用户可感知调用”只写一行：

| 入口 | 一条记录的边界 |
|---|---|
| 网页 KB 检索 | 用户点击/回车发起到最终返回证据或错误 |
| 普通检索 API | 一次外部 HTTP 请求 |
| MCP `search_knowledge` | 一次 `tools/call` |
| MCP `get_knowledge` | 一次 `tools/call`；具体 read/navigate/query 子动作写入 `details_json` |
| MCP `upload_document` | 一次 Tool 调用记一条；票据签发后为 `pending`，一次性上传票据与实际 PUT 通过同一 `id` 关联，最终状态以 PUT 结果为准；只签发上传地址不能误报为文件已上传/已挖掘 |

不建内部算子/span 记录。范式内部的 FTS、dense、rerank 等诊断仍走现有 debug 通道，不进入本业务记录表。

### 4.3 写入职责

- MCP 服务作为 MCP Tool 的用户边界，保证三个 Tool 每次调用只产生一个 `id`。
- MCP 不直连数据库；复用已有 `httpx` 和内部鉴权通道，把最终记录发给 Mining 内部写入端点。
- Java Serving 负责 Web/API 检索的记录。对于来自 MCP 的检索，只向 MCP 返回执行结果/摘要，不再额外插入第二条主记录。
- 网关、MCP 和 Serving 复用同一个请求 ID 传递约定；不得在各服务重新生成互不相关的 ID。
- 记录写入失败不得把正常业务响应改成 500，但必须有结构化 warning 和失败计数，不得无声吞掉。

### 4.4 查询 API

在现有 Mining API 中扩展，不新建服务：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/retrieval-records/summary` | KPI、趋势、范式/Tool/来源分布、热门和零结果查询 |
| `GET /api/retrieval-records` | 分页列表；时间、source、tool、operation、KB、用户、status、范式筛选 |
| `GET /api/retrieval-records/{id}` | 单条详情 |
| `POST /api/internal/retrieval-records` | MCP 等受信服务写入/完成记录；必须复用 `X-Internal-Auth` |

`summary` 和其他静态路径必须在 `/{id}` 动态路由之前注册，避免被识别为记录 ID。

列表默认按 `occurred_at DESC, id DESC`。分页须稳定，不使用仅 offset 导致新数据插入时翻页重复/遗漏。

原 `/api/ops/usage` 在过渡期可保留响应形状，但数据源必须切到新表；前端迁移完成后可并入 `summary` 并退役旧路由。

### 4.5 权限边界

权限不是本需求的独立子系统。实施时：

- 先经 `current_user` 鉴别用户与账号状态；
- 沿用 55 号实施后的用户域绑定和域管理逻辑；
- KB 内视图沿用现有 KB 可见性/管理结果；
- MCP Key 深链只允许现有 Key owner 范围；
- 不新增 `retrieval.records.*` capability、动态 RBAC 或角色编辑器。

具体页面字段可见性以 55 号最终实施结果为准，不阻断本文的表/API/页面主线实施。

## 6. 旧表退役与新表保护

### 6.1 本次允许的破坏性变更

本需求明确授权：

```sql
DROP TABLE IF EXISTS serving_query_logs RESTRICT;
```

不做任何数据回填、导出、备份或展示兼容。删除范围只是旧表 `serving_query_logs`。

注意：52 号方案要求 `offline_rebase` 的旧物理库作为回滚副本至少保留 30 天。因此“删除旧历史”指活跃新库不再含旧表；回滚副本的删除仍按已有数据库运维规则单独人工执行。

### 6.2 旧表必须完整退役

不能只删物理表。同一个发布须同时完成：

1. 旧 Java DDL 退出 current bootstrap，最终删除 `001_serving_query_logs.sql`；
2. `knowledge_mining.mining.maintenance.database_upgrade.bootstrap.JAVA_BOOTSTRAP_SQL` 不再引用旧 DDL；
3. `FORMAL_TABLES` 用 `knowledge_access_records` 替换 `serving_query_logs`；
4. `serving_query_logs` 加入 `RETIRED_TABLES`；
5. 旧 `ServingQueryLog` entity、Mapper、Mapper XML、`QueryLogService` 及其旧测试退役或被新记录器完整替换；
6. `QueryLogAspect` 如继续作为 Web/API 检索入口，必须改名/改写为新表记录器；不得继续引用旧表；
7. Python `query_log_db.py`、`/api/ops/usage`、`db_tables.py`、reset/export 工具和前端旧文案/测试全部切换或清理；
8. 静态扫描断言正式生产代码、bootstrap 和 mapper 不再出现 `serving_query_logs`。

### 6.3 新表未来版本保留规则

1. `knowledge_access_records` 进入正式 schema contract 和 current bootstrap。
2. 后续 migration 只能 append；已发布 migration ID、SQL、mode 和 checksum 不得修改。
3. 后续 `online_expand` 不得对新表执行 DROP/TRUNCATE/无条件 DELETE。
4. 后续 `offline_rebase` 必须把新表列为保留表，校验行数和确定性内容摘要；不一致则拒绝切库。
5. 新表不加入任何日常资产 reset/purge 清单。全库重置仅属于显式的开发/灾备操作，不属于版本部署。
6. 自动化增加“连续两个测试 schema 版本升级后，新表原有记录仍存在”回归。

## 7. 严格按 `deploy-sync.sh` 发布

### 7.1 migration 分类

本次包含 `DROP TABLE`，是 52 号定义的破坏性结构变更，必须宣告为 `offline_rebase`，不得伪装成 `online_expand`。

新 migration 必须：

- 以新 ID 和 SQL 文件 append 到 `databases/migrations/manifest.yaml`；
- 更新 `schema_version`；
- 写入经过实际文件内容计算的 checksum；
- 不修改任何已发布 migration 文件和 checksum。

迁移顺序：

```text
deploy-sync.sh apply
→ 同步 Python / databases / Java jar / 前端 dist
→ database_upgrade plan
→ 停 mcp / serving / mining / llm_service
→ 克隆当前库到固定轮换目标
→ 在目标库 CREATE knowledge_access_records
→ 在目标库 DROP serving_query_logs RESTRICT
→ 验证所有保留表、索引、schema contract 和迁移账本
→ 原子切换数据库配置
→ 重启服务
→ 健康检查与业务冒烟
```

### 7.2 上一版本识别

当前 rebase 源校验由 `PRE51_REQUIRED_TABLES = FORMAL_TABLES - BRIDGE_51_TABLES` 推导。若直接用新表名替换 `FORMAL_TABLES`，上一版生产库会因“缺少新表”在克隆前被拒绝。

本版必须同步演进源库基线校验：

- 显式接受紧邻上一版的表集合（包含 `serving_query_logs`、不包含 `knowledge_access_records`）；
- 目标版表集合包含新表、不包含旧表；
- 行数/内容比对只针对真正保留的业务表交集；
- 旧记录表不参与保留数据校验；
- 新记录表在本次目标库初始验收时行数必须为 0。

### 7.3 schema 契约同步

必须同时更新：

- `databases/migrations/manifest.yaml` 的 `schema_version`；
- Python `database_upgrade/contract.py` 的 schema version/checksum、`FORMAL_TABLES`、`RETIRED_TABLES` 和表数断言；
- Python/Mining/LLM 的启动 schema contract；
- Java `ServingRuntimeSchemaInitializer` 的 expected version/checksum；
- 现有 Python/Java 一致性测试。

任一处版本/checksum 不一致，服务必须拒绝 Ready，不得降级放行。

### 7.4 不新增依赖和不换镜像

本次实现只使用镜像已有的：

- Python：FastAPI、psycopg、httpx、Pydantic；
- Java：Spring、MyBatis/JDBC；
- 前端：Vue、Element Plus、Axios、ECharts。

不得修改依赖集合：

- `pyproject.toml`；
- `agent_serving_java/pom.xml`；
- `kb-ui/package.json`；
- `kb-ui/package-lock.json`；
- Dockerfile、supervisord、nginx 的基础依赖。

因为同时修改 Java 和前端，本次必须使用完整增量包：

```bash
cd agent_serving_java && mvn -DskipTests package
cd kb-ui && npm run build
bash deploy-sync.sh pack
```

不允许使用 `deploy-sync.sh pack --code-only`；不需执行 `deploy-build.sh`。

`deploy-sync.sh` 目前对依赖清单变化只输出警告，不强制终止。因此本能力验收必须显式比对上述三份 manifest，确认依赖集合无变化，否则不得以 sync 包发布。

## 13. A0 定案：完整但不蠢记（本节覆盖前文相冲突表述）

本次不重写现有主表、API、权限与页面结构。沿用轻量主表 knowledge_access_records，并新增一张一对一详情附表 knowledge_access_record_payloads。列表、筛选、统计只查主表，只有单条详情在既有权限判定通过后按需读取附表。

附表以 record_id 作为主键并通过 ON DELETE CASCADE 与主记录同寿命。当前不设置独立过期策略；后续如需清理必须单独立项，普通部署和升级不得删除。

| 字段 | 用途 |
|---|---|
| request_json | 调用方传入的完整业务参数 |
| effective_context_json | 系统归一化后真正执行的 KB 范围、范式、筛选等上下文 |
| response_mode | snapshot / reference / summary |
| response_json | 用户实际收到、且应保留快照的返回内容 |
| response_refs_json | 不重复保存正文时的文档、章节、证据与版本引用 |
| request_bytes / response_bytes | 实际持久化 JSON 的 UTF-8 字节数 |
| response_truncated / response_original_bytes / response_omitted_count | 超限及省略事实，禁止静默截断 |
| response_sha256 | 持久化响应快照的确定性摘要 |
| redactions_json | 已剔除的结构化敏感字段说明，不保存原值 |
| payload_schema_version | 载荷结构版本 |

留存边界：

| 操作 | 输入 | 返回 |
|---|---|---|
| Web/API/MCP 检索 | query、KB 范围、文档/章节范围、筛选、top_k、范式、展开及 debug 等完整业务参数 | 保存用户实际收到的有序证据快照，包括 ref、类型、内容、来源、结构引用、分页/截断及诊断信息 |
| 文档/证据正文读取 | ref、mode、cursor、limit、KB 范围等完整参数 | 不复制库内已有正文，只存文档/章节/证据引用、快照或构建版本、返回范围、长度与 hash |
| 结构化查询 | 完整 DSL、ref 与范围 | 保存实际 rows 或 aggregate 计算结果 |
| 导航/能力/库树/文件列表 | 完整业务参数 | 保存实际返回的小型元数据 |
| 上传 | KB 与完整文件名列表 | 不存文件字节、上传 URL 或 ticket；保存最终 document ID、run ID、逐文件状态与汇总 |
| 失败 | 完整安全业务参数 | 保存面向调用方的稳定错误码和安全消息，不存异常堆栈 |

请求载荷上限为 256 KiB，响应载荷上限为 4 MiB。超限必须在业务响应本身按证据/行边界分页或截断，并同步记录截断事实；不能给用户返回一份无法完整留痕的更大响应。

结构化敏感键在入库边界递归拒绝，包括 token、secret、password、authorization、API/MCP key、JWT、Cookie 与 credential。自然语言 query 和 evidence content 属于质量评测正文，保持原样，不做猜测式正则脱敏。

详情抽屉在现有十列列表不变的基础上，增加可折叠的调用参数、有效执行参数、返回内容/引用三个区块。两张账本表都进入正式 schema contract、current bootstrap、reset 保护和 future rebase 保留校验。后续 online_expand 必须静态拒绝针对两表的 DROP、TRUNCATE 和无 WHERE DELETE；连续两个 schema 版本升级后两表原有记录必须仍在。
