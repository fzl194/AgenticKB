### 架构铁律（用户追加拍板）

**任何新功能服务层只实现一遍**；三个入口（网页前端、API 脚本、MCP/Agent）只是薄适配：

```
网页前端 ─┐
脚本/API ─┼─→ 网关(JWT) ──→ mining/serving【用户端点】────┐
          │                                                ├→ 服务层单实现
Agent ────┴─→ mcp_server(密钥) ─→ 【内部端点】──────────────┘
                                              (DocumentService / KbDB / serving 管线)
```

- "API"与"网页前端"共用同一门面（同一套 HTTP 端点 + JWT）。
- mcp_server **禁止出现业务逻辑**：只允许鉴权翻译（密钥→用户）、形状翻译（内部 id→ref/name）、错误翻译（HTTP→Agent 可自纠提示）。
- 双 HTTP 门面并存的既有理由不变：身份模型（JWT+kb_members vs 密钥+开放库）、网络位置（公网网关 vs 内网内部密钥）、返回形状（管理字段 vs Agent 协议）。

## 1. 关键设计发现：目录信息已在检索索引里

挖掘投影（`retrieval_projection/projector.py:114`）给每个检索单元写入
`facets.document = document_ref`，而 document_ref 就是
`"doc:/{directory_path}/{filename}"`（`kb/storage.py:60 build_document_key`，挖掘管线
jobs/run.py:880 同推导）。

因此 **`directory_prefix` 过滤可以直接前缀匹配 `facets_json->>'document'`**：

```sql
un.facets_json->>'document' LIKE 'doc:/{prefix}/%'
```

- 递归子树语义由 `/%` 边界天然保证（`产品` 不会误中 `产品文档`——边界字符是 `/`）；
- **免投影改动、免存量回填、免迁移**——老库已挖数据立即可用；
- 根目录文件是 `doc:/{filename}`（无目录段），任何非空 prefix 都不会命中它们，语义正确；
- 注：数组 containment（`@>`）**不可用于此**（无序、会误中），必须字符串 LIKE 前缀。

这使原估"最大工作线"的 D3 从"投影+回填+下推"缩为"仅 serving 下推+白名单+双入口透传"。

## 2. 工作线①：文件搜索（名 + 目录 + 状态）

### 2.1 服务层（单实现：`kb/db.py`）

`list_documents_in_kb` / `count_documents_in_kb` 新增可选参数（两个方法同口径）：

| 参数 | 类型 | 语义 |
|---|---|---|
| `query` | str | 文件名子串，`document_name ILIKE '%{kw}%'`（大小写不敏感；`%`/`_`/`\` 由调用侧转义，`ESCAPE '\'`） |
| `directory_prefix` | str | 目录前缀（含子目录）：`directory_path = %s OR directory_path LIKE %s || '/%'`（目录段不做 LIKE 转义之外的处理；值先 strip 首尾 `/`） |
| `status` | str | 派生状态过滤。status 是 SELECT 内联 CASE——**用子查询包一层再过滤**：`SELECT * FROM (…现有查询…) t WHERE t.status = %s`（count 同理 `SELECT COUNT(*) FROM (…) t WHERE …`）。合法值 `uploaded/mining/mined/failed/update_failed` |

兼容性：三参全不传时 SQL 与现状完全一致（不加子查询层，避免无谓开销）。

psycopg 坑提醒：SQL 文本中的字面 `%` 必须写成 `%%`（params 走 execute 绑定时）。

### 2.2 用户门面（`kb/routes/documents.py`，前端/API 共用）

- `GET /api/kb/{kb_id}/documents` 加 Query 参数 `query`、`directory_prefix`、`status`（均可选）；
- `GET /api/kb/{kb_id}/documents/count` 同步加同口径参数（前端分页总数）；
- 响应体不变（现有字段已含 directory_path/status/content_revision）。

### 2.3 MCP 门面（`kb/routes/mcp_tools.py` `POST /list-documents`）

- body 新增 `query` / `directory_prefix` / `status`（同上口径，透传服务层）；
- `kb_id` **可选化**：省略时 `query` 必填（否则 422）；跨库 = 遍历 `key_open_kb_ids`
  ∩ 实时可见 的每个库执行同参查询，按 `modified_at DESC` 合并、总 limit≤200/offset 分页；
  跨库结果每项附加 `kb`（库显示名），便于 Agent 定位；
- 单库模式响应项新增 `content_revision`（D5 版本暗号的来源，跨库模式同样返回）；
  `directory_path` 在单库模式也返回（原来是 referenced 文档才有）；
- 修订 docstring 中过时的状态优先级注释（`published/withdrawn` → 实际
  `update_failed/failed/mining/mined/uploaded`）。

### 2.4 MCP 工具层（`mcp_server/server.py` `get_knowledge`）

分流矩阵新增一行（保持三件套，纯加参数）：

| 入口 | 行为 | view |
|---|---|---|
| 只传 `query`（不传 kb_name/ref） | **跨全部开放库搜文件** | file_results |
| `kb_name` + `query` | 该库内搜文件 | documents（搜索模式） |

- `get_knowledge` 新增参数：`query`（文件名关键词）、`directory_prefix`（可选）、
  `status`（可选）；`kb_name` 变为"与 query 二选一可省"——省略 kb_name 且传 query
  → 跨库；两者都不传 → 顶层 kb_tree（现状不变）；ref 与 kb_name/query 互斥规则不变；
- documents/file_results 返回项字段：`name/kb/status/file_size/modified_at/
  content_revision/directory_path/referenced`（+跨库时 `kb` 库名）；
- 工具 docstring 同步（这是 Agent 唯一的"说明书"）；
- kb_tree 的 hint 增补一句"找文件传 query"。

### 2.5 前端（`KbFileManager.vue` + `api/kb.ts`）

- 工具栏新增：搜索框（回车/防抖触发）+ 状态下拉（全部/已入库/待挖掘/挖掘中/失败/更新失败）+ 范围切换（默认"当前目录及子目录"，可切"整个库"）；
- 搜索态：调 `listDocuments(query=…, directory_prefix=…, status=…)` + `countDocuments` 同参；结果表多展示"所在目录"列（面包屑）；清空搜索即回到浏览态（现有 exact-directory 逻辑零改动）；
- `api/kb.ts` listDocuments/countDocuments 签名扩展（可选参数对象）。

### 2.6 明确不做

- 文件类型筛选（D1）；拼音/错字 fuzzy；跨域搜索（钥匙单域语义不变）。

## 4. 工作线④：MCP 替换（D5）

### 4.1 版本暗号的来源（先让 Agent 看得到）

- serving `/api/internal/document/{ref}`（`EvidenceToolService.getDocument`）响应新增
  `document_id` 与 `content_revision`（内部端点，不外泄到公开协议；evidence 公开协议不动）；
- mining `/api/kb/mcp-tools/list-documents` 每项加 `content_revision`（见 2.3）。

### 4.2 mining 票据扩展（`mcp_tools.py`）

`begin-upload` body 新增可选：

| 键 | 语义 |
|---|---|
| `document_id` | 替换目标（与 filename 同时给出） |
| `expected_revision` | 版本暗号（≥0） |

校验（签发票据时，全部失败即时 4xx）：`get_document_identity(document_id)` 存在且未软删、
`kb_id` 匹配、`can_write`、**filename 扩展名 == 目标文档扩展名**（400 引导语同网页端）、
`expected_revision == doc.content_revision`（不符 → 409，提示重新查看）。票据条目多存
`document_id/expected_revision`。

`upload-direct/{ticket}`：票据含替换目标时走 `doc_svc.replace_content(...)`（**服务层单实现
复用**，CAS/同扩展名/旧知识保底全部继承），成功后同样 `enqueue_auto_mining`；响应
`{"kind":"replace", "document_id", "document_name", "auto_mined", …}`。CAS 冲突 → 409
（Agent 可重新 get_knowledge 取新 revision 再试）。

### 4.3 开箱检查（magic bytes，replace 路径）

`DocumentService.replace_content` 存流时对临时文件头做廉价校验（复用
`_store_source_stream`，加 `expect_suffix` 开关）：

| 扩展 | 要求文件头 |
|---|---|
| `.pdf` | `%PDF-` |
| `.zip/.docx/.xlsx/.pptx`（zip 容器族） | `PK\x03\x04`（或 `PK\x05\x06` 空包） |
| 其余（md/txt/html/json/chm/hdx…） | 不校验（无可靠魔数，维持现状） |

不符 → 400"文件内容与扩展名不符"。**只挂在替换路径**：新上传维持现状（挖掘层失败兜底），
行为面最小化。

### 4.4 MCP 工具层（`upload_document`）

新增参数：`replace_document_ref: str | None`（doc_ 引用，来自 search 证据的
`source.document_ref` 或文档读取）、`expected_revision: int | None`。

流程（mcp 层只做形状翻译，不做业务）：

```
upload_document(kb_name, filenames, replace_document_ref?, expected_revision?)
  ├─ 无 ref → 现状新增流程
  └─ 有 ref（此时 filenames 恰一个，多文件+替换 → 422 工具层即拒）
       → serving /api/internal/document/{ref} 解析 → {document_id, content_revision}
       → begin-upload(document_id, expected_revision, filename)
       → PUT 直传（票据即凭证，与新增共用）
```

- `expected_revision` 与 Agent 从 documents/ document_content 视图看到的
  `content_revision` 对齐；省略 → 默认 0 并由 mining 按实际校验（不猜）；
- 409 错误文案转成 Agent 可自纠提示（"版本已变化，请重新 get_knowledge 获取新
  content_revision"）；
- docstring 更新：两步直传说明 + 替换用法示例。

### 4.5 明确不做

- Agent 删除（D6）；替换的历史版本浏览/回滚 UI（原材料 content_revision+对象去重已在，
  能力后置）；批量替换。
