## 2. 形态决策：三案比选

工作台"应该长什么样"有三个候选，差异本质是**首版把复杂度放在哪**：

| | 方案甲：完整通用 DAG 工作台 | **方案乙：模板驱动步骤流工作台（推荐）** | 方案丙：固定向导 |
| --- | --- | --- | --- |
| 形态 | 自由画布拖拽建图、typed dataset 协议、算子市场（64号 W05/W06 全量） | 工作区=图草稿（JSONB DAG），UI 用垂直步骤卡+下拉选输入；从模板或空白创建；算子目录封闭 | 每类制品一个固定向导（现有 Wiki 编译面板的泛化） |
| 交互能力 | 任意拓扑、画布编辑 | 任意无环拓扑（数据模型同甲），编辑靠"节点表单下拉选上游输出"，画布只读呈现 | 单线流程，不能组合 |
| 首版工作量 | 大：画布编辑器+执行协议+失效传播 UI 全要新建 | 中：复用 hi-fi 已验证的交互，画布编辑延后 | 小 |
| 满足 64号 W05（多输入多输出） | 完全 | 完全（端口模型不简化） | 不满足 |
| Agent 可程序化 | 好 | **好且更稳**（模板=可引用的构建函数签名） | 差 |

**推荐方案乙的依据藏在原型自身**：`workspace-1116.fragment.html` 的画布连线是**只读 SVG 渲染**，实际输入选择走 `availableInputs` 下拉（":100 data-input-index"），节点 x/y 只是布局装饰；且原型的窄屏降级形态就是"垂直步骤卡+↓箭头"列表。也就是说：**画布在原型中的价值是"看依赖"，不是"编辑拓扑"**——首版用步骤流呈现依赖、下拉编辑拓扑，交互本质无损，画布（vue-flow 只读+自动布局）作为二期观感增强。同时图数据模型按完整 DAG 设计（nodes/edges/ports），后续升级画布零迁移。

**模板（Template）的定义**：一份预置的图草稿+算子参数默认值+说明。首版内置两个：`表格抽取模板`（来源→LLM抽取→关联→筛选，对应 hi-fi 表格示例）与 `Wiki 编纂模板`（来源→知识类型→编纂→引用检查，对应 hi-fi Wiki 示例，阶段E 才启用）。模板存 `kb_workspace_templates` 种子数据或代码内常量（首版选**代码内常量**，YAGNI，不做模板管理界面）。

| WB-07 试跑/执行/快照（W07）★ | 试跑（≤3 条输入，只读不落库不导出）/执行此节点/运行工作区（按依赖拓扑序）/下游 stale 传播/历史快照回看（只读）/用新资料重跑（批次+1，人工修正保留） | 执行前冻结图修订+配置+输入版本；旧快照不可覆盖；"配置已改"与"上游已变"是两种 stale 标签（原型同款语义） |

```
  row_count · content_hash · quality_json                -- 覆盖/过滤/失败/断链计数，机器可读（D9 种子②）
  is_current BOOLEAN                                     -- 每 (workspace_id,node_id,port_id) 至多一行 true（部分唯一索引）
  stale_since_run TEXT NULL                              -- "上游已变"：产生本输出后上游再执行的 run_id；NULL=新鲜
  created_at
  -- 护栏见 4.2；超限直接失败提示收窄，不静默截断

kb_workspace_output_bindings  输出→制品稳定绑定
  (workspace_id,node_id,port_id) PK → artifact_id · artifact_kind
  last_run_id · last_exported_at · created_by/created_at
  -- 首期一个输出只绑一个制品（64号 §10.7 单绑定裁定）；删除/改接输出需显式解绑

kb_workspace_exports     导出操作记录（名字避开已被占用的 kb_export_tasks）
  id PK · request_id TEXT UNIQUE                          -- 幂等键（X03）
  workspace_id · node_id/port_id（或新目标参数快照）
  mode CHECK(create_draft)                                -- 首版唯一模式；update_draft 待阶段D
  target_artifact_id · snapshot_run_id · mapping_json
  status CHECK(pending,succeeded,failed) · result_json · error
  actor_kind/actor_id · created_by/created_at
```

人工修正账 `kb_workspace_overrides`（(workspace_id,node_id,port_id,record_id) PK，field 纒纷粒度 JSONB{before,value,reason}+origin_run_id+status）随批次3 加入；制品侧人工修订保护（64号 X04 的正式版保护）仍留待阶段D 评审，首版不建。

### 4.2 容量与存储护栏（D5）

- 首版输出快照**全部 inline JSONB**，护栏：单输出 ≤5 万行 / ≤20MB 序列化 / 单工作区保留最近 10 个 run 的快照（更早 run 保留索引行、清 content_inline，状态行可回看不可回读内容）。
- 触发对象存储溢出的条件（二期再建）：单输出超护栏且业务确需，扩展 `asset_storage_objects.artifact_class` 新枚举值 `workspace_output`（枚举是 CHECK 约束，需迁移）+ 引用计数回收。**首版不碰该枚举**。
- 理由：B.3 验收材料与真实首批场景（产品规格库/库存关联，千行级）远低于护栏；先 DB 后对象存储符合"不过于复杂"。

### 4.3 明确不做的数据库事项

- 不建独立"流程版本表"：图草稿在 `kb_workspaces.graph_json`，冻结图在 `kb_workspace_runs.graph_snapshot_json`，两点即可覆盖"改图历史"需求（回看任意 run 即回看当时的图）。
- 不改任何既有制品表结构（kb_artifacts 族零改动）。
- **不写 `kb_artifact_batches`**：批次=制品导入账（Excel 导入与 Wiki 编译状态机的载体，`channel` 枚举现有四值不动）。工作台导出的可追溯性由 `kb_workspace_exports` + bindings + run 快照完整承载，制品侧不重复记账——省一次纯为记账的枚举迁移。批次5 编译状态机迁入 runs 后，batches 的 `wiki_compile` 通道仅存历史行（与 D7"两套状态不并存"一致）。
- 不复用/不改动 mining_workflows、mining_runs、mining_workflow_node_events（1.2 节第 3 条）。

### 5.2 执行器（复用 Wiki 编译三件套模式）

1. **串行与查重**：`pg_advisory_xact_lock(hashtext(workspace_id))` 锁内做在飞检查+INSERT queued（照抄 `db_compile_inputs.py:459` 的 TOCTOU 消除模式）；同工作区同时至多一个活动 run。
2. **后台任务**：mining 进程内 asyncio 任务（`_run_prepare/_run_writing` 同款），按冻结图拓扑序执行节点；确定性算子纯同步；LLM 算子走 `LlmTaskClient.submit_chat`（幂等键=`run+node+行身份`）+ `batch_status` 轮询 + 失败子集重提（`max_attempts=3` 由 llm_service 兜底）。
3. **恢复语义**：启动即冻结 `graph_snapshot_json` + 来源 `input_manifest`，进程重启后 running run 判 failed 可整批重跑——**根治 `_PREPARE_CACHE` 类缺陷**（1.2 节第 2 条）。
4. **stale 传播（两标签分工已定）**：节点执行成功后，其下游全部 `is_current` 输出置 `stale_since_run`（**上游已变**，落输出行）；**配置已改**（pending）存 `graph_json` 节点态——前者看输出行、后者看节点态，UI 两种提示条据此渲染（hi-fi 同款语义）。
5. **导出事务**（批次4）：单 DB 事务内=校验（目标并发令牌+输出 is_current+未过期）→ 复用 `db_artifacts` 创建事务（含"指定 owner+操作者 editor"新分支）→ 写 rev0 草稿（表格：列+行；Wiki：pages+links 同事务；行键复用 `_row_key` hex，来源账写 rows/pages 的 provenance 字段）→ 写 bindings+exports（不写 batches，见 §4.3）。重复 request_id 返回原结果（X03 全套）。

### 5.3 算子实现约定

- 算子=纯函数 `(输入数据集列表, 配置) → {端口: 数据集} + 质量账`，注册在封闭目录（dict 常量+校验器），无插件机制。
- 表格算子的类型转换/行键/表头清洗复用 `artifact_import_service` 纯函数族（1.3 节）。
- LLM 抽取算子输出列类型声明式（名称+类型枚举对齐 `kb_table_columns.column_type` 六类型），失败行进 quality_json 待重试。

## 8. Agent 自主构建知识资产：三阶段演进（D9）

这是 64号 未覆盖的新命题。结论先行：**可行且路径清晰，工作台正是 Agent 与人共用同一个构建管线的交汇点；安全边界（S1–S2 的默认态）="Agent 到草稿为止，发布权永远在人"**——S3 的"自动发布"是需要显式开启+独立评审的可选开关，不改变默认边界。分三阶段：

### S1 现状（已具备，无需开发）

- Agent 作为**消费者**：`get_knowledge` 的 `art_` 分支（表格 DSL/Wiki 四形态），走 `selectVisibleArtifact` 的 published+成员+public+钥匙开放子集谓词。
- Agent 作为**原料供给者**：`manage_files` upload → `auto_mine` 入队（`triggered_by='mcp_upload'`，域级 FIFO）。产出的是检索单元（原材料），不是制品。
- 缺口：Agent 无法参与"从原料到制品"的加工段——这正是工作台补的位。

### S2 工作台工具化（批次6，随工作台成熟后启用）

新增 MCP 第 4 个工具 `build_knowledge`（动作族，复用 `manage_files` 的 action 模式）：

```
list_templates            列可用模板（名称/输入要求/输出端口）
create_workspace          从模板建工作区（绑定域内知识库范围）
bind_source / run         绑定来源 / 触发执行（入队+轮询，照 auto_mine 模式）
get_run_status            读进度与 quality_json
deliver_draft             导出为制品草稿（幂等，仅 create_draft 模式）
```

- **权限**：钥匙→user 身份，工作区操作按该 user 的成员角色判定（钥匙不放大权限，同"开放子集不放大"铁律）；`open_tools` 白名单可单独关闭此工具。
- **审计**：runs 的 `actor_kind='mcp_key'`+actor_id=key 即构建审计；MCP 中间件记账扩展 tool_name 维度。
- **边界**：Agent 与人在工作台内能力**完全同面**——都是改图/执行/导出草稿；制品发布（publish 端点）不经 MCP 暴露，人工审阅在制品设计态完成（diff 预览+说明卡填写是人的动作）。

### S3 自主闭环（远期，本文只定方向不排期）

触发器（新资料到达/定时/检索记录暴露的知识缺口）→ Agent 自动建 run → **质量门**（quality_json 机器可读：丢事实率/断链数/覆盖率为门槛字段，直接复用 Wiki 编译质检报告的口径）→ 通过则 deliver_draft → 人工审阅队列（制品设计态"待审草稿"列表）→ 人发布。可选演进：低风险配方（连续 N 次人工零修改通过）开启"自动发布"开关，回滚兜底已有（制品版本回滚不删历史）。

### 本版必须埋的四颗种子（否则 S2/S3 要返工）

1. **actor 字段**：runs/exports/workspaces 建 表 即 带 `actor_kind/actor_id`（补 schema 层"人 vs Agent"空白——现状仅 `kb_wiki_pages.origin` 一个局部枚举）。
2. **quality_json 机器可读**：算子质量账从第一天按"门槛字段"设计（覆盖率/失败数/断链数），不是自由文本。
3. **模板可版本化可引用**：模板=图+算子版本+提示词版本的快照，Agent 以模板身份引用而非每次自然语言重述（run 冻结图已保证可追溯）。
4. **构建审计通道**：MCP 记账扩展预留 tool_name 枚举位，S2 上线即有账。

与 60号三贯穿面的对位：治理=三分离权限+actor 审计；交付=导出草稿/人工发布两级门；运营=quality_json 回流形成配方改进候选（呼应 54号"反馈只形成变更候选"）。
