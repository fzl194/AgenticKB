# 文件格式支持补全——现状调研与实施规划

> 生成：2026-11-25 · 基于 `master@e0ae611+`（v1.2.1 之后）与 feat/figcap-operator 分支工作区实测代码逐环核读
> 性质：**只读调研产物，本文档不含任何代码改动**。定位：交给后续 Agent 的实施依据。
> 需求方（用户）已对齐的目标见 §一。

---

## 一、需求与边界（用户已拍板）

1. **独立需求，独立分支**：与图片图注功能（feat/figcap-operator）解耦，后续新开分支实施（建议名 `feat/file-format-support`）。
2. **支持范围**：csv、json、xls（旧版 Excel）、ppt（旧版 PowerPoint）、图片 jpg/png。其余格式（rtf/gif/bmp/tar 等）本报告仅盘点现状并给建议，默认不做。
3. **图片口径**：VLM 整图转结构化文字描述（复用图注那套 VLM 通道），产出可检索文本；依赖多模态模型在线。
4. **拦截原则**：**前端拦截，后端不动**。前端 accept 过滤 + 上传前 JS 校验双保险；绕过前端的文件维持现状（挖掘时报 unsupported_format），后端不加预检。
5. **总原则**：哪些文件能解析，前端就支持上传哪些；三层（前端可选 / 上传可收 / 挖掘可解析）逐字对齐。

## 二、现状：一条判定链，三层各管一段

```
文件字节
  → ① 魔数探测 MIME     safe_intake._SUPPORTED_MIMES（frozen_input/safe_intake.py:64）
  → ② 格式标签          inspect._MIME_TO_FORMAT（file_inspector/inspect.py:44，只有 7 个键）
  → ③ 路由              router._FORMAT_TO_MIME + ParserRouter.plan（file_inspector/router.py:25,72）
                       硬规则：只选 backend_kind="local" 且 license_status="ok" 的注册项（router.py:125-132）
  → ④ 解析器            parse_adapters/ 各文件 supported_mimes
```

外加两个旁路通道：

- **旧版转换通道**：`.doc`（application/msword）在解析前经 LibreOffice 转 docx（parse_operator/service.py:139 `_convert_legacy_doc`，转换器 ingestion/doc_preprocessing.py:142 `doc_to_docx`，LibreOffice 优先、Windows Word COM 回退）。**只认 msword 一种**（service.py:452 显式判断）。
- **压缩包通道**：`.zip/.hdx/.chm` 在上传时拆成员（document_service.py:658 `upload_archive_path`；hdx=zip 同构、chm 走 7z 提取器），成员各自回到上面这条链。

前端与上传层现状：

- 前端 accept（kb-ui/src/components/kb/KbFileManager.vue:24）：`.md,.markdown,.txt,.html,.htm,.pdf,.doc,.docx,.xls,.xlsx,.zip,.chm,.hdx` —— **手写清单，与后端无对账**；
- 前端提示文案（kb-ui/src/locales/zh/kbManage.ts:150，另有 en 对应条目）："支持 Markdown、文本、HTML、PDF、Word（.doc/.docx）、Excel（.xls/.xlsx）及 ZIP 等格式" —— **第二份手写清单**，与 accept 也不一致；
- 上传层（document_service.py:50 `_EXTENSION_MIME` + upload_config.py:21 `archive_extensions=".zip .hdx .chm"`）：**基本来者不拒**，只做 MIME 登记与归档分流，不预检"能不能挖"。

## 三、权威格式矩阵（逐环核读结论，2026-11-25）

### 3.1 能端到端解析（8 种 + 3 种压缩包）

| 格式 | MIME | 路径 |
|---|---|---|
| md / markdown | text/markdown | legacy_markdown |
| txt | text/plain | legacy_txt |
| html / htm | text/html | native_html（inspect 映射只认 text/html；application/xhtml+xml 解析器支持但探测链不认，实际走不到） |
| pdf | application/pdf | native_pdf（无文本层扫描件被守卫拦：parse_operator/service.py:402-432） |
| docx | …wordprocessingml.document | native_docx |
| **doc** | application/msword | **先 LibreOffice 转 docx** → native_docx（容器内 /usr/bin/soffice 已验证存在） |
| xlsx | …spreadsheetml.sheet | native_xlsx |
| pptx | …presentationml.presentation | native_pptx |
| zip / hdx / chm | — | 上传时解压，成员按上表 |

### 3.2 不能解析（上传可收、挖掘必报 unsupported_format）

| 格式 | 收件白名单 | 失败表现 |
|---|---|---|
| **xls**（vnd.ms-excel） | ✅ 收 | 挖掘 unsupported_format——**前端 accept 与文案都在宣传，属虚假宣传** |
| **ppt**（vnd.ms-powerpoint） | ✅ 收 | 同上（前端没宣传，拖拽/API 直传会踩） |
| rtf | ✅ 收 | 同上 |
| png / jpeg / gif | ✅ 收 | inspect 无映射 → unknown → 路由失败；图片解析槽位 cloud_vlm 是**未配置占位**（registry.py:71-83，backend_kind="cloud" + license "unconfigured"），路由器硬规则不选 cloud，**与 llm_service 配没配多模态模型无关** |
| csv / json | ⚠️ `_EXTENSION_MIME` 有映射（text/csv、application/json）但 safe_intake 白名单没有 | 上传成功 → 挖掘报"文件类型不支持"（失败时机最晚，体验最差） |
| rar / 7z / gz / tar | ✅ 白名单放行（"仅供暂存/展开"） | 上传后既不自动解压（解压器仅 zip 系，archive_extractor.py:1-5）也无解析器，纯死胡同 |

### 3.3 前端 accept 单独的问题

- **pptx 选不了**（后端全链路支持，包括图注链）——能力被藏起来；
- **xls 在列**（后端必失败）——宣传了假能力；
- 提示文案没提 PPT，提到 Word/Excel 的口径与 accept 不一致。

## 四、xls 与 xlsx 的区别（用户问过）

| | xls | xlsx |
|---|---|---|
| 容器 | **OLE2 复合二进制**（Excel 97-2003 旧格式） | **OOXML**（zip 包 + XML，Office 2007 起） |
| 平台现状 | 解析器注册表无对应项、转换通道不认 | native_xlsx 原生支持（含表格区域识别/合并单元格/公式） |
| 补齐方式 | 复用 doc 的机制：LibreOffice xls→xlsx 转换（`soffice --convert-to xlsx`，同一函数换个目标格式参数即可） | — 已支持 |

ppt 同理：OLE2 旧格式 → LibreOffice ppt→pptx → 复用 native_pptx。**xls 和 ppt 是同一条改造线，机制全部现成，成本最低**。

## 五、差距 → 方案映射

| 需求 | 差距 | 方案（概要，细节见 §六） |
|---|---|---|
| xls | 转换通道只认 msword | 放宽 `_convert_legacy_doc` 为通用"旧二进制→OOXML"转换（msword/ms-excel/ms-powerpoint → docx/xlsx/pptx） |
| ppt | 同上 | 同上 |
| csv | 探测/路由/解析器全缺 | 新增 native_csv 适配器（复用 xlsx 的表格→结构化事实思路：csv 即单 sheet 表格） |
| json | 同上 | 新增 native_json 适配器（结构化文档：顶层键→章节、叶子值→段落/事实，数组→表格语义视内容而定；注意与既有 onenet_jsonl 适配器区分——后者是一张网专用 jsonl 行流，不通用） |
| jpg / png | 无图片解析器；cloud_vlm 只是占位 | 新增 **vlm 图片解析器**：整图调 VLM（复用 feat/figcap-operator 的 VlmFigureCaptioner/图注提示词资产）产出结构化描述作为解析 IR；模型不可用=解析失败（诚实降级，不伪造空文档） |
| 前端对齐 | accept/文案双清单漂移 | 单一事实源：把"可解析扩展名清单"收口为一处常量，accept 与文案从它派生；加上传前 JS 扩展名校验 |

## 六、实施规划（建议分四段，各自可独立验收）

### S1 · 旧二进制转换通道泛化（xls/ppt）——最小改动，先行

- 改造 `parse_operator/service.py` `_convert_legacy_doc` → `_convert_legacy_office`：输入 MIME 分派目标格式（msword→docx、ms-excel→xlsx、ms-powerpoint→pptx）；`ingestion/doc_preprocessing.py` 增加 `office_to_ooxml(src, target_format)`（`soffice --convert-to <fmt>`，保留 Word COM Windows 回退仅对 doc）。
- 产物对象命名沿用现约定：`原key--legacyconv-<hash>.<ext>`（参考现有 `--doc2docx-<hash>.docx`）；原件不动、幂等复用同实测。
- safe_intake / inspector / router 无需动（转换后 MIME 就是 OOXML，走既有链）。
- 测试：msword 回归锁定 + 新增 ms-excel / ms-powerpoint 转换分发用例（转换器可 mock soffice 产物文件）。
- 风险：LibreOffice 对个别损坏/加密旧文件的转换失败——沿用 doc 现状：留痕为 FAILED 终态（`legacy_office_convert_failed`）。

### S2 · csv / json 原生解析器

每个新格式要动**四个对账点**（这就是"三层各管一段"的代价，缺一处即断链）：
1. `safe_intake._SUPPORTED_MIMES` 加 text/csv、application/json（同时决定收件白名单是否收紧 csv/json 之外的死胡同格式——见 §八遗留决策）；
2. `inspect._MIME_TO_FORMAT` 加 csv、json 标签；
3. `router._FORMAT_TO_MIME` 加映射（格式标签→MIME）；
4. 新增 `parse_adapters/native/native_csv.py`、`native_json.py`（ParserDescriptor supported_mimes + Parser + Normalizer 三件套，照 native_xlsx.py 结构）。
- csv 设计要点：单 sheet 表格 → 沿用 xlsx 的 data_region/表格语义（列头识别、类型推断），产出 paragraph + table 元素；大文件流式读（csv stdlib）；编码探测（utf-8/gbk 回退）。
- json 设计要点：浅层文档结构（键路径→heading_chain，字符串叶子→paragraph，数值/布尔叶子→事实、数组 of object→表格）；深度与体积上限（防单文件 10 万键轰炸，参考 xlsx 的区域上限思路）。
- 测试：goldens + 单测各一目录；跨层契约测试（`test_mining_operator_catalog` 类似的对账测试如有格式清单断言需同步）。

### S3 · 图片 VLM 解析器（jpg/png）

- 定位：**本地 backend 的新解析器**（不是激活 cloud_vlm 占位——那是云端 OCR 槽位，语义不同，保留不动）。
- 依赖 llm_service 的 vision-default 端点（feat/figcap-operator 已就绪：GET /api/v1/models/vision-default）；模型解析不出 → 解析 FAILED（诚实失败，不产空 IR）。
- 实现骨架：`parse_adapters/native/native_image.py`（或独立 `vlm_image.py`）——Parser 调 VlmFigureCaptioner 同源的 VLM 通道，把图转成结构化描述（提示词独立版本，比图注更完整：要求输出"图类型/主体/全部可见文字/数值/结论"分节描述）；产物 = 单元素文档（1 个 figure 元素 + caption/描述文本），从而**下游切片、检索、甚至图注缓存全部复用既有投影**。
- 同样补四个对账点 + safe_intake 放行 image/jpeg（现已有 png/jpeg/gif，gif 建议不进——动图语义不明，留白）。
- 与图注功能的关系：图注算子处理"文档内嵌图"，本解析器处理"独立图片成为文档"；两条线共用 VLM 通道与提示词资产，互不依赖。
- **顺序建议：S3 放在 feat/figcap-operator 合并之后做**（复用其 VLM 基建，避免并行冲突）。

### S4 · 前端单一事实源 + 双保险拦截

- kb-ui 新增共享常量 `SUPPORTED_UPLOAD_EXTS`（含展示名），accept、format 提示文案、上传前校验三处消费同一常量；zh/en 文案同步（字典有对账闸门，漏改会被测试拦住）。
- 上传前 JS 校验：el-upload 的 before-upload（或 handleUpload 入口）按扩展名白名单拦截，弹 i18n 错误提示（复用既有 ElMessage 通道）；批量上传中不合格文件逐个提示、合格文件继续。
- MCP 通道（begin-upload/upload-direct）维持后端现状不拦（用户原则：前端拦，后端不动）；但 mcp 工具描述里的格式清单建议同步更新，避免 Agent 侧传废文件。
- 验收清单：accept 与后端"能解析清单"逐字一致；文案一致；绕过 accept（选"所有文件"）的非法扩展名在上传前被拦且提示明确。

## 七、测试与部署注意（写给执行 Agent）

- 测试基建：`%TEMP%\kb-venv`（python -e . + pytest pytest-asyncio）从 `knowledge_mining` 目录跑；无 PG 的预存失败与 master 基线逐条对照，不背锅。前端测试在 kb-ui 目录 npm test。
- 本机部署是 bind-mount（./knowledge_mining → /app），改 Python 重启 mining 即生效；前端要 npm run build 后清空 kb-ui-dist 拷 dist。
- 提交纪律：**git add 显式路径，禁用 add -A**（历史事故：把本地内网配置改动带进提交）；master 只收发版合并，功能分支开发。
- 契约测试四处对账：格式新增会牵动 catalog/模板/预设之外的**格式清单类断言**（如 `test_mining_workflow_api.py` 集合断言），跑全量而非只跑新增。
- 发版走五步流程（docs/平台指南/40-部署与发版.md「发版到 GitHub Releases」节）；若动了 Java/DDL 才涉及 jar 重建与迁移，本需求预计纯 Python+前端，无 DDL。

## 八、遗留决策（本报告不替用户拍板）

1. **收件白名单是否收紧**：csv/json 进白名单后，rar/7z/gz/tar、rtf、gif 等死胡同格式是否从 `_SUPPORTED_MIMES` 剔除（后端也拦）？用户原则是"前端拦后端不动"，但收件白名单属挖掘层非上传层——**建议保持不剔除**（现状行为，改了会动存量语义），仅前端拦截。待确认。
2. **xlsx 家族的 xlsm（宏启用）**：探测上与 xlsx 同 MIME 族，未盘点宏处理，默认不在本次范围。
3. **html 的 xhtml 变体**（application/xhtml+xml）：native_html 支持但探测链不认，属顺手可修的小项，是否纳入待定。
