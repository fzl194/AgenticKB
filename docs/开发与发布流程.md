# 开发与发布流程

> 任何人改动本仓库（尤其 `knowledge_mining` / `kb-ui` / `agent_serving_java`）都按此流程走。
> 目标：分支隔离、小批提交、PR 合并、可回溯；上线有确定的重启与验证步骤。

---

## 0. 前置认知（项目特性，必读）

- **配置唯一来源是 `main_control_service`**：mining / serving / llm 的配置都从主控制服务拉，**不读 `.env`**（`.env` 已废弃，别恢复）。`main_control_service` 必须最先启动。
- **代码改完必须重启对应服务才生效**：
  - Python（mining / llm / main_control / mcp）：宿主机改文件后 `supervisorctl restart <name>`（容器内）或重起进程；**无热重载**。
  - Java（serving）：改了必须**重新 build 镜像**（无 volume 挂载）。
  - 前端（kb-ui）：`npm run dev` 有 HMR；构建产物部署需重新 `npm run build`。
- **数据库是远程共享 PG**（默认 `kb_db`）。测试只能打 `*_test` 库，**绝不**对 `kb_db` / 生产库跑测试或清表。

---

## 1. 分支与提交

1. **从最新 master 切分支**（不在 master 上直接提交）：
   ```bash
   git checkout master && git pull origin master
   git checkout -b <type>/<short-desc>     # 如 fix/kb-mining-bugs2、feat/xxx
   ```
2. **按工作面分批提交**，每批一个 coherent 的 commit，写清根因+修法：
   - 类型用 `feat / fix / refactor / docs / test / chore / perf / ci`。
   - 一条 commit 只做一件事；跨前后端的大改动拆成"后端一批 + 前端一批"。
   - message 正文写**根因**（最好附联调实测数据）+ **修法**，便于他人复盘。
3. **提交前自检**：`git status` 确认只含预期文件；自动生成文件（如 `kb-ui/components.d.ts`）的 IDE 噪声用 `git restore` 清掉再提交。

## 2. 本地验证（提交前必跑）

### 后端（knowledge_mining）
```bash
# Windows：用 anaconda 的 python，PATH 要带 Library/bin（libpq）
export PATH="/c/ProgramData/anaconda3/Library/bin:$PATH"
PY="/c/ProgramData/anaconda3/python.exe"

# 语法快检（秒级）
"$PY" -m py_compile <改动的.py>

# 跑相关测试（必须用 _test 库 + 允许清表护栏）
PG_HOST=121.89.90.178 PG_PORT=5432 PG_DBNAME=kb_db_test \
PG_USER=kb_user PG_PASSWORD=nis123qwe KB_ALLOW_TEST_TRUNCATE=1 \
  "$PY" -m pytest knowledge_mining/tests/kb/ -q        # KB 相关
  "$PY" -m pytest knowledge_mining/tests/test_v14_domain_pack.py -q   # 域包/检索单元
```
> 约束：库名必须以 `_test` 结尾（conftest 护栏）；`KB_ALLOW_TEST_TRUNCATE=1` 才会清表隔离。
> 远程库往返 ~40-80ms/查询，套件较慢（kb 全量 ~3.5min），可 `-k <名>` 只跑相关。

### 前端（kb-ui）
```bash
npm run build --prefix kb-ui        # vue-tsc 类型检查 + vite 构建，全绿才能合
# 单测（可选，Vitest）
cd kb-ui && npx vitest run --reporter=dot
```
> Node 用 v24（v18 跑不动 Vite）。

### Java（agent_serving_java）
```bash
cd agent_serving_java
rm -rf target/classes target/test-classes && mvn -o test    # 强制全量重编（增量编译会假绿）
```

## 3. 推送与 PR

1. **推送分支**（首次带 `-u` 设上游）：
   ```bash
   git push -u origin <branch>
   ```
2. **在 GitHub 建 PR**：`base: master ← compare: <branch>`。
   - 线性无分叉时显示 "Able to merge"；有冲突回本地 `git rebase origin/master` 解决。
   - PR 正文写清：做了什么 / 根因 / 验证证据 / 部署注意。
3. **合并方式选「Create a merge commit」**，**不要选 Squash**——会丢掉精心分的批次历史。
4. 合并后**先别删分支**，等本地同步完再删（见 §4）。

---

## 4. 合并后本地同步 + 清理

```bash
git checkout master
git pull origin master          # 或 git merge --ff-only origin/master
git branch -d <branch>          # 删本地分支
git push origin --delete <branch>   # 删远端分支
```
> 坑：切换分支前若工作区有 IDE 自动生成的幻影改动（`git diff` 为空但 status 显示 modified，多为 CRLF），`git restore <file>` 清掉即可，别带上提交。

---

## 5. 部署上线（按序）

合并到 master 后，让线上生效的顺序：

```bash
python -m main_control_service            # 1. 必须最先（配置中心）
python -m llm_service                      # 2.
python -m knowledge_mining.mining.api      # 3. 改了 mining 代码必重启
# serving 改了 application.yml / Java → 必须重新 build 镜像后重启
cd kb-ui && npm run build                  # 4. 前端构建产物部署
```
> 容器部署：`docker compose exec app supervisorctl restart mining`（Python 改宿主机文件后重启即生效）；Java/前端必须重建镜像。

## 5.1 品牌外观（网站名 / 图标）

站名、favicon、侧边栏 logo 均为**运行时可配**，配置在 `main_control_service/config/system/ui.yaml` 的 `site:` 块（`title` / `name` / `badge` / `logo_text` / `icon`）。

- **改法**：系统设置 → **品牌外观** Tab → 表单 + 图标选择（文件→base64 内嵌，或贴 data URI/URL）→ 保存即生效（前端启动期与保存后都会拉取并应用到 DOM，不必整页刷新）。
- **生效条件**：
  - 改名/换标**无需**重建前端镜像——值在 volume 挂载的 `ui.yaml`，`main_control` 重启或直接保存即生效。
  - 「读配置」的前端代码是一次性上线（本特性首次部署那次），那次才需重建 kb-ui 镜像（`npm run build`）。
  - `icon` 接受 data URI 或 http(s) URL；留空回落 `/favicon.svg` + `logo_text`。
- **粒度**：整站一份（部署级），不按 domain 区分。domain 的「显示名」是另一回事——来自 `domain_registry.yaml` 的 `display_name`。

## 6. 挖掘相关运维要点

改了挖掘算子 / 范式 / 域包检索策略后，**已挖文档不会自动重生**（内容哈希去重 → SKIP 复用旧 snapshot）。要应用新逻辑：

1. **重启 mining**（加载新代码）。
2. **强制重挖**：挖掘 Tab 勾「强制重挖」→「强制整库重挖」（或文件列表多选 → 强制重挖选中）。
   - force_redo 会清空旧 snapshot 的派生资产（单元/向量/关系/切片）并重跑 pipeline。
3. **范式签名变更自动失效**：换范式 / 版本 / 图变了，mine 时自动 force_redo，无需人工勾。

### 常见坑
- **检索单元 table_row 爆量**：已发布工作流的 manifest 编译期冻结算子参数；域包 `retrieval_policy.table_row:"off"` 是域级权威，会覆盖 manifest。改算子默认值对已发布 manifest 无效——靠域包策略或重新发布工作流。
- **移动文件后状态异常**：移动/改名必须同步 `document_key`（= 磁盘相对路径），否则挖掘派生的 key 对不上、状态永远 uploaded。当前已修；新写移动逻辑时注意。
- **挖掘请求延迟数秒**：后台线程冷导入 `mining.jobs.run`（~2.5s）曾占 GIL 卡 202；已在 lifespan 预热。若再出现类似延迟，先查是否又在请求路径里懒导入重模块。

## 7. 速查：一次完整迭代

```
master 最新 → 切分支 → 改代码 → py_compile/pytest/build 验证 →
分批 commit → push -u → GitHub PR（merge commit，不 squash）→
合并 → checkout master + pull + 删分支 → 重启服务 → 强制重挖验证
```
