# 文档入库解析地基：工业调研与演进方案

> 日期：2026-08-13
> 范围：文档发现、格式识别、解析路由、结构化解析、质量评估、原子制品持久化，以及到现有切片链路和上层知识消费的衔接。
> 不在本轮范围：具体代码实现、检索范式重构、领域知识编译实现、Agent 框架选型；但本文定义解析资产向这些上层能力开放的读取与证据契约。
> 状态：讨论稿，供架构评审和样本评测使用。

> 落地细化：本文的流程、状态、数据契约、验收场景和 Agent 工作包已展开到 `docs/文档解析平台化-能力规格与工作拆解.md`。后续实施应以该能力规格为入口，本文保留为工业调研和选型依据。

## 0. 结论先行

当前系统的问题不只是“解析库不够强”，而是把解析结果过早收缩成 `SectionNode -> ContentBlock -> RawSegmentData`，导致原文件中的页、坐标、阅读顺序、表格网格、图题关系、公式、脚注、置信度和解析证据无法成为稳定资产。之后再加强切片算法，只能在已经丢失的信息上优化。

新的地基应当是：

```text
Mining Run 冻结的源对象
  -> 文档探测与解析路由
  -> 一个或多个解析后端
  -> 统一 Parse IR（保真、可定位、可版本化）
  -> 规范化与质量门禁
  -> 原子文档制品
  -> Knowledge Access Layer 按需组装结构化上下文
  -> 按场景编译 Knowledge Artifact
```

这里的“原子知识”更准确地说是“带证据定位的原子文档元素”，它还不是领域知识。领域事实、规则、过程、实体关系和场景知识属于后续知识编译层。第一层必须先忠实回答：原文中有什么、位于哪里、彼此是什么结构关系、解析可信度多高。

本方案建议：

1. 以项目自有、后端无关的 `Parse IR` 为核心契约，而不是以 Markdown 为核心契约。
2. 默认采用 Docling 作为通用本地解析基线；中文复杂 PDF/扫描件并行评测 PP-StructureV3 与 MinerU；简单数字 PDF 设置低成本快速路径。
3. Unstructured 主要借鉴和复用其 Element/partition/chunk 思路，不建议直接让其数据模型成为项目真相源。
4. LlamaParse、Google Document AI、Azure Document Intelligence、AWS Textract 作为可插拔托管后端，不绑定核心数据模型。
5. Agent/LLM 不参与首轮确定性抽取；只用于解析路由辅助、低置信区域修复、图片/图表语义描述和质量复核。
6. `asset_raw_segments` 保留为兼容性派生资产；新链路先 shadow write Parse IR，再逐步让切片从 Parse IR 编译产生。
7. 在选定解析器前建设项目自己的 golden corpus 和评测门禁。工业界不存在对所有文档类型都最优的单一解析器。

## 1. 当前代码的真实链路

### 1.1 不是纯 Markdown 链路，但最终仍被统一压扁

当前摄入路径按格式分流：

| 格式 | 当前处理 | 主要位置 |
|---|---|---|
| Markdown/TXT | 直接读取文本 | `knowledge_mining/mining/ingestion/__init__.py` |
| HTML/CHM/HDX | 先转换为 Markdown | `ingestion/preprocessing.py` |
| XLS/XLSX | 识别工作表区域，渲染成 Markdown 表格并提前按 token 拆行 | `ingestion/excel_preprocessing.py` |
| DOC | LibreOffice/Word 转 DOCX | `ingestion/doc_preprocessing.py` |
| DOCX | `python-docx` 直接遍历段落、表格和图片 | `infra/docx_parser.py` |
| PDF | ingest 阶段先用 pdfminer 提文本，parse 阶段再用 pdfminer layout API 建结构树 | `ingestion/pdf_preprocessing.py`、`infra/pdf_parser.py` |

因此，现状并不是每种格式都先转 Markdown。PDF 和 DOCX 已有原生分支，Excel 也做了比普通 loader 更多的区域检测。然而所有路径最终只能写入：

```text
SectionNode
  title, level, children, blocks

ContentBlock
  block_type, text, language, level,
  line_start, line_end, structure
```

随后 `segment_document()` 立即进行合并、孤儿吸收、跨章节拼接和大段切分，产生 `RawSegmentData`；数据库的第一层内容资产也是 `asset_raw_segments`。

### 1.2 当前模型在进入切片前已经丢失的信息

`ContentBlock` 没有稳定 element id、父子关系 id、页对象、统一坐标、字符级来源 span、阅读顺序置信度、解析器置信度、样式、解析后端和版本。`structure` 是无约束字典，不足以成为跨解析器契约。

具体表现如下：

| 当前行为 | 结果 |
|---|---|
| PDF 页面元素按 `(-y0, x0)` 排序 | 双栏、跨栏标题、浮动图表容易产生错误阅读顺序 |
| PDF 文本块分类后只保留 text/type | 原先的 page、bbox、font size 没有进入普通段落元素 |
| PDF 通过题注正则判断 table | 不能恢复 table/cell/rowspan/colspan/header 网格 |
| DOCX 表格渲染为 Markdown 文本 | 合并单元格、单元格坐标、样式、表头语义、批注等难以保留 |
| Excel 在 ingest 阶段直接渲染并按 token 拆表 | 原工作簿的 cell identity、公式、命名区域、合并关系与展示值被混在一起 |
| HTML/帮助文档转 Markdown | DOM id、链接目标、列表层级、rowspan/colspan 等原始证据被改写或展开 |
| segment 会合并不同 block | 一个 segment 可能不再对应单一原文区域，精确引用和重编译困难 |
| parser 失败通常返回 None | 缺少统一质量分、逐页诊断、后端回退决策和可运营重试队列 |

还有两个基础性问题：

1. PDF 在 ingest 与 parse 两次读取和解析，前一次主要用于 `content` 与 hash，后一次才生成树，两个结果之间没有同一 Parse Run 契约。
2. `asset_document_snapshots.normalized_content_hash` 表达的是预处理文本或原始文件 hash，不表达“某个解析器配置下的结构化解析制品版本”。解析器升级后的结果无法被自然区分和重建。

### 1.3 当前值得保留的部分

本次重构不应否定已有底座。以下能力可以保留：

| 可保留能力 | 后续定位 |
|---|---|
| document/snapshot/link 分离 | 继续承担文档身份、内容版本与来源追踪 |
| 原文件 raw hash 与 snapshot 生命周期 | 继续作为幂等和复用依据 |
| `SectionNode` 与现有 segmenter | 作为兼容投影和旧链路 adapter，不再作为 Parse IR |
| `asset_raw_segments`、relations、retrieval_units | 作为 Parse IR 下游派生制品 |
| 图片物化和 hash | 合并进统一 BinaryAsset 管理 |
| build/release | 继续发布可检索制品，不直接承担解析真相源 |
| domain profile 中的切片策略 | 后移到 Chunk Compiler，不进入解析后端 |

### 1.4 仓库已有方案不是从零开始

仓库已有 `docs/superpowers/plans/2026-07-25-document-processing-mining-refactor.md`，曾提出不可变 Parse Result、Parsed Blocks、Segment Set，以及 Build 固定多层制品身份。代码核验显示对应 schema、repository 和 `document_processing` 包尚未落地，当前运行链路仍从 `asset_raw_segments` 开始持久化。结合产品对版本复杂度的复盘，本报告只继承其中的 Parse IR、来源映射和解析/切片工程分层，不继承三套并行版本实体。

本报告应视为对这份计划的工业化补全，而不是另起一套概念：

| 已有计划可直接继承 | 本报告建议补强 |
|---|---|
| Parse 与 Segment 工程阶段分离 | 统一提交到 Document Snapshot；增加 Parse Run、backend raw artifact 和多后端 adapter |
| parser/config 版本化 | 增加模型版本、依赖指纹、路由版本和 SBOM |
| parsed block 与 source ranges | 提升为 Page/Sheet/Slide/Topic + Element + Evidence Span + Relation |
| PDF page+bbox | 统一 coordinate envelope、polygon、confidence 和 page quality |
| structure_json | 表格 cell、图片、公式成为独立 structured asset |
| Build 固定不可变制品 | 简化为固定 Document Snapshot，作为 release 可复现不变量 |

已有 snapshot workflow binding 会将 `workflow_id/version/graph_hash` 写入 snapshot 身份。目标是在同一 Snapshot 上补齐 parser 代码、模型、依赖、Parse IR schema 和 compiler 指纹，而不是另建 Parse Result 版本表。

### 1.5 还需要纳入重构范围的底层风险

| 风险 | 影响 |
|---|---|
| Workflow 的 `parse_segment` handler 连续执行 parse 和 segment | Parse 与 Segment 在运行契约上仍未真正分层 |
| TXT parser 内部已经按 300 token/30 overlap 切分 | parser 输出不是纯原子结构，无法独立重切 |
| segment 合并/拆分复制或覆盖单一 offsets | 来源证据不能表达 segment 与多个 element span 的真实映射 |
| 主链 parser identity 常退化为 `unknown` | 解析 provenance 不足，无法审计和复现 |
| Excel 被改写为 `file_type=markdown` | 原生 MIME 与 rendered view 混淆，内容身份被预处理形式污染 |
| 文件被全量 `read_bytes()`，部分压缩包直接 `extractall` | 超大文件、压缩炸弹、路径穿越和内存资源需要统一 intake 门禁 |

因此第一里程碑不能只是“接入 Docling”，还必须把运行身份、来源映射、资源限制和安全准入一起做成解析模块契约。

## 2. 工业级文档解析已经在做什么

### 2.1 主流范式：Document Intelligence，而非文本转换

工业系统通常把解析拆成多个可观察步骤：

```text
格式/MIME 探测
  -> 原生结构提取或页面渲染
  -> OCR（按需）
  -> Layout Detection
  -> Reading Order
  -> Element Classification
  -> Table / Formula / Figure 专项识别
  -> Hierarchy Reconstruction
  -> Unified Document Model
  -> Quality Evaluation
```

各产品输出名字不同，但共同点很稳定：解析结果是元素或 block 图，而不是一串 Markdown。Markdown、HTML、JSON、chunks 都只是这个模型的导出视图。

- Docling 提供统一 `DoclingDocument`，保存文本、表格、图片、层级、布局框和 provenance，可再导出 Markdown/HTML/JSON。[Docling document model](https://docling-project.github.io/docling/concepts/docling_document/)
- Unstructured `partition` 输出带类型和 metadata 的 Element 列表，支持 parent/category depth、page、coordinates，并明确承认 chunk 合并会损失部分元素级信息。[Document elements](https://docs.unstructured.io/api-reference/legacy-api/partition/document-elements) [Chunking](https://docs.unstructured.io/open-source/core-functionality/chunking)
- AWS Textract 输出 PAGE/LINE/WORD/TABLE/CELL/KEY_VALUE/LAYOUT 等 Block，以 ID 和 relationship 连接，带 geometry 和 confidence。[AnalyzeDocument](https://docs.aws.amazon.com/textract/latest/APIReference/API_AnalyzeDocument.html)
- Azure Layout 输出 pages、paragraphs、words、selection marks、tables、figures、sections 与 spans，并可额外生成 Markdown。[Azure Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-3.1.0)
- Google Gemini Layout Parser 强调元素层级、表格、图片、标题和祖先标题上下文，再从布局树产出 RAG chunks。[Google Layout Parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk)

### 2.2 专用模型与 VLM 已成为补充路径

传统 pipeline 仍然适合高吞吐、可解释的文字和布局解析；VLM 更适合复杂视觉语义、图表、手写、极端版式和局部修复。成熟系统开始混合使用二者，而不是让所有页面都经过昂贵 VLM。

PP-StructureV3 将版面检测、OCR、文档预处理、表格、公式、印章、图表拆成可选模块，并提供 JSON、可视化和 Markdown 输出；它还保留比纯 Markdown 更细的坐标信息。[PP-StructureV3](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-StructureV3.en.md)

MinerU 和 Marker 都提供页面/element JSON、阅读顺序、表格、公式与图片能力；Marker 的 JSON 直接以 Page、Line、Span、Table、Equation、Caption 等 block 组成树。[MinerU](https://github.com/opendatalab/MinerU) [Marker](https://github.com/datalab-to/marker)

### 2.3 工业上的真正难点已经转向评测与路由

OmniDocBench 对九类来源、19 类布局和多种属性进行分层评测，说明不同方法会在文本、布局、阅读顺序、表格等维度表现不同。[OmniDocBench](https://openaccess.thecvf.com/content/CVPR2025/html/Ouyang_OmniDocBench_Benchmarking_Diverse_PDF_Document_Parsing_with_Comprehensive_Annotations_CVPR_2025_paper.html)

2026 年的 ParseBench 进一步按表格、图表、内容忠实度、语义格式和视觉 grounding 评估 Agent 所需的解析正确性；其结论同样是没有一个方法在所有维度稳定占优。[ParseBench paper](https://arxiv.org/abs/2604.08538) [ParseBench repository](https://github.com/run-llama/ParseBench)

对本项目的含义是：不能先凭 GitHub 热度选一个解析器再让全部文档迁移。应先定义内部契约和项目语料评测，然后让路由策略随评测结果演进。

## 3. 可直接复用的主流方案

### 3.1 方案比较

| 方案 | 适合角色 | 优点 | 主要边界 | 建议 |
|---|---|---|---|---|
| Docling | 通用本地基线、统一模型参考 | Python 友好；格式广；布局、阅读顺序、表格、公式、图片、OCR；`DoclingDocument` 完整；MIT | 模型依赖较重；复杂中文和特定表格仍需项目样本验证；模型许可证需逐项核对 | 首选默认 adapter，不能把其模型直接暴露为数据库契约 |
| Unstructured OSS | 多格式 partition、元素与 chunk 参考 | Element 类型成熟；格式路由广；fast/hi_res/OCR 策略；Apache 2.0 | 部分高级质量由 API/托管能力提供；元素模型在不同格式间保真度不一致 | 可作为补充 adapter，也适合复用 element/chunk 思路 |
| PP-StructureV3 | 中文扫描件、复杂版式、表格公式图表 | 中文生态强；模块可拆；坐标细；可训练/微调；Apache 2.0 主项目 | Paddle/GPU 依赖较重；需要独立服务化和模型版本治理 | 作为中文复杂 PDF 的重点候选，与 Docling 做 A/B |
| MinerU | 中文/科研 PDF、公式表格、复杂阅读顺序 | rich JSON、可视化质量检查、OCR/VLM 双路径、部署方式完整 | 2026 许可证为 Apache 2.0 加附加商业和标识条款；依赖和资源较重 | 可作为高质量 sidecar；法务确认后再进入默认生产栈 |
| Marker | 科研 PDF、公式和图片、LLM 修复 | JSON block 丰富；公式/表格能力强；支持局部 LLM 增强 | 代码 Apache 2.0，但模型权重有额外商业门槛；依赖 PyTorch/GPU | 作为专项候选，不建议现在成为全局默认 |
| PyMuPDF4LLM | 简单数字 PDF 快速路径 | 速度快；页面 chunks、表格和图片；纯本地 | AGPL 或商业许可；复杂布局理解弱于完整 DI pipeline | 若许可证允许，可做 fast path；否则以 pypdfium/pdfplumber 类方案替代 |
| Apache Tika | 长尾格式探测、元数据、嵌套文件 | 支持上千格式；流式；成熟；可提取嵌套内容；Apache 2.0 | Java 服务；重点是文本/metadata，不是高保真视觉结构 | 适合作为文件类型与长尾 fallback，不是复杂 PDF 主解析器 |
| OCRmyPDF | 扫描 PDF 预处理 | deskew、cleanup、PDF/A、可搜索文本层；大规模验证充分 | 不是布局和语义结构解析器；需要 Tesseract/Ghostscript | 作为扫描件规范化组件，不直接产 Parse IR |
| LlamaParse | 托管高质量/Agentic fallback | 对复杂表格、图表、视觉 grounding 有竞争力；接入快 | 云成本、数据外发、供应商依赖；SDK 开源不等于服务开源 | 合规允许时作为 failover 和 benchmark baseline |
| Azure Document Intelligence | 企业 Layout/表单 fallback | sections/figures/tables/spans/polygon 成熟；表单生态强 | 云成本、区域/合规、供应商绑定 | 表单、票据、复杂企业文档的可插拔后端 |
| AWS Textract | 表单、票据、表格、签名 | Block graph、geometry、confidence、query/form 能力成熟 | 输入格式和通用文档层级能力有限；云绑定 | AWS 环境中的表单专项后端 |
| Google Document AI Layout | 高保真 RAG 布局和分块 | 层级、图表、表格、祖先标题 chunks；OCR + Gemini | 云成本、区域/合规、模型行为版本化 | Google Cloud 环境下的高质量后端 |

许可证是架构约束，不是上线前补查事项：PyMuPDF/PyMuPDF4LLM 是 AGPL 或商业许可；Marker 的代码与模型权重不是同一许可；MinerU 2026 版有附加商业与在线服务标识条件。[PyMuPDF licensing](https://github.com/pymupdf/PyMuPDF) [Marker licensing](https://github.com/datalab-to/marker#commercial-usage) [MinerU license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)

Docling 代码使用 MIT 许可，不代表其所有可选 OCR/VLM/版面模型都自动继承 MIT。正式选型应对 Python 包、系统动态库、模型权重、数据集派生约束和容器镜像生成统一 SBOM，并把许可证扫描放入 parser backend 的准入门禁。只扫描 `pip` 依赖是不够的。

### 3.2 建议的初始技术组合

建议避免把十个库都装进当前 FastAPI 进程。解析器应通过 adapter 接口运行，重型模型后端优先 sidecar 化。

| 层级 | 初始建议 |
|---|---|
| MIME/格式探测 | `python-magic`/libmagic；必要时用 Tika 服务覆盖长尾与嵌套格式 |
| Markdown/TXT | `markdown-it-py` + 编码检测，直接产 Parse IR |
| HTML/CHM/HDX | `lxml` 或 BeautifulSoup 保留 DOM 关系；CHM/HDX 先解包，不先拼成单一 Markdown |
| DOCX/PPTX/XLSX | Docling 作为统一入口；保留 `python-docx`、`python-pptx`、`openpyxl` 专项 adapter 作为高保真补充 |
| 简单数字 PDF | Docling standard 或经评测后的轻量路径 |
| 中文复杂/扫描 PDF | PP-StructureV3 与 MinerU A/B；OCRmyPDF 可做可选预处理 |
| 科研公式密集 PDF | MinerU/Marker 专项候选 |
| 表单、票据、签名 | Azure/AWS/Google 专项 adapter，不让通用 parser 硬猜 |
| 极低置信页 | VLM 或托管 parser 逐页修复，不重跑整份文档 |

Docling 适合作为首个默认后端，原因不是认定其对所有文档质量最高，而是其统一模型、Python API、本地部署、许可和格式覆盖最适合帮助本项目快速建立正确架构。复杂中文 PDF 的生产选择必须由项目样本评测决定。

Tika 的定位需要保持克制：它适合 MIME 检测、嵌套附件、元数据以及 `.doc/.ppt/.xls` 等长尾/遗留格式兜底，不负责复杂 PDF 的高保真原子结构。这样既利用成熟生态，也不会因为“支持上千格式”而误判其布局理解能力。

## 4. 建议的模块边界

```text
File Management + MinIO Object Store
  -> Logical Document 当前内容
  -> Mining Run 冻结输入
  -> File Inspector
  -> Parser Router
  -> Parser Adapter(s)
  -> Parse IR Normalizer
  -> Structural Reconciler
  -> Parse Quality Gate
  -> Atomic Artifact Store
  -> Chunk / View Compiler
  -> Knowledge Access Layer
```

### 4.1 Document Intake

职责仅包含原文件接收、上传会话、病毒/压缩包安全检查、文件数/展开后大小/压缩比限制、单文件与总批次大小限制、流式 raw hash、MinIO 对象提交和来源元数据。它不生成 Markdown，也不做切片。

本版本固定采用 MinIO 作为 S3 兼容对象存储；PostgreSQL 保存文件目录、权限、Document 当前内容、知识 Snapshot 和对象引用。MinIO 不是数据库，object key 不是用户目录，presigned URL 不是持久化引用。

产品不提供文档版本管理。用户编辑文档时保持 document id 不变，采用新对象写入加当前指针切换；知识更新时 Mining Run 冻结当时的 `storage_object_id + raw_hash + content_revision`，成功后由一个 Document Snapshot 统一承载 Parse IR、elements、segments 和后续知识资产。

### 4.2 File Inspector

不能只按扩展名路由。应输出 `DocumentProfile`：

```json
{
  "detected_mime": "application/pdf",
  "source_format": "pdf",
  "page_count": 86,
  "has_text_layer": true,
  "text_coverage": 0.91,
  "image_page_ratio": 0.08,
  "suspected_scan": false,
  "layout_complexity": "high",
  "multi_column_ratio": 0.42,
  "table_page_ratio": 0.18,
  "formula_page_ratio": 0.03,
  "languages": ["zh", "en"],
  "encrypted": false
}
```

这一步主要是确定性探测，可用抽样页完成。Agent 只能辅助解释异常，不应成为基本 MIME/安全判断的唯一来源。

### 4.3 Parser Router

Router 输入 DocumentProfile、domain policy、数据外发策略、成本/SLA 和历史评测结果，输出不可变 `ParsePlan`：

```json
{
  "route": "pdf_complex_zh",
  "primary_backend": "pp_structure_v3",
  "fallback_backends": ["docling_standard", "mineru_pipeline"],
  "ocr_policy": "auto",
  "table_policy": "structure",
  "formula_policy": "latex",
  "figure_policy": "extract",
  "cloud_allowed": false,
  "quality_profile": "technical_manual_v1"
}
```

路由版本必须写入 Parse Run，以便回放、对比和解释成本。

### 4.4 Parser Adapter

每个 adapter 只负责把第三方输出转换成项目 Parse IR，不允许直接写 segment 表。建议接口：

```python
class DocumentParser(Protocol):
    parser_id: str

    def inspect(self, source: SourceArtifact) -> BackendCapabilities: ...
    def parse(self, source: SourceArtifact, plan: ParsePlan) -> ParseResult: ...
```

Adapter 的运行输出同时包含 Parse IR candidate、backend raw artifact、metrics 和 diagnostics。保留 backend raw artifact 很重要：当 IR adapter 有 bug 时，可以重放转换而不必再次调用昂贵云 API 或模型。

术语上区分：`Parse Run` 是一次可失败、可重试的执行；Parse IR 是 Run 产生的结构化解析制品；`Document Snapshot` 是成功知识更新的唯一不可变业务结果。失败只留 Run，成功才形成 Snapshot，Build/Release 只选择 Snapshot。

### 4.5 Parse IR Normalizer

负责坐标系统统一、element type 映射、稳定 id、文本规范化、页码、阅读顺序、关系规范化和 schema 校验。第三方库升级只影响 adapter，不影响下游资产契约。

### 4.6 Structural Reconciler

处理跨页表格、跨页段落、caption 关联、脚注、目录与正文、重复页眉页脚、hyphenation、列表续接等文档级问题。它与 parser 分开，便于后续替换规则或局部使用 LLM。

### 4.7 Parse Quality Gate

解析成功不等于结果可发布。质量门禁需要决定 `PASS / WARN / FAIL / NEEDS_REPAIR`，并可把低质量页路由到另一个后端。

### 4.8 Chunk / View Compiler

它从通过门禁的 element graph 编译切片，不修改原子元素。不同场景可产生不同 view：

| View | 示例 |
|---|---|
| paragraph view | 段落 + 祖先标题 |
| section view | 一个小节的标题、正文、局部摘要 |
| table view | 整表、表头 + 行、表格结论 |
| procedure view | 前置条件 + 步骤 + 警告 |
| figure view | 图题 + 图片描述 + 正文引用 |
| citation view | 精确页码/bbox 的证据片段 |

这一步才读取 domain/scenario 的 chunk policy。解析层不应该知道检索 token 上限。

### 4.9 Knowledge Access Layer

工业级结构化解析的价值，不是多存几张表，而是让上层稳定地读取完整结构。Agent 不应直接拼接 `elements + relations + table_cells`，否则每个场景都会重复实现标题补全、跨页表、权限和证据定位。

建议提供统一读模型：

| View | 回答的问题 | 产生方式 |
|---|---|---|
| Outline View | 文档整体结构是什么 | 根据 container/heading relations 动态组装 |
| Section View | 某一章节完整讲了什么 | 聚合标题链、正文、表格、图片、脚注和 spans |
| Evidence Bundle | 一组召回结果需要补哪些证据 | 围绕命中 elements 扩展父级、邻居和引用关系 |
| Table View | 表格的真实结构和上下文是什么 | 读取 grid/header/merge/caption/footnote/reference |
| Procedure Candidate View | 哪些原文片段可能共同描述一个过程 | 结构规则聚合，仍需场景编译和校验 |

这些 View 是 Snapshot 上的动态读模型，不是新的版本层。默认不为每种 View 建业务表；只有高频、高成本结果才缓存，缓存可以随时删除并从不可变 Snapshot 重建。

### 4.10 从 Retrieval Unit 到 Knowledge Artifact

现有检索不是废弃，而是改变职责：Retrieval Unit 负责低成本找候选，Knowledge Access Layer 负责把候选还原成完整、可引用的上下文，Agent 才负责按场景 schema 编译高级知识。

```text
用户问题 / 编译任务
  -> keyword/vector/hybrid 检索 Retrieval Units
  -> 命中 segment/element ids
  -> hydrate Section View / Evidence Bundle
  -> Agent 按领域模型和场景 schema 抽取
  -> 规则校验、冲突检查、证据覆盖检查
  -> Knowledge Artifact + Evidence Links
```

例如检索命中“步骤 3：执行切换”，不能直接生成 SOP。Evidence Bundle 还要补齐该步骤所属章节、前置条件、步骤 1-2、警告、结果判据以及引用的参数表。最终 SOP 是新知识制品，原步骤和表格仍是其证据。

这里还要区分两种 Agent 使用方式：在线问答只临时读取 Evidence Bundle 并返回带引用的答案，不修改知识库；知识编译才把可长期复用的 SOP、规则、FAQ 等持久化。不能把每次 Agent 回答都当成知识资产。

## 5. Parse IR：新地基的核心契约

### 5.1 顶层对象

```text
ParsedDocument
  document_snapshot_id
  parse_run_id
  schema_version
  pages[]
  elements[]
  relations[]
  binary_assets[]
  structured_assets[]
  diagnostics
```

### 5.2 Page

```text
page_id, page_number, width, height, coordinate_unit,
rotation, rendered_image_ref, text_layer_kind, language,
quality, metadata
```

任何 bbox 都必须绑定 page 与 coordinate system。不能再把 PDF 坐标、像素坐标和 Office 逻辑坐标混在无约束 JSON 中。

### 5.3 Element

建议首版 element types：

```text
title, heading, paragraph, list, list_item, code, quote,
table, figure, chart, formula, form_field, key_value,
footnote, page_header, page_footer, page_number, toc_entry,
caption, reference, signature, selection_mark, unknown
```

基础字段：

```text
element_id
element_type
parent_id
order_index
text
normalized_text
page_spans[]
source_spans[]
style
confidence
parser_annotations
metadata
```

`confidence` 需要说明来源和维度，不建议只存一个模糊浮点数：

```json
{
  "text": 0.98,
  "layout": 0.91,
  "type": 0.88,
  "reading_order": 0.76,
  "source": "pp_structure_v3"
}
```

### 5.4 Evidence Span

Evidence Span 是引用与审计的最小单位：

```text
page_id
char_start / char_end（相对 element text）
bbox / polygon
source_object_ref（如 DOCX paragraph id、XLSX sheet!A1、HTML xpath）
raw_text
ocr_confidence
```

PDF 用 page+bbox，DOCX 可用 OOXML 节点/段落索引，Excel 用 sheet+cell/range，HTML 用 DOM path。不同格式不必伪造同一种坐标，但必须有统一 envelope。

### 5.5 Structured Assets

表格、图片、公式不能只塞进 `structure_json`。

表格至少保存：

```text
table_id, caption_element_id, page_spans,
rows, columns, cells[], header_regions,
footnote_element_ids, continuation_of, confidence

cell:
  row_index, column_index, row_span, column_span,
  text, normalized_value, value_type, formula,
  is_header, source_span
```

图片/图表至少保存原图、裁剪区域、caption、正文 mention 关系；VLM 描述属于 derived annotation，不能覆盖原始 caption。

公式保存原始视觉区域、识别 LaTeX、行内/块级类型和置信度。表格/公式的 HTML、Markdown、CSV 都是导出形式，不是真相源。

### 5.6 Relations

首版关系建议控制在确定性文档关系：

```text
parent_of, next_in_reading_order, contains,
caption_of, footnote_of, continues_on,
references, anchored_at, derived_from
```

领域语义关系，例如 `causes`、`depends_on`、`implements`，属于后续 Knowledge Compiler，不应混入 Parse IR。

## 6. 持久化建议

不建议把完整 Parse IR 只存为数据库一行超大 JSONB，也不建议一开始把每个 word/cell 完全关系化。采用“不可变 artifact + 可查询投影”更稳妥：

```text
MinIO 对象存储
  source binary
  backend raw output
  canonical Parse IR JSON
  rendered pages / extracted images

PostgreSQL
  logical document / folder / permission
  upload session / storage object registry / document current content
  parse run 与冻结输入
  page/element 索引
  structured asset 索引
  quality report
  到现有 segment/unit 的映射
  Knowledge Access 查询投影/可选缓存
  后续 Knowledge Artifact 与 element/span 证据关系
```

建议概念表：

| 表 | 作用 |
|---|---|
| `asset_upload_sessions` | 上传状态、staging object、幂等、过期和失败原因 |
| `asset_storage_objects` | MinIO bucket/key/version、hash、size、MIME、状态、retention |
| `asset_storage_object_refs` | Document/Snapshot/Binary Asset 对对象的显式引用和 GC 保护 |
| `asset_documents` 扩展 | 当前 storage object、raw hash、content revision、更新时间和知识过期状态 |
| `mining_run_documents` 扩展 | Run 启动时冻结 source object、raw hash 和 content revision |
| `asset_document_snapshots` 扩展 | 唯一知识版本根；固定源输入、parser/workflow/compiler 指纹、Parse IR object 和质量结论 |
| `asset_document_pages` | 页维度、渲染图、页面质量、文本层类型 |
| `asset_document_elements` | element id/type/parent/order/text/page range/confidence/source refs |
| `asset_document_element_relations` | 确定性结构关系 |
| `asset_document_structured_assets` | table/figure/formula/chart 的细结构或 artifact URI |
| `asset_document_binary_assets` | 图片、附件、页面渲染及 hash |
| `asset_parse_quality_reports` | 指标、问题、低置信页、修复动作 |
| `asset_segment_element_links` | segment 与 source elements/spans 的多对多映射 |

Knowledge Access View 首期不新增永久业务表。若性能评测证明需要缓存，可增加统一的 `asset_document_view_cache`，键为 `snapshot_id + view_type + view_config_hash`，内容较小则存 JSONB，较大则指向 MinIO object；它不是事实源，不参与 Build 版本选择。

后续知识编译建议增加两张边界清晰的表，而不是把 Agent 总结写回 elements 或 retrieval units：

| 表 | 作用 |
|---|---|
| `asset_knowledge_artifacts` | 保存 Snapshot 下、特定 scenario/schema/compiler 生成的规则、SOP、FAQ、事实、实体关系等 |
| `asset_knowledge_artifact_evidence` | 保存 artifact 内每个 claim 到 element/evidence span 的支持、反证或上下文关系 |

Knowledge Artifact 直接继承 `document_snapshot_id` 的知识历史边界，不再建立第二套 Artifact Version。同一次知识更新可在 Snapshot 提交前生成多个场景制品；Snapshot 进入 READY 后不得追加或覆盖。新增场景或重新编译需要产生新 Snapshot。制品可以成为新的检索来源，但必须保留回到原子证据的链路。

在线 Agent Answer 默认只保存请求 trace、所用 Release/Snapshot 和引用 ids，不写入 Artifact 表。只有用户或流程明确触发“沉淀为知识”，才启动新的知识更新和 Snapshot。

不新增 Source Version、Parse Result 和 Segment Set 三条并行版本线。Parse IR 可以作为 MinIO artifact 被新 Snapshot 复用，但业务历史统一由 `asset_document_snapshots` 表达；Build/Release 继续选择 Snapshot。

建议身份关系：

```text
LogicalDocument 1 -- 1 current StorageObject
MiningRunDocument -> frozen StorageObject / raw hash / content revision
Successful Run 0..1 -> DocumentSnapshot
DocumentSnapshot 1 -- N Page / Element / Asset / Segment
RawSegment       N -- M ElementSpan
RetrievalUnit    N -- M RawSegment / ElementSpan
```

文档更新只更新当前内容并令知识变为 outdated，不自动改变旧 Release。解析器或切片策略升级并执行知识更新时产生新 Snapshot；旧 Build/Release 仍固定旧 Snapshot，因此历史可复现。

## 7. 质量体系与评测

### 7.1 单文档运行质量指标

建议至少记录：

| 维度 | 指标示例 |
|---|---|
| 完整性 | page coverage、text coverage、empty page ratio、orphan element ratio |
| OCR | mean/p10 confidence、乱码率、语言匹配、重复文本率 |
| 布局 | overlap ratio、out-of-page bbox、unknown type ratio、多栏顺序异常 |
| 层级 | heading tree completeness、level jump、孤立 caption、TOC 对齐率 |
| 表格 | cell coverage、row/col consistency、merged cell validity、跨页连续性 |
| 图片/公式 | extraction success、caption binding、formula parse validity |
| 来源 | element source span coverage、可渲染引用率 |
| 性能 | pages/s、CPU/GPU memory、cost/page、retry count |

质量分不能只用于 dashboard。它必须参与路由：例如 table validity 低但页面含表格，就把相关页送到表格专项后端；OCR 置信度低则重跑 OCR/VLM；无法修复则进入人工检查队列。

### 7.2 项目自己的 Golden Corpus

第一阶段不需要上千份文档，但必须覆盖真实难例。建议 80-150 份、约 1,000-2,000 页：

| 类别 | 建议样本 |
|---|---|
| 云网设备手册 | 单栏、多栏、命令、告警表、流程图 |
| 中文规范/标准 | 多级标题、页眉页脚、脚注、跨页表 |
| 扫描文档 | 倾斜、低分辨率、印章、双语 |
| Word | 样式标题、嵌套列表、合并表格、浮动图 |
| Excel | 多 sheet、区域表、合并表头、公式、隐藏行列 |
| HTML/CHM/HDX | TOC、内部链接、嵌套表格、图片引用 |
| 异常文件 | 加密、损坏、超大、空白、错误扩展名 |

标注优先级：先标 element type、reading order、heading tree、table grid、caption relation 和 citation span；不必一开始逐字标注所有 OCR。

### 7.3 三层验收

1. Parse fidelity：使用 OmniDocBench/docling-eval 类指标检查文本、布局、顺序、表格。
2. Retrieval impact：在固定检索器下对比 Recall@K、证据命中、表格问答正确率。
3. Agent task success：对垂直场景任务检查引用正确、步骤完整、数字不串行、图表结论可验证。

最终选型应是质量、成本、吞吐、部署、许可和合规的 Pareto 结果，不只看 Markdown 肉眼效果。

## 8. Agent/LLM 在解析层的合理位置

### 8.1 不应负责的事情

- 不应作为文件类型识别、原文件 hash、基础文本抽取的唯一执行者。
- 不应把整份文档自由总结后当作原子资产。
- 不应在没有 source span 的情况下“修正”原文。
- 不应让生成结果覆盖确定性 parser 输出。

### 8.2 适合负责的事情

| 能力 | 使用方式 |
|---|---|
| 路由辅助 | 根据 inspector 特征和历史失败解释选择后端，但决策写入 ParsePlan |
| 局部修复 | 只处理低置信页/区域，输出 patch 与 source region |
| 图表理解 | 从 chart image 生成结构化 series/description，保留模型与 prompt 版本 |
| caption 绑定 | 在规则无法确定时给候选关系和置信度 |
| 层级修复 | 对标题跳级、跨页表、目录映射给出候选 patch |
| 质量复核 | 根据页面图与 IR 对照发现漏表、错序、数字错位 |

所有 LLM 结果都作为 annotation/patch：包含 model、prompt、input artifact、输出、confidence、review status。原始 Parse IR evidence 不被静默改写。

## 9. 与现有资产链路的演进方式

### Phase 0：先立契约与评测，不替换生产链路

产出：Parse IR v0.1、adapter contract、quality schema、golden corpus、基线评测脚本。

使用当前 parser、Docling、PP-StructureV3/MinerU 各跑一版，统一转换成 Parse IR，对比结果。此阶段不改 serving。

### Phase 1：Shadow Parse

新解析模块与旧 `parse -> segment` 并行运行。新链路写 Parse Run/IR/quality，但发布仍使用旧 segments。

目标是验证资源、稳定性、schema 完整度和可回放性。失败不影响当前生产入库。

### Phase 2：Parse IR 生成兼容 SectionNode

实现 `ParseIR -> SectionNode` compatibility adapter，让现有 segmenter 从新 IR 的兼容投影运行。这样可先替换解析而不同时重写 enrich/retrieval_units。

同时建立 `segment -> element spans` 映射，补上精确引用链。

### Phase 3：Chunk Compiler

把 `segment.py` 从“解析树后处理器”重构为“基于 element graph 的 view compiler”。支持 paragraph/section/table/procedure 等多种策略，并保证每个 chunk 可回溯 element spans。

### Phase 4：按场景知识编译

先交付 Knowledge Access Layer：Retrieval Unit 用于粗召回，Access Layer 根据命中的 element ids 返回 Section View/Evidence Bundle。Agent 再按领域模型和场景 schema 生成领域事实、规则、流程、FAQ、wiki、实体图等知识制品，并通过 Artifact Evidence 回指原子元素。解析层到此才真正为上层 Agent 提供可靠地基。

### Phase 5：删除旧直连路径

在新链路覆盖率、质量和回滚达到要求后，删除 PDF/DOCX 自研 heuristic 主路径；保留其作为轻量 fallback 或测试 fixture。`asset_raw_segments` 继续存在，但明确是版本化派生资产。

## 10. 必须先拍板的架构决策

### 建议现在拍板

| 决策 | 建议 |
|---|---|
| Markdown 是否继续作为核心中间格式 | 否，只作为导出/调试视图 |
| 原子层是否等于 chunk | 否，原子层是 element + evidence span + structural relation |
| 是否绑定一个解析器的数据模型 | 否，建立项目 Parse IR 和 adapter |
| 知识历史由什么表达 | 只由 Document Snapshot 表达；Run 记录执行，Parse IR/Segments 是 Snapshot 子制品 |
| 解析与切片是否分离 | 是，切片是可重编译 view |
| 是否全量用 LLM/VLM | 否，按低置信区域和专项能力使用 |
| 是否先换库再评测 | 否，先 golden corpus 与统一评测 |
| 是否保留旧链路迁移期 | 是，shadow write + compatibility adapter |
| 正式文件存储是否继续使用共享本地卷 | 否，本版本固定 MinIO；本地 `storage_path` 仅作迁移双读 |
| 文件夹是否映射为 MinIO 前缀 | 否，`kb_folders`/PostgreSQL 是逻辑目录事实源，移动不搬对象 |
| 是否建设文档版本管理 | 否，Document 只维护当前内容；MinIO version id 仅作运维防护 |

### 需要样本评测后拍板

| 问题 | 评测后决定 |
|---|---|
| 默认 PDF backend | Docling standard、PP-StructureV3、MinerU 的项目语料结果 |
| 是否引入 PyMuPDF fast path | 质量收益、吞吐收益与 AGPL/商业许可决策 |
| MinerU 是否进入默认栈 | 中文复杂 PDF 收益、资源成本与附加许可接受度 |
| VLM 使用哪家/是否本地化 | 数据合规、图表/手写效果、成本和延迟 |
| Parse IR 存储粒度 | 每 element 关系化范围、JSON artifact 大小与查询需求 |
| word/span 是否全量保存 | 精确 citation 需求与存储成本 |

## 11. 推荐的第一轮验证项目

本轮讨论之后，不能立即重写 parser。应先完成 MinIO 文件地基，再开展一个 2-3 周的“解析地基验证”：

1. 冻结 Storage Object、Upload Session、Document 当前内容、Frozen Input 与 Snapshot 契约，部署 MinIO 和统一 Object Store Port。
2. 改造文件上传/下载/在线编辑/移动/删除，建立存量本地文件的 MinIO 回填和双读方案。
3. 从现有垂直语料抽取 30-50 份代表文档，建立最小 golden corpus。
4. 定义 Parse IR v0.1 和 `ParserAdapter`，只覆盖 page/element/table/figure/span/relation/quality。
5. 编写当前 parser、Docling、PP-StructureV3、MinerU 四个离线 adapter 原型，统一从 Run 冻结的 Storage Object 获取输入。
6. 评测文本完整性、阅读顺序、标题树、表格、引用定位、吞吐和资源，选出 default/fast/complex/fallback 路由。
7. 产出数据库投影与 shadow-write RFC，再进入 TDD 实现。
8. 用现有 Retrieval Unit 做一次候选召回，再从 Parse IR 组装 Evidence Bundle，验证 Agent 无需直接查询底层表即可获得完整章节、表格和引用上下文。

这一验证项目结束时，应该能回答四件事：项目的 Parse IR 是否足够表达真实文档；各类文档该路由到哪里；新解析结果能否无损编译回当前 segments；Retrieval Unit 命中能否稳定还原为 Agent 可消费且可验证的 Evidence Bundle。
