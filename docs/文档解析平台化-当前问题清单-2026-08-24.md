## P01：完整 Upload Session 未接入当前 KB 上传入口

**状态：已讲解。**

### 准确结论

当前文件上传是真实的 MinIO 上传，不是假上传，也不是继续把本地文件路径当成 MinIO。

当前生产调用链为：

```text
浏览器 multipart/form-data
  -> FastAPI UploadFile
  -> 后端完整读取文件内容
  -> 计算 SHA-256
  -> 按内容哈希生成 MinIO object key
  -> 上传 MinIO
  -> asset_storage_objects 登记对象
  -> asset_documents 创建逻辑文档并保存 storage_object_id
```

因此，当前 demo 和中小文件上传可以正常工作，后续解析 Worker 也会根据 PostgreSQL 中的对象指针从 MinIO 读取原文件。

### 当前未接入的能力

仓库已经实现了 `UploadSessionService` 及相关数据契约和 DDL，但 KB 上传接口当前没有调用这套编排。以下能力没有进入当前 KB 上传热路径：

- staging object 与正式提交阶段分离；
- multipart 大文件上传与断点续传；
- 明确的上传会话状态机；
- KB 配额预留、提交和释放；
- 客户端重试使用显式幂等键；
- 上传中断、会话过期和数据库提交失败后的补偿清理；
- 孤儿对象治理和存储副作用 outbox。

### 当前实现的限制

当前路由通过 `await file.read()` 将文件完整读入后端内存，随后 `_bytes_stream` 以一个完整 bytes 对象向 MinIO 写入。因此：

- 单个大文件会按文件大小占用后端内存；
- 并发上传时内存占用会叠加；
- 网络中断后不能从已完成分片继续；
- MinIO 写入成功、后续 PostgreSQL 写入失败时，缺少完整的会话级补偿闭环；
- 上传进度、过期和配额状态没有统一的可查询业务实体。

### 问题性质

这不是“MinIO 没接通”，而是：

> MinIO 直接上传已经接通；完整的工业化 Upload Session 能力已经开发，但尚未接入当前 KB 上传 API。

### 影响判断

- Demo 与中小文件：当前实现足够使用。
- 大文件、高并发、弱网络和生产故障恢复：存在明显风险。
- 代码复杂度解释：`file_management`、上传会话、配额和 outbox 中有一部分代码目前属于尚未进入生产热路径的库存能力。

### 后续处理建议

暂不在本次只读分析中修改代码。后续若进入整改阶段，应先确定产品需要支持的最大文件、并发量和是否要求断点续传，再决定：

1. 将现有 KB 上传入口接入 `UploadSessionService`；或
2. 保留直接上传作为“小文件通道”，大文件切换为 presigned multipart，并让两条通道最终汇合到同一个 verify/commit 流程。

## 后续问题

后续问题将按讲解进度逐项补充，不在尚未解释清楚前直接下最终结论。

## P02：Fallback 编排已实现，但生产 Parse Plan 没有真实备用后端

**状态：已讲解。**

### 准确结论

系统已经实现了解析 fallback 的通用编排能力，包括：

- `ParsePlan` 中的 primary parser、有序 fallback parser 列表；
- `AttemptBudget` 中的最大 backend 尝试次数；
- primary 失败或质量门禁给出 `FALLBACK/REPAIR` 后切换下一后端；
- 每次尝试写入 `asset_parse_run_attempts`；
- 尝试耗尽后将 Parse Run 标记为失败，防止无限重试。

但是当前生产 `default_plan_factory` 只根据 MIME 选择一个 `license_status == "ok"` 的 primary parser，构造 `ParsePlan` 时没有填写 `fallback_parser_ids`。所以当前计划的真实 backend chain 长度恒为 1。

`maxBackendAttempts=3` 只是“最多允许尝试三次”的预算上限，不会自动产生三个可尝试的解析器。当前实际语义是：

```text
允许最多尝试 3 个 backend
但计划中只提供了 1 个 backend
因此最多只会执行 1 次
```

### 多格式解析与 fallback 的区别

当前有七个真实 parser：Markdown、TXT、DOCX、XLSX、PPTX、HTML、PDF。它们解决的是“不同 MIME 各自用什么解析”，不是“同一 MIME 的主备切换”。

例如 PDF 当前只有一条真实链：

```text
application/pdf -> native_pdf
```

如果 `native_pdf` 失败或质量门禁要求 fallback，计划中没有第二个 PDF backend 可以继续执行。

### 占位后端现状

- `docling`：只注册了 descriptor，许可状态为 `pending_review`，没有进入实现工厂，不会被生产选择。
- `cloud_vlm`：只注册了云端 OCR/VLM 槽位，状态为 `unconfigured`，没有真实 provider、endpoint 或模型调用实现。

因此二者目前都不是可运行 fallback。

### 当前生产路由的限制

代码中虽然存在 `FileInspector` 和 `ParserRouter`，但 workflow 的生产 `default_plan_factory` 没有使用文件画像和 Router 决策，而是直接遍历 Registry，按 MIME 选择第一个许可状态为 `ok` 的 parser。

这意味着扫描 PDF 也会先被当作普通 PDF 交给 `native_pdf`，生产计划不会因为“没有文本层”自动生成一条真实 OCR fallback。

### 运行数据证据

截至本次只读检查：

- `asset_parse_run_attempts` 中共有 16 条记录；
- 16 条全部是 `attempt_kind=primary`；
- `attempt_kind=fallback` 为 0；
- 出现多个 backend attempt 的 Parse Run 为 0；
- 已运行 parser 只有 `legacy_markdown` 和 `native_pdf`。

这说明 fallback 当前不仅是代码推断上未接通，在现有 demo/运行数据中也从未实际发生。

### 影响判断

- Markdown/TXT 和普通 Office 文档：主解析器正常时不受影响。
- 数字文本层 PDF：依赖 `native_pdf` 的规则和质量。
- 扫描 PDF：没有真实 OCR 路径，通常无法形成有效结构化内容。
- 复杂排版、复杂表格 PDF：没有 Docling/VLM 等第二后端进行质量兜底。
- 主解析器抛异常：记录失败后结束，不会因为预算配置为 3 就自动换一个解析器。
- 质量门禁给出 FALLBACK/REPAIR：没有下一 backend 时最终仍会失败。

### 问题性质

这不是“fallback 代码没写”，而是：

> fallback 执行框架、状态机和审计已经实现并通过测试，但生产 Parse Plan 没有装入真实备用 backend，因此当前运行效果仍是单解析器模式。

### 后续处理建议

暂不在本次只读分析中修改代码。进入整改阶段前应先决定实际需要的 PDF/OCR 路线，例如：

1. `native_pdf -> Docling` 的本地 fallback；
2. `native_pdf -> cloud OCR/VLM` 的受控云端 fallback；
3. 根据文本层、页数、表格密度等文件画像生成版本化 RouteDecision；
4. 明确数据外发、许可、成本和超时策略后，才把候选 backend 写入生产 `fallback_parser_ids`。

## P03：冻结输入已实现，但生产快照提交使用空 stale checker

**状态：已讲解。当前未发现数据事故，但保护缺口已经确认。**

### 设计目标

解析开始时，系统应冻结文档当前内容三元组：

```text
(storage_object_id, source_raw_hash, content_revision)
```

假设开始解析时文档为版本 A：

```text
storage_object=A
content_revision=1
```

解析期间用户又把文档内容替换成版本 B：

```text
storage_object=B
content_revision=2
```

本次 Run 仍然读取和解析 A，这是正确的；但提交快照之前必须再次读取文档当前 revision。如果已经从 1 变为 2，应把 Parse Run 标为 `SUPERSEDED`，不能让 A 自动成为当前知识结果。

### 已实现能力

仓库已有 `FrozenInputService`：

- `freeze(document_id)` 捕获对象、哈希和 revision；
- `check_stale(frozen)` 在提交前重新读取文档；
- 文档消失或 revision 变化时抛出 `FrozenInputStale`；
- `DocumentParseService` 已有捕获该异常并把 Run 标记为 `SUPERSEDED` 的处理机制；
- `SnapshotCommitService` 支持注入 `stale_checker`，且检查发生在写快照记录之前。

### 当前生产接线

workflow 的 `build_new_chain_services` 没有构造并注入 `FrozenInputService.check_stale`，而是定义：

```python
async def _no_stale(frozen):
    return None
```

随后把 `_no_stale` 作为 `SnapshotCommitService.stale_checker`。

因此当前真实提交顺序变成：

```text
冻结并解析对象 A
  -> 校验 Parse IR 对象存在
  -> 调用 _no_stale（什么也不检查）
  -> 提交 A 的 READY Snapshot
  -> 继续切片、资产持久化和 Build
```

### 不会发生什么

这个缺口不会导致解析过程中把 A、B 两个对象的字节混在一起。`FrozenInput` 已经固定了对象 A 的位置，所以解析输入本身仍然一致。

它也不会把 `asset_documents.storage_object_id` 从 B 改回 A；文档当前内容指针仍然保持 B。

### 可能发生什么

风险发生在“解析结果是否还能代表文档当前内容”：

- A 的解析快照可能在文档已经切换到 B 后仍被标为 READY；
- 当前 Run 会继续为 A 编译切片；
- A 的知识资产可能进入本次 Build；
- Parse Run 会显示成功，而不是 `SUPERSEDED`；
- 系统不会自动对 B 重新排队解析。

结构化数据读取服务会按当前 `storage_object_id + content_revision` 过滤快照，因此普通文档详情页通常不会把 A 显示成 B 的当前结构化结果。这降低了 UI 误展示风险，但不能阻止 A 已进入当前 Run/Build。

### 当前风险触发条件

当前常用 KB 文档接口主要接通了首次上传、改名和修改文档类型；同名上传会冲突，在线 `replace_content` 尚未成为当前 UI 的常用热路径。因此普通 demo 很难触发这个并发窗口。

但仓库中已经存在内容替换、上传会话完成和迁移等可推进 `content_revision` 的服务。一旦这些路径正式接入，或其他服务直接更新文档当前对象，这个保护缺口就会变成真实的一致性风险。

### 运行数据证据

截至本次只读检查：

- 共有 15 个文档存在最新 READY 新链快照；
- 这 15 个最新快照的来源对象和 revision 均与文档当前内容一致；
- 当前未发现最新快照错配事故。

因此结论是“保护未接线”，而不是“现有数据已经错乱”。

### 问题性质

> 冻结输入契约、stale 检查服务、`SUPERSEDED` 状态和异常处理都已经实现，但生产组合根用空函数替代了真实检查，导致提交前版本防护没有生效。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时至少应：

1. 在生产组合根构造真实 `FrozenInputService`；
2. 将 `FrozenInputService.check_stale` 注入 `SnapshotCommitService`；
3. stale 时把 Run 标记为 `SUPERSEDED`，不进入切片和 Build；
4. 明确是否自动为最新 revision 重新排队；
5. 增加“解析过程中替换内容”的真 PostgreSQL + MinIO 并发验收。

## P04：基础文档入库已完成 Build，但尚未产生 Serving 可检索入口数据

**状态：已讲解。当前 demo 是“解析与切片就绪”，不是“检索就绪”。**

### 三种成功状态不是一回事

当前系统中需要区分：

```text
Run completed
  != Build validated
  != Agent 可检索
```

- `Run completed`：所选 workflow 中要求的算子已经完成。
- `Build validated`：Build 有 active Snapshot，且每个 active Snapshot 至少有一条 segment。
- `Agent 可检索`：Serving 使用的检索入口表中存在有效候选数据，并能在正确 KB/Release scope 下被查询。

### 当前选择的 workflow

当前 demo KB `test23` 选择的是“基础文档入库”，其生产图只有：

```text
input_ingest
  -> document_parse
  -> segment_compile
  -> asset_persist
  -> mining_finalize
```

它没有以下算子：

- `retrieval_unit_build`
- `embedding`
- `enrich`
- `discourse_line`
- `entity_extract`
- `entity_resolve`
- `entity_relation_extract`
- `graph_write`

因此这套范式成功完成时，本来就只承诺“原文件已解析、快照已形成、切片已落库”。

### Build validated 实际检查什么

当前 `validate_build` 只检查：

1. Build 至少有一个 active Snapshot；
2. 每个 active Snapshot 至少有一条 `asset_raw_segments`；
3. incremental Build 的 parent 存在。

它不要求：

- 存在 `asset_retrieval_units`；
- 存在 `asset_retrieval_embeddings`；
- 存在切片关系；
- 存在实体提及或知识图谱；
- 用真实查询验证能够召回结果。

`demo_quality_summary` 会统计缺失的 generated question 和 discourse relation，但只记录 warning，不阻止 Build 进入 `validated`。

所以当前 Build 状态的准确含义是：

> 文档快照选择有效，而且每份文档至少有一个切片。

它不等价于“全文检索、向量检索和图谱检索都已经准备好”。

### Serving 实际查询什么

Java Serving 支持两种作用域：

- 域级检索：读取 active Release 对应的 Build；
- KB 检索：绕过域级 Release，直接解析 KB 最新 validated/published Build 中的文档快照。

因此 KB Run 使用 `publish=false` 并不会让 KB 知识天然不可见；只要请求明确携带 KB scope，Serving 能解析到这些 Snapshot。

但 Serving 的主要召回算子查询的是：

- FTS：`asset_retrieval_units`，并在该表上执行 tsvector → trigram → LIKE 三级降级；
- Dense Vector：`asset_retrieval_embeddings JOIN asset_retrieval_units`；
- Entity Exact：依赖 Retrieval Unit 的 entity refs；
- Graph/邻接扩展：依赖关系和已有种子候选。

`asset_raw_segments` 当前主要用于候选回填、窗口扩展、证据和原文读取，不是 FTS 算子的首轮召回表。

因此只有 segment、没有 retrieval unit 时，Serving 虽然能解析出合法 KB scope，却无法从 FTS 或 Dense Vector 产生候选。

### 当前 demo 的真实数据状态

`test23` 的最新 KB scope：

| 资产 | 数量 |
|---|---:|
| 可见文档快照 | 6 |
| `asset_raw_segments` | 50 |
| `asset_retrieval_units` | 0 |
| `asset_retrieval_embeddings` | 0 |
| `asset_raw_segment_relations` | 0 |
| `asset_segment_entity_mentions` | 0 |

所以它目前可以：

- 在 KB UI 查看结构化大纲、元素、表格和切片；
- 按 Snapshot 和 Build 管理解析结果；
- 通过 document/parse-result API 读取结构化数据。

但它目前不能依靠现有 Serving 算子完成：

- FTS 全文召回；
- trigram/LIKE 降级召回（它们同样查 Retrieval Unit 表）；
- 向量召回；
- 实体精确召回；
- 图关系扩展。

### 仓库是否有后续范式

有。“快速向量检索”范式包含：

```text
document_parse
  -> segment_compile
  -> retrieval_unit_build
  -> embedding
  -> asset_persist
```

“篇章增强检索”和联合范式还会增加 enrich、discourse 和 contextual retrieval。它们说明架构已经预留后续生产线，但当前 demo 没选择这些范式；当前全库 embedding 行数仍为 0，也说明向量链尚未通过当前实盘数据证明。

### 问题性质

这不一定是“基础文档入库”范式本身设计错误。作为低成本的解析/切片阶段，它可以是合理的分层入口。

真正的问题是：

> 当前状态名称和 Build 校验容易让人把“切片已落库”理解成“知识已可检索”，而系统没有显式的 retrieval readiness 状态或检索验收门禁。

### 后续处理建议

暂不在本次只读分析中修改代码。整改或产品设计阶段建议：

1. 明确区分 `parsed / segmented / lexical_ready / vector_ready / graph_ready`；
2. 如果 KB 的目标是 Agent 查询，不应默认停在“基础文档入库”；
3. 按 workflow 能力定义 Build 验收条件，例如向量范式必须有 Retrieval Unit 和 Embedding；
4. 决定是否让 FTS 直接检索 `asset_raw_segments`，或保证每条有效 segment 至少生成一个 `raw_text` Retrieval Unit；
5. 增加“上传 -> 挖掘 -> Serving 按 KB scope 查询 -> 至少召回一条正确证据”的真实端到端验收。

## P05：Parse IR 虽按对象存储流式下载，但结构化结果接口仍会整份读入和反序列化

**优先级：P2（当前 demo 可用；在超大文档、并发访问或 Agent 高频深挖前需要处理）**

### 最新代码复核（提交 `b8ba6cf`）

最新提交 `b8ba6cf feat(kb): 预览性能优化(预签名直连+流式下载+大文本分段) + 结构化数据 tab 重构` 已经修复了相邻但不同的“原始文件预览/下载”问题：

- PDF、图片通过短时效 MinIO 预签名 URL 由浏览器直连，并利用 Range 按需加载；
- 文档 download 路由改为 `StreamingResponse`，不再把完整原文件先缓冲到后端内存；
- 文本类预览先渲染 20 万字符，并支持逐步“展示更多”；
- 结构化数据页签重排为可折叠的快照、大纲、切片、元素和表格卡片。

这些改动对原始文件预览链路有效，但没有改变 Parse IR 的读取链路：

- `snapshot_store/read_service.py` 在该提交中没有修改；
- `ParseResultReadService._load_ir` 仍收集全部 chunk，执行 `b"".join(chunks)`、`json.loads` 和完整 `ParsedDocument.from_dict`；
- KB 前端仍在打开文档详情时直接调用 `loadParseResult()`，而不是首次进入“结构化数据”页签时按需调用；
- 可折叠卡片只控制前端展示，不会阻止后端提前加载完整 Parse IR。

因此本问题仍然成立，但它不是当前 demo 的功能故障，也不是最新预览优化的回归。基于当前 parse bucket 体量和使用方式，优先级由 P1 下调为 P2。

### 当前实现

完整 canonical Parse IR 以 JSON 对象存放在 MinIO parse bucket 中。读取结构化数据时，调用链为：

```text
打开文档详情
  -> 前端自动请求 /api/kb/{kb_id}/documents/{document_id}/parse-result
  -> 查询当前文档 revision 对应的最新 Snapshot
  -> 从 MinIO 下载完整 Parse IR 到后端临时文件
  -> 以 chunk 形式从临时文件读出
  -> chunks.append(...) 收集全部分块
  -> b"".join(chunks) 拼成完整 JSON bytes
  -> json.loads(...) 构造完整 Python JSON 对象
  -> ParsedDocument.from_dict(...) 构造完整领域对象图
  -> 从完整对象中截取预览后返回前端
```

MinIO 适配器的 `get_stream` 并非直接把整个远端对象一次性装入内存：它先下载到临时文件，再按 chunk 产出。这解决了 SDK 响应跨 await 和远端读取稳定性问题。

但消费端 `ParseResultReadService._load_ir` 会把所有 chunk 收集到 `list[bytes]`，随后执行 `b"".join(chunks)`、`json.loads` 和 `ParsedDocument.from_dict`。因此从业务服务的角度看，Parse IR 仍然是整份加载。

### 响应已经做了哪些限界

当前接口并非把所有内容原样返回给浏览器，已经存在部分展示限界：

- element 最多返回 500 条；
- segment 最多返回 200 条；
- element/segment 文本预览最多 400 字符；
- warning 最多返回 50 条；
- 表格只预览前 5 行。

这些限制可以控制一部分 HTTP 响应体和前端渲染成本，但不能降低读取 Parse IR 时的后端峰值内存，因为截取发生在完整 IR 下载、JSON 解析和领域对象构造之后。

此外，以下内容目前没有统一分页边界：

- outline 会遍历并返回所有 heading/title；
- tables 会遍历并返回所有 TableAsset（每张表虽然只展示前 5 行）；
- segment 查询先取出当前 Snapshot 的全部 segment，再切前 200 条返回。

### 前端触发时机

文档详情页的 `load()` 在拿到文档元数据后会直接调用 `loadParseResult()`。因此用户只是打开文档、停留在“预览”页签，也会触发完整 Parse IR 的读取和反序列化；不是等用户点击“结构化数据”页签后才按需加载。

依赖工厂缓存的是按 domain 装配好的 `ParseResultReadService` 实例，不是 Parse IR 内容。再次打开或刷新文档仍会重新读取对象存储并重新反序列化。

### 资源放大

单次请求处理过程中，内存里可能在不同时刻同时存在：

1. chunk 列表中的 JSON bytes；
2. `join` 后的连续 JSON bytes；
3. `json.loads` 生成的 dict/list/string 对象；
4. `ParsedDocument` 的 elements、relations、structured assets 等领域对象；
5. 最终响应 dict。

因此峰值内存不是简单等于 MinIO 对象大小。JSON 中包含大量短字符串、字典和列表时，反序列化后的 Python 对象通常会明显大于原始 JSON 字节；并发打开多个大文档时会按请求数叠加。

### 当前 demo 为什么没有暴露

2026-08-24 的实盘盘点中，parse bucket 共 14 个对象、总计约 2.1 MB；当前文档规模下单份 Parse IR 较小，所以整份读取的延迟和内存成本不明显。

这说明当前 demo 能正常展示结构化结果，但不能证明以下场景已经可承载：

- 数百页或上千页 PDF；
- 大型 Excel、多表工作簿；
- 包含大量单元格、关系和 evidence span 的 Parse IR；
- 多用户同时打开文档详情；
- Agent 高频按 element 深挖多个文档。

### 问题性质

完整 Parse IR 放在 MinIO 是合理的：它是低频访问、体积较大的完整结构和溯源制品，不适合全部塞进 PostgreSQL 热表。

问题不在“使用 MinIO”，而在于当前唯一读取粒度仍是“整份对象”，并且展示接口和未来 Agent 深挖接口尚未形成可分页、可寻址、可缓存的读模型。

### 后续处理建议

暂不在本次只读分析中修改代码。后续可以分层处理：

1. 前端只在用户首次进入“结构化数据”页签时加载；
2. outline、element、table、segment 拆成可分页的独立接口；
3. 在 PostgreSQL 中保存轻量目录/索引，例如 `element_id -> object/page/chunk`；
4. 大 IR 按页、章节或元素块拆分成多个内容寻址对象，保留 manifest 作为总入口；
5. 对 immutable Snapshot/Parse IR 使用 ETag 或 snapshot fingerprint 做服务端与客户端缓存；
6. 为单请求 IR 大小、反序列化耗时、峰值并发和超限行为增加门禁及压测。

## P06：旧版 parse-result 路由与前端调用仍留在仓库，但当前生产应用没有挂载

**状态：已讲解。当前不是线上越权漏洞，属于 P3 级遗留代码与误接风险。**

### 两套路由的现状

仓库中可以同时看到两套结构化结果入口：

```text
旧入口：GET /api/knowledge/documents/{document_id}/parse-result?domain=...
新入口：GET /api/kb/{kb_id}/documents/{document_id}/parse-result
```

旧入口定义在 `mining/api/routes/parse_result.py`，只校验 `domain` 是否有效，然后按 `document_id` 读取解析结果；它不消费 `current_user`，也不检查调用者是否是对应知识库成员。

新入口定义在 `mining/kb/routes/documents.py`，依次检查：

1. `current_user` 校验 `X-KB-User + X-Internal-Auth`；
2. 当前用户是否可见该 `kb_id`；
3. `document_id` 是否真实属于 URL 中的 `kb_id`；
4. 根据文档自身记录的 domain 读取当前 revision 的 Parse Result。

### 当前生产实际暴露哪一套

`mining/api/app.py:create_app()` 当前只导入和挂载 `kb_documents_router`，没有导入或 `include_router` 旧的 `api.routes.parse_result.router`。

当前 KB UI 的 `KbDocPreviewView` 也只调用 `kbApi.getDocumentParseResult`，实际请求新入口：

```text
/api/kb/{kb_id}/documents/{document_id}/parse-result
```

因此，虽然旧路由源码仍存在，但在当前生产 FastAPI 应用中不可达。不能把它描述成“当前任意用户可以绕过 KB 权限读取 Parse IR”的线上漏洞。

### 遗留前端方法

`kb-ui/src/api/mining.ts` 中仍保留 `getParseResult(docId)`，目标地址仍是旧入口：

```text
/api/knowledge/documents/{docId}/parse-result
```

当前源码搜索没有发现页面调用这个方法；实际文档页使用的是 `kb.ts` 中的新方法。因此它也是未使用的兼容残留。

### 为什么仍然值得记录

当前风险主要是维护和未来误接：

- 开发者看到旧前端方法并复用时，会得到 404，容易误判 Parse Result 服务故障；
- 如果为了“修复 404”直接把旧 router 重新 `include_router`，会同时恢复一条没有 KB 成员校验的入口；
- 两套 URL、错误语义和权限模型并存，增加代码阅读和测试判断成本；
- 旧路由文件看起来完整可用，但是否生效只能继续追到应用组合根才能确定，是典型的“源码存在不等于生产接线”。

### 问题性质

这不是当前数据泄露事故，而是：

> 权限正确的新 KB 路由已经完成切换，但旧路由和旧客户端方法没有随切换一起删除或明确标为 deprecated，留下了容易误用、误接和误判的幽灵接口。

它也是仓库代码量和理解成本偏高的一个具体来源：平台迭代时新旧入口阶段性并存，热路径已经迁移，但兼容骨架没有完全收口。

### 后续处理建议

暂不在本次只读分析中修改代码。后续整改时建议：

1. 若确认无外部调用者，删除未挂载的旧 router 和未使用的 `mining.ts.getParseResult`；
2. 若必须保留兼容入口，则让它复用与 KB 路由相同的身份、KB 可见性和文档归属校验；
3. 增加应用路由表测试，明确旧 URL 必须为 404、新 URL 必须经过成员鉴权；
4. 在迁移文档中写明 `/api/knowledge/.../parse-result` 已退役，避免后续人员重新接回。

## P07：Run 状态已持久化，但实际执行仍依附 API 进程内 daemon 线程

**状态：已讲解。生产可靠性 P1；当前单实例 demo 正常运行时不阻塞。**

### 当前真实执行链

用户点击“更新知识”后，KB `/mine` 路由会：

```text
1. 在 PostgreSQL 插入 mining_runs，状态为 queued
2. 补充 kb_id、workflow binding、publish=false 等 metadata
3. 在当前 FastAPI 进程创建 threading.Thread(daemon=True)
4. 线程直接调用 knowledge_mining.mining.jobs.run.run(...)
5. 线程执行解析、切片、资产持久化和 Build
6. 执行过程中持续把 Run/Stage/Document 状态写回 PostgreSQL
```

所以当前系统确实具备持久化运行记录、阶段记录、错误摘要和部分恢复信息；它不是“所有状态只放在内存”。

但 PostgreSQL 中的 `queued` 行不是由独立 Worker 通过队列协议认领的。创建它的 API 请求会立即在同一个服务进程内启动后台线程，实际工作与 API 进程共生。

### 为什么 demo 可以正常运行

在以下条件下，当前模式完全能跑通：

- 单个 Mining API 实例；
- 服务在整个解析期间不重启；
- 操作系统不杀进程；
- Python 线程能正常启动并执行；
- 当前 domain 不同时启动第二个 Run。

HTTP 请求可以很快返回 `queued`，前端通过轮询数据库状态看到 Run 从 queued/running 进入 completed。对于本地或受控 demo，这种实现简单且有效。

### daemon 线程意味着什么

`daemon=True` 的线程不会阻止 Python 进程退出。若 Mining API 在 Run 中途发生以下情况：

- 服务重启或部署滚动更新；
- 进程崩溃或被 OOM Kill；
- 容器/主机退出；
- 开发环境手工停止服务；

后台线程会随进程直接消失，没有机会执行 `finally` 或 `_mark_thread_failure`。

`_mark_thread_failure` 只覆盖“线程仍在运行、Python 调用抛出可捕获异常”的情况；它无法覆盖整个进程突然消失。

因此数据库中的 Run 可能停留在：

```text
queued
或
running / 某个 current_stage
```

并且没有 `finished_at`，看起来仍在执行，实际已经没有任何执行者。

### 已有恢复能力

仓库并不是完全没有恢复设计。当前 `/api/runs/{run_id}/resume` 已允许 workflow Run 从以下状态继续：

- `failed`；
- `interrupted`；
- `running` 且 `finished_at is None`（用于 crashed running）；
- `awaiting_review`。

Workflow 的阶段与文档状态持久化，也为幂等续跑提供了基础。这说明系统已经考虑“中断后继续”，不是只能从头重跑。

但当前恢复是人工触发的，而且 `resume` 本身仍然创建新的 `daemon=True` 后台线程。应用启动的 lifespan 中没有发现：

- 扫描遗留 queued/running Run；
- 根据 heartbeat 判断 Worker 已失联；
- 自动把陈旧 Run 标为 interrupted；
- 自动重新认领并续跑；
- 按租约续期和超时回收任务。

### 进程内 domain lock 的边界

当前使用 `_run_locks: dict[str, threading.Lock]` 为每个 domain 加锁，可以阻止同一个 Python 进程中同域并发运行。

但这个锁只存在于当前进程内：

- 进程重启后锁全部丢失；
- 两个 Mining API 实例各自有一套锁；
- 多实例可能同时接受同一 domain 的 Run；
- 数据库中已有 crashed running 行不会自动持有或恢复这把锁。

发布 Build 时另有 PostgreSQL advisory lock，可保护发布临界区；但它不等价于完整 Run 的跨实例任务租约。

### Cancel 也只是 best-effort

`/cancel` 当前主要把数据库状态更新为 `cancelled`。它没有直接终止 Python 线程；后台阶段需要在后续检查点观察到状态变化后自行停止。因此取消不是硬中断，也不能代替 Worker 租约和故障恢复。

### 问题性质

当前系统具备：

- 持久化 Run/Stage/Document 状态；
- 后台异步执行；
- 异常兜底；
- 手工 resume；
- 部分幂等恢复基础。

但尚未具备一个完整的 durable job execution 模型：

> Run 数据是持久化的，执行权却没有持久化；没有独立 Worker、认领租约、心跳和自动接管，所以 API 进程退出会造成“数据库显示还在跑，但执行者已经消失”。

### 影响判断

- 当前单机 demo：只要服务不中断，可以正常使用。
- 长文档、耗时数分钟的 Run：部署重启窗口明显增大。
- 容器化滚动发布：可能留下僵尸 running Run。
- 多实例水平扩容：进程内 domain lock 无法防止跨实例并发。
- 自动化生产环境：需要人工识别和点击 resume，恢复闭环不完整。

### 后续处理建议

暂不在本次只读分析中修改代码。进入生产整改时可按规模选择：

1. 最小方案：启动时扫描陈旧 queued/running Run，按明确阈值标记 interrupted，并提供自动/人工恢复；
2. 增加数据库任务认领字段，例如 `worker_id / lease_until / heartbeat_at / attempt_no`，用事务和 `FOR UPDATE SKIP LOCKED` 认领；
3. 将执行器拆为独立 Worker 进程，API 只创建任务和查询状态；
4. 或接入成熟的 durable queue，但仍要保留当前 Run/Stage 幂等契约；
5. 将 per-domain 并发限制升级为数据库级租约或 advisory lock，覆盖整个 Run；
6. 增加“运行中强制杀掉 Worker -> 重启 -> 自动识别并续跑”的故障注入验收。

## P08：KB 文档删除通过硬删身份行改变历史 Build，正式 Withdrawal 尚未接入

**状态：已讲解。当前删除能让文档退出 KB 可见范围，但版本不可变性与审计语义存在 P1 缺口；demo 使用影响较低。**

### 三种动作需要区分

文档系统中至少存在三种不同语义：

```text
删除文件身份：用户不再管理或看到这份文档
撤回知识：新版本知识范围不再选择这份文档
物理清理：确认无引用后删除 Snapshot/Parse IR/原文件对象
```

工业化实现通常不会用同一个数据库 `DELETE` 同时表达这三件事，因为知识 Build、审计记录和内容寻址对象各有独立生命周期。

### 当前 KB 删除实际做什么

当前 KB 路由：

```text
DELETE /api/kb/{kb_id}/documents/{document_id}
```

调用 `DocumentService.delete()`。服务会：

1. 读取 `asset_documents` 身份行；
2. 按文档真实 `kb_id` 校验用户写权限；
3. legacy 本地文档存在 `storage_path` 时尝试删除磁盘文件；
4. 执行 `DELETE FROM asset_documents WHERE id = %s`。

对于当前 MinIO 文档，`storage_path` 通常为 NULL，因此这条路径不会直接调用 `ObjectStorePort.delete()`，也不会删除 `asset_storage_objects` 注册行。

### 外键级联造成什么效果

当前 DDL 中：

```text
asset_document_snapshot_links.document_id
  -> asset_documents.id ON DELETE CASCADE

asset_build_document_snapshots.document_id
  -> asset_documents.id ON DELETE CASCADE
```

所以删除文档身份行时，会同步删除：

- 该逻辑文档与所有 Snapshot 的 link；
- 该逻辑文档在所有历史 Build 中的 selection 行。

Snapshot 本身使用独立内容身份，并且可能被多个文档共享，因此不会随文档身份一起删除；挂在 Snapshot 上的 raw segment、retrieval unit 等资产也通常继续保留。MinIO 原文件和 Parse IR 对象同样不会由当前 KB 删除路径立即清理。

### 为什么当前页面和 Serving 看起来是正确的

KB 文档列表直接查询 `asset_documents`，身份行删除后自然不再显示。

Java Serving 的 KB scope 查询还会把 `asset_build_document_snapshots` JOIN `asset_documents`，并只选择 `selection_status='active'` 的行。文档身份与 selection 行均已删除，因此它也会立即退出 KB 检索范围。

所以从用户当前体验看：

```text
点击删除
  -> 文档列表消失
  -> 当前 KB scope 不再选择它
```

这个即时结果是有效的，不是“删除后仍然继续被检索”。

### 真正的问题：历史 Build 被原地改变

假设已有 validated Build B1：

```text
B1 selections:
  doc-A -> snapshot-A active
  doc-B -> snapshot-B active

B1 summary.snapshot_count = 2
```

删除 doc-A 后，数据库级联直接删除 B1 中 doc-A 的 selection：

```text
B1 selections:
  doc-B -> snapshot-B active

B1 自身仍为 validated
B1 summary/validation 仍可能记录 snapshot_count = 2
```

没有生成 B2，没有 `removed` tombstone，也没有记录“谁在何时因删除撤回 doc-A”。因此同一个 Build ID 在删除前后解析出的有效成员集合发生变化，历史 Build 不再是稳定的版本快照。

这会影响：

- Build 摘要、validation_json 与实际 selection 数量的一致性；
- 历史 Run/Build 的可重放和审计解释；
- “某次 Agent 回答当时使用了哪一版知识”的证据固定；
- 删除后的恢复能力；
- 后续增量 Build 对 parent selection 的继承逻辑。

### 仓库已有正确方向，但 KB 没有接上

`mining/stages/withdrawal.py` 已实现 domain release 模型下的软撤回：

```text
锁定当前 active release
  -> 读取父 Build 的全部 selections
  -> 新建增量 Build
  -> 目标文档写 selection_status=removed / reason=remove
  -> 其他文档原样继承
  -> validate 新 Build
  -> 发布新 Release
```

这能保留旧 Build 不变，并用一个新版本表达知识范围变化。

但是 `DocumentService.withdraw()` 当前仍直接抛出 `NotImplementedError`，注释说明尚未接入 release machinery。

此外，KB Run 使用 `publish=false`，KB Serving 直接从 KB 的 validated/published Build 解析 scope，不依赖 domain active release。因此现有 domain withdrawal 不能不加设计地直接套用：KB 需要定义自己的“新建 removal Build 并使其成为每文档最新决定”的语义。

### MinIO 对象为什么没有一起删

不立即删除不一定是错误。原文件与 Parse IR 使用内容寻址，同一个对象可能被多个逻辑文档、Snapshot 或历史证据引用。安全物理清理通常需要：

```text
先撤回逻辑引用
  -> 保留一段审计/恢复窗口
  -> 计算全局引用
  -> 无引用且超过保留期
  -> 通过 GC/outbox 删除 MinIO 对象和注册行
```

当前缺口是这条生命周期没有在 KB 删除入口闭环，而不是“每次点删除都应该立刻删 MinIO”。

### 问题性质

当前删除同时取得了两种效果：

- 删除逻辑文档身份；
- 让知识立即退出当前 KB scope。

但它通过 FK cascade 修改所有历史 Build，而不是创建新 Build 表达 Withdrawal：

> 当前可见性结果基本正确，但版本历史、审计、恢复和物理 GC 被混在一次硬删除中，绕过了系统已经设计的 Build/Release 生命周期。

### 影响判断

- 未挖掘文档：主要是身份删除，风险较小；
- 已进入 validated Build 的文档：会改变历史 Build selection；
- 当前 KB Serving：文档会立即消失，不会继续作为当前候选；
- 历史审计/回答溯源：Build ID 不能再稳定代表删除前的知识集合；
- MinIO 容量：对象不会立即释放，长期需要引用感知 GC；
- 恢复误删：当前硬删后缺少简单 restore 路径。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时建议先明确产品语义，再实现：

1. 用户“删除”默认先软删 `asset_documents.deleted_at`，保留可恢复窗口；
2. 对已挖掘文档创建新的 KB removal Build，不修改任何旧 Build selection；
3. 在新 Build 中保留目标文档的 `removed/reason=remove` tombstone，使每文档最新决策能压住旧 active selection；
4. 让 KB Serving 和 `get_document_knowledge` 明确消费这套最新决策；
5. 将永久删除拆成单独动作，并在保留期后交给引用感知 GC/outbox；
6. 增加“上传 -> 挖掘 -> 删除 -> 当前检索消失 -> 历史 Build 仍完整 -> 恢复/审计可解释”的端到端测试。

## P09：质量门禁框架已实现，但生产链缺少覆盖率基准，质量档位也未生效

**状态：已讲解。属于解析正确性 P1；当前 demo 的成功只能证明结构合法，不能充分证明内容完整。**

### 设计上的质量门禁

仓库中的 `parse_quality` 已实现一套较完整的指标与决策模型：

```text
QualityMetrics
  -> QualityGate
  -> PASS / WARN / REPAIR / FALLBACK / FAIL
```

可计算的指标包括：

- `element_count`：是否至少解析出元素；
- `char_coverage`：原文实义字符有多少出现在 Parse IR；
- `evidence_locatability`：元素是否有可回原文的定位信息；
- `table_cell_evidence`：表格单元格是否有独立 evidence span；
- `table_grid_consistency`：表格行列跨度是否自洽；
- `reading_order_monotonicity`：同页阅读顺序是否出现明显回退；
- `empty_container_ids`：是否存在没有任何元素的空页/空容器；
- Golden Expectations 下的标题、锚文本和表格数量匹配。

默认阈值中，字符覆盖率低于 85% 应触发 FAIL 或 FALLBACK，85%～95% 应 WARN。这套设计目标明确：解析器没有抛异常，并不自动等于内容可用。

### 生产调用缺少 source_text

`compute_metrics` 只有在收到独立的 `source_text` 时才计算字符覆盖率：

```python
char_coverage = None
if source_text is not None:
    char_coverage = _char_coverage(source_text, ir_text)
```

但当前 workflow 的 `DocumentParseFacade._parse()` 调用是：

```python
self._operator.execute(frozen, plan, domain=domain)
```

没有传 `source_text`。参数默认值为 None，并一路进入 `compute_metrics`。

因此当前生产链的实际值通常是：

```text
char_coverage = None
```

而 `QualityGate` 的覆盖率判断显式要求 `char_coverage is not None`。结果是 85%/95% 两道覆盖率阈值在当前生产工作流中不会执行。

### 这会造成什么误判

假设一份 100 页 PDF 中，解析器只成功读出前 10 页，但仍生成若干合法 Element：

```text
element_count > 0
char_coverage = None
部分 Element 有 bbox/evidence
```

质量门禁无法判断“90% 正文丢失”。只要其余可计算指标没有严重问题，它就可能得到 PASS；即使证据定位或空页信号有问题，也往往只是 WARN，并继续提交 READY Snapshot。

所以当前最硬的失败条件主要是：

```text
element_count == 0 -> FAIL
```

“完全没有解析出内容”能够被挡住；“解析出少量合法内容但漏掉很多正文”未必能被挡住。

### Golden Expectations 不属于生产门禁

`compute_metrics` 支持通过 Golden Expectations 比较：

- 预期标题；
- 预期段落锚点；
- 预期表格数量；
- 综合结构准确率。

但这依赖人工标注的测试语料，当前生产调用没有传 expectations。因此这些指标适合离线评测 parser 版本，不能解释为每次线上文档都在执行结构准确率验证。

### 可计算指标也不全部参与阻断

当前门禁对下列问题主要给 WARN：

- evidence locatability 低；
- table cell evidence 低；
- reading order monotonicity 低。

`table_grid_consistency` 虽然会计算，但当前 `QualityGate.evaluate()` 没有根据它产生决策。

因此 Schema/引用校验可以保证 Parse IR 自洽，质量门禁可以暴露一部分问题，但不能把“逻辑结构合法”和“业务内容准确完整”画等号。

### REPAIR 当前会降级为 WARN

当存在空页/空容器时，Gate 会产生 `REPAIR` 请求，理论上应只对目标页重新 OCR 或调用更强后端。

但当前 M4 没有真实 repair executor。`DocumentParseService._resolve_decision()` 会把 REPAIR 改成：

```text
WARN + repair_unavailable
```

随后仍提交 Snapshot。

这保留了问题可见性，比静默忽略更好；但它不是实际修复。再结合 P02 中生产 fallback chain 为空，当前低质页通常没有第二条真实处理路径。

### strict/default/lenient 档位没有进入生产阈值

`DocumentParseOptions` 对外暴露：

```text
qualityProfile = strict | default | lenient
```

但当前 `default_plan_factory` 构造 `ParsePlan` 时没有读取 `qualityProfile`，`ParsePlan.quality_profile` 保持默认值；生产组合根也固定注入一次 `QualityGate()`，没有按 Plan 选择不同 `QualityProfile`。

因此用户或 Workflow 即使配置 `strict`，当前实际阈值仍不会变严格。这个参数目前属于已定义但未生效的配置表面。

同样，`AttemptBudget.max_duration_seconds` 当前只在契约中定义和校验正数，未找到执行器使用它中断超时 Parse Run；它还不是实际墙钟预算。

### 质量结果的可观测性也不完整

Shadow Parse 写入的 `quality_metrics` metadata 当前包含：

- element_count；
- evidence_locatability；
- table_cell_evidence；
- reading_order_monotonicity。

它没有把 `char_coverage` 写入该 metadata。即使未来某条调用传入 source_text，当前审计摘要也不能直接看到覆盖率数值，需要同步补齐持久化和 UI 展示。

### 当前 demo 的成功应如何理解

当前 demo 能证明：

- Parser 成功返回；
- Parse IR 通过 schema 和引用完整性校验；
- 至少生成一个 Element；
- Snapshot、Segment 和 Build 能完成；
- 部分证据、表格和阅读序指标已计算并可告警。

它尚不能单凭 `PASS/completed/validated` 证明：

- 原文正文没有大量漏失；
- 所有页都成功解析；
- 标题层级和阅读顺序符合业务事实；
- 表格没有漏行、漏列或合并错误；
- `strict` 档位已经执行更高标准；
- 低质页已经被真实修复或 fallback。

### 问题性质

这不是“完全没有质量代码”。相反，指标、Gate、决策、预算和问题记录框架已经写得比较完整。

真正缺口是：

> 生产调用没有提供关键的独立覆盖率基准，部分质量参数和修复动作没有接线，所以当前 Gate 更擅长验证 Parse IR 是否结构合法、是否存在明显信号，而不能充分证明解析内容完整准确。

这也是代码看起来复杂、实际效果却有限的典型例子：质量平台骨架已经存在，但当前生产数据与执行后端没有把它的关键能力喂满。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时建议：

1. TXT/Markdown/HTML 等文本格式直接从冻结源对象构造独立 source_text；
2. PDF/Office 不能用同一解析结果自证覆盖率，应设计独立文本层、页级锚点、对象数量或第二解析器对照；
3. 按页记录 expected/observed 字符、块数量和空页率，避免文档级平均掩盖局部灾难；
4. 让 `qualityProfile` 真正选择 strict/default/lenient 阈值并固化在 Parse Plan/Run；
5. 将 char_coverage、table_grid_consistency、空页比例等关键指标持久化并在 UI 展示；
6. 明确哪些指标只 WARN、哪些必须阻断 Build；
7. 接入真实 repair/fallback 后端，或在没有后端时不要把“待修复”呈现为普通成功；
8. 用标注语料做 parser 版本离线回归，再用真实生产抽样做人工复核；
9. 增加“解析器故意只返回部分页面但格式合法”的反例测试，验证门禁必须拒绝或降级。

## P10：Figure/Binary Asset 契约已形成，但图片字节没有进入当前生产资产链

**状态：已讲解。文本型 demo 影响较低；若目标包含 PPT/图表/图文证据，则属于 P1 能力缺口。**

### 需要区分三层能力

图片解析不是一个单一的“支持/不支持”，至少分为：

```text
1. 检测：知道文档里存在图片
2. 建模：在 Parse IR 中生成 Figure Element/FigureAsset/引用
3. 物化：把真实图片 bytes 存入对象存储，并让引用可读取
```

当前各格式在这三层上的完成度不同，不能因为 Parse IR 中出现 `figure` 或 `binary_asset_id` 就认为图片文件已经进入 MinIO。

### PPTX：做到了检测和建模，未做到字节物化

`NativePptxParser` 读取 picture shape 时确实取得：

```python
blob = shape.image.blob
sha = sha256(blob)
```

随后生成的 block structure 包含：

- `image_sha256`；
- `binary_asset_id`；
- MIME；
- size；
- shape name。

`PptxNormalizer` 再将其转换成：

- element_type=`figure` 的 Element；
- `FigureAsset.original_image_ref = binary_asset_id`；
- `FigureAsset.image_hash`；
- `ParsedDocument.binary_assets[binary_id]` 的 metadata。

但 `binary_assets` 中只有：

```text
sha256 / mime / size / origin
```

没有图片 bytes，也没有指向 `asset_storage_objects.id` 或 MinIO bucket/object_key/version 的物理地址。Parser 返回后，局部变量 `blob` 不再保留。

### 当前持久化只写 Parse IR 和 backend raw

`ShadowParseService` 当前会持久化：

```text
Parse IR JSON -> parse bucket，artifact_class=parse_ir
Backend artifact JSON -> parse bucket，artifact_class=backend_raw
```

源码中没有找到生产阶段遍历 `ParsedDocument.binary_assets` 并执行以下动作：

```text
build_object_key(binary_asset, image_sha256)
  -> ObjectStorePort.put_stream(image bytes)
  -> asset_storage_objects register
  -> 把 storage_object_id/location 回填 FigureAsset
```

因此 Parse IR JSON 中虽然存在 binary asset metadata，`original_image_ref` 当前只是逻辑引用，不是可解引用的存储对象指针。

2026-08-24 实盘盘点中 binary bucket 为 0 个对象，与当前代码路径一致。

### 其他格式的当前边界

#### DOCX

Native DOCX 会统计文档中的 `blip` 图片数量并写 warning：

```text
image extraction not supported yet (diagnosed, not parsed)
```

所以它只做到“检测并告警”，没有生成可用图片资产。

#### XLSX

Native XLSX 会统计 worksheet `_images` 和 `_charts`，分别记录：

```text
image extraction not supported
chart extraction not supported
```

图片、图表都不会进入结构化资产。

#### HTML

`<img>` 会变成 figure block，structure 保留：

```text
src / alt
```

但 Parser 是无网络 IO 的纯适配器，不会下载远程图片，也不会把 data URI、本地相对路径或远程 URL 统一物化。诊断会明确记录 `image materialization not supported`。

#### Markdown

Legacy Markdown 能检测 inline image token，但当前 normalizer 明确将其降为 unknown，并注明 binary asset 通道未接；不会伪造已保存的 FigureAsset。

#### PDF

当前 Native PDF 的能力声明是 pages/tables/coordinates，主要从文本层和表格结构产块；没有生产级 PDF 内嵌图片提取、页面渲染或 crop 物化链。扫描 PDF 的 OCR/VLM 又属于 P02 尚未接通的后端能力。

### 对切片和检索的影响

Segment Compiler 对 figure 的策略是：

```text
有 caption 或 element.text
  -> 生成 figure 文本切片

没有 caption、没有文本
  -> 不生成切片（不伪造可索引内容）
```

因此纯图片 PPT 页面可能出现：

- Parse IR 中有 Figure Element 和 hash metadata；
- 没有图片 bytes；
- 没有 caption/VLM description；
- Segment Compiler 不为该图生成任何文本段；
- 下游 Retrieval Unit/Embedding 也无内容可消费。

即使页面中还有其他文本使整个文档 Build 成功，图片表达的架构图、流程图、曲线、截图和表格信息仍然不会进入当前检索语义。

### 为什么测试会让人误以为已经完成

PPTX 适配器测试已经断言：

- 存在 figure Element；
- 存在 FigureAsset；
- image_hash 正确；
- binary_assets key 中包含 hash。

这些测试证明检测与 IR 建模正确，但没有断言：

- binary bucket 中真实存在对象；
- `binary_asset_id` 可解析到 StorageObject；
- 下载字节与原图 hash 一致；
- 删除/保留/共享引用生命周期正确；
- Caption/VLM/检索能消费该图。

所以“binary asset 契约测试通过”不等于“图片资产生产链已完成”。

### 问题性质

当前系统并非完全忽略图片：不同格式已做到计数诊断、figure 类型、hash、元数据和未来引用契约的一部分。

真正缺口是：

> 图片资产目前主要停留在“被识别和被描述”的控制面，真实 bytes 没进入可寻址、可下载、可审计的 MinIO binary 数据面，也没有形成 Caption/OCR/VLM 到检索文本的闭环。

这也是几万行平台代码复杂度的一个来源：契约、类型、bucket、引用和编译策略已经提前搭好，但生产物化与消费阶段仍未完成。

### 影响判断

- TXT/Markdown 纯文本知识：影响较低；
- 普通 DOCX 正文和表格：文字仍可用，但图片内容缺失；
- PPTX：架构图、流程图、截图等关键信息可能完全不可检索；
- XLSX：图表不进入知识；
- HTML：只保留 src/alt，远程资源没有冻结证据；
- PDF/扫描件：图片与视觉内容依赖尚未接通的 OCR/VLM 路线；
- 证据回放：无法通过 FigureAsset 稳定取回当时解析的原图 bytes。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时建议：

1. Parser artifact 设计可传递 binary payload（流/临时对象引用），不能只留下 hash metadata；
2. 增加 binary materialization 阶段，按 sha256 内容寻址上传 MinIO binary bucket；
3. 每个 binary asset 注册 `asset_storage_objects`，Parse IR 引用稳定 storage_object_id/location；
4. 对 HTML 外链区分 data URI、相对资源和远程 URL，冻结抓取策略、超时、安全与许可；
5. 为 DOCX/PPTX/XLSX/PDF 分别实现原生图片或 page crop 提取；
6. Caption/OCR/VLM 产物作为 derived annotation，不能覆盖原图和原始 caption；
7. 让 Figure Segment 至少消费原始 caption、alt、OCR 或受控 VLM 描述，并保留证据引用；
8. 复用 P08 的引用感知 retention/GC，避免共享图片被误删；
9. 增加“上传含图 PPTX -> binary bucket 有对象 -> hash 一致 -> Parse IR 可解引用 -> Figure 生成检索内容”的真实 MinIO 端到端测试。

## P11：MinIO 源对象虽然流式读取，但当前解析热路径仍会整文件聚合到内存

**状态：已通过最新代码核实，待逐项讲解。文本 demo 通常不受影响；大文件或并发解析场景属于 P1 可扩展性风险。**

### 当前真实调用链

`ShadowParseService._read_and_parse()` 的读取方式是：

```python
chunks: list[bytes] = []
async for chunk in self._reader.open_stream(frozen):
    chunks.append(chunk)
data = b"".join(chunks)
artifact = await asyncio.to_thread(self._parser.parse, data, mime=frozen.mime)
```

因此这里要区分两个概念：

```text
对象存储读取是流式的
    !=
解析器输入和解析过程是流式的
```

`ObjectStoreSourceArtifactReader` 能够分块从 MinIO 读取，并在读取过程中做 sha256 校验；但 `ShadowParseService` 随后会把所有 chunk 保存进列表，再通过 `b"".join(chunks)` 拼成完整 `bytes`，最后把整份内容交给同步 Parser Adapter。

### 为什么可能不只是“一份文件大小”的内存

在某些时刻，同一文档相关内存可能同时包含：

- `chunks` 列表中的全部原始分块；
- `join` 后形成的完整 `data`；
- PDF、DOCX、PPTX、XLSX 等第三方解析库建立的文档对象；
- `BackendParseArtifact` 中的 blocks、raw_output 和 structure；
- Normalizer 生成的完整 Parse IR；
- 随后序列化持久化时形成的 JSON bytes/string。

实际峰值取决于格式和解析库，不能简单按“源文件大小”估算。例如压缩率很高的 Office 文件，磁盘上几十 MB，解压后的 XML、图片和对象树可能明显更大。

`asyncio.to_thread` 只解决同步 Parser 阻塞事件循环的问题，不会减少解析占用的内存，也不会给并发任务提供内存背压。

### 与 P01、P05 的区别

这是第三个独立的整包内存环节：

```text
P01：HTTP 上传阶段，UploadFile 被整体 read 后再上传 MinIO
P11：从 MinIO 读取源文件后，解析前重新聚合为完整 bytes
P05：读取已经生成的 Parse IR/解析结果时整包加载
```

所以即使将 P01 改成真正的 multipart streaming，解析阶段仍可能在 P11 再次把文件完整装入内存；修复其中一个不能自动修复另外两个。

### 问题性质

当前不是“假的 MinIO 流式读取”。分块读取和增量 hash 校验确实存在。

真正缺口是：

> 流式能力停在 SourceArtifactReader 边界，Parser Adapter 契约仍以完整 `bytes` 为输入，生产热路径又显式聚合全部 chunk，因此没有形成端到端流式解析、临时文件卸载或基于资源预算的并发控制。

### 影响判断

- 当前约 14 MB 的单文档 demo：通常可以成功，不代表这里已具备规模化能力；
- 大 PDF/Office 文件：解析峰值内存可能远高于源文件大小；
- 多个 Run 并发：峰值会叠加，可能触发容器 OOM；
- OOM 时：daemon thread 与当前 Run 执行模型还会叠加 P07 的恢复问题；
- 云解析后端：如果未来仍先在本进程聚合完整 bytes，切换后端也不会自然消除此风险。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时建议：

1. 按格式区分能力，不要强迫所有 Parser 只接受完整 bytes；
2. 对支持文件路径/文件对象的库，采用受控临时文件或 seekable spool，设置磁盘额度和清理规则；
3. 对纯文本格式提供增量解码与增量 block 生成能力；
4. 对必须整包处理的格式显式声明最大输入、解压膨胀风险和资源需求；
5. 在调度层增加按预计内存成本计算的并发背压，而不是只依赖线程池；
6. 记录 source_size、解析峰值内存、耗时和 artifact_size，建立真实容量基线；
7. 增加大文件与多任务并发压测，并验证 OOM/取消后的 Run 状态和临时文件清理。

## P12：保留期、Purge 与 Storage Operation 契约存在，但没有发现真正执行物理清理的运行链

**状态：已通过最新代码核实，待逐项讲解。与 P08 强相关，但这里关注的是“清理执行器不存在”，属于 P1 生命周期与存储治理缺口。**

### 已经存在的设计

代码和 DDL 中已经出现了存储治理所需的一部分概念：

- `retention_until` 等保留期限字段；
- `asset_storage_operations` 表；
- 文件审计事件；
- `soft_delete`、`restore`、`purge` 等文件管理服务接口；
- 删除前必须检查 active reference、Build reference 和 retention hold 的设计说明。

这些说明项目并非完全没有考虑对象生命周期。

### 当前 Purge 实际只做什么

`FileManagementService.purge()` 的注释明确写明：

```text
Register a purge request + audit. Does NOT delete bytes.
Physical deletion is deferred to M1 GC.
M1.3 only records intent.
```

当前方法实际执行的是写一条 `purge_request` 审计记录，没有调用对象存储删除，也没有创建一个能够确认被 Worker 消费的物理删除任务。

### 没有发现的运行时能力

截至最新提交 `cfbf918`，在生产 Python 代码中没有找到以下闭环：

```text
扫描到期/待清理对象
  -> 解析对象与业务实体的全部引用
  -> 检查 Build、Release、审计和 retention hold
  -> 加锁或领取 asset_storage_operations
  -> 删除 MinIO 对象/版本
  -> 更新操作结果、重试次数和终态
  -> 对失败任务告警与人工恢复
```

`asset_storage_operations` 当前主要出现在 DDL/契约测试中；没有发现生产侧的 producer、repository、sweeper 或 worker 真正消费它。

### 与 P08 的关系

P08 关注的是：当前文档删除语义会不会破坏历史 Build，以及“从当前知识库移除”和“永久清理”是否被混为一谈。

P12 关注的是另一个层面：

> 即使未来删除语义定义正确、也成功生成了 purge/GC 意图，当前仍缺少一个能够安全、幂等地删除 MinIO bytes 并记录结果的执行系统。

所以两者有关联，但不是同一个问题：P08 是引用与产品语义，P12 是物理回收的执行闭环。

### 影响判断

- 删除数据库记录不等于释放 MinIO 空间；
- Parse IR、backend raw、binary asset、旧版本 source 等对象可能持续累积；
- 仅有 retention 字段不能证明到期对象会被处理；
- 容量、费用和合规删除无法通过当前代码得到闭环证明；
- 如果以后直接补一个简单定时删除，又可能反向触发 P08 的共享引用和历史证据误删风险。

### 后续处理建议

暂不在本次只读分析中修改代码。整改时建议：

1. 明确 soft delete、从 KB 移除、purge request、retention expiry 和物理删除五种状态；
2. 以 `asset_storage_operations` 或可靠 outbox 作为可领取、可重试的删除任务来源；
3. 删除前统一计算 source/parse/binary 与 Build/Release/审计证据的引用；
4. 使用 lease、幂等键、attempt count、next_retry_at 和终态，避免重复删除或任务丢失；
5. 对 MinIO versioning 场景明确删除当前版本还是所有版本；
6. 对对象不存在、数据库行不存在和 hash 不匹配分别记录结果；
7. 增加 GC dry-run、容量报表、失败队列和管理员审计入口；
8. 用真实 MinIO 做“共享引用不删、最后引用释放后删除、失败后可重试”的端到端测试。

## P13：已挂载 API 的身份认证与授权策略不一致，部分读写接口未接入统一用户校验

**状态：已通过最新代码核实，待逐项讲解。属于 P1 安全与租户边界问题；不等同于已经确认公网暴露。**

### 最新代码已经修复的部分

最新版本并不是所有接口都没有鉴权：

- `/api/kb/*` 的主要 KB 路由普遍依赖 `current_user`；
- `current_user` 要求同时提供 `X-KB-User` 和正确的 `X-Internal-Auth`；
- 用户状态会从数据库现查，disabled 用户会被拒绝；
- `/api/runs` 已增加 router 级 `Depends(current_user)`，部分操作再叠加细粒度 Run 权限或 `require_admin`；
- `/api/ops/*` 已按管理员权限保护。

这说明项目已经建立了认证模型，而且最新提交确实在补安全边界。

### 仍然存在的不一致

`knowledge_mining/mining/api/app.py` 同时挂载了两组不同历史阶段形成的路由：

```text
受 current_user/require_admin 保护的 KB、Run、Ops 路由
以及
没有统一认证依赖的 legacy/domain 路由
```

截至最新提交，以下已挂载路由文件的 `APIRouter` 和具体端点中没有发现 `current_user` 或 `require_admin`：

- `api/routes/knowledge.py`：知识、文档、Segment、Unit、Relation 查询；
- `api/routes/builds.py`：Build 与 Release 查询；
- `api/routes/uploads.py`：上传配置、上传和上传列表；
- `api/routes/ontology.py`：Ontology bootstrap/review/promote/publish、mention resolve、graph merge/retype/delete 等读写操作；
- `api/routes/workflows.py`：Workflow 创建、编辑、校验、发布、克隆、归档；
- `api/routes/document_lifecycle.py`：文档下载、文档删除、批次删除；
- `api/routes/config.py`：配置、domain pack 和 stage 查询。

其中 `Depends(get_*_service)` 只是服务注入，不是身份认证或权限校验。

### 为什么不能仅用“这是内部服务”解释

`docker-compose.yml` 当前包含：

```yaml
"${CMKB_MINING_PORT:-8901}:8901"
```

这意味着 mining 服务端口发布到宿主机。`kb/auth.py` 自身也明确以“8901 被 publish，单凭身份头可被直连伪造”为威胁模型，才要求 `X-Internal-Auth`。

因此可以确认的是：

> 这些无鉴权接口可能被绕过网关直接访问，具体可达范围取决于宿主机绑定地址、防火墙、内网和部署环境。

当前证据不足以直接断言它们已经暴露到公网，但也不能在应用层假设网络一定会替它们完成保护。

### 可能造成的影响

- 未认证调用者可能读取文档、知识结构、Build/Release 或配置元数据；
- 未认证调用者可能直接发起上传；
- Ontology、Workflow 和图谱写接口可能被修改；
- 文档生命周期接口包含删除操作，可能绕过新的 KB 权限模型；
- 新旧接口同时存在时，同一业务资源可能出现“新入口有权限、旧入口没权限”的绕行路径；
- 审计记录即使保存了 actor 字段，也不能替代请求入口的可信身份认证。

### 问题性质

这不是“系统完全没有登录鉴权”。新的 KB 路由、Run 和 Ops 已经有较明确的安全模型。

真正缺口是：

> 鉴权改造尚未覆盖整个已挂载 API surface；安全边界以路由家族为单位出现分裂，导致调用者可能绕开受保护的新接口，使用仍挂载的旧接口访问或修改同一类数据。

### 后续处理建议

暂不在本次只读分析中修改代码。整改前建议先完成接口分层决策：

1. 列出全部已挂载 endpoint，并标注 public、authenticated、KB member、KB admin、site admin、service-only；
2. 对 legacy/domain 路由决定迁移、下线，还是纳入统一 `current_user`/RBAC；
3. 对上传、Ontology、Workflow、删除等写接口优先补权限和可信 actor；
4. 服务间调用采用明确的 service identity，不依赖可由外部任意填写的普通头；
5. 在应用入口设置默认拒绝策略，再显式开放 health 等公共端点，降低漏挂依赖的风险；
6. 对 KB 资源校验调用者是否属于目标 KB，不能只验证“已经登录”；
7. 收紧 CORS 与宿主机端口暴露范围，但不把网络隔离当作应用授权的替代品；
8. 增加路由枚举测试，确保每个非公共 endpoint 都声明了认证和细粒度授权；
9. 增加“绕过网关直连 8901、调用旧写接口必须失败”的集成测试。
