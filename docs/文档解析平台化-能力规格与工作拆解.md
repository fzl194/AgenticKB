# 文档解析平台化：能力规格与工作拆解

> 日期：2026-08-13
> 文档类型：能力规格 / 实施前 SRS
> 状态：讨论稿，架构评审通过后进入实现计划
> 上游调研：`docs/文档入库解析地基-工业调研与演进方案.md`
> 继承设计：`docs/superpowers/plans/2026-07-25-document-processing-mining-refactor.md`
> 本文不提供具体代码和 SQL，而是定义可交给多个 Agent 落地的职责、流程、数据契约、状态、验收和依赖。
> 本版本固定范围：文件管理与 MinIO 对象存储必须和解析平台一起建设，不再继续以共享本地目录作为正式文件底座。
> 产品决策修订：不建设文档版本管理和 Source Version 实体。文档只维护当前内容；解析、切片和知识更新统一由现有 Document Snapshot 承载历史。

## 0. 如何阅读本文

本文解决的不是“应该选 Docling 还是 MinerU”，而是把文档解析建设成平台能力，使任何解析库都只能作为可替换后端。

阅读时先记住四句话：

1. 原文件是事实源，Markdown 不是事实源。
2. Parser Adapter 只负责接第三方库，Document Parse Operator 负责编排一次完整解析。
3. Parse IR 是 Snapshot 内的解析事实，Segments 是同一 Snapshot 内面向下游的编译视图。
4. 一份文档通常只跑一个主解析器；只有质量不合格时才切换后端或局部修复，不是把所有库串行跑一遍。
5. MinIO 是对象存储而不是业务数据库；对象字节进入 MinIO，文档当前态、目录、权限和知识快照进入 PostgreSQL。

本文把“原子知识”称为“原子文档元素”。它是后续知识编译的可靠原料，还不是领域事实、规则或实体关系。

## 1. CAPABILITY：最终要获得什么能力

### 1.1 能力陈述

当用户把一份文档放入知识库后，系统先通过统一文件管理能力完成上传、校验、目录归属和 MinIO 持久化；文档可被在线编辑或替换，始终只展示当前内容。触发知识更新时，Mining Run 冻结当时的 MinIO 对象、内容哈希和文档修订号，再选择解析后端并生成统一 Parse IR；解析事实、原子元素、切片及后续知识资产共同归入一个不可变 Document Snapshot，继续复用现有 Build 和 Release 能力。

能力上线后的核心变化：

```text
当前：multipart 全量读内存 -> 共享本地卷/storage_path -> Parser -> SectionNode -> Segment -> DB

目标：文件管理 -> Logical Document -> 当前 MinIO Storage Object
                                      -> Mining Run 冻结输入
                                      -> Document Snapshot
                                           ├─ Parse IR / 原子元素资产
                                           └─ Segment / 下游知识资产
```

### 1.2 用户可感知结果

- 文档解析失败时能看到具体失败阶段、失败页面、使用过的后端和建议动作，而不是只有“跳过”。
- 用户可以在知识库中上传、查看、下载、改名、移动、软删除、恢复和查看版本；这些操作不依赖应用容器共享磁盘。
- 同一文档可以更换解析器重新生成知识快照，不覆盖当前 Release 使用的旧快照。
- 同一快照中保存的 Parse IR 可供重切片复用；需要形成新的知识结果时创建新快照，不再另建一套 Parse Result 版本体系。
- 检索答案能够定位回原文件的页码、区域、工作表单元格或 DOM 节点。
- 复杂表格、图片、公式不会只剩一段 Markdown 字符串。
- 已发布 Release 永远能解释自己使用了哪个文档内容哈希、MinIO 对象和知识快照。

### 1.3 系统层结果

- 解析后端可插拔：legacy、Docling、PP-StructureV3、MinerU、云服务都遵循同一 Adapter 契约。
- 文件存储可替换：业务层只依赖 Object Store Port；本版本生产实现固定为 MinIO/S3 API，禁止业务代码直接拼本地路径。
- 解析质量可量化：不同后端可在同一语料和同一 IR 上比较。
- 解析成本可治理：按文档特征选择 fast/standard/complex/cloud 路由。
- 旧 workflow 和 serving 可以渐进兼容，无需一次性重写整条挖掘链。

## 2. CONSTRAINTS：必须守住的不变量

### 2.1 资产分层不变量

```text
LogicalDocument -> current StorageObject
MiningRunDocument -> frozen StorageObject + raw hash + content revision
DocumentSnapshot
  -> Parse IR Artifact / ParseContainer / ParseElement / StructuredAsset / BinaryAsset
  -> RawSegment / SegmentRelation
    -> RetrievalUnit / Embedding / KnowledgeArtifact
```

| 不变量 | 解释 |
|---|---|
| Snapshot 输入不可变 | Snapshot 一旦建立，其 source storage object、raw hash 和 content revision 永不变化 |
| 对象引用不可伪装成业务身份 | bucket/object key/version id 只定位字节；文档、目录、权限和版本身份以 PostgreSQL 为准 |
| Presigned URL 不持久化 | 它是短期访问凭证，只能按权限即时生成，不能写入 Document、Snapshot 或 Build |
| 逻辑目录与对象 key 解耦 | 改名/移动只修改 PostgreSQL 中的逻辑位置，不复制或重命名不可变源对象 |
| 对象删除受引用保护 | Document Snapshot 或已发布 Build 仍引用对象时不得物理删除 |
| Parse Run 可失败 | 每次执行都有记录，失败也不能消失 |
| Snapshot 不可变 | 文档内容、Parser、模型、配置、规范化或切片规则变化并执行知识更新时，生成新 Snapshot |
| Element 身份稳定 | 一个 Snapshot 的 Parse IR 内 element id 不因数据库分页或切片变化而变化 |
| Build 固定 Snapshot | Build 只选择不可变 Snapshot，不跟随文档当前内容变化 |
| 解析不做领域推理 | Parse IR 只表达文档结构和证据，不写领域本体关系 |
| 切片不修改原子元素 | 合并和拆分只产生映射，不回写 element |
| LLM 结果不可冒充原文 | LLM annotation 必须带模型、输入、来源和生成标识 |
| 后端输出不直接入业务表 | 所有后端必须经过 Normalizer 和 schema validation |

### 2.2 执行不变量

- 一次普通 Parse Run 只有一个 primary backend。
- fallback 只能由失败或质量策略触发，必须留下原因。
- 局部修复优先处理页面/区域，不默认重跑整份文档。
- cloud backend 必须先通过数据外发策略判断。
- Parser 进程失败不能使主 API 进程退出；重型后端按 sidecar/worker 边界设计。
- Parse IR 通过质量门禁之前不得进入 Segment Compiler 和 Snapshot Commit。
- 相同 document、source raw hash、parser/workflow identity 的知识更新请求必须可幂等复用 Snapshot。
- PostgreSQL 与 MinIO 之间不假设分布式事务；所有跨存储写入必须采用状态机、幂等键和补偿/回收任务。
- Parser 不得接收 MinIO 长期凭据；只通过 Object Store Port 获取流或受控临时文件。

### 2.3 兼容不变量

- 迁移期 `asset_raw_segments`、`asset_retrieval_units` 和 serving 查询行为保持可用。
- 旧 `parse_segment` workflow manifest 继续可执行。
- 新链路产生的 segments 必须能被当前 enrich、discourse、retrieval unit 和 embedding 阶段消费。
- 历史 Release 不强制回填无法证明的精确 source spans。
- KB、domain、workflow 和 channel 的现有隔离语义不得因解析重构被绕过。
- 迁移期允许 MinIO 优先、本地 `storage_path` 回退；新文件和在线编辑从切换日起只写 MinIO，禁止继续产生新的本地路径依赖。

### 2.4 安全与许可不变量

- 扩展名不可信，必须探测 MIME 和文件签名。
- 压缩包必须限制文件数、展开大小、压缩比和路径，禁止目录穿越。
- 加密文件、宏、嵌入附件和远程图片必须按策略处理。
- 云解析、远程图片和外部 VLM 默认不允许静默外发。
- 每个 Parser Backend 都必须登记代码、模型权重、系统库和容器许可证信息。
- 未通过 SBOM 和许可审查的 backend 不得进入 production route。
- MinIO bucket 禁止公开访问；客户端不得获得服务账户密钥，只能取得短时、单对象、单动作的 presigned URL。
- 对象下载必须先做 KB 权限判断；文件名仅用于展示和 `Content-Disposition`，不得直接作为 object key。

## 3. 关键概念与职责边界

### 3.1 Logical Document

用户视角的逻辑文档身份，对应当前 `asset_documents`。文件内容更新不会创建新 Logical Document，也不创建用户可见的文档版本；只更新当前 Storage Object 指针、raw hash 和 content revision。

它负责：KB 归属、目录、标题、owner、文档类型、当前内容、在线编辑修订号和逻辑删除。

它不负责：保存解析器版本、切片策略或解析质量。

### 3.1A Storage Object

MinIO 中一个不可变对象的登记记录。它不是用户看到的“文件”，也不表达 KB 目录；它只回答“哪一组字节存在哪里、是否完整、由谁引用”。

最低信息：

- `storage_object_id`
- provider=`minio`、bucket、object key、可选 object version id
- SHA-256、size、MIME、ETag、加密方式
- artifact class：`source / backend_raw / parse_ir / page_render / binary_asset / temporary`
- 状态：`STAGING / AVAILABLE / QUARANTINED / DELETING / DELETED / MISSING`
- 创建时间、最后校验时间、retention deadline

规则：

- PostgreSQL 的 Storage Object Registry 是对象引用清单，MinIO 是对象字节事实源。
- object key 使用系统生成的不可变、无业务语义 key；原文件名、文件夹名和 KB 名不进入 key 身份。
- 同一对象可被多个业务资产引用，但每个引用关系必须显式登记；不能仅靠“扫描 bucket 前缀”推断业务归属。
- MinIO 自身 versioning 仅用于运维防护，不向业务暴露为文档版本。

### 3.1B Upload Session

一次可恢复的上传事务。它解决浏览器/服务端、PostgreSQL 和 MinIO 无分布式事务时的一致性问题。

最低信息：`upload_session_id`、KB/目标目录、提交者、原始文件名、预期大小/MIME、临时 object key、幂等键、过期时间、状态和失败原因。

推荐状态：

```text
INITIATED -> UPLOADING -> OBJECT_STAGED -> VERIFYING -> COMMITTED
          -> ABORTED / EXPIRED / REJECTED
```

只有 `COMMITTED` 会创建或更新 Logical Document 和 Storage Object。中断上传不能产生“列表里可见但没有字节”的正式文档。

### 3.2 Frozen Source Binding

它不是独立业务实体和版本表，而是 Mining Run 开始时记录在运行文档上的输入绑定。它解决“用户在线编辑与后台解析并发”问题。

最低信息：

- `document_id`
- `source_storage_object_id`
- `source_raw_hash`
- `source_content_revision`
- 原始 MIME、文件名和大小
- 捕获时间

解析器只读取这次绑定的对象。解析过程中即使用户继续编辑文档、让当前对象从 A 切换为 B，本次 Run 仍然处理 A；如果完成时发现文档 current revision 已变化，产出的 Snapshot 可以保留，但不得自动成为最新知识，系统应标记 stale 并触发/提示对 B 重新更新知识。

因此需要“冻结输入”，但不需要 `asset_document_source_versions`。失败历史由现有 Mining Run/Run Document 记录；成功的历史由 Document Snapshot 记录。

### 3.3 Processing Snapshot

当前 `asset_document_snapshots` 升级为唯一的知识版本根。它代表“针对某次冻结文档内容，使用某套解析和知识加工配置，成功形成的一次知识结果”。

目标关系：

```text
Frozen Source Binding + Parser/Workflow Binding
  -> Document Snapshot
       -> Parse IR artifact / Elements / Structured Assets
       -> Segments / Retrieval Units / Existing Asset Tables
```

Snapshot 至少固定：document、source storage object、source raw hash、source content revision、parser/model/config fingerprint、workflow binding、Parse IR schema 和质量结论。Parse Result 不再作为并列版本实体，而是 Snapshot 内的解析制品；完整 Parse IR 存 MinIO，查询投影和后续资产以 `document_snapshot_id` 关联。

### 3.4 Parse Run

一次实际解析执行，可成功、失败、取消、超时或进入修复。

它记录“发生过什么”：

- 使用的 Parse Plan
- primary/fallback backend
- 每个阶段开始结束时间
- backend job id
- 输入/输出 artifact URI
- 资源、页数、成本、重试次数
- errors、warnings、低质量页

Parse Run 是运行记录，可以有状态变化。

### 3.5 Parse Artifact

一次通过 schema validation 的解析制品。它记录“解析出来了什么”，但不再建立独立的业务版本线；其生命周期归属于 Document Snapshot。

身份指纹至少包括：

- source raw hash
- parser name/version
- model versions
- parser config hash
- Parse IR schema version
- normalizer/reconciler version
- dependency fingerprint

同一文档内容可以因 parser/workflow 变化形成多个 Document Snapshot。哪个知识结果进入 Build/Release，继续由现有 Build 选择 Snapshot；不再增加 Parse Selection 版本体系。

### 3.6 Parse Container

原生内容容器：

- PDF/Image：Page
- DOCX：Section/Page（若可获得）
- PPTX：Slide
- XLSX：Workbook/Sheet
- HTML/CHM/HDX：Topic/DOM Document
- Email/Archive：Message/Attachment

Container 让系统统一处理不同格式，同时不伪造不存在的页码。

### 3.7 Parse Element

文档中可独立定位的基础元素，例如 title、heading、paragraph、list item、table、figure、formula、footnote、caption。

Element 是原子结构单位，不按 token 大小定义。一个长段仍然可以是一个 Element，切分由 Segment Compiler 完成。

### 3.8 Evidence Span

Element 在原文件中的证据定位：

- PDF：page + bbox/polygon
- DOCX：paragraph/table/cell/OOXML ref
- XLSX：sheet + A1 range/cell
- HTML：DOM path/id + character range
- TXT/Markdown：line/character range
- PPTX：slide + shape id/bbox

它是 citation、人工复核和 segment 映射的依据。

### 3.9 Structured Asset

不能只靠一段文本表达的结构：Table Grid、Figure、Chart、Formula、Form、Key-Value Group。

Structured Asset 关联一个或多个 Elements 和 Binary Assets。其 Markdown、HTML、CSV 是 rendered view，不是事实源。

### 3.10 Segment Views

Snapshot 内的 Parse IR 使用指定 segment policy、document profile 和 compiler version 产生的一组 segments。它是 Snapshot 的子制品，不再单独形成一条面向业务的版本线。

它回答“为了某个场景怎么切”，不回答“原文件里有什么”。

### 3.11 Knowledge Access View

上层 Agent 不应直接查询 Element、Relation、Table Cell 等多张底层表，也不应把某个 Retrieval Unit 当成完整事实。Knowledge Access Layer 以 Snapshot 为边界，按请求把原子元素组装成可消费的结构化读模型：

- `Outline View`：文档目录、标题树和容器范围。
- `Section View`：一个章节的标题链、正文、表格、图片、脚注和证据定位。
- `Evidence Bundle`：围绕若干命中元素补齐父标题、前后文、被引用表格/图片和 source spans。
- `Table View`：表头、单元格网格、合并关系、标题、脚注及正文引用。
- `Procedure Candidate View`：按文档结构聚合前置条件、步骤、警告和结果，但不直接宣称它已经是领域 SOP。

这些 View 默认由 Snapshot 下的 Elements/Relations/Structured Assets 动态组装，不是新的知识版本，也不要求每种 View 建一张永久表。只有高频或高成本 View 才按 `snapshot_id + view_type + view_config_hash` 缓存；缓存可删除、可重建，不能成为事实源。

### 3.12 Knowledge Artifact

Knowledge Artifact 是 Agent 面向特定领域和场景编译出的高级知识制品，例如事实、规则、SOP、FAQ、检查清单、实体关系和 wiki 页面。它与 Parse Element 的区别是：

- Element 忠实表达“原文有什么”，由解析链路产生。
- Knowledge Artifact 表达“在某个业务场景下如何理解和使用”，由场景 schema、领域模型、Agent 和校验器共同产生。
- 每个 Artifact 必须归属于一个 `document_snapshot_id`，并通过 Evidence Link 回指支持它的 Elements/Evidence Spans。
- Artifact 可以进入检索和发布，但不能覆盖或静默修改原子元素。

普通问答中 Agent 临时组装 Evidence Bundle 并生成回答，不自动形成 Knowledge Artifact，也不写入 Snapshot。只有需要长期复用、检索、发布、审计或人工维护的结果，才进入知识编译流程并在新的 Snapshot READY 前持久化。

## 4. 端到端流程：一份文档究竟如何流转

### 4.1 总览

```text
00 创建 Upload Session
  -> 01 上传并提交 MinIO 对象
  -> 02 更新 Logical Document 当前内容
  -> 03 Mining Run 冻结输入并探测文件
  -> 04 生成 Parse Plan
  -> 05 执行主解析器
  -> 06 转换为 Parse IR
  -> 07 文档级结构修复
  -> 08 质量评估
       -> 合格：09 固化 Document Snapshot
       -> 可修复：局部修复后回到 08
       -> 需回退：换 backend 后回到 06
       -> 不可用：记录失败并停止
  -> 10 编译 Snapshot 内的 Segments
  -> 12 运行现有增强/检索单元/向量
  -> 13 Build/Release
```

文件管理和知识更新是两条相连但独立的业务链。文件管理维护文档当前内容；知识更新启动时冻结 `document_id + storage_object_id + raw_hash + content_revision`，解析链不再接收任意本地路径。

### 4.1A 新文件入库的完整事务

```text
Client
  -> File Management API：申请 upload session，校验 KB 写权限和配额
  -> 小文件：API 流式代理上传；大文件：返回短时 presigned PUT/multipart 信息
  -> MinIO temporary prefix：写入 staging object
  -> Commit API：HEAD/stat 校验 size，服务端流式计算/复核 SHA-256，执行 MIME/安全扫描
  -> PostgreSQL transaction：登记 Storage Object，创建/更新 Logical Document 当前内容、目录关系和审计事件
  -> object/session 标记 AVAILABLE/COMMITTED
  -> 异步触发 inspect/parse，或等待用户手动触发
```

事务边界与补偿：

- 不能使用“先插正式文档行，再尝试上传”的顺序。
- MinIO 写成功、数据库提交失败时，对象留在 staging，由 orphan sweeper 按 session 过期时间回收。
- 数据库提交成功前必须用 `stat_object`/HEAD 证明对象存在、大小匹配；提交后发现缺失则把对象标记 `MISSING` 并阻断解析，不静默回退为空文件。
- Commit API 必须接受幂等键；重复提交返回同一文档更新结果，不重复创建对象或文档。
- 小文件也禁止 `await file.read()` 全量读入内存，应采用有上限的流式上传和 hash。
- 大文件 multipart 中断后可续传或过期终止；未完成 parts 由清理任务回收。

第一期默认上传策略：API 代理支持小文件和内部导入；浏览器大文件优先使用短时 presigned URL。无论传输路径如何，最终都必须走同一个 Commit/Verify 流程。

### 4.2 Step 01：接收原文件

责任模块：File Management API + Document Intake + MinIO Object Store Adapter。

输入：用户上传、目录扫描或 API 导入；旧 KB 文档路径只允许走迁移适配器。

处理：

- 创建 Upload Session，校验 KB 写权限、配额和文件策略。
- 限制单文件、批次、归档展开规模。
- 计算流式 raw hash。
- 先写 MinIO staging object，完成 size/hash/MIME/恶意内容验证后登记为不可变 Storage Object。
- 记录来源和安全扫描结果。

输出：`SourceArtifactCandidate`。

失败：文件不安全、损坏、超过限制时拒绝创建/更新正式文档内容，但保留 intake audit event；staging 对象进入隔离或等待回收，不能出现在普通文件列表。

### 4.3 Step 02：更新文档当前内容

责任模块：File Management。

输入：已验证 Storage Object + 新建或已有 Logical Document。

处理：

- 首次上传时创建 Logical Document；在线编辑/替换时保持 document id 不变。
- 使用 copy-on-write 写入新 Storage Object，再原子切换 Document 当前对象指针。
- 更新 raw hash、size、MIME、content revision 和 content updated time。
- 将知识状态派生/标记为 `outdated`，但不修改当前 Release 使用的旧 Snapshot。

输出：更新后的 `document_id + current_storage_object_id + content_revision`。

数据库写入：Storage Object Registry、Logical Document 当前内容和文件审计事件。

注意：“用户直接更新文档”是产品语义；物理实现不能原地覆盖旧对象。先写新 object key 再切换指针，旧对象若被 Snapshot/Build 引用则保留，否则由 GC 清理。这不是文档版本管理，而是保证解析和已发布知识不被并发修改破坏。

### 4.3A 文件管理操作语义

| 用户操作 | PostgreSQL 变化 | MinIO 变化 | 是否产生 Snapshot |
|---|---|---|---|
| 首次上传 | 新建 Logical Document、Storage Object，设置当前对象/hash/revision | 写新对象 | 否，等待知识更新 |
| 在线编辑/替换内容 | Logical Document 不变，切换当前 Storage Object，revision +1，知识标记 outdated | 写新对象；旧对象延迟 GC | 否，等待知识更新 |
| 改显示名称 | 修改 `document_name` 和审计 | 无 | 否 |
| 移动文件 | 修改 folder relation/directory projection | 无 | 否 |
| 移动/改名文件夹 | 修改文件夹树和路径投影 | 无 | 否 |
| 下载/预览 | 权限校验和访问审计 | 服务端流式返回或签发短时 presigned GET | 否 |
| 软删除 | 标记文档 deleted，隐藏于正常列表 | 无 | 否 |
| 恢复 | 恢复逻辑状态和原目录/指定目录 | 无 | 否 |
| 永久删除 | 创建 purge request，检查 Snapshot/Build 引用和 retention | 满足条件后异步删除对象 | 否 |
| 复制到另一 KB | 新建目标 Logical Document 和权限关系 | 默认复用同一 Storage Object；隔离策略要求时再 server-side copy | 否 |
| 更新知识 | 冻结当前对象/hash/revision，成功后新建 Snapshot 并进入 Build 选择 | 写 Parse IR/图片等解析制品 | 是 |

MinIO 没有真实目录，`/` 只是 object key 前缀。`kb_folders` 必须继续作为逻辑文件夹唯一事实源，不能通过 MinIO `list_objects(prefix=...)` 实现用户文件树。

名称与版本冲突规则：

- 同一 KB/逻辑文件夹内，active 文档显示名称唯一；软删除文档不阻塞恢复，但恢复遇到同名必须让用户选择新名称。
- 普通“上传文件”遇到同名返回 conflict，不得静默覆盖；只有进入已有文档的“编辑/替换内容”动作才更新该 document。
- 在线编辑/替换必须带 `content_revision` 条件，避免两人并发保存相互覆盖。
- 多文件/归档展开按每个成员返回结果清单，默认允许部分成功但必须明确列出失败项；需要全有或全无时由调用方选择 atomic batch 模式。
- Upload Session 创建时预留 KB 配额，COMMITTED 后转为实际占用，ABORTED/EXPIRED 后释放；不能只在上传完成后检查配额。

### 4.4 Step 03：文件探测

责任模块：File Inspector。

输入：Mining Run 冻结的 Storage Object、raw hash 和 content revision。

处理：

- MIME、真实格式、加密和压缩探测。
- 页数、sheet/slide/topic 数量探测。
- 对 PDF 抽样判断文本层、扫描比例、多栏、表格、公式和语言。
- 对 Office 判断宏、隐藏内容、嵌入附件和结构复杂度。
- 生成成本和资源预估。

输出：不可变 `DocumentInspection`。

失败：无法识别格式时输出 `unsupported`，不能偷偷当 TXT 解码。

### 4.5 Step 04：生成 Parse Plan

责任模块：Parser Router。

输入：DocumentInspection + domain policy + workflow options + compliance policy + backend registry。

处理：

- 选择一个 primary backend。
- 给出有序 fallback 列表。
- 指定 OCR、table、formula、figure、remote fetch 等策略。
- 指定质量 profile、timeout、page limit 和 cost budget。
- 检查后端健康、许可状态、数据外发策略和资源可用性。

输出：不可变 `ParsePlan`。

示意路由：

| 文档特征 | primary | fallback |
|---|---|---|
| Markdown/TXT | native adapter | 无或 legacy |
| DOCX/PPTX/XLSX | Docling/native adapter | legacy Office adapter |
| 简单数字 PDF | Docling standard/经评测 fast path | legacy PDF adapter |
| 中文复杂 PDF | PP-StructureV3 或 MinerU | Docling standard |
| 扫描 PDF | OCR + complex parser | cloud/VLM（策略允许时） |
| 表单票据 | 表单专项 backend | Docling/Azure/Google |

路由结果必须可解释，例如：`selected=pp_structure_v3, reason=scan_ratio_high+language_zh+table_ratio_high`。

### 4.6 Step 05：执行主解析器

责任模块：Document Parse Operator + Parser Adapter。

Operator 创建 Parse Run，调用 Adapter。Adapter 负责：

- 将本次 Run 冻结的 Storage Object 转换为第三方库输入。
- 调用库、本地 sidecar 或云 API。
- 保存 backend 原始输出。
- 把后端 errors、warnings、usage 和版本返回给 Operator。

Adapter 不负责：

- 写业务 element 表。
- 选择切片策略。
- 发布 Build。
- 静默调用 fallback。

输出：`BackendParseArtifact`，它是候选解析制品，还不是正式 Snapshot。

### 4.7 Step 06：转换为 Parse IR

责任模块：Parse IR Normalizer。

输入：BackendParseArtifact + Adapter mapping profile。

处理：

- 后端 block type 映射为项目 element type。
- 统一 container、坐标 envelope、阅读顺序和关系表示。
- 生成稳定 element id。
- 保存 backend 原始 id 和 provenance。
- 规范文本，但不改写原文含义。
- 运行 schema validation 和引用完整性检查。

输出：`CanonicalParseIRCandidate`。

失败：后端返回成功但 JSON 缺字段、关系悬空或坐标非法时，记为 normalization failure，不可进入质量门禁。

### 4.8 Step 07：文档级结构修复

责任模块：Structural Reconciler。

处理的是跨元素、跨页问题：

- 页眉页脚重复识别。
- 跨页段落和列表续接。
- 跨页表格 continuation。
- caption 与 figure/table 绑定。
- 标题层级和目录对齐。
- 脚注与正文引用绑定。
- hyphenation、错误换行等可逆规范化。

输出：Reconciled Parse IR Candidate + patch log。

规则修复优先；LLM 修复必须产生单独 annotation/patch，不能覆盖原始 backend artifact。

### 4.9 Step 08：质量评估与决策

责任模块：Parse Quality Gate。

输入：Reconciled Parse IR Candidate + quality profile。

输出：

- metrics
- issues
- low-confidence containers/elements
- decision：`PASS / WARN / REPAIR / FALLBACK / FAIL`
- recommended action

决策语义：

| 决策 | 后续动作 |
|---|---|
| PASS | 允许继续编译并固化 Snapshot |
| WARN | 允许继续编译并固化 Snapshot，但保留质量警告 |
| REPAIR | 只修复指定页/区域，然后重新评估 |
| FALLBACK | 使用 Parse Plan 的下一个后端重新执行 |
| FAIL | 停止本文档，不生成新 Snapshot |

防止死循环：每个 Parse Plan 有最大 backend attempts、repair attempts、cost 和总时长。

### 4.10 Step 09：固化 Document Snapshot

责任模块：Atomic Artifact Store。

只有 PASS/WARN 才执行：

- 提交前重新读取 Document 当前 `storage_object_id/raw_hash/content_revision`；与 Run 冻结输入不一致时，Run 标记 `SUPERSEDED`，不创建 Snapshot，staging artifacts 按短期策略回收。
- 保存 canonical Parse IR artifact。
- 保存 Containers、Elements、Relations 的查询投影。
- 保存 Structured/Binary Assets。
- 保存质量报告和完整 provenance。
- 编译并保存 Snapshot 下的 segments、element links 和兼容投影。
- 计算 Snapshot identity fingerprint。
- 固定 source storage object、raw hash、content revision 和 parser/workflow fingerprint。
- 标记 Parse Run 成功并关联 Snapshot。

结果不可变。后续发现问题或重新加工只能创建新的 Parse Run/Snapshot。

### 4.11 Step 10：判断知识是否可以进入 Build

责任模块：Mining Orchestrator。

Snapshot Commit 已保证输入仍是 Document 当前内容。之后：

- Snapshot 是当前内容的新知识候选，可进入新 Build。
- Snapshot 创建后如果用户再次编辑 Document，它自然变为 outdated，但不会被修改或删除。
- 当前 Release 不因文档编辑或 Snapshot 生成而自动变化；只有新 Build/Release 才切换线上知识。

### 4.12 Step 11：Snapshot 内部切片

责任模块：Segment Compiler Operator。

输入：

- snapshot candidate / canonical Parse IR
- document profile
- scenario/domain segment policy
- compiler name/version/config

处理：

- 读取 element graph，不重新读取原文件。
- 根据结构边界决定合并/拆分。
- 表格、图片、公式使用类型化策略。
- 注入祖先标题等派生上下文。
- 为每个 segment 保存到 Element/Evidence Span 的多对多映射。

输出：归属于 `document_snapshot_id` 的 segments 和 element links。

同一个 Snapshot 可以按需要保存多类视图：

- generic retrieval segments
- procedure-oriented segments
- table-oriented segments
- future Agent knowledge compilation view

如果切片策略变化并要更新知识，创建新 Snapshot；实现上可以复用旧 Snapshot 的 Parse IR 对象，避免重新 OCR/解析，但不再为这种复用引入独立 Parse Result 版本表。

### 4.13 Step 12：运行现有下游能力

现有 enrich、discourse、entity extraction、retrieval unit、embedding 可先继续消费 `RawSegmentData` 兼容投影。

变化仅在 provenance：

- segment 必须带 document_snapshot_id 和 compiler fingerprint。
- source reference 来自 element links。
- 表格行 unit 从 Table Asset 编译，不再解析 Markdown pipe table。
- 图片描述属于 annotation，并回指 Binary Asset。

### 4.13A Step 12A：为 Agent 提供结构化知识访问

责任模块：Knowledge Access Layer。

推荐消费链路：

```text
Query / Scenario Task
  -> Retrieval Unit 粗召回候选
  -> candidate segment/element ids
  -> Knowledge Access Layer 补齐 Section View / Evidence Bundle
  -> Agent 按场景 schema 编译
  -> 确定性校验与证据覆盖检查
  -> Knowledge Artifact + Evidence Links
```

这里保留现有向量、关键词和混合检索作为“找候选”的能力，但 Agent 不直接使用命中的扁平文本完成高风险推理。它必须再回到 Snapshot 的原子结构，补齐标题层级、表头、上下文和精确证据。对于已知文档/章节的任务，也可以跳过粗召回，直接通过 Snapshot/Element id 获取 View。

本阶段必须交付 Knowledge Access 的读取契约；自动生成领域 Knowledge Artifact 属于后续知识编译阶段。

### 4.14 Step 13：Build 和 Release

新 Build 文档选择必须固定：

```text
document_id
document_snapshot_id
source_storage_object_id
source_raw_hash
```

之后文档在线编辑、parser 升级或重新切片都不会影响历史 Release。新结果必须通过新 Snapshot 和新 Build 发布。

## 5. 一个具体例子：复杂 PDF 入库后变成什么

输入：`设备告警处理手册.pdf`，120 页，中英文混排，含 35 张表、18 张流程图，部分页面是扫描件。

### 5.1 运行资产

```text
LogicalDocument: doc-manual-001
SourceVersion:   src-v3 (raw hash = abc...)
Inspection:      inspection-003
ParsePlan:       route=complex_zh_pdf, primary=pp_structure_v3
ParseRun:        run-parse-008
ParseResult:     parse-result-005
QualityReport:   warn (2 pages repaired)
SegmentSet:      segment-set-retrieval-v2
```

### 5.2 Snapshot 的解析资产

```text
120 Page Containers
2,843 Elements
  1 title
  186 headings
  2,190 paragraphs
  144 list items
  35 tables
  18 figures
  21 captions
  74 headers/footers
  174 other elements

35 Table Assets
18 Figure Binary Assets
2,842 next_in_reading_order relations
186 heading parent relations
39 caption_of / continues_on relations
```

某张表不再只是：

```text
| 告警码 | 原因 | 处理建议 |
```

而是：

```text
Element table-12
  caption -> caption-12
  evidence -> page 48 bbox(...)
  structured_asset -> table-grid-12

TableGrid table-grid-12
  header rows = [0, 1]
  cells = 54
  merged cells = 6
  continues_on = table-13 on page 49
```

### 5.3 Segment Compiler 的产物

通用检索视图可能生成：

- 告警概述段：由 heading + 2 paragraphs 编译。
- 告警表整表 segment：供表级召回。
- 告警表行 segments：每行携带两层表头和 caption。
- 流程图 segment：caption + VLM annotation + 正文引用。

每个 segment 都保存来源：

```text
segment-324
  -> heading-88 span all
  -> paragraph-901 chars [0, 342)
  -> table-12 rows [3, 5]
```

因此检索返回 segment-324 时，可以精确显示第 48 页并高亮相关区域。

## 6. 功能能力拆解

### C00 MinIO Object Storage Foundation

功能：提供统一、可观测、可替换的对象读写底座，本版本生产实现固定为 MinIO。

必须支持：bucket bootstrap/health check、stream put/get/stat/delete、multipart、presigned GET/PUT、server-side copy、对象 version id、SSE、超时/重试、校验和、metrics 和错误归一化。

公共端口只暴露项目类型：`ObjectRef`、`ObjectStat`、`ObjectReadStream`、`UploadTicket`、`PresignedAccess` 和项目错误码。MinIO SDK response、S3Error、bucket 命名和凭据不得越过 adapter 边界。`SourceArtifactReader` 在此端口之上提供 `open_stream(storage_object_id)` 与 `materialize_temp(storage_object_id, run_id)`，供 Inspector/Parser 复用。

验收：业务模块不依赖本地绝对路径；MinIO 不可用、对象缺失、权限失败和 checksum 不一致有不同错误码；客户端永远看不到 MinIO 长期密钥。

### C01 File Management and Document Intake

功能：安全、幂等地管理知识库文档当前内容。

必须支持：上传会话、小文件流式代理、大文件 presigned/multipart、提交校验、目录扫描、API 导入、文件列表/详情、在线编辑/替换、改名、移动、下载/预览、软删除/恢复；流式 hash、乐观并发、大小限制、archive 安全和审计事件。不提供版本列表和版本回滚。

建议 API 资源边界：

```text
POST   /api/kb/{kb}/upload-sessions
POST   /api/kb/{kb}/upload-sessions/{session}/complete
DELETE /api/kb/{kb}/upload-sessions/{session}
GET    /api/kb/{kb}/documents
GET    /api/kb/{kb}/documents/{document}
PUT    /api/kb/{kb}/documents/{document}/content
PATCH  /api/kb/{kb}/documents/{document}
POST   /api/kb/{kb}/documents/{document}/move
POST   /api/kb/{kb}/documents/{document}/download-url
DELETE /api/kb/{kb}/documents/{document}
POST   /api/kb/{kb}/documents/{document}/restore
```

核心错误语义必须稳定：

| error code | HTTP 建议 | 含义 |
|---|---:|---|
| `upload_session_expired` | 410 | 会话已过期，客户端应重新申请 |
| `upload_incomplete` | 409 | 对象/parts 未完成，不能 complete |
| `file_too_large` / `quota_exceeded` | 413 | 单文件或 KB 配额超限 |
| `checksum_mismatch` | 422 | 声明内容与对象字节不一致 |
| `unsafe_file` / `archive_limit_exceeded` | 422 | 安全准入失败 |
| `storage_unavailable` | 503 | MinIO/网络短时不可用，可重试 |
| `storage_object_missing` / `storage_object_corrupt` | 409 | 目录记录存在，但对象完整性事故 |
| `document_revision_conflict` | 409 | 文档已被他人更新，需基于最新 revision 重试 |

验收：恶意 archive 不越界；超大文件不被全量读入内存；网络中断可恢复/终止；重复 complete 幂等；相同字节可复用 Storage Object，但不会错误共享文档权限或生命周期。

### C02 Frozen Input Binding

功能：知识更新开始时，在 Mining Run Document 中冻结当时的文档输入。

必须支持：document、storage object、raw hash、content revision、MIME/size、capture time 和并发变化检测。

验收：解析期间用户更新文档不会改变本次 Run 的输入；失败由 Run 记录；成功 Snapshot 固定相同输入；完成时输入已过期则不自动发布。

### C03 File Inspector

功能：以低成本生成路由需要的文档画像。

必须支持：MIME、格式、加密、页/容器数、文本层、扫描比例、语言、布局复杂度、表格/公式/图片信号。

验收：错误扩展名不导致错误 parser；不支持/加密文件给出明确状态。

### C04 Backend Registry

功能：管理可用解析后端及其能力边界。

每个 backend 登记：格式、语言、OCR/table/formula/chart 能力、部署方式、健康状态、资源需求、成本、数据外发属性、许可证状态、版本。

验收：未通过许可或不健康 backend 不会被 Router 选中。

### C05 Parser Router

功能：根据 Inspection 和 policy 生成可解释 Parse Plan。

必须支持：规则优先级、domain overrides、fallback chain、budget、cloud prohibition、版本化 route policy。

验收：同一输入和同一 policy 产生确定计划；每个选择有 reason codes。

### C06 Parser Adapter SDK

功能：让不同库转换成统一 BackendParseArtifact。

必须支持：capability declaration、parse、cancel、timeout、raw output、usage/error normalization、version fingerprint。

验收：legacy 与 Docling adapter 可被同一 Operator 调用；adapter 无权直接发布业务资产。

### C07 Parse IR Normalizer

功能：把后端结果转换成项目 Parse IR。

必须支持：type mapping、container、evidence span、relation、stable id、coordinates、schema validation、backend provenance。

验收：不同 adapter 输出可被同一 Segment Compiler 消费。

### C08 Structural Reconciler

功能：文档级结构修复。

必须支持：headers/footers、cross-page continuation、caption、heading tree、TOC、footnote；patch log。

验收：所有修复可追踪到原元素和规则/模型版本。

### C09 Parse Quality Gate

功能：评估结果是否足够进入知识链路。

必须支持：quality profile、指标、issues、container-level score、PASS/WARN/REPAIR/FALLBACK/FAIL、预算控制。

验收：空页、错序、表格破损等问题可以触发明确决策，而不是只写日志。

### C10 Atomic Artifact Store

功能：把 Parse IR 及查询投影不可变地保存到 Document Snapshot。

必须支持：所有大 artifact 写 MinIO、element indexes 写 PostgreSQL、structured assets、binary assets、relations、quality、Snapshot 幂等提交和 orphan 回收。

验收：Parser Adapter 升级后旧 Snapshot 及其 Parse IR 仍可读取和复现。

### C11 Segment Compiler

功能：从 canonical Parse IR 编译 Snapshot 内的多种 segment view。

必须支持：结构边界、token limit、typed strategy、context injection、segment-element mappings、compiler versioning。

验收：更改 segment policy 并更新知识时创建新 Snapshot；如果 Parse IR 可复用，不重新 OCR/调用云解析。

### C12 Workflow Compatibility

功能：让新能力逐步进入现有 workflow。

必须支持：旧 `parse_segment` compatibility handler、新算子版本、manifest migration、capability mapping、旧 templates 升级。

验收：历史 manifest 可执行；新 manifest 能显式分开 parse 与 segment。

### C13 Build/Release Reproducibility

功能：发布时固定完整制品链。

必须支持：Build selection 固定 Document Snapshot；Snapshot 固定 source object/hash、parse/segment fingerprints；旧 release 兼容。

验收：给定 Release 可以查询并重建其精确解析与切片来源。

### C14 Operations and Evaluation

功能：解析运行可运营、可评测。

必须支持：运行列表、阶段 trace、失败页、成本/耗时、后端成功率、质量分布、golden corpus、A/B 评测和人工复核入口。

验收：能按 backend/version/document type 比较质量、速度、成本和失败原因。

### C15 Knowledge Access Contract

功能：让检索器、Agent 和人工复核以统一接口读取 Snapshot 的结构化上下文，而不是耦合底层表。

必须支持：outline、section、evidence bundle、table、source region、按类型流式遍历 elements；所有响应包含 `snapshot_id`、稳定 element ids、source spans、quality/provenance 摘要和访问权限上下文。

建议接口语义：

```text
get_outline(snapshot_id)
get_section(snapshot_id, anchor_element_id, depth, include_assets)
get_evidence_bundle(snapshot_id, element_ids, neighbor_window, relation_depth)
get_table(snapshot_id, structured_asset_id)
get_source_region(snapshot_id, element_id)
stream_elements(snapshot_id, type_filter, container_range)
```

验收：同一 Snapshot 和同一 view config 得到确定结果；一个 Retrieval Unit 可还原到支持它的 Evidence Bundle；调用方不需要知道 Element/Table Cell 的物理表结构。

## 7. Parse IR 功能契约

### 7.1 Parsed Document

必须包含：schema version、source identity、parse identity、document metadata、containers、elements、relations、assets、diagnostics。

不得包含：检索 topK、embedding、领域实体、本体类型、场景摘要等下游信息。

### 7.2 Container

必需字段语义：稳定 id、类型、顺序、名称/页码、尺寸/坐标系统、语言、渲染资产、质量指标、原生引用。

允许层级，例如 workbook -> sheet、archive -> topic。

### 7.3 Element

首版必须支持：

```text
title, heading, paragraph, list, list_item, code, quote,
table, figure, chart, formula, form_field, key_value,
footnote, page_header, page_footer, page_number,
toc_entry, caption, reference, signature, selection_mark, unknown
```

必需语义：id、type、parent、order、text、normalized text、spans、style、language、confidence、parser annotations。

### 7.4 Evidence Span

必须区分：

- `text_range`：element text 中的字符范围。
- `source_locator`：原文件定位。
- `visual_region`：page/slide 上的 bbox/polygon。
- `native_ref`：sheet cell、DOM path、OOXML object 等。

未知时可以缺失，但不得伪造。系统必须能统计 source span coverage。

### 7.5 Relation

首版只允许确定性文档关系：

```text
parent_of, contains, next_in_reading_order,
caption_of, footnote_of, continues_on,
references, anchored_at, derived_from
```

每条关系含 source/target、type、confidence、method 和 provenance。

### 7.6 Table Asset

必须表达：行列数、cells、row/column span、header regions、caption、footnotes、continuation、cell source span、识别 confidence。

单元格 value 可以有 normalized type，但必须保留 raw text。公式值和展示值应分开。

### 7.7 Figure/Chart Asset

必须表达：原图/裁剪图、region、caption、正文 mention、图片 hash。

VLM description、chart series、OCR text 是 derived annotations，不覆盖原图与原 caption。

### 7.8 Formula Asset

必须表达：visual region、raw OCR、LaTeX/MathML（若可用）、inline/block、confidence 和 parser provenance。

## 8. 数据持久化能力规格

### 8.1 总体策略

采用混合存储：

- MinIO 对象存储：原文件、backend raw output、完整 Parse IR、页面渲染图、图片和大型表格 artifact。
- PostgreSQL：身份、状态、索引、关系、质量摘要、selection、下游引用。

不把完整大文档塞进一行 JSONB，也不强制第一期保存所有 word-level 元素。

推荐默认 bucket 按 artifact 生命周期划分，而不是“一 KB 一 bucket”：

| bucket class | 内容 | 默认保留策略 |
|---|---|---|
| `source` | 文档当前对象和被 Snapshot 引用的历史对象 | 当前 Document/Snapshot 引用期间保留 |
| `parse` | backend raw、canonical Parse IR、quality artifact | 与 Document Snapshot/Build 同生命周期 |
| `binary` | page render、figure、chart、附件和大型表格 | 与所属 Document Snapshot 同生命周期 |
| `staging` | 未提交上传、临时转换产物 | 短期 TTL，自动回收 |

实际 bucket 名由环境前缀配置，例如 `agentickb-prod-source`，不写死在业务代码。bucket 不表达 KB 权限，业务权限仍由 PostgreSQL 判断。

object key 推荐使用无业务语义的分散前缀，例如 `v1/ab/cd/<uuid-or-sha256>`。不得使用用户文件名作为 key，不在重命名/移动时改 key，也不得把 presigned URL 当 URI 保存。

### 8.2 新增逻辑实体

| 逻辑实体 | 数据所有者 | 核心职责 |
|---|---|---|
| Upload Session | File Management | 上传状态、临时对象、幂等和过期回收 |
| Storage Object | Object Store Registry | MinIO 对象定位、hash、大小、状态、加密和 retention |
| Storage Object Reference | 各资产 Repository | 业务资产到对象的显式引用及引用类型 |
| Document Inspection | File Inspector | 路由画像和版本 |
| Parse Run | Parse Orchestrator | 执行状态、计划、尝试、错误、成本 |
| Document Snapshot | Artifact Store | 唯一知识版本根，固定源对象、解析与切片制品 |
| Parse Container | Artifact Store | page/sheet/slide/topic 投影 |
| Parse Element | Artifact Store | 原子元素查询投影 |
| Element Relation | Artifact Store | 文档结构关系 |
| Structured Asset | Artifact Store | table/figure/formula 等 |
| Binary Asset | Artifact Store | 图片、渲染页、附件 |
| Quality Report | Quality Gate | 指标、issues、decision |
| Segment Element Link | Segment Compiler | segment 与 element/span 多对多映射 |
| Knowledge Access Cache | Knowledge Access | 可选的可重建 View 缓存，不是事实源或版本根 |
| Knowledge Artifact | Future Knowledge Compiler | 场景化事实、规则、SOP、FAQ 等高级制品 |
| Knowledge Artifact Evidence | Future Knowledge Compiler | Artifact 到 element/span 的证据关系 |

### 8.3 现有实体变化

| 现有实体 | 变化 |
|---|---|
| `asset_documents` | 保持逻辑文档身份；增加 `folder_id`、`storage_object_id`、raw hash、content revision、content updated time 和逻辑删除/恢复字段；`storage_path` 降级为 legacy 字段 |
| `kb_folders` | `parent_id` 关系树是目录事实，`path` 仅为可重建查询投影；创建/移动/改名不再创建、移动或删除 MinIO 前缀 |
| `asset_document_snapshots` | 作为唯一知识版本根；保留 raw/normalized hash 和 workflow binding，增加 snapshot/parser/IR/compiler fingerprint、Parse IR object、quality 和 lifecycle status |
| `asset_document_snapshot_links` | 继续表达“哪个 Document 用哪个 MinIO 对象形成该 Snapshot”；增加 source storage object/content revision，`source_uri` 降级为 legacy 字段 |
| `asset_raw_segments` | 继续归属 document snapshot；增加 element links 和 compiler fingerprint |
| `asset_retrieval_units` | 继续归属 snapshot/segments，并可追溯 element spans |
| `asset_build_document_snapshots` | 继续作为 Build 对唯一知识 Snapshot 的选择关系 |

现有 Snapshot 允许相同内容被多个 Document 通过 link 复用，因此 source storage object 和 document content revision 不应直接塞进共享 Snapshot 行，而应写在 `asset_document_snapshot_links`。新 Build 建议增加 `snapshot_link_id`，从而同时固定知识快照和精确来源对象；这只是 provenance 关系，不是新增版本体系。

### 8.3A Snapshot 表的目标字段

现有字段尽量保留：`id/domain/raw_content_hash/normalized_content_hash/mime_type/title/parser_profile_json/workflow_*/metadata_json/created_at`。

建议新增：

| 字段 | 作用 |
|---|---|
| `snapshot_fingerprint` | Snapshot 唯一身份；由 raw hash、parser/model/config、workflow graph、IR schema、normalizer/compiler 指纹计算 |
| `parse_ir_storage_object_id` | 指向 MinIO 中完整 canonical Parse IR |
| `parse_ir_schema_version` | 解释 Parse IR 的契约版本 |
| `parser_fingerprint` | parser 代码、模型、配置和依赖的合成指纹 |
| `compiler_fingerprint` | 切片/视图编译策略指纹 |
| `quality_status` | PASS/WARN；FAIL 不创建 READY Snapshot |
| `lifecycle_status` | READY/DEPRECATED/REVOKED |
| `created_by_run_id` | 追溯产生该 Snapshot 的 Mining Run |

唯一性从当前以 normalized content/workflow 为主的约束，演进为 `UNIQUE(domain, snapshot_fingerprint)`。这样 parser 或切片规则改变会产生新 Snapshot；完全相同的文档内容和加工指纹可以幂等复用，不需要 Parse Result/Segment Set 表。

`asset_document_snapshot_links` 建议新增 `source_storage_object_id`、`source_content_revision`；`asset_build_document_snapshots` 建议新增 `snapshot_link_id`。Snapshot 已有 `raw_content_hash`，无需再复制一套 source hash 版本表。

### 8.4 写入边界

| 模块 | 允许写入 |
|---|---|
| File Management | Upload Session、Logical Document 当前内容、folder relation、delete/restore/content edit audit |
| Object Store Registry | Storage Object、reference、verification/retention state |
| Mining Run Document | 冻结 storage object/raw hash/content revision |
| Inspector | Inspection |
| Parse Operator | Parse Run、attempt events |
| Snapshot Artifact Store | Document Snapshot、Parse IR、containers/elements/assets/relations |
| Quality Gate | Quality Report |
| Segment Compiler | Snapshot 下的 segments、element links、compiler fingerprint |
| Existing asset persist | retrieval units、embeddings、下游关系 |
| Knowledge Access | 只读 Snapshot 原子投影；可写可重建 view cache |
| Future Knowledge Compiler | knowledge artifacts、artifact evidence links、编译与校验元数据 |
| Build/Publish | build selection、release |

Adapter 不能直接写任何上述业务表。

### 8.5 建议表级边界

本节定义逻辑表，不冻结最终命名；WP0/WP2 必须用 ADR 和迁移脚本确定物理名。

| 建议表 | 关键字段 | 关键约束 |
|---|---|---|
| `asset_upload_sessions` | id、kb_id、folder_id、actor、filename、expected_size、staging_object_key、idempotency_key、expires_at、state、error | `(kb_id, actor, idempotency_key)` 唯一；终态不可逆 |
| `asset_storage_objects` | id、provider、bucket、object_key、object_version_id、sha256、size、mime、etag、artifact_class、encryption、state、retention_until | `(provider,bucket,object_key,object_version_id)` 唯一；AVAILABLE 前必须验证 |
| `asset_storage_object_refs` | storage_object_id、owner_type、owner_id、purpose、created_at | 可作为统一引用索引；若采用多态 owner，不能替代 owner 表上的真实外键 |
| `asset_file_audit_events` | id、kb_id、document_id、storage_object_id、content_revision、actor、action、before_json、after_json、created_at | append-only；审计不是可回滚版本表 |
| `kb_storage_quotas` / usage ledger | kb_id、limit_bytes、reserved_bytes、used_bytes、version | session 预留与提交原子更新；支持并发控制和对账重算 |
| `asset_storage_operations` / outbox | id、operation_type、object_id、session_id、payload、state、attempts、next_retry_at、last_error | DB commit 后驱动 promote/cleanup/GC/通知；幂等执行，可观测重试 |

`asset_documents.storage_object_id` 只指向当前内容，并用 `content_revision` 做乐观并发。Mining Run Document 和 Snapshot 各自复制固定 `source_storage_object_id + source_raw_hash + source_content_revision`，不能在运行中跟随 Document 当前指针漂移。

Document、Document Snapshot、Parse/Binary Asset 等 owner 表应各自持有到 `asset_storage_objects.id` 的真实外键。若保留统一 `asset_storage_object_refs`，它只用于 GC/审计加速，必须由事务或 outbox 同步，不能以一个无外键的 `owner_type + owner_id` 多态表作为唯一完整性保障。物理唯一约束还必须规范化 nullable `object_version_id`，避免 PostgreSQL 的 NULL 语义放过重复 current objects。

### 8.6 一致性、去重与回收

- SHA-256 是内容校验和，不直接充当权限边界。允许物理去重时 Storage Object 可共享，但 Logical Document 的权限、当前态和知识状态完全独立。
- ETag 不能替代 SHA-256，multipart ETag 不保证是整文件 MD5。
- 所有对象写入先进入 staging 或不可见状态；数据库只能引用已验证对象。
- 物理删除采用异步 GC：先确认无 active reference、无 Build/Release 引用、已过 retention、无 legal hold，再删除 MinIO 对象并记录结果。
- 对象找不到或 hash 不匹配时进入 `MISSING/CORRUPT`，阻断新 Parse Run并告警；禁止自动创建空对象补洞。
- MinIO bucket versioning 建议生产开启作为误删防护，但不向业务提供版本管理。合规场景才启用 Object Lock，且必须在建 bucket 时决定。

### 8.7 当前实现到目标实现的替换边界

| 当前实现 | 当前耦合 | 目标替换 |
|---|---|---|
| 路由 `await file.read()` | 上传大小直接占 API 内存 | Upload Session + 流式代理/presigned multipart |
| `DocumentService.upload()` 写 `Path.write_bytes()` | KB 服务绑定本地 POSIX 路径 | File Management 调 Object Store Port，complete 后创建/更新 Document 当前对象 |
| `asset_documents.storage_path` | 物理路径同时被当作位置、身份查找和下载依据 | `storage_object_id + raw_hash + content_revision`；路径仅为 legacy 字段 |
| `FolderService` 用 `shutil.move()` | 改名/移动需要搬磁盘字节和补偿回滚 | 仅事务更新 `kb_folders`、folder relation 和逻辑路径投影 |
| 下载返回 `FileResponse(path)` | 服务必须挂同一共享卷 | 权限校验后服务端流式 GET 或短时 presigned GET |
| mining 通过 `rglob` 扫 KB 目录 | workflow 输入依赖目录结构和本地 walk | 从所选 Document 当前对象清单冻结 Run 输入，Materializer 按需取对象 |
| Docker `uploads:/app/uploads` | 多服务共享卷是隐式文件协议 | 增加 MinIO 服务/外部 endpoint；应用只共享数据库和对象 API |

因此可以把当前解析封装成 legacy Parser Adapter，但不能只把当前 `storage_path` 换成 `s3://...` 字符串。文件枚举、上传、下载、移动、删除、挖掘选文档和 serving 原件访问都必须改为显式接口。

### 8.8 存量文件迁移方案

```text
Phase 0 盘点
  -> 对每行 asset_documents 检查 storage_path、文件存在性、大小、KB 归属和重复 hash
Phase 1 建表与 MinIO 上线
  -> 只加新表/列，不改变现有读写
Phase 2 历史回填
  -> 对单文档加迁移锁/版本条件 -> 流式计算 SHA-256 -> 上传 staging/final object -> HEAD + 抽样下载/必要时全量 hash 校验
  -> 创建 Storage Object -> 设置 document.storage_object_id/raw_hash/content_revision
Phase 3 双读
  -> 读取优先 Document.storage_object_id/MinIO；没有新引用才回退 storage_path
  -> 新上传和在线编辑只写 MinIO，不再写本地卷
Phase 4 消费方切换
  -> KB 下载、serving 原件、mining input、parser materializer 全部改用对象引用
Phase 5 停止回退
  -> 指标证明无 local fallback 后禁用；storage_path 保留一个版本周期只读
Phase 6 受控清理
  -> 对账、备份和审批后再清理本地文件；数据库删列另走后续 ADR
```

迁移任务必须按 document 幂等，记录 `PENDING/UPLOADING/VERIFIED/SWITCHED/FAILED` 和错误原因。迁移期间若文档内容或逻辑文档发生修改，当前任务必须基于乐观 revision 失败并重新盘点，不能覆盖新内容。任何文件在 MinIO 的 size/hash 验证未通过前都不能设置 current pointer。迁移报告至少输出：总数、已迁移、缺失、hash 冲突、权限失败、孤儿文件、回退读取次数。

### 8.9 运行拓扑与访问边界

```text
Browser / API Client
  -> KB File Management API ----> PostgreSQL control plane
             |                            |
             | short-lived URL            | document/folder/version/permission
             v                            |
          MinIO <---- Object Store Port <-+
             ^
             |
  Source Artifact Reader / Materializer
             ^
             |
  Inspector / Parser Workers / Serving source access
```

- MinIO endpoint、access key、secret key、TLS、bucket prefix 和 SSE/KMS 配置由主控配置/Secret 管理，不进入 workflow manifest、数据库业务行或日志。
- 浏览器直传要求一个客户端可达、TLS 保护并配置受限 CORS 的 S3 endpoint；部署环境不允许暴露该 endpoint 时自动使用 API 流式代理，不能为了直传把 bucket 改成 public。
- 建议至少区分 file-management、parser-worker、GC 三类服务账户和权限；parser 只读 source、读写其 parse run 前缀，GC 才有受控删除权限。
- Java serving 若需要原件，不再读取共享 `upload-root`；通过内部 File Management/Source Artifact API 获取受权流或短时 URL，避免在每个服务复制 MinIO 凭据和权限逻辑。
- bucket notification 可用于辅助审计和完整性巡检，但不能作为提交事务的唯一事实源；通知可能延迟或丢失，正式状态以 Commit API 和 PostgreSQL 为准。

### 8.10 Knowledge Access 与高级知识制品的持久化边界

Knowledge Access View 首期不按类型拆成 `section_view/table_view/evidence_bundle` 多张永久表。它们是查询模型：从 Snapshot 下的 Container、Element、Relation、Structured Asset、Segment Element Link 组装，必要时使用 Redis、PostgreSQL cache row 或 MinIO JSON 加速。缓存键必须包含 Snapshot 和 view config；因为 Snapshot 不可变，缓存失效只涉及删除或策略升级，不产生业务版本。

现有 Retrieval Unit 继续作为检索优化资产，职责是提高召回效率。两者边界如下：

| 资产 | 主要问题 | 是否事实源 | 典型消费方 |
|---|---|---|---|
| Parse Element / Structured Asset | 原文中有什么、在哪里 | 是，Snapshot 内的解析事实 | Access Layer、复核工具 |
| Segment | 为某种策略如何聚合原子元素 | 否，可派生 | enrich、unit compiler |
| Retrieval Unit | 查询时如何高效召回 | 否，可派生和重建 | keyword/vector/hybrid retriever |
| Section View / Evidence Bundle | 命中后需要哪些完整上下文 | 否，默认动态组装 | Agent、知识编译器、引用展示 |
| Knowledge Artifact | 场景中可直接使用的规则、SOP、FAQ 等 | 是，但属于派生领域知识 | Agent、Serving、业务应用 |

后续进入知识编译阶段时，建议增加而不是复用原子元素表：

| 建议表 | 关键字段 | 边界 |
|---|---|---|
| `asset_knowledge_artifacts` | id、document_snapshot_id、scenario_id、artifact_type、schema_version、content_json、compiler/prompt/model fingerprint、validation_status、created_at | 小型结构化内容存 PostgreSQL；大型正文或图谱包可由 storage object 引用 |
| `asset_knowledge_artifact_evidence` | artifact_id、element_id、evidence_span_id、claim_path、support_type、confidence | 每个 claim 到原子证据的可审计映射 |

Artifact 不建立独立“知识版本表”；其历史边界直接继承 `document_snapshot_id`。同一次知识更新可以在 Snapshot 提交前，按多个 `scenario_id + artifact_type` 编译不同制品，它们都是 Snapshot 的场景化子资产。Snapshot 一旦进入 READY 就禁止追加或覆盖 Artifact；新增场景、重新编译、源文档变化或编译规则变化都重新执行知识更新并产生新 Snapshot，不覆盖旧 Release 使用的 Artifact。

查询时的即时 Agent Answer 不写入上述两表。它只记录普通请求日志/trace，并携带所使用的 Release、Snapshot 和 evidence ids；除非用户明确把结果“沉淀为知识”，否则不能让一次问答改变知识库。

## 9. 状态机与失败恢复

### 9.0A Upload Session

```text
INITIATED -> UPLOADING -> OBJECT_STAGED -> VERIFYING -> COMMITTED
          -> ABORTED
          -> EXPIRED
OBJECT_STAGED / VERIFYING -> REJECTED
```

`COMMITTED` 后会产生正式 Storage Object，并创建或更新 Document 当前内容；`ABORTED/EXPIRED/REJECTED` 只保留审计和有限期 staging 对象。重复 complete 必须返回原提交结果。

### 9.0B Storage Object

```text
STAGING -> AVAILABLE -> DELETING -> DELETED
       -> QUARANTINED
AVAILABLE -> MISSING / CORRUPT
```

只有 AVAILABLE 可被 Document、Run 或 Snapshot 新引用。`MISSING/CORRUPT` 是完整性事故状态，不等价于业务删除。

### 9.1 Document Content

```text
READY -> UPDATING -> READY
      -> UPDATE_FAILED
READY -> DELETED -> READY(restored)
```

Document 只有当前内容。每次成功编辑切换 storage object 并增加 content revision；失败不改变旧内容。知识是否过期通过当前 raw hash/revision 与最新可用 Snapshot 的 source raw hash/revision 比较得出。

### 9.2 Parse Run

```text
QUEUED
  -> INSPECTING
  -> PLANNED
  -> PARSING
  -> NORMALIZING
  -> RECONCILING
  -> EVALUATING
       -> REPAIRING -> EVALUATING
       -> FALLING_BACK -> PARSING
       -> SUCCEEDED
       -> FAILED
  -> CANCELLED
```

状态只前进；重试创建新的 attempt event。进程重启后可依据最后完成阶段恢复或安全重启 backend attempt。

### 9.3 Document Snapshot

Document Snapshot 一旦 READY 即不可变。它固定文档输入、Parse IR、解析/切片指纹和质量结论。

被发现有缺陷的 Snapshot 可以标记 `deprecated/revoked/stale_at_completion`，但不能物理覆盖；已经被历史 Build 引用时仍需可读取。

### 9.4 Snapshot Commit

```text
STAGING_ARTIFACTS -> COMPILING -> READY
          -> FAILED
          -> CANCELLED
```

READY 后不可变。失败由 Run 记录，不产生半成品知识快照。

### 9.5 恢复策略

| 故障 | 恢复方式 |
|---|---|
| Upload Session 到期 | 中止未完成 multipart，清理 staging 对象，保留审计摘要 |
| MinIO 短时不可用 | 返回可重试 `storage_unavailable`；不能伪装成 document not found |
| 对象写成功但 DB 失败 | orphan sweeper 根据未提交 session 回收 |
| DB 成功但对象缺失/损坏 | 标记 `MISSING/CORRUPT`，阻断解析并告警 |
| primary backend 超时 | 记录 attempt；按预算重试或 fallback |
| 某几页质量低 | 只修复页面并重新评估 |
| adapter mapping bug | 用保存的 backend raw artifact 重新 normalize |
| normalizer 升级 | 复用 backend artifact，成功后产生新 Snapshot |
| segment compiler bug | 复用旧 Parse IR，成功后产生新 Snapshot |
| 解析期间文档被编辑 | Run 继续或取消；提交前 revision 校验失败，Run 标记 SUPERSEDED，不创建 Snapshot |
| DB 投影写入中断 | artifact 保持；幂等重建投影 |
| Build 前失败 | 不发布；旧 active release 不变 |

## 10. Workflow 算子演进规格

### 10.1 当前问题

当前固定算子：

```text
input_ingest -> parse_segment -> ... -> asset_persist -> mining_finalize
```

`parse_segment` 同时解析与切片，输出 capability `parsed_segments`。它的参数也同时混入切片、图片 VLM 和远程图片策略，使结构化 Parse IR 无法独立保存和复用。

### 10.2 目标算子

```text
input_ingest
  -> document_parse
  -> segment_compile
  -> enrich / discourse / entity / retrieval_unit / embedding
  -> asset_persist
  -> mining_finalize
```

| 算子 | requires | provides | 策略 |
|---|---|---|---|
| `document_parse` | frozen document inputs | `parsed_documents` | fixed，保证任何知识线都有解析事实 |
| `segment_compile` | `parsed_documents` | `parsed_segments` | fixed 或 protected，第一期 fixed |

`document_parse` 参数只表达解析策略：route profile、OCR、table/formula/figure、quality、cloud、budget。

`segment_compile` 参数只表达分段策略：min/max tokens、merge、structural context、typed views。

图片 VLM 应从旧 `parse_segment` 移到解析 annotation/repair 或独立的 figure enrichment 能力，不再混在 token 切片参数中。

Parser Adapter 获取输入时只提交 Run 冻结的 `storage_object_id + raw_hash` 给 Object Materializer：支持流式的 parser 直接读对象流；必须使用文件路径的第三方库下载到 run-scoped 临时目录，校验 hash 后调用，run 结束立即清理。临时路径不是资产字段，也不能被写入 Snapshot、provenance 或 Build。

### 10.3 旧算子兼容

旧 `parse_segment` 保留版本 1，内部兼容调用：

```text
freeze current Document input in Run Document
-> execute/reuse Document Parse capability
-> execute Segment Compile capability
-> 返回现有 parsed_segments shape
```

它不应继续直接调用旧 `parse_stage + segment_stage`。

新 workflow template 发布版本 2，显式包含两个算子。历史 manifest 不自动改写。

### 10.4 asset_persist 边界调整

Canonical Parse IR 必须在 segment 前形成可复用的 staging artifact，但正式知识资产仍由一个 Snapshot 统一提交。

目标职责：

- `document_parse` 负责 Parse Run 和 canonical Parse IR staging artifact。
- `segment_compile` 负责 segments/element links。
- `asset_persist` 继续合并并持久化 enrichment、relations、retrieval units、embeddings 等下游结果。
- Snapshot Commit 统一固定 source、parse、segment 和下游资产身份。

这意味着“资产持久化”从一个末端大事务演进为分层不可变制品提交。每层通过 identity 和状态衔接，失败不会发布半成品。

## 11. NON-GOALS：本阶段明确不做什么

- 不把 MinIO 当关系数据库、权限数据库或用户文件树数据库。
- 不把每个 KB 建成一个 bucket，也不通过 object key 前缀模拟可变目录。
- 不在改名/移动时复制 MinIO 对象，不把 MinIO version id 暴露为业务文档版本。
- 不建设文档版本列表、版本回滚、Source Version 表和 Parse Result/Segment Set 并行版本体系。
- 不在第一期提供面向终端用户的 MinIO Console；所有文件操作都经过 KB API 和权限模型。
- 不在第一期自动生成领域事实、规则、SOP、wiki 或本体；但必须交付供后续编译使用的 Knowledge Access 读取契约和证据链。
- 不在第一期改写 Java serving 的所有检索器。
- 不要求一次接入所有解析库。
- 不把 Agent 作为首轮 parser。
- 不追求 word-level 全量关系化存储。
- 不对历史 segments 伪造精确 source spans。
- 不在第一期自动选择“全球最优 parser”；只建立可评测路由能力。
- 不立即删除 legacy parser 和旧 workflow operator。
- 不允许因为引入 Docling 而把 DoclingDocument 直接变成数据库公共契约。

## 12. 验收场景

### A01 简单 Markdown

上传 Markdown 并更新知识后生成包含 line-addressable Parse IR 的 Snapshot；切片可回溯行号。

### A02 数字 PDF

解析得到 pages、heading tree、paragraph bbox、tables；检索结果能定位页码和区域。

### A03 扫描 PDF

Inspector 识别扫描比例；Router 选择 OCR backend；低置信页触发 repair/fallback；最终质量报告可见。

### A04 复杂表格

表格保留 merged cells、header regions、跨页 continuation；表格行 retrieval unit 携带完整表头。

### A05 主后端失败

primary 超时后按 Parse Plan 切换 fallback；两个 attempts 均可审计；只选中通过门禁的结果。

### A06 所有后端失败

Parse Run 失败记录保留；不产生新 Snapshot/Build；Document 当前内容和旧 active release 均不受影响。

### A07 Parser 升级

同一文档当前内容用新 parser/model 生成新 Snapshot；旧 Build 仍引用旧 Snapshot。

### A08 切片策略升级

复用旧 Snapshot 的 Parse IR artifact 编译新切片并形成新 Snapshot；不重新 OCR/调用云服务。

### A09 Adapter 映射修复

利用 backend raw artifact 重新 normalizing；不重复调用收费解析服务。

### A10 旧 Workflow

历史 `parse_segment@1` manifest 能运行并产生与当前下游兼容的 segments。

### A11 新 Workflow

`document_parse -> segment_compile` 被 compiler 校验为完整固定骨架，其他能力线继续可编辑。

### A12 KB 隔离

KB 触发的 Parse Run、冻结输入、Snapshot、Build 都关联正确文档身份，不产生 `kb_id=NULL` 幽灵文档。

### A13 恶意文件

路径穿越 archive、压缩炸弹、超限文件和错误 MIME 在 parser 前被阻断并留下审计事件。

### A14 Cloud 禁用

政策禁止外发时 Router 不选择 cloud backend，即使本地质量较低；结果明确 FAIL/人工处理，不静默外发。

### A15 发布可复现

给定任意新 Release，可查询其 Document Snapshot、精确 source storage object/content revision、Parse IR、segments、parser/model/config 和 source spans。

### A16 大文件上传

大文件通过 multipart/presigned 上传；API 进程内存不随文件大小线性增长；中断后可继续或安全终止；complete 后 size/hash 与 MinIO 对象一致。

### A17 重复提交与物理去重

同一 upload session 重复 complete 返回同一结果；相同字节上传到不同 KB 时可复用 Storage Object，但权限、目录、Document 当前态和删除状态完全隔离。

### A18 改名与移动

文档和文件夹改名/移动只改变逻辑树；`storage_object_id`、object key、Snapshot 和历史 Build 不变化，也不发生 MinIO copy。

### A19 删除与恢复

软删除后普通列表和新 Build 不再选中该文档，恢复后原版本可用；仍被 Release 引用的对象不会物理删除。

### A20 MinIO 故障

MinIO 不可用返回可重试的 `storage_unavailable`；上传 session 保留可恢复状态；已发布检索的元数据服务不会把存储故障误报为 404。

### A21 对象完整性事故

数据库引用的对象缺失或 checksum 不一致时标记 `MISSING/CORRUPT`、阻断 Parse Run 并告警，不创建空 Snapshot。

### A22 授权下载

无 KB 读取权限的用户无法获得下载流或 presigned URL；URL 短时、单对象、单动作有效，过期后和替换 object key 后均不可复用；审计记录 actor/document/storage object/content revision。

### A23 本地文件迁移

现有 `storage_path` 文件经 hash、上传、HEAD 校验后绑定 Document 当前 Storage Object；迁移重跑幂等；校验失败不切换该文档；切换期 MinIO 优先、本地回退。

### A24 归档文件

ZIP/RAR 先进入 staging 并受展开数量、大小、压缩比和路径安全限制；按“保留归档”或“展开为多个文档”的显式导入模式处理，每个展开成员形成独立 Document/Storage Object。

### A25 临时文件隔离

要求本地路径的 parser 只能在 run-scoped 临时目录读取物化文件；完成、失败、取消和进程恢复后均可清理，数据库中不出现该临时路径。

### A26 Retrieval Unit 证据补全

任意 Retrieval Unit 都能经 segment-element links 获取 Evidence Bundle，补齐祖先标题、相邻语境、相关表格/图片和精确 source spans；删除 View 缓存后结果仍可从 Snapshot 重建。

### A27 高级知识制品证据归属

试验性 Knowledge Compiler 生成一条规则或 SOP 时，每个关键 claim 都关联 Artifact Evidence；缺少证据、引用其他 Snapshot 或证据质量不达标时不能进入可发布状态。

## 15. OPEN QUESTIONS：实施前仍需拍板

### 已固定、不再开放的决策

1. 本版本正式对象存储使用 MinIO；业务代码经自有 Object Store Port 调用 S3 API。
2. PostgreSQL 是文件目录、权限、Document 当前态、知识 Snapshot 和对象引用的业务事实源；MinIO 只保存对象字节及存储侧 metadata。
3. 新文件 MinIO-only；`storage_path` 只用于存量迁移回退，完成退场后不得继续作为身份或下载依据。
4. 不建设文档版本管理、Source Version 表、版本列表和版本回滚；Document 只维护当前 Storage Object/hash/content revision。
5. 在线编辑使用 copy-on-write 新对象加原子指针切换；这是并发与引用保护，不是产品版本能力。
6. Parser 只消费 Mining Run 冻结的 Storage Object/hash/revision；需要本地路径时由 Materializer 创建 run-scoped 临时文件。
7. `asset_document_snapshots` 是唯一知识版本根；Parse IR、原子元素、segments 和后续知识资产都归属于 Snapshot，不再增加 Parse Result/Segment Set 并行版本体系。
8. `asset_documents.id` 是永久文档身份；`folder_id`/名称/路径均可变，路径派生 `document_key` 只保留为迁移期兼容别名。
9. 文档更新只令知识变为 outdated；旧 Release 保持不变，只有知识更新成功并通过新 Build/Release 才切换线上知识。
10. Section View/Evidence Bundle 是 Snapshot 上的动态读模型，不新建版本体系；高级 Knowledge Artifact 是 Snapshot 的场景化子资产并必须保留 element/span 证据链，READY 后不得追加或覆盖。

### 阻塞 WP0 的决策

1. Snapshot 唯一指纹的具体字段。建议 `document_id + source_raw_hash + parser/model/config fingerprint + workflow_graph_hash + compiler fingerprint`。
2. word/span 保存粒度。建议第一期 element + cell +必要字符范围，word-level 仅对 OCR/引用高要求格式开启。

### 阻塞 M1 文件地基的决策

3. 跨 KB/跨 domain 是否允许物理去重。建议默认仅在同一部署安全域内复用 Storage Object；有独立密钥/保留策略的 domain 禁止共享。
4. 原件、Parse IR、staging 的 retention 天数和永久删除审批。建议原件跟随业务保留，staging 24 小时，物理 purge 至少双重确认并异步执行。
5. 是否启用 Object Lock。建议默认不开，仅在有 WORM 合规要求的独立 bucket 开启；bucket versioning 在生产默认开启。
6. 归档默认导入语义。建议 UI 明确选择“保留为单文件”或“展开为多个文档”，API 默认保留原归档，禁止静默展开。

### 不阻塞契约、由评测决定

7. 简单 PDF fast path 使用哪个 backend。
8. 中文复杂 PDF 默认使用 PP-StructureV3 还是 MinerU。
9. 是否允许任何 cloud fallback，以及允许的 domain/KB 范围。
10. PASS/WARN 阈值和各 domain quality profile。
11. 是否第一期支持 PPTX、Email、更多 archive 类型。

## 16. HANDOFF

本文完成的是实施前能力规格，尚不能直接由单个 Agent 开始全量编码。正确交接顺序：

1. 先进行 WP0 架构评审，冻结 Document 当前态/Frozen Input/Snapshot/Parse IR 契约和阻塞决策。
2. 将 WP1A、WP2 文件模型、WP1B、WP1D、WP1C 依次转换成独立 TDD 实施计划，先完成 M1。
3. 同步建立 30-50 份最小 golden corpus；M1 后再启动 legacy/Docling adapters。
4. M2 shadow parse 成功后再改 Workflow 算子和 Build；WP10 后实现 Knowledge Access Layer，再让上层 Agent 基于稳定接口开展场景知识编译。
5. 文件地基、解析地基、Knowledge Access 和 serving 迁移必须分 PR、按里程碑集成。

进入实现阶段时必须使用 `tdd-workflow`；涉及上传、压缩包、外部 URL、云凭据和新 API 时同时使用 `security-review`；每个里程碑结束后使用 `verification-loop`。
