## 1. 第一性原理与三维模型

### 1.1 核心命题(用户原话提炼)

> "面向不同的场景,知识的形态是不一样的,挖掘和检索也是不一样的。需要从业务场景反向来调整知识的形态,挖掘和检索范式能够基于原子能力直接组装出来。"

三个不可拆分的判断:
1. **场景是上游**——不同业务场景对"知识"的要求不同(精准事实 vs 全局综述 vs 拓扑分析 vs 长文理解),不存在一种"通用知识"通吃所有场景。
2. **知识形态是中枢**——场景首先翻译成"需要什么结构的资产"(扁平切片 / 实体图 / 社区摘要 / 层级树 / wiki 条目),形态决定了挖掘要怎么产、检索要怎么查。
3. **双侧范式 = 原子组装**——挖掘范式(产出某形态)和检索范式(消费某形态)都不是写死的 pipeline,而是从**原子能力池**里挑原子组装出来的 DAG。

### 1.2 三维模型

```
        业务场景(S1~S5)
            │
            ▼ 决定"需要什么形态的知识"
        知识形态(F1~F6)  ← 中枢
       ╱              ╲
      ▼ 产出            ▼ 消费
  挖掘范式          检索范式
  (DAG 组装)       (DAG 组装)
      │                │
      └──► 原子能力池 ◄─┘
        (跨双侧共享:embed/cluster/summarize/compose/cite/...)
        + 挖掘专属原子(parse/segment/extract/...)
        + 检索专属原子(recall/walk/rerank/fuse/...)
```

### 1.3 落地基础:双侧算子化底座已就位/在位

"原子组装"不是空想——检索和挖掘**两侧都有(或已有设计)对称的算子化系统**:

| 维度 | 检索侧(已实现) | 挖掘侧(已有设计,代码待建) |
|---|---|---|
| 算子抽象 | `Operator` + `OperatorDef`(19 个) | `MiningOperator` + `MiningOperatorDef`(9 个) |
| 类型契约 | `SlotDecl`/`SlotType` | `SlotDecl`/`SlotType`(同构) |
| 编排 | `ParadigmCompiler`(7 校验)+ `ParadigmExecutor`(拓扑波次) | `compiler.py`(10 校验)+ `executor.py`(拓扑) |
| 持久化 | `operator_paradigm` + `_version`(不可变) | `mining_workflows` + `_versions`(不可变) |
| 生命周期 | draft→publish→rollback→archive | draft→publish→rollback→archive |
| 前端 | paradigm 画布(待建) | mining workflow 画布(待建,参考检索侧) |

**这意味着**:用户要的"双侧范式原子组装"已有结构基础。需求文档的核心任务变成:**在两侧算子化底座上,补齐支撑各场景的原子 + 形态 + 范式 + 资产契约**。

## 2. 业务场景清单(S1~S5,合并后)

合并原则:同类检索合并为一个场景,内部用"模式"区分子形态(覆盖兼容不同功能,不丢能力)。

| 场景 | 业务诉求 | 典型问题 | 知识形态 | Agentic? |
|---|---|---|---|---|
| **S1 精准事实问答** | 用户/应用问一个具体问题,返回最相关的原文片段 | "SMF 的 PDU 会话建立流程第 3 步是什么" | F1 flat chunk | 否(固定范式) |
| **S2 图谱分析检索**(合并实体图+社区) | 基于实体关系/社区的全局或局部图谱问答 | "SMF 依赖哪些网络功能"(local) / "整库关于会话管理的主题综述"(global) | F2 实体图 + F3 社区摘要 | 可选 |
| **S3 层级结构与导航检索**(合并 RAPTOR+PageIndex) | 长文档/文档集的层级理解与多轮下钻导航 | "这篇 3GPP 规范整体讲什么"(语义树) / "带我定位到关于 X 的章节"(目录树) | F4 语义层级树 + F5 结构目录树 | 是(Agentic 下钻) |
| **S4 知识合成问答** | 带引用的合成长文知识检索(类 STORM/LLM-wiki) | "综合所有资料,系统讲解 5G 切片管理" | F6 wiki 条目 | 可选 |
| **S5 Agentic 多轮检索** | Agent 主导,根据中间结果动态调整检索策略 | Agent 解复杂任务时按需检索、评估、重写、再检索 | 跨 F1~F6 | 是(闭环 loop) |

> S5 是"入口模式"而非"新形态"——它调度 S1~S4 的检索范式,本身不产新形态。

## 3. 知识形态清单(F1~F6,中枢)

每个形态是"场景 ↔ 双侧范式"的契约。**这是整份文档的核心**。

### F1 · flat chunk(扁平切片)—— 已有

| 项 | 内容 |
|---|---|
| **结构** | 文档 → 段落级切片(raw_segment)→ 检索单元(retrieval_unit: raw_text/generated_question/entity_card/table_row)→ 向量 |
| **schema** | `asset_raw_segments` / `asset_retrieval_units`(6 种 unit_type)/ `asset_retrieval_embeddings` —— **全部已有** |
| **挖掘范式** | `input_ingest → parse_segment → enrich → retrieval_unit_build → embedding → asset_persist`(挖掘算子化 baseline) |
| **检索范式** | `query_understand → (dense_recall ‖ keyword_recall) → fuse → rerank → assemble` |
| **现状** | 挖掘 ✅ 稳健产出 / 检索 ✅ 稳健消费(内置 + 范式路径都通) |
| **场景** | S1 |
| **前置依赖** | 无 |

### F2 · 实体图(entity graph)—— 半有,本体线断

| 项 | 内容 |
|---|---|
| **结构** | canonical 实体 + 类型 + 关系边 + 出处。`ontology_entities`/`ontology_entity_relations`/`ontology_evidence_nodes`/`ontology_node_types`/`ontology_relation_types` |
| **schema** | **已有**(生产级 DDL,出处强约束、版本治理、active 唯一) |
| **挖掘范式** | `ontology_entity_line`(entity_extract→resolve→entity_relations)→ `mining_finalize`(graph_write→人审 Gate→induction→finalize_graph) |
| **检索范式** | `entity_link → graph_walk(递归 CTE + confidence 衰减) → evidence_recall`(`entity_graph` 算子) |
| **现状** | 挖掘 🔴 **三大阻塞**:① 本体默认未引种(`ontology_bootstrap` 只人工触发,4 pack 默认 `has_ontology=False` 整条短路);② `ontology_induction` 模板真死 no-op(类型永不自动归纳);③ `entity_relations` 没挂进流式 stages(只在 finalize 重聚合)。检索 🟡 `entity_graph` 算子范式路径可用,内置 `/api/v1/search` 特定路由下因 ThreadLocal 恒空 |
| **场景** | S2(local 模式) |
| **前置依赖** | **本体引种自动化 + induction 模板注册 + entity_relations 挂载**——不修这三条,F2/F3/F6 全断 |

### F3 · 社区摘要(community report)—— 无,强依赖本体

| 项 | 内容 |
|---|---|
| **结构** | 实体图 → Leiden 层级聚类 → 每社区 LLM 摘要(title/summary/findings[]/rank)。类微软 GraphRAG |
| **schema** | **新增**:`asset_communities`(level/parent/member_entity_ids)+ `asset_community_reports`(community_id/report_text/findings) |
| **挖掘范式** | `(复用 F2 实体图) → community_build(cluster) → community_report_build(summarize)` |
| **检索范式** | local:`community_recall`(社区内实体邻域);global:`global_map_reduce`(遍历社区报告 map-reduce);drift:anchor+HyDE 细化 |
| **现状** | 挖掘 ❌ 无 / 检索 ❌ 无 |
| **场景** | S2(global 模式) |
| **前置依赖** | F2 全通 + 新增 cluster/summarize 原子 + release 闸口扩展(社区跨多 snapshot,见 §7.2) |

### F4 · 语义层级树(RAPTOR)—— 无,独立性最好

| 项 | 内容 |
|---|---|
| **结构** | raw_segment → GMM 软聚类 + 摘要 → 递归建树(叶=segment,内节点=摘要)。`tree_nodes`(layer/summary/embedding/children[]) |
| **schema** | **新增**:`asset_tree_nodes`(node_id/level/parent/member_segment_ids/summary_text/embedding) |
| **挖掘范式** | `(复用 F1 segment+embedding) → tree_build(cluster→summarize→recurse)` —— **不依赖本体线** |
| **检索范式** | `tree_walk`(collapsed tree:扁平化所有层节点 top-k 检索,实测最稳);或层级遍历 |
| **现状** | 挖掘 ❌ 无 / 检索 ❌ 无 |
| **场景** | S3(语义树模式) |
| **前置依赖** | **无本体依赖**(4 类新资产中独立性最好,推荐第一个做);只需新增 cluster/summarize 原子 + release 闸口扩展 |

### F5 · 结构目录树(PageIndex)—— 可由现有 section_path 聚合

| 项 | 内容 |
|---|---|
| **结构** | 文档的章节目录树(标题层级),叶节点指向 segment。Agentic 导航入口 |
| **schema** | **新增**:`asset_doc_trees`(document_id/section_path tree/segment_ref)—— 数据源是 raw_segment 已有的 `section_path`(breadcrumb),只需聚合 |
| **挖掘范式** | `parse_segment`(已有 section_tree)→ `doc_tree_build`(聚合 section_path 成索引树) —— 轻量,复用现有产出 |
| **检索范式** | `tree_browse → drill`(Agent 多轮:看目录→选章节→看段落→下钻)—— 暴露给 Agent 的 PageIndex tool |
| **现状** | 挖掘 🟡 有 section_path 但没聚成索引树 / 检索 ❌ 无 |
| **场景** | S3(目录树模式,Agentic 导航) |
| **前置依赖** | 轻量;新增 doc_tree_build 算子 + tree_browse/drill 检索算子;release 走"伪 document"最自然 |

### F6 · wiki 条目(合成知识)—— 无,强依赖本体

| 项 | 内容 |
|---|---|
| **结构** | STORM 式:多视角研究→大纲→带引用长文。`wiki_articles`(topic_entity_id/outline/sections/citation_refs) |
| **schema** | **新增**:`asset_wiki_articles`(article_id/topic_entity_id/section_json/citation_list_json/staleness_score)。出处用 W3C PROV(现有 `ontology_evidence_nodes` 是简化 PROV,只缺 Activity/Agent) |
| **挖掘范式** | `(复用 F2 实体+关系 + F1 segment) → wiki_compose(research→outline→compose→cite)` |
| **检索范式** | 双轨:`wiki_recall`(合成层) ‖ `raw_recall`(原始层)→ RRF fuse → rerank → cite_aware assemble |
| **现状** | 挖掘 ❌ 无 / 检索 ❌ 无 |
| **场景** | S4 |
| **前置依赖** | F2 全通(否则 topic/建链无依据)+ compose/cite 原子 + 双轨检索算子;release 走"伪 document"最自然 |

## 4. 原子能力池

按"能力"组织(非实现),区分跨双侧共享 / 挖掘专属 / 检索专属。**这是组装范式的零件库**。

### 4.1 跨双侧共享原子

| 原子 | 挖掘侧用途 | 检索侧用途 | 现状 |
|---|---|---|---|
| `embed` | 给资产建索引(retrieval_unit→向量) | 给 query 嵌入(HyDE/query_vector) | ✅ 两侧都有 |
| `cluster` | RAPTOR 聚类 segment / GraphRAG Leiden 聚实体 | (检索少用) | ❌ 两侧都无(待建) |
| `summarize` | 社区报告 / RAPTOR 内节点摘要 / wiki 段落 | 检索结果压缩(assemble 内) | 🟡 检索 assemble 有压缩;挖掘无独立 summarize 算子 |
| `compose` | wiki 条目生成(STORM 式) | (检索不用) | ❌ 待建 |
| `cite` | wiki 条目挂出处 / 关系挂 evidence | 检索结果带引用标注 | 🟡 挖掘 evidence 机制有;检索来源标注待补 |

### 4.2 挖掘专属原子(对齐挖掘算子化设计第一版 + 未来新增)

**第一版已有设计(包装现有 stage,中等粒度)**:
`input_ingest` / `parse_segment` / `enrich` / `discourse_line` / `ontology_entity_line` / `retrieval_unit_build` / `embedding` / `asset_persist` / `mining_finalize`

**支撑新形态需要新增的挖掘原子**:
| 新原子 | 支撑形态 | 粒度建议 |
|---|---|---|
| `community_build` | F3 | 独立(全局阶段,Leiden) |
| `community_report_build` | F3 | 独立(LLM summarize) |
| `tree_build` | F4 | 独立(GMM 聚类 + 递归摘要) |
| `doc_tree_build` | F5 | 独立(轻量,聚合 section_path) |
| `wiki_compose` | F6 | 中等(research→outline→compose→cite 可参数化) |

> **粒度策略**(对齐挖掘设计文档 §算子粒度):第一版中等粒度,先跑通;后续若某策略需独立消融(如 `wiki_compose` 内的 research vs compose),再拆子算子。`ontology_entity_line` 第一版合并 entity_extract+resolve+entity_relations 就是此策略的先例。

### 4.3 检索专属原子(现有 19 + 未来新增)

**现有**:`query_understanding` / `hyde` / `multi_query` / `scope_resolve` / `dense_vector` / `fts` / `entity_exact` / `entity_graph` / `graph_expand` / `rrf` / `weighted_rrf` / `model_rerank` / `llm_rerank` / `score_rerank` / `collect` / `assemble` 等(19 个)

**支撑新形态需要新增的检索原子**:
| 新原子 | 支撑形态 | 备注 |
|---|---|---|
| `community_recall` | F3 local | 社区内实体邻域召回 |
| `global_map_reduce` | F3 global | 遍历社区报告 map-reduce(算子内 LLM,见 §9 待1) |
| `tree_walk` | F4 | RAPTOR collapsed tree 检索 |
| `tree_browse` / `drill` | F5 | Agentic 目录导航(多轮) |
| `wiki_recall` | F6 | wiki 合成层召回 |
| `cite_aware_assemble` | F6 | 带引用的上下文组装 |

### 4.4 正交化问题(检索侧,Agent 4 发现)

当前检索算子有两处不够正交,影响"组装"的干净度:
1. **`dense_vector` 算子直接调 mapper 绕过 Retriever**(`DenseVectorOperator.java:64`)——旧 `Retriever.retrieve(query,snapshotIds,topK)` 三参签名表达不了 `textKind`。修法:演算 Retriever 接口加 `RetrieverOptions`。
2. **`rrf` vs `weighted_rrf` 职责重叠**(仅权重差异)——合并为一个参数化算子。
3. **算子硬编码 JOIN `asset_retrieval_units`**——资产耦合,需资产抽象层(见 §7.1)。

## 5. 场景 × 形态 × 范式 组装矩阵

每个场景展开为"需要的形态 → 挖掘范式 → 检索范式 → 入口"。

### S1 精准事实问答
```
形态: F1 flat chunk
挖掘范式: input_ingest→parse_segment→enrich→retrieval_unit_build→embedding→asset_persist→mining_finalize(无本体)
检索范式: query_understand→(dense_vector‖fts)→weighted_rrf→rerank→assemble
入口: 固定范式 API / Agentic search tool
```

### S2 图谱分析检索
```
形态: F2 实体图(local) + F3 社区摘要(global)
挖掘范式: ...→ontology_entity_line→mining_finalize(本体线)→community_build→community_report_build
检索范式:
  local:  entity_link→graph_walk→evidence_recall
  global: global_map_reduce(社区报告) 或 community_recall
入口: 固定范式 API / Agentic search tool
```

### S3 层级结构与导航检索
```
形态: F4 语义层级树(RAPTOR) + F5 结构目录树(PageIndex)
挖掘范式: ...→retrieval_unit_build→embedding→tree_build; parse_segment→doc_tree_build
检索范式:
  语义树: tree_walk(collapsed)
  目录树: tree_browse→drill(Agentic 多轮下钻)
入口: Agentic search tool(目录导航天然适合 Agent)
```

### S4 知识合成问答
```
形态: F6 wiki 条目(双轨:合成层 + 原始层)
挖掘范式: ...→ontology_entity_line→mining_finalize→wiki_compose(research→outline→compose→cite)
检索范式: (wiki_recall ‖ raw_recall)→rrf→rerank→cite_aware_assemble
入口: 固定范式 API / Agentic search tool
```

### S5 Agentic 多轮检索
```
形态: 跨 F1~F6(按需)
挖掘范式: 不直接参与(消费已产资产)
检索范式: Agent loop 调度 S1~S4 的检索范式
  loop: retrieve→grade→rewrite→re-retrieve(CRAG/Adaptive-RAG 模式)
入口: 暴露粗粒度三件套 tool(search/fetch/expand)
  - search(query, scope, topk) → 内部展开成子范式
  - fetch(doc_id, segment?) → 取原文
  - expand(doc_id, direction, depth) → 图扩展
```

|---|---|

);

    document_id TEXT PRIMARY KEY,
