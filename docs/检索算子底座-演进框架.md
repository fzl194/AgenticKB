## 0. 这份框架要回答什么

用户的北极星:**检索是一个可编排的 pipeline,底层算子足够通用和正交,能自由组装出任意检索范式**(Agentic / 纯 embedding / GraphRAG / PageIndex 树导航 / LLM-wiki …),**不被现有 asset_* 资产类型限制**;同时**暴露基础检索接口给 Agent 作为 Agentic search 入口**;且因为新范式需要新资产(社区摘要/树节点/wiki 条目),**挖掘侧也要能扩展产出**。

这份框架给出从现状到目标态的**阶段式演进路径**,核心是回答三个问题:
1. 算子底座要怎么设计,才能"新增检索策略 = 新增算子/资产,不改框架"?
2. 算子底座怎么同时支撑"固定范式检索"和"Agent 主导的 Agentic 检索"?
3. 检索(消费)和挖掘(产出)怎么协同,才能让新资产类型无缝接入?

## 1. 北极星:通用检索算子底座(三层架构)

```
┌─────────────────────────────────────────────────────────────────┐
│  入口层(多场景)                                                  │
│   ┌──────────────────┐  ┌──────────────────┐  ┌──────────────┐ │
│   │ 固定范式 API      │  │ Agentic tool     │  │ 范式库/画布   │ │
│   │ /paradigm/{id}   │  │ search/fetch/    │  │ (可视化编排   │ │
│   │ (确定性,低延迟)  │  │ expand + CRAG    │  │  + 选 KB 集合)│ │
│   └────────┬─────────┘  └────────┬─────────┘  └──────┬───────┘ │
│            │     Adaptive-RAG 前置 router        │           │
│            └──────────────┬──────────────────────┘           │
├───────────────────────────┼─────────────────────────────────────┤
│  编排层(可编排 pipeline) ▼                                     │
│   静态 DAG(主路径,竞争优势)+ 4 项加性能力:                   │
│    · 类型化 channel + reducer                                   │
│    · 动态 fan-out(Send 概念)                                   │
│    · PipelineCheckpoint(PG,顺带修语义缓存污染)                │
│    · interrupt_before 静态 HITL                                 │
├─────────────────────────────────────────────────────────────────┤
│  算子层(正交、资产无关)                                         │
│   retrieve / fuse / rerank / assemble / expand / generate       │
│   角色接口 + paramSchemaJson + cost class                       │
├─────────────────────────────────────────────────────────────────┤
│  资产抽象层(跨检索/挖掘)                                       │
│   Retrievable 接口 + AssetStore ABC + AssetTypeRegistry         │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐         │
│   │ text_unit│ │ community│ │ tree_node│ │ wiki_art │ ...可扩展│
│   │  Store   │ │ _report  │ │  Store   │ │  Store   │         │
│   └────▲─────┘ └────▲─────┘ └────▲─────┘ └────▲─────┘         │
│        │            │            │            │                 │
│   ┌────┴────────────┴────────────┴────────────┴────┐           │
│   │  mining 产出 → build/release → serving 只读     │           │
│   └────────────────────────────────────────────────┘           │
└─────────────────────────────────────────────────────────────────┘
```

**三条核心不变量**(贯穿所有阶段):
1. **新增检索策略 = 新增算子 + (如需)新增 AssetStore,不修改框架核心**(ParadigmCompiler / Executor / Registry / 现有算子)
2. **新增资产类型 = 新增 AssetStore 实现 + 注册,算子核心不动**
3. **mining 是 asset_* 唯一写方;serving 对 asset_* 只读;KB 独占 asset_documents**(承接 KB 需求 D8)

## 2. 调研改变设计的关键结论(4 路综合,只列重塑性的)

### 结论 1 —— 资产抽象 = **演进已有的 `Retriever` 接口**(不是新引入)

Agent 4 核验代码发现:CoreMasterKB **已经实现了 LlamaIndex `BaseRetriever` 模式**——`retrieval/Retriever.java` 接口已存在,`DenseVectorRetriever`/`FtsRetriever`/`EntityExactRetriever`/`EntityGraphRetriever`/`GraphExpander` 都在,4 个 retrieve 算子已委托给 `*Retriever` bean。

**唯一破例**:`DenseVectorOperator.java:64` 直接调 `OperatorEmbeddingMapper`,绕过 `DenseVectorRetriever`——根因是旧 `Retriever.retrieve(query, snapshotIds, topK)` 三参签名表达不了 `textKind` 新维度,作者写新 mapper 而非演进接口。

**含义**:资产解耦不是"引入 `Retrievable` 接口"那种大改,而是"演进 `Retriever` 接口 + 抽 `AssetStore` ABC"。`RetrievalCandidate` 已是 LlamaIndex `NodeWithScore` 形状。**资产特异性集中在 5 个 retrieve 算子,fuse/rerank/output 已全资产无关——修复范围比预想小得多。**

### 结论 2 —— 编排模型**保持静态 DAG**,不迁移 LangGraph/Temporal

Agent 4 的编排模型决策矩阵:CoreMasterKB 的"编译期 7 校验 + 拓扑波次执行 + 不可变 paradigm 版本"是**竞争优势**(LangGraph/Haystack/LlamaIndex 都没有一等图版本化)。它匹配实际负载(单轮检索 <2s、确定性、缓存友好)。

- ❌ **不迁移 LangGraph 状态图**(HIGH 风险:重写 `checkAcyclic`、放弃不可变版本)
- ❌ **不引入 Temporal**(VERY HIGH:目标延迟 1s~1day,撑爆 2s 预算;只用于外层异步层如 indexing)
- ❌ **不做无界循环 agent**(重蹈 v4 "intent 驱动路由"死代码覆辙)
- ✅ **借鉴 LangGraph 4 个原语**(类型化 channel+reducer / 动态 fan-out / Checkpoint / interrupt_before),以加性方式叠加到静态 DAG

### 结论 3 —— Agentic 入口是**上层封装**,不是底层算子

Agent 1:工业共识是**粗粒度三件套 `search / fetch / expand`**(OpenAI file_search、Anthropic web_search、LangChain RetrieverTool、MCP 都如此),**没人把 embed/retrieve/rerank 拆成独立 tool 暴露给 Agent**——它们是"机制"不是"决策点"。

**三层分离**:算子层(纯函数,已有)/ 范式编排层(DAG,已有)/ **Agent loop 层(新增,状态机)**。Agent 不直接调算子,只调范式层暴露的高层 tool,每个 tool = 一个预编译子范式。**闭环 loop(检索→grade→rewrite→再检索)在 Agent 层,用状态图;算子保持无状态。** 前置 Adaptive-RAG router 分界:简单 query 走固定范式,复杂 query 走 Agent loop(实测 Agentic 成本可达固定 pipeline 3.6×,不能全走 Agentic)。

### 结论 4 —— 新范式需要新资产,新资产需要**挖掘侧扩展**

Agent 2/3:GraphRAG 的 `community_reports`、RAPTOR 的 `tree_nodes`、LLM-wiki 的 `wiki_articles` 都是**新资产类型**,不是现成的。这是用户说"也要考虑挖掘那边"的根因。

**挖掘侧要新增产出阶段**(现有 14+ 阶段之外):
- `community_detect`(hierarchical Leiden)→ `asset_communities`
- `community_report_build`(自底向上 LLM 摘要)→ `asset_community_reports`
- `tree_summarize`(GMM 软聚类 + 递归摘要,per-doc 独立)→ `asset_tree_nodes`
- `wiki_compose`(STORM 式多视角研究 + 大纲 + 带引用长文)→ `asset_wiki_articles`

⚠️ **模板必须逐字注册进 scenario pack**,否则 `submit_task` 静默 no-op(CLAUDE.md 记录的坑)。

### 结论 5 —— 新资产 schema 有工业蓝本,直接平移

Agent 2/3 给出了带 `release_id` + `domain` 列的完整 schema 草图,对齐微软 GraphRAG / RAPTOR / STORM:
- `asset_communities`(层级 + parent/children + entity_ids/relation_ids)
- `asset_community_reports`(title/summary/full_content/findings[]/rank)
- `asset_tree_nodes`(layer/text/summary/embedding/children[])
- `asset_wiki_articles`(section_json/citation_list_json/staleness_score/source_segment_ids)

**出处建模用 W3C PROV 标准**(Entity/Activity/Agent + wasGeneratedBy/wasDerivedFrom)——现有 `ontology_evidence_nodes` 是简化版 PROV,**只缺 Activity/Agent 两元**,扩展即可。

**巨大优势**:现有 ontology 可作 GraphRAG 抽取 schema(OG-RAG 思路,降幻觉),本体 type 层级可约束 Leiden 聚类(解决小图退化)。`entity_graph` 算子的递归 CTE + confidence 衰减基础设施可被 `community_retrieve` / `tree_walk` 直接复用。

## 3. 阶段式演进路径(核心)

> 依赖关系:`P0→P1`(资产抽象需先正交化)→ `P2`(编排增量)→ `P4`(新资产/范式,可与 P3 并行)→ `P5`(Agentic + 下架)。P3(性能/缓存)依赖 P2 的 checkpoint,可与 P4 并行。挖掘侧工作(P4-mining)可与检索侧(P4-serving)并行,节奏由 KB 模块 `asset_documents.kb_id` 落地决定。

### Phase 0 —— 底座清理与算子正交化(1~2 周)

**目标**:让现有 19 算子干净、正交,为资产抽象铺路。零功能新增,全是清理。

工作项:
- **修 `DenseVectorOperator` 破例**:演进 `Retriever` 接口为 `retrieve(query, snapshotIds, options, topK)`,`RetrieverOptions` 携带 `textKind`;`DenseVectorOperator` 改回委托 `DenseVectorRetriever`(`OperatorEmbeddingMapper` 逻辑下沉到 retriever)
- **算子角色 marker 接口**:`Retriever`/`Fuser`/`Reranker`/`Assembler`/`Expander`/`Generator extends Operator`;`ParadigmCompiler` 加第 8 项校验——**response 阶段算子不能在 retrieval 算子前**(借鉴 Weaviate 模块类别 + OpenSearch processor 三分)
- **合并 `rrf` + `weighted_rrf`**:参数化权重列表(空=等权),一个算子两种模式
- **反序列化白名单 + 算子版本号**:paradigm JSON 从 DB/用户上传只允许 `com.coremasterkb.operators.*`;每个算子 `definition()` 加 `int version()`(Haystack 没做、CoreMasterKB 必须做的安全门)
- **修已知 bug**(顺带):`SearchService.java:294/323` 两个 runAsync 包 `wrapRunnable`(entity_graph ThreadLocal);`SemanticCacheService.store` 空/降级不写 + `evict` 接 release 钩子

**验收**:`mvn -o test` 全绿;`DenseVectorOperator` 不再直接调 mapper;角色接口编译期拦住"rerank 在 retrieve 前"的错误范式。

### Phase 1 —— 资产抽象层(2~3 周,最高价值)

**目标**:`新增资产类型 = 1 个 AssetStore bean + 1 个 mapper,零新算子、零改框架`。这是整个框架价值最高的一步,且代码库已搭好骨架。

工作项(4 步,Agent 4 给出):
1. **`Retrievable` 接口**(LlamaIndex `BaseNode` + GraphRAG 7 类资产形状):
   ```java
   interface Retrievable {
       String getId();                    // 带类型前缀防冲突
       AssetType getType();               // TEXT_UNIT / COMMUNITY_REPORT / TREE_NODE / WIKI_ARTICLE / ...
       String getContent(ContentView v);  // 类比 MetadataMode:EMBED/LLM/ALL/NONE
       float[] getEmbedding(String name); // 支持命名多向量(ColBERT 等)
       Map<String,Object> getMetadata();
       List<NodeRelationship> getRelationships();   // SOURCE/PARENT/CHILD/PREVIOUS/NEXT
       Optional<Retrievable> getIndexTarget();      // IndexNode 间接层(递归检索)
   }
   ```
2. **`AssetStore` ABC**(借鉴 GraphRAG `VectorStore` + LlamaIndex `PropertyGraphStore` + Haystack `DocumentStore` Protocol):
   ```java
   interface AssetStore {
       String assetKind();
       Set<AssetCapability> capabilities();   // VECTOR_SEARCH / KEYWORD_SEARCH / GRAPH_WALK / ...
       List<Retrievable> retrieveByVector(float[] vec, ActiveScope scope, RetrievalFilters filters, int topK);
       List<Retrievable> retrieveByKeyword(String query, ActiveScope scope, RetrievalFilters filters, int topK);
       default List<Retrievable> expandGraph(List<String> seedIds, int maxDepth, ActiveScope scope) { return List.of(); }
   }
   ```
   Spring 按 `assetKind()` 自动发现所有 bean。
3. **`AssetTypeRegistry`**:启动时由 mining 侧注册资产类型描述符;serving 侧 `OperatorCatalog` 的 `retrieve` 算子 paramSchema enum 从 `registry.allTypes()` 动态填充。
4. **5 个 retrieve 算子坍缩为 1 个 generic `retrieve` 算子**(参数 `assetKind`)+ N 个 `AssetStore` 实现。旧 paradigm 通过一对一映射继续工作(向后兼容)。

**验收**:写一个 `MockAssetStore`(新资产类型),配一个范式 JSON 用它检索,**不改 ParadigmCompiler / Executor / 任何现有算子**就能跑通。`graph_expand` 取种子改成 `candidate.getRetrievableId()` 而非 `metadata.get("source_segment_id")`。

### Phase 2 —— 编排能力增量(2~3 周)

**目标**:让范式能表达"变体 fan-out 并行检索""运行时按 complexity 切路""崩溃可恢复"。保持静态 DAG,4 项加性能力。

工作项(按价值排序):
1. **类型化 channel + reducer**(最高价值,借鉴 LangGraph):`ExecContext` 从扁平 `Map<String,Object>` 升级为 `Map<String, Channel<T>>`,每 channel 声明 `Reducer<T>`(overwrite / list-merge / map-merge / ID-aware)。**一举消灭 `AssetRawSegmentMapper.selectWithMeta` 1:N 行放大 + 各消费者手工去重的灾难**(CLAUDE.md 记录)。编译期强制 `scope` 必须连线(消灭 ENTRY_SLOTS 脚枪)
2. **动态 fan-out**(借鉴 LangGraph `Send`,80/20 版):扩展 `ParadigmExecutor` 让节点声明"为下个 wave 产 N 个子任务"。`multi_query` 算子返回 `List<QueryBundle>` 在 `queries` 槽,下游 `retrieve` 声明 `fanned` → executor spawn N 个并行调用并按 reducer 合并。**接通 multi_query 孤立算子 + 子查询分解**(上一份规划的 P0 缺口 C2/C3)。编译期无环检查仍成立
3. **`PipelineCheckpoint` 接口**(PG 后端,借鉴 LangGraph checkpointer):长检索崩溃恢复 + 调试回放 + **语义缓存污染的架构修复**(`serving_query_cache` 变成检索子图检查点,正确失效)
4. **`interrupt_before` 静态 HITL**:paradigm 声明 `interruptBefore: ["llm_rerank"]`,executor 持久化 checkpoint 返回 `paused`,后续 `POST /resume` 继续(为 Agentic 人审 / 本体评审铺路)。**不做动态 `interrupt()` + Pregel 运行时**

**验收**:范式能表达"N 个变体并行检索再 RRF 合并";checkpoint 能在任意节点崩溃后从该节点恢复;`selectWithMeta` 行放大问题在 channel 层消失。

### Phase 3 —— 语义缓存 + 性能 + 观测性(1~2 周,可与 P2/P4 并行)

**目标**:把"检索慢"在算子路径上彻底解决。慢在 LLM(诊断瀑布:Rerank 级联 + LLM 调用密度 + 无效串行),解法全在算子路径。

工作项:
- **语义缓存接入算子路径**:复用 P2 的 `PipelineCheckpoint`;从零做对(空/降级不写、store 异步、`evict` 接 release)
- **Rerank 不级联**:model 失败直接 score 兜底,砍掉 cascade 里那次 llm_rerank(单点省最多 LLM 延迟)
- **范式级裁剪**:简单查询用轻范式(如 `retrieve→collect`,零 LLM 重排),复杂查询才上全链。比内置"单 pipeline 自适应"更彻底
- **观测性**:trace 细化到检索语义(候选数/分数分布/每路 latencyMs)+ Prometheus metrics(P2 缺口 C8)

**验收**:`/api/v1/paradigm/{id}/search` p95 ≤ 内置 `/api/v1/search`;重复查询命中缓存 <100ms。

### Phase 4 —— 新资产 × 新范式 × KB 承载(4~6 周,可分批)

**目标**:让底座真正"通用"——能跑 GraphRAG / RAPTOR / LLM-wiki 等新范式,且范式承载 KB 集合。这是"算子化应用"的主战场,挖掘侧和检索侧并行。

#### 4-M(挖掘侧,Python,可独立先行)
新增阶段(独立模块,不碰现有 pipeline):
- `community_detect`(hierarchical Leiden,小图退化时用本体 type 兜底)→ `asset_communities`
- `community_report_build`(自底向上 LLM 摘要)→ `asset_community_reports`
- `tree_summarize`(GMM 软聚类 + UMAP + 递归摘要,per-doc 独立,不依赖本体)→ `asset_tree_nodes`
- `wiki_compose`(STORM 式:多视角提问→检索→大纲→带引用长文)→ `asset_wiki_articles`
- ⚠️ 每个阶段的 LLM 模板逐字注册进 4 个 scenario pack 的 `llm_templates` 段(含 `generic`,否则降级)
- 走 build → publish release 才对 serving 可见(对齐不可变快照语义)

#### 4-S(检索侧,Java)
- 资产层:4 个新 `AssetStore` 实现(community / community_report / tree_node / wiki_article)+ mapper
- 算子层:**零新算子**(P1 之后 generic `retrieve` 算子自动支持);仅可能新增几个输出/编排算子:`global_map_reduce`(GraphRAG global)、`tree_walk`(RAPTOR collapsed)、`wiki_summary_search`(LLM-wiki 双轨)
- 范式模板:GraphRAG local/global/drift、RAPTOR tree_walk、LLM-wiki 双轨(wiki 合成层 + raw 原始层 RRF 融合 + rerank)
- KB 承载:`scope_resolve` 扩展,范式绑定的 KB 集合收窄 `snapshotIds`(B1);结果标注 `kb_id` 通过 `unit→snapshot→link→document→kb_id` 回溯(B2);范式绑定 KB 集合机制(P1 的 `AssetTypeRegistry` 自然支持)

**验收**:能跑通 GraphRAG global(整库主题问答)、RAPTOR tree_walk(长文档叙事性问答)、LLM-wiki 双轨(带引用长文检索);结果带来源 KB;F1 复刻范式召回率/precision 对标 `/api/v1/search` 达标。

### Phase 5 —— Agentic 入口 + 内置 pipeline 下架(3~4 周)

**目标**:暴露 Agentic search 入口,内置 `/api/v1/search` 下架。依赖 P1~P4 基本就绪。

工作项:
- **三层分离落地**:Agent loop 层(ReAct/CRAG 状态机)+ 范式层 + 算子层
- **暴露粗粒度三件套 tool**(Agent 1 共识):
  - `kb_search(query, scope, top_k, filter)` → 内部展开成 `query_understand→multi_recall→fuse→rerank→assemble` 子范式
  - `kb_fetch(doc_id, segment?)` → 调 `ContextAssembler`
  - `kb_expand(doc_id, direction, depth)` → 调 `entity_graph`/`GraphExpander`(务必修 DomainContext.set)
  - 不暴露 embed/rerank/grade 作为独立 tool(机制不是决策点)
- **Adaptive-RAG 前置 router**:轻量分类器(规则即可,关键词是 complexity 强信号)把简单 query 路由到固定范式,复杂 query 走 Agent loop
- **Agent loop 用状态图**(LangGraph 风格,在 Agent 层不在算子层):状态字段 `question/documents(累积并集)/searched_queries/visited_doc_ids/scratchpad`;闭环 `retrieve→grade_documents→rewrite→web_fallback→再检索`;双轨返回(LLM 看精炼文本 + 程序看 doc_id+score)
- **内置下架**:`/api/v1/search` 改薄壳(内部跑默认范式,URL 兼容)或废弃;死代码清理(`BUILTIN_ROUTES` 等)

**验收**:Agent 能通过三件套 tool 完成多轮检索(召回→评估→重写→再检索);`/api/v1/search` 行为可由默认范式完全复现;内置 pipeline 死代码清零。

### Phase 6 —— 前端范式画布 + 增量更新 + 收尾(2~3 周)

**目标**:让范式系统真正可用(可视化编排),收敛长尾。

工作项:
- **kb-ui 范式画布**:可视化编排 DAG + 选 KB 集合;后端 catalog/CRUD API 已就绪
- **增量更新优化**:社区/树这类全局结构本质非增量;折中——平时 LightRAG 式增量(图并集),周期性全量重建社区报告(参考微软 `period`/`size` 字段 + delta 子图重聚类)
- **Late Chunking 接入**(Jina 2024):long-context encoder 一次 embed 整篇再切,无需 LLM 让 chunk 自带上下文(对已大量调 LLM 的系统更划算)
- **文档收敛**:过时文档(`pipeline-0X-*.md`/`code_guide.md`)归档或重写

**验收**:用户能在画布拖拽编排范式并选 KB 集合;新文档增量更新不触发全量重建社区。

## 4. 跨检索/挖掘的资产扩展契约

新资产类型从"挖掘产出"到"检索消费"的完整链路(P1 之后确立):

```
①  mining 新增产出阶段(如 wiki_compose)
       ↓ 写 asset_wiki_articles(带 domain + release_id)
②  build → publish release(不可变快照,asset_wiki_articles 进入 release)
③  AssetTypeRegistry 注册新类型(serving 启动时发现)
④  新 AssetStore 实现(Java,@Component,assetKind="wiki_article")
⑤  generic retrieve 算子 paramSchema 自动多出 "wiki_article" 选项
⑥  范式 JSON 用 retrieve(assetKind=wiki_article) 组装新范式
⑦  入口层暴露(固定范式 API / Agentic tool)
```

**每一步都是加性的**——不修改现有算子、不修改编译器/执行器。这是"新增检索策略不改框架"的机制保证。

## 6. 风险与取舍

| 风险 | 缓解 |
|---|---|
| P1 资产抽象重构破坏现有范式 | 一对一映射 + 向后兼容;`MockAssetStore` 验收门 |
| P2 channel+reducer 引入回归 | 先在 `selectWithMeta` 去重场景试点(本来就是 bug 重灾区) |
| P4 新资产 LLM 模板静默 no-op | 模板逐字注册进 pack,CI 加"模板存在性"检查 |
| P5 Agentic 成本失控(3.6×) | Adaptive-RAG 前置 router,简单查询坚决走固定范式 |
| 挖掘侧新阶段拖慢检索侧 | 4-M 独立先行,4-S 用 MockAssetStore 解耦开发 |
| 全局结构(社区/树)增量非增量 | 接受"周期性全量重建"起步,数据量上去再优化 |

**明确不做**:换声明式 DSL(丢组合力)/ 引入 OSGi(重,Spring @Component 严格更好)/ 采用事件驱动 Workflow(对静态检索是开销)/ schema-on-write(与不可变快照 publish 模型冲突)/ 无界循环 agent(重蹈 v4 覆辙)。
