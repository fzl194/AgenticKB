# 概览页指标说明

本文解释概览页（`/`）与「设置 → 系统状态」上每个数字与图表的**含义、数据来源、统计口径**，
以及容易读错的地方。

---

## 先看这一节：页面上同时存在三套口径

这是最容易出错的地方。**相邻的两个数字很可能不是同一个范围里的东西**，看数前先确认口径。

| 口径 | 覆盖范围 | 出现在 | 接口 |
|---|---|---|---|
| **A. 我可见的知识库** | 当前用户在本域能看到的全部知识库（admin = 全域） | 概览页「知识库概况」与四张图表、知识库卡片 | `GET /api/kb/stats`、`GET /api/kb/overview` |
| **B. 全域检索流量** | 本域所有检索请求，**不按知识库收敛** | 概览页「运维概览」、设置页「检索使用分析」 | `GET /api/ops/usage` |
| **C. 域级 active release** | 已发布语料的快照范围 | 设置页「知识资产」 | `GET /api/knowledge/stats` |

三条要点：

1. **A 和 B 的「文档数」与「检索次数」没有可比性。** A 是"我的库里有多少东西"，B 是"这个域被查了多少次"。
2. **口径 C 在纯知识库部署下恒为 0。** 知识库挖掘走 `publish=false`，永远不产生 release。
   页面上会显示「该域无发布语料」而不是一排 0 —— 那是**口径不适用**，不是"知识丢了"。
3. **运维数据（口径 B）只有管理员能看到**，普通成员看不到「运维概览」区块，界面上也不会请求它。

## 一、概览页

### 1. 知识库概况（口径 A）

顶部六个数字。除「知识库」外，都只统计**当前知识**——即每篇文档最近一次成功挖掘产出的快照。

| 指标 | 含义 | 注意 |
|---|---|---|
| **知识库** | 你能看到的知识库数量 | admin 看到的是全域，成员看到的是自己拥有/参与/公开的 |
| **文档** | 文档总数 | 取"文档状态分布"六档之和，**不是**各库文档数相加。两者来自不同查询，用同一个来源才不会自相矛盾 |
| **已挖掘** | 挖掘成功、已产出知识的文档数 | 与"文档"的差额就是待挖掘 + 挖掘中 + 失败 |
| **检索单元** | 可被检索命中的最小知识单位 | 一篇文档会切出多个，所以远大于文档数 |
| **实体提及** | 从正文里识别出的实体出现次数 | 是"提及次数"不是"实体个数"，同一实体出现十次记十次 |
| **切片关系** | 段落之间的结构/语义关系条数 | 如上下文相邻、同章节、引用等 |

> **为什么这些数不是简单地对表求和**
> 一篇文档每重挖一次就会产生一份新快照。如果直接统计全部快照，一个挖过 3 遍的
> 10 篇文档的库会显示成 30 篇的知识量。所以只统计每篇文档**最近一次**进入
> validated/published 构建的那份快照。

### 2. 待处理

只在**有内容时**才出现；没有待办时整块不渲染。只列你有写权限的库——对只读的库列待办没有意义。

| 类型 | 触发条件 | 动作 |
|---|---|---|
| 挖掘已暂停，等待人工审核 | 该库有 run 停在 `awaiting_review` | 点进 run 详情处理 |
| N 篇文档解析失败 | 该库有文档处于 `failed` | 点进知识库查看 |

待人审排在解析失败之前：它卡住的是整条挖掘流水线，失败文档只影响它自己。

### 3. 运维概览（口径 B · 仅管理员）

窗口默认**近 7 天**，趋势折线固定 **30 天**。

| 指标 | 含义 | 怎么读 |
|---|---|---|
| **检索次数** | 窗口内的检索请求总数 | 掉到 0 通常意味着接入断了，而不是"没人用" |
| **零结果率** | 没有返回任何结果的请求占比 | **最有行动价值的指标**，直接反映知识覆盖缺口 |
| **P95 延迟** | 95% 的请求比这个值快，最慢的 5% 比它慢 | 见下方专门说明 |
| **活跃范式** | 窗口内被调用过的检索范式数量 | 新发布的范式如果一直不计入，多半是路由没配对 |

#### P95 延迟为什么不用平均值

把窗口内所有请求按耗时排队，站在 95% 位置的那个值就是 P95。

平均值会被大量快请求稀释，把少数卡死的用户藏起来。20 次检索里 18 次 10ms、2 次 5000ms：

| | 值 | 读起来像 |
|---|---|---|
| 平均延迟 | 509ms | 「有点慢，还行」 |
| P95 | 5000ms | 「每 10 个人就有 1 个等了 5 秒」 |

同一批数据，平均值让你以为没事。**没有人体验到"平均延迟"，但真有人体验到那条尾巴。**

#### 零结果告警

只有**同时满足**两个条件才会出现橙色告警条：

- 窗口内检索次数 ≥ 20
- 零结果率 ≥ 20%

样本门槛是刻意的：3 次检索里 1 次没答上就是 33%，据此弹红只会训练人忽略告警。

#### 答不上来的问题

**这是整个运维区块里最该看的一段。** 列出用户实际输入、但系统没能返回结果的问题原文，
按出现次数排序。概览页显示前 5 条，设置页「检索使用分析」给出全部（最多 10 条，并附
最近一次被问到的日期）。

零结果率只告诉你"有缺口"，这份清单告诉你"缺口在哪、该补什么"。同一个问题被问了 12 次，
和 12 个各问一次的不同问题，是完全不同的两件事——所以按原文聚合而不是逐条罗列。

> 这里显示的是**真实用户输入原文**（截断到 200 字），因此整个区块仅管理员可见。

#### 范式调用排行

各检索范式在窗口内的调用次数。其中 **「未走范式（旧检索）」** 不是一个范式，而是仍走旧
检索路径、没有经过范式引擎的那部分流量——它的占比本身就是有用的信息。

### 4. 图表（口径 A）

| 图表 | 说明 |
|---|---|
| **文档状态分布** | 环形图。已挖掘 / 挖掘中 / 待挖掘 / 失败四档；域内有 active release 时才追加「已发布」「已撤回」。计数为 0 的档**保留**（"失败 0"本身是有用的信息），但不适用的档整个摘掉 |
| **近 30 天入库文档数** | 每天成功入库的文档数。没有挖掘的日期补 0，不会跳过——跳过会把"停了三周"画成持续产出 |
| **各知识库文档数（前 8）** | 横向柱状，文档数为 0 的库不进图。完整列表见知识库页 |
| **检索单元类型分布** | 各类检索单元的数量占比 |

文档六档状态的含义：

| 状态 | 含义 |
|---|---|
| 待挖掘 | 已上传，尚未挖掘（或未产出过结果） |
| 挖掘中 | 正在处理 |
| 已挖掘 | 挖掘成功，知识已入库 |
| 失败 | 解析或挖掘失败，**需要人工处理** |
| 已发布 | 已进入域级 active release（纯知识库部署下不会出现） |
| 已撤回 | 曾发布、后被移出（同上） |

### 5. 我的知识库

每张卡片右上角一个状态角标，优先级 **失败 > 挖掘中 > 就绪**：

| 角标 | 含义 | 副行文案 |
|---|---|---|
| ⚠ | 有文档处理失败 | `N 篇待处理` |
| ⏳ | 正在挖掘 | `挖掘中 N/总数` |
| ✓ | 就绪 | 最近挖掘时间，或「尚未挖掘」 |

失败优先于挖掘中：一个库可能正在挖新文档、同时还有上一轮失败的没处理，这时该提醒的是失败——
它需要人动手，挖掘中只需要等。

角色徽标：拥有者 / 编辑者 / 只读 / 管理员。

### 6. 最近挖掘

跨知识库的最近 5 次挖掘记录，整行可点进 run 详情。

各列依次为：知识库名 · 状态 · 文档增量 · 耗时 · 开始时间。

- **文档增量**：`+N` 新增、`~M` 更新；都没有时显示本次处理的文档总数。
- **开始时间**用的是挖掘启动时刻（`started_at`），不是记录创建时间——挖掘记录没有创建时间这个字段。
- **状态**共 7 种：排队中 / 运行中 / 已完成 / 已中断 / 失败 / 已取消 / 待人审。

## 二、设置 → 系统状态（详情页）

概览页放摘要，这里放全量。三段内容口径**各不相同**，页面上都有标注。

### 1. 检索使用分析（口径 B）

概览页那四个数字在这里扩成五个，多出**零结果**（绝对数）与**平均延迟**——
平均延迟单独列出是为了和 P95 对照看：两者差距越大，说明长尾越严重。

除数字外，这里还比概览页多出三块：完整的「答不上来的问题」清单、各范式明细表、
意图与渠道分布。

#### 各检索范式

| 列 | 说明 |
|---|---|
| 范式 | 范式 ID；「未走范式（旧检索）」为未经范式引擎的流量 |
| 调用 | 窗口内调用次数 |
| 零结果 | 该范式的零结果次数与占比 |
| P95 | 该范式自身的 P95 延迟 |

**调用多不等于跑得好。** 一个调用量最高、零结果率也最高的范式，是优先要调的。

#### 热门查询

窗口内出现最多的 20 条查询原文，带各自的无结果次数。
**"问得多又答不上"的那几条优先级最高**——它们同时说明需求强烈和覆盖缺失。

> 同样是真实用户输入，仅管理员可见。

#### 查询意图分布 / 接入渠道分布

- **意图**：查询被归类到的意图类型；未能识别的归入「(未知)」。
- **渠道**：请求从哪个入口进来（如 MCP、API 等）。

### 2. 服务状态

三个服务的健康探测：**挖掘服务** / **检索服务** / **LLM服务**。

探测超时（3 秒）按不健康处理——健康检查不该把整页拖住。这块信息在服务正常时恒为绿色，
所以**没有放在概览页**：它占位置但几乎不传达信息。

### 3. 知识资产（口径 C）

**只统计域级 active release 范围**，页面上有明确标注。

| 指标 | 含义 |
|---|---|
| 文档 / 快照 / 段落 / 检索单元 / 关系 | 已发布语料中各类对象的数量 |
| 检索单元类型分布 | 已发布语料中检索单元的类型构成 |

> **纯知识库部署下这里会显示「该域无发布语料」**，因为知识库挖掘只构建不发布，永远不产生
> release。这是口径不适用，不是数据丢失。要看知识库自己的资产量，请看概览页顶部的「知识库概况」。

## 三、数据从哪来 / 多久更新一次

| 区块 | 接口 | 底层数据 |
|---|---|---|
| 知识库概况 / 四张图表 | `GET /api/kb/stats` | 文档表 + 构建快照 + 挖掘记录 |
| 待处理 / 知识库卡片 / 最近挖掘 | `GET /api/kb/overview` | 同上 |
| 运维概览 / 检索使用分析 | `GET /api/ops/usage` | 检索服务写入的查询日志 |
| 服务状态 | 各服务 `/health` | 实时探测 |
| 知识资产 | `GET /api/knowledge/stats` | 域级发布语料 |

**全部是请求时实时查询，没有缓存也没有预聚合。** 页面加载即最新，刷新按钮只是重新请求。

切换域会重新拉取全部数据；旧域慢到的响应会被丢弃，不会串到新域的数字里。

## 四、常见疑问

**Q：概览页说有 120 个检索单元，设置页「知识资产」却显示 0？**
两个不同口径。概览页是你的知识库里的当前知识（口径 A），设置页那块只统计域级已发布语料
（口径 C）。知识库挖掘不产生发布语料，所以后者为 0 属于正常。

**Q：为什么"文档"数和各知识库文档数加起来对不上？**
不应该对不上。顶部「文档」取的是状态分布六档之和，与图表同源。若确实不一致，说明有文档
的归属状态异常，值得排查。

**Q：零结果率很高，怎么办？**
看「答不上来的问题」清单，那是按出现频次排好序的知识缺口。补充对应文档并重新挖掘后，
这些查询就能被命中。

**Q：某个范式一次都没被调用？**
先确认它是否已发布并绑定到当前域。范式调用排行只统计实际发生的调用，"配好了但没人走"
和"没配"在这里长得一样。

**Q：检索次数是 0，但确实有人在用？**
检索日志由检索服务写入。如果该服务从未启动过，日志表根本不存在，页面会显示
「尚未产生检索日志」而不是 0。看到 0 而不是这句提示，说明表在、只是窗口内确实没有流量。

**Q：普通成员看不到运维数据？**
是设计如此。运维指标对无权处理的人只是噪声，而且这些区块包含真实用户输入原文。
