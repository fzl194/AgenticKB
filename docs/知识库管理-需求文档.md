# 知识库管理 —— 需求文档

> **状态**：草案 / 讨论中
> **版本**：v0.2（2026-07-27）—— 在 v0.1 基础上整合：数据归属三类划分、检索范式化、发布内置、归档概念砍掉、目录层级、跨 KB 移动不做
> **范围**：需求层 + **数据归属的概念划分**。本文不含服务边界、接口契约、DDL 列设计等实现细节；现有底座的表名作为「概念锚点」出现，仅为说明归属，新表的列设计留待实现设计。
> **关联**：现状摸底见 `docs/研讨/` 下的现状文档与本体检索说明。

---

## 1. 背景与目标

### 1.1 现状的痛点

当前系统里「文档」和「挖掘任务」是**绑定**的：文档在 mining run 里被创建，用户没有独立的「文档管理」心智；上传只是把文件落盘，要触发挖掘还得另起 run；产出知识的归属也模糊（挂在 run / snapshot 上，而非用户能理解的「我的文档」）。

### 1.2 目标（一句话）

把「知识库 / 文档管理」从挖掘 pipeline 里**抽出来做成用户可见的一等公民**：用户创建知识库、管理库内文件、显式决定何时挖掘；挖掘退化为「文档上的一次可重复动作」；产出知识归属于文档；检索时可以把多个知识库叠加组合。

### 1.3 锚点重定向（本次需求的核心思想）

| | 当前 | 未来 |
|---|---|---|
| 文档的绑定对象 | 挖掘任务（run） | **知识库（KB）** |
| 文档身份的归属 | mining 建 | **KB 建 / 改 / 删** |
| 挖掘的地位 | 与文档绑定的流程 | **文档上的运行态动作**（可重复：首挖 / 重挖 / 重试） |
| 知识的归属 | 模糊（run / snapshot） | **归属于文档**（文档的「当前知识」= 最近一次成功挖掘产出） |
| 检索范围 | 单个 domain | **范式内配置的一组 KB**（域内组合） |

## 2. 核心概念模型

```
用户 ──拥有──▶ 知识库(KB) ──包含──▶ 文档
                                     │
                                     ├── 被〔挖掘动作〕施加   ← 运行态、可重复、与文档不绑定死
                                     │
                                     └── 产出── 知识(切片/检索单元/实体/关系)
                                                ↑ 归属文档，不归属某次挖掘
                                                ↑ 文档的「当前知识」= 最近一次成功挖掘产出

检索：在一组 KB 上进行 ── 检索范围 = 范式内配置的 KB 集合（限同一 domain 内）
```

### 2.1 四条核心推论

1. **文档有独立生命**：上传后即存在于 KB 中，即使从未被挖掘也是 KB 的一员（只是「还没有知识」）。
2. **挖掘是文档上的操作**：可对同一文档多次挖掘（修正、重抽、模型升级后重跑），每次产新版本；文档身份不变，其「当前知识」始终是最新成功版本，旧版本留档但不服务检索。
3. **知识跟文档走**：任何一条知识都能回溯到「来自哪个文档 → 属于哪个 KB」（检索结果可标注来源 KB）。
4. **KB 是检索的组合单元**：检索不锁定单个 KB，而是按检索范式配置的一组 KB（限域内）。

## 3. 数据归属：三类概念与现有底座的承接

> 本节是把现有挖掘底座的概念，按「归谁管」切成三类（外加本体这个域级资产），并写清关联与隐藏约束。这是 KB 叠加的核心设计依据。

### 3.1 三类概念（+ 本体域级资产）

| 类 | 含义 | 用户是否感知 |
|---|---|---|
| 🟦 **知识库（用户面）** | 用户管理的对象：用户、KB、文档 | 是 |
| 🟨 **挖掘运行态（瞬态）** | mining 的执行足迹（任务、阶段、批次、构建） | 否 |
| 🟩 **知识资产（稳态）** | 挖掘产出、被检索的内容（快照、切片、单元、向量、发布） | 否（结果可感知，内部不可见） |
| 🟪 **本体（domain 级资产）** | 跨 KB 的领域知识结构（实体、关系、类型） | 否（检索时被消费） |

### 3.2 现有底座表的归属划分

| 表 | 归属 | 角色 | 与 KB 的关系 |
|---|---|---|---|
| **🟦 知识库（用户面，KB 管）** | | | |
| `kb_users` / `knowledge_bases` / `kb_members`（新增） | KB | 用户 / KB / 成员 | KB 属于 domain |
| `asset_documents` | **KB 接管**（原由 mining 建） | 文档身份 + CRUD + 存储 + 目录 | 加 kb_id / storage_path / directory_path / owner；UNIQUE 改 (kb_id, document_key) |
| **🟨 挖掘运行态（瞬态，mining 管）** | | | |
| `mining_runs` | 运行态 | 一次挖掘任务 | 「文档上的运行态动作」；输入从 KB 选 |
| `mining_run_documents` | 运行态 | 每文档的 run 状态 | 引用 asset_documents；回填 snapshot_id |
| `mining_run_stage_events` | 运行态 | 阶段时间线 | — |
| `asset_source_batches` | 运行态 | 一次触发的一批输入 | 可重定义为「一次挖掘触发的 provenance」 |
| **🟩 知识资产（稳态，mining 产、serving 读）** | | | |
| `asset_document_snapshots` | 资产 | 内容版本（**hash 去重**） | `UNIQUE(domain, hash)` → 域内共享；KB 文档经 link 复用 |
| `asset_document_snapshot_links` | 资产 | doc ↔ snapshot 桥（N:N） | KB 文档 ↔ 共享 snapshot 的挂接点 |
| `asset_raw_segments` | 资产 | 切片（原子知识） | FK→snapshot，hash 同则共享 |
| `asset_raw_segment_relations` | 资产 | 篇章关系 | 同上 |
| `asset_retrieval_units` | 资产 | 检索单元 | 同上 |
| `asset_retrieval_embeddings` | 资产 | 向量 | 同上 |
| `asset_builds` / `asset_build_document_snapshots` / `asset_publish_releases` | 资产·发布层 | 构建 / 选择 / 生效发布 | **对用户隐藏**（见 §5.2）；serving 入口；每 KB 文档一条选择行 |
| **🟪 本体（domain 级资产）** | | | |
| `ontology_versions` / `node_types` / `relation_types` | 资产 | 本体 schema（TBox） | **domain 级，跨 KB 共享** |
| `ontology_entities` / `entity_relations` / `alias_dictionary` | 资产 | 实体 / 关系实例（ABox） | domain 级聚合 |
| `ontology_evidence_nodes` | 资产 | 出处 → segment | 可回溯到 KB 文档 |
| `ontology_candidates` | 运行态 | 候选评审中 | 人审后升资产 |

### 3.3 关键决策

1. **`asset_documents` 升格为 KB 管**：文档身份（建 / 改 / 删）由 KB 负责；mining 只**读**文档（拿去挖），产 snapshot 及以下。文档是 KB 与 mining 的交接点。
2. **不变量进化得更干净**：原「mining 是 asset_* 唯一写方」→ **「每个表单一写方」**——KB 独占 `asset_documents`；mining 独占其他所有 asset_* 表 + 运行态表。mining **不再写 `asset_documents`**。
3. **hash 相同 → 零新增原子知识**：所有原子知识（切片 / 单元 / 向量 / 篇章关系 / 实体提及 / 出处）都挂在 **snapshot** 下（FK→snapshot_id），不是挂在 document 下。两个 KB 各持一份同 hash 文档时，mining 走 SKIP/RESTORE，**只新增 3 条结构链接行**（文档身份、doc↔snapshot link、build 选择），无任何知识重复构建。

### 3.4 影响 KB 的隐藏约束（务必留意）

1. **snapshot 去重是 domain 级**（`UNIQUE(domain, normalized_content_hash)`）：同内容跨 domain 不共享（本体不同），**域内共享**。与「域内组合 KB」一致——同域 KB 间才能共享挖掘。
2. **原子知识全挂 snapshot**（FK→snapshot_id，非 document）：这是「零新增原子知识」的根因，也是 KB 文档可共享挖掘产出的机制基础。
3. **本体是 domain 级，不是 per-KB / per-document**：KB_A 文档产出的实体，KB_B 在同域也能看到（域级聚合）。组合检索时：实体图是域级的，但检索返回的 unit / evidence 可按 KB 过滤（通过 document→snapshot 链）。「知识归属 KB」靠 `unit → snapshot → link → document → kb_id` 这条链回溯实现。
4. **release 部分唯一索引**（一域一 active release per channel）+ **advisory lock 域级串行**：多 KB 共用一个域级 release，靠 `build_document_snapshots` 区分文档；KB 维度的发布仍受域锁约束。
5. **出处链完整**：`evidence → segment → snapshot → link → document → kb_id`，任何知识都能回溯到 KB。

### 3.5 三类关联（数据流）

```
🟦 KB                       🟩 知识资产                         🟪 本体（域级）
asset_documents ──link──▶ asset_document_snapshots
  (身份/CRUD/存储)            │  └─ segments / units / embeddings    domain 内跨 KB 聚合
                             │     （原子知识，全挂 snapshot）       entities / relations
        ▲                    │                                      ▲
        │ 引用               │                                      │ 从 segment 抽
🟨 挖掘运行态 ─────产───────┘                                      │
mining_runs ──▶ mining_run_documents                               │
  (读 KB 文档, 产 snapshot,                                           │
   不动文档身份)              ▲                                      │
                             │                                      │
                     发布层 builds/releases                             │
                     （选 document+snapshot 对 → serving 读）            │
                                                                    │
serving 检索：release 定范围 ─▶ snapshot 的 units/embeddings ─▶ 实体图（域级）
              （可按 KB 过滤文档）         （原子知识，hash 共享）
```

## 5. 实体生命周期（需求层状态）

### 5.1 文档生命周期

```
uploaded ──触发挖掘──▶ mining ──成功──▶ mined（=published，对用户）
                         │                   │
                         │                   ├── re-mine ──▶ mining（产新 snapshot，旧的留档不服务检索）
                         │                   └── 软撤回 ──▶ withdrawn（不可检索，数据保留，可恢复）
                         └──失败──▶ failed（可重试）
```

- `uploaded`：在 KB 中，未挖掘，无知识。
- `mining`：挖掘进行中。
- `mined`：挖掘完成，**即可检索**（发布是挖掘内置动作，对用户不可见，见 5.2）。
- `withdrawn`：被软撤回，不可检索，数据保留，可恢复。
- `failed`：挖掘失败，可重试。
- re-mine 不产生新文档，只产生该文档的知识新版本（新 snapshot）；文档身份不变。

### 5.2 发布对用户隐藏

现有 build / release 机制是挖掘的**内置尾段**：挖完即自动构建并发布，对用户不可见。用户侧的文档状态到 `mined` 即等同「可检索」，不暴露 build / release 概念。

### 5.3 知识

- 永远归属某文档（通过 snapshot 挂接）。
- 某文档的「当前知识」= 它最近一次成功挖掘产出的 snapshot 下的切片 / 单元。
- 旧 snapshot 留档（可审计），不服务检索。

## 6. 检索行为（范式化）

> v0.1 此节写「查询时传 kb_ids」，**作废**。检索是算子化 / 范式化的，KB 范围在设计态确定。

1. **KB 范围在设计态确定**：构建检索范式（复用现有 operator/paradigm 系统）时，选定该范式覆盖的一组 KB；范式发布后，KB 集合随之固定。
2. **查询时只选范式**：实际检索请求不再传 kb_ids；不同 KB 组合 = 不同范式（或范式的不同 scope 配置，机制细节留实现设计）。
3. **域内约束**：一个范式覆盖的 KB 必须同属一个 domain（不同 domain 本体不同，不混搜）。
4. **来源标注**：每条结果标注来自哪个 KB（通过 `unit → snapshot → link → document → kb_id` 回溯）。
5. **无查询时权限失败场景**：因为 KB 集合在设计态（由有权设计范式的人）确定，查询时不会出现「选了无权 KB」。

## 7. 用户与权限

### 7.1 多用户与归属
- 每个用户有身份（起步经控制面头部注入用户名；后续接真实登录）。
- 每个 KB 有唯一 owner；owner 可创建 / 删除 / 挖掘 / 改可见性。

### 7.2 可见性三档

| 可见性 | 谁能读 | 谁能写 |
|---|---|---|
| `private` | 仅 owner | owner |
| `shared` | owner + 被加入的成员 | owner + editor 成员 |
| `public` | 所有认证用户 | owner（+ editor 成员） |

### 7.3 检索范围的自然产生
「用户可见的 KB 集合」= 自己 owner 的 + 被加为成员的 + public 的。设计范式时从这个集合里选。

### 7.4 auth 分阶段
- **Phase 1（随本需求一起上）**：无登录，控制面头部注入用户名（内网 + ip 白名单）。
- **Phase 2（后续）**：接真实登录（SSO 或本地账号）。数据模型现在就多用户就绪，Phase 2 只换身份来源。

## 8. 明确不做（起步边界）

| 不做 | 理由 |
|---|---|
| 跨 domain 组合 KB | 不同 domain 本体不同，语义混乱；真有需求是另一个大设计 |
| 上传即自动挖掘 | 手动触发起步（可控成本、批量、可整理）；按 KB 配 auto 留作后续 |
| 命名「检索画像」 | 范式内已可配置 KB 集合，起步够用；独立画像实体作后续 |
| 完整 RBAC / 多团队多组织 | 简单归属 + 可见性起步已够 |
| 文档跨 KB 共享（N:N） | 独占归属起步；底层 hash 去重已实现「同内容只挖一次」 |
| KB 归档（archived 状态） | YAGNI；KB 只有 active（要停用就软删） |
| 文档跨 KB 移动 | 不做 |
| 回收站保留期等细节 | 暂不细讨 |

## 9. 验收标准

1. 用户能完成 US1–US7 全流程：建 KB → 上传（含压缩包解压）→ 文件管理 → 显式挖掘 → 看文档状态 → 用配置好 KB 集合的范式检索 → 结果带来源。
2. **数据归属不变量**：KB 独占 `asset_documents` 写；mining 独占其他 asset_* + 运行态表写；serving 对 asset_* 只读。
3. **零重复挖掘**：同 hash 文档（不同 KB 各持一份）共享一个 snapshot，只挖一次，零新增原子知识。
4. **向后兼容**：现有挖掘 / 检索行为不破坏（存量未归类文档 kb_id 留空，仍可搜到）。
5. re-mine 产出新 snapshot，文档身份不变，检索始终用最新成功版本。
6. 多用户隔离正确：AB 看不到 AC 的 private KB；权限边界清晰。

## 10. 讨论结论（原开放问题）

| 原问题 | 结论 |
|---|---|
| 9.1 权限失败行为 | **作废**：检索范式化，KB 集合在设计态确定，查询时无此场景（§6） |

| 9.6 文档跨 KB 移动 | 不做（§8） |
