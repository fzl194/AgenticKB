# 融合决策：挖掘算子化 × 知识库管理

> 状态：机械合并已完成（commit `c22653d`，feat/kb-management）。本文是"从需求角度梳理两边各实现了什么 + 二者断裂面 + 待拍板的融合决策"，供决策融合方向。
> 数据来源：三路并行代码分析（挖掘算子化 / 知识库管理 / 集成断裂面），结论均带文件:行号，已交叉印证。

---

## 0. 一句话结论

挖掘算子化（master）和知识库管理（feat）**当前完全正交、互不相交**：
- 算子化把"挖掘怎么跑"重构成**全局、domain 维度、无 KB 概念**的 workflow 算子图；
- 知识库管理把"文档归属"升级成 **KB 维度、走旧 legacy pipeline、无 workflow 概念**的多库文件系统。

机械合并**没有编译/导入级断裂**（两条线只通过 DB 耦合），但存在 **1 个致命静默数据错误（发布互相覆盖）+ 2 个语义不一致**。要让"在知识库里选 workflow 挖掘、按库隔离检索"这个产品形态成立，需要拍 3 个设计决策。

---

## 1. 两个特性各实现了什么（需求级）

### 1.1 挖掘算子化（master 带来的）

**定位**：把挖掘从"硬编码 10 段线性流水线"重构成"用户可在画布编辑、编译、发布成不可变版本、Run 时冻结执行的 DAG 算子图"。挖掘流程本身从常量变成带版本治理的数据资产。

**核心概念**：
| 概念 | 是什么 |
|---|---|
| Operator（算子） | 16 个内置原子能力，Pydantic 定义参数 → JSON Schema draft-07 给前端自动渲染表单 |
| DAG | nodes + edges（slot 命名槽位）+ output（锚定 `mining_finalize.result`） |
| Zone | `input`（整批一次）/ `document`（逐文档并行）/ `global`（整批聚合），编译器强制 document→global 必须经 `asset_persist` |
| Manifest | 发布时生成的冻结执行清单（graphHash + 每节点 paramsHash + 拓扑序），Run 恢复只读它 |
| Version | `mining_workflows.current_version` + 不可变版本行，乐观锁发布 |
| WorkflowRunBinding | 4 元组 `workflow_id/version/version_id/graph_hash` + 完整 manifest，Run 与"某个不可变版本"的合约 |

**算子目录（16 个）**：`input_ingest / parse_segment / enrich / discourse_line / contextual_retrieval_enrich / retrieval_unit_build / embedding / entity_extract / entity_resolve / entity_relation_extract / entity_review_gate / graph_write / ontology_induction / ontology_review_gate / asset_persist / mining_finalize`。`editPolicy` 三态：fixed（4 个骨架）/ protected（审核落图算子，按能力线动态）/ editable。

**一次 Run 怎么提交**（`POST /api/runs`）：读 `mining_run_submission_engine`（legacy/workflow）→ workflow 模式经 `workflow_run_binder.resolve` 绑定版本 + 注入 runtimeBinding → `POST /api/runs/preflight` 按 `domain+upload_batch+workflow 版本`预检（NEW/REUSED/RESTORABLE/...7 类）→ create_run 复算 preflight 比对 state_token → `mining_runs.execution_engine` 字段锁定引擎，之后永不可改。

**数据模型**：
- 全局（Control 库）：`mining_workflows`、`mining_workflow_versions`（**无 domain 列、无 kb_id 列**）
- 域（Domain 库）：`mining_runs`(+9 个 workflow_* 列)、`mining_workflow_node_events`、`asset_document_snapshots`(+4 个 workflow_* 列 + 部分唯一索引)
- `asset_persist` handler **直接复用旧 `persist_document_assets`**，没重写；workflow 模式传 `strict_embeddings=True` + workflow_binding 4 字段写入 snapshot
- 等价性：`test_full_workflow_equivalence.py` + `test_workflow_legacy_golden.py` 保证与 legacy 业务输出一致

**发布/检索**：`mining_finalize` 仍调 `stages/publishing` 的同一套 build/publish/release，落 `asset_publish_releases`，受 `(domain, channel)` 部分唯一索引约束（**一域一 channel 至多一个 active release**）。

**关键结论：算子化完全不知道 KB 的存在。** `grep kb_id|knowledge_base knowledge_mining/mining/workflow/` 零命中；Workflow 定义全局、Run/snapshot 按 domain 隔离，**kb_id 从不入参**。

### 1.2 知识库管理（feat 原有）

**定位**：把系统从"文档由挖掘 run 创建、与 run 绑死、归属模糊"升级成"用户可见的多知识库 + 云端文件管理器一等公民"：文档是 KB 拥有的稳定实体，挖掘退化为文档上的可重复动作。

**数据模型**：
- `kb_users`（用户）、`knowledge_bases`（KB 主体，domain + `UNIQUE(domain,name)` + visibility + 软删）、`kb_members`（role: viewer/editor）、`kb_folders`（一等文件夹，自引用树，`path` 全路径唯一真相源，磁盘镜像）
- `asset_documents` 改造：+ `kb_id`(FK RESTRICT) / `storage_path`(位置,可变) / `directory_path`(逻辑目录) / `owner_id` / `file_size` / `modified_at`；UNIQUE `(domain,document_key)` → `(kb_id,document_key)`

**身份/位置分离（G1，核心）**：
- `document_key` **冻结**（首次上传值，改名/移动不更新）= 逻辑身份
- `storage_path` / `directory_path` / `document_name` **可变** = 当前位置
- mining walk-time 用 `storage_path`（含 `<kb_id>` 前缀，全库唯一）查 `get_document_lifecycle_state` 命中身份 → 走"复用 id"分支绕过 upsert → 同一文件多次挖掘 `document_key` 恒等、status join 不断链。顺带消解多库歧义。

**文件管理能力**（逐项已实现）：上传 / zip 自动解压 / 在线预览（md/html/文本/图片/PDF；office/zip/chm 不支持）/ 下载（越界保护）/ **真删除** / 重命名 / 拖拽移动 / 文件大小+修改时间 / 右键菜单（下载/重命名/删除）。**软撤回（从发布移除）未接线**（`withdraw` raise NotImplementedError）。

**KB→挖掘触发**（`POST /api/kb/{id}/mine`）：**直接复用旧 legacy pipeline**（`jobs/run.py:run()` 起后台线程），靠 `input_path` 锁到 `{upload_root}/{kb_id}/` 整库扫盘 + `mining_runs.metadata_json` 写 `{"kb_id":...}` provenance。靠 storage_path 含 kb_id 前缀间接隔离产物，**不传 doc_ids 子集**。

**发布/检索衔接**：KB **没有自己的 build/release**，完全复用域级 release。**serving 按 KB 检索完全没实现**（设计 P5 TODO：`AssetRepository.resolveActiveScope` 仍 `(domain,channel)` 两参，`ScopeResolveOperator.PARAM_SCHEMA` 仍空 `{}`）。当前多 KB 产物只要进了 active release 就**全部可检索、混在一起**。

## 2. 断裂面（合到一起 ≠ 正确）

### A 类（编译/导入/报错）：**无**
能编译、能导入、能起服务。架构使然——两条线只通过 DB 耦合，合流是 schema + 签名对齐，不是控制流拼接。

### B 类（静默错误：能跑但数据/隔离不对）

#### B1 【致命】同域多 KB 的发布互相覆盖，检索侧只剩最后一个 KB 的资产
- **位置**：发布唯一索引 `databases/asset_core/schemas/002_asset_core_postgresql.sql:416-420`（`uq_asset_publish_releases_domain_channel_active ON (domain,channel) WHERE status='active'`）；发布执行 `stages/publishing.py:318`；调用点 `jobs/run.py:2003`（**无 kb_id**）；KB 状态派生 `kb/db.py:54-69`。
- **现象**：KB-A 发布→R1 active；KB-B 发布→R1 被 retire、R2 active（仅 KB-B）。检索只认 active release → **KB-A 资产一夜消失**，KB-A 文档状态从 published 跌回 uploaded。**无任何报错**。
- **影响**：多 KB 是核心卖点；同域建第二个 KB 并发布即触发。**判定：融合设计问题（发布层从未为 KB 扩展）**。

#### B2 KB 挖掘始终走 legacy 引擎，绕开 workflow 引擎与配置默认
- **位置**：`kb/routes/mining.py:73-79`（INSERT 不写 `execution_engine`）→ DB 默认 `'legacy'`；引擎分流 `jobs/run.py:445-474`；配置默认 `mining_config.py:39`（`workflow`，仅 `/api/runs` 读）。
- **现象**：KB 挖掘永远跑老管线，`/api/runs` 跑 workflow 算子图。同一域同一批文档走出两条代码路径（产出可能分叉：workflow 严格 embedding vs legacy best-effort）。workflow 编辑器对 KB 挖掘**完全无效**。
- **判定：实现 bug 偏融合设计**。

#### B3 【潜在】workflow 路径不填 existing_doc（今天因 B2 不触发）
- **位置**：`workflow/executors/document_executor.py:133-180`（无 lifecycle 查询）。
- **现象**：一旦把 KB 挖掘切到 workflow，`existing_doc=None` → 走 by-key 分支 → `upsert_document` 写出 **kb_id=NULL 幽灵身份行** + 触碰 `(kb_id,document_key)` 唯一约束 → 跨库泄漏。
- **判定：融合设计问题**。今天静默安全；切引擎前必修。

### 已排除的非问题
- **前端共存** ✅：路由 `/kb` vs `/mining/workflows` 不冲突；Sidebar 两个菜单项都在，`isActive('/mining')` 显式排除 `/mining/workflows`。导航合理。
- **existing_doc shape** ✅：feat 与 master 都用 `{"id","domain","document_key"}` dict；`PipelineContext.existing_doc` 字段存在；`with_updates` + workflow merge 白名单都认它。
- **jobs/run.py 的 existing_doc 调用方** ✅：903/1808 传给 `DocumentContext(...)` 构造器，非直接传 snapshot 函数；签名兼容。
- **域级锁** ✅：`mine_kb` 与 `/api/runs` 共用 `_domain_run_lock(domain)`，同域互斥、跨域并发。

## 3. 三个核心决策（需要你拍板）

### 决策 1：发布隔离粒度（B1 的根因，**上线前必修**）
当前按 `(domain, channel)`。多 KB 必须二选一+：
- **(a) 给 release/build/build_document_snapshots 加 kb_id，唯一约束改 `(kb_id,domain,channel)`**：每 KB 独立发布。正确终态，但要联动改 Java serving 全部读路径（8 个 mapper + 控制面 domain→DataSource 路由升级成 KB 路由）。改动量大。
- **(b) 约束"一域至多一 KB"**：`create_kb` 前加一条存在性检查。零侵入、5 行，但多 KB 卖点失效。
- **(c) 混合：每 KB 独立发布单元，active release 域级"合成"**：发布 KB-B 时合并而非替换。复杂，检索结果无法标注来源 KB，权限语义糊。
- **推荐：短期 (b) 兜底让分支可发布；长期规划 (a) 走 ADR**。

### 决策 2：KB 挖掘的执行引擎（B2/B3 的根因）
要不要把 KB 挖掘对齐到 workflow 引擎？
- **(a) 显式钉 legacy**：`mine_kb` INSERT 写 `execution_engine='legacy'` + 注释。1 行，零风险，把"碰巧没炸"变"显式策略"。
- **(b) 让 mine_kb 走 create_run 同等路径**：调 `insert_queued_run` + binding resolve。
- **(c) 先给 workflow 路径补 existing_doc 填充（扫 B3 雷），再切 (b)**。
- **推荐：先 (a) 让语义自洽；长期 (c)+(b) 让 KB 享受算子图可观测性**。

### 决策 3：身份入口收敛（snapshot 三参数）
`select_or_create_snapshot` 现收 `existing_doc`(KB,dict) / `existing_document_id`(workflow,str) / 都空 by-key。`pipeline.py:795` 把 KB 的 dict 拍扁成 str 走 workflow 分支，绕过优先级最高的 KB 分支（结果正确但与注释不符，维护陷阱）。
- **(a) pipeline 直透传 `existing_doc=ctx.existing_doc`**；(b) **收敛成单参数 `existing_doc: dict|None`，workflow 自己包成 dict**；(c) 不动改注释。
- **推荐：(b)**，三入口塌成两入口，优先级问题消失。

## 4. 推荐融合路线

**第一阶段（让当前分支可发布、语义自洽，本 PR 收口）**：
1. 决策 1 → (b)：一域一 KB 兜底（防 B1 事故）
2. 决策 2 → (a)：`mine_kb` 显式 `execution_engine='legacy'`（消 B2 歧义）
3. 决策 3 → (b)：身份入口收敛（消维护陷阱）
4. 在 `document_executor.py` 顶部加 `# FIXME: existing_doc not populated; see B3` 防后人踩雷
5. 跑 kb 测试套件确认未回归

**第二阶段（独立 ADR + feature，不在本 PR）**：
- 决策 1 → (a)：release/build 加 kb_id + Java serving 读路径 KB 感知
- 决策 2 → (c)+(b)：workflow 执行器补 existing_doc，KB 切 workflow 引擎
- serving P5 落地：`resolveActiveScope(kb_ids)` + `ScopeResolveOperator` 加 kb_ids + `SourceRef` 加 kb_id/kb_name
