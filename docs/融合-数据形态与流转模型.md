## M2. 知识库与文件管理模块

这是用户直接操作的层。三张表回答"这个文件是谁的、在哪个 KB 的哪个文件夹"。

| 表 | 关键列 | 关键约束 | 写/读 |
|---|---|---|---|
| `knowledge_bases` | `id`, `domain`, `name`, `owner_id`, `visibility∈{private,shared,public}`, `status∈{active,deleted}`(软删), **`mining_workflow_id`(🆕 选的挖掘范式)** | `UNIQUE(domain,name)` | KB API 写；mining/serving 读 |
| `kb_folders` | `id`, `kb_id`, `parent_id`(自引用), `name`, `path`(全路径) | `UNIQUE(kb_id,path)`；部分唯一`(kb_id,parent_id,name)` | KB API 写；mining walk 读 |
| `asset_documents` | `id`, `domain`, **`document_key`(冻结=身份)**, `document_name`, **`storage_path`(可变=位置)**, `directory_path`(可变), `kb_id`, `owner_id`, `file_size`, `modified_at` | `UNIQUE(kb_id,document_key)`；`kb_id` FK→knowledge_bases `ON DELETE RESTRICT` | **只 KB API 写**；mining/serving 读 |

**核心设计——身份/位置分离**（解释"文件管理不影响挖掘"）：
- `document_key` 是**冻结的身份**，首次上传定死，改名/移动都不变。
- `storage_path` / `directory_path` / `document_name` 是**可变的位置**，文件管理只动它们。
- 所有挖掘产物（快照/资产）都挂在 `document_key`（身份）上，不挂位置。所以你在前端怎么改名、移动、归类，后面挖出来的知识都不受影响——身份没变，链不断。
- `UNIQUE(kb_id, document_key)` 让每个 KB 是独立文件系统；`storage_path` 带 `<kb_id>` 前缀全库唯一，消解多库同名歧义。
- `knowledge_bases.mining_workflow_id`（🆕 要加）= 这个 KB 选的挖掘范式，指向 M3 的 `mining_workflows.id`。

## M4. 挖掘任务模块

**回答 Q2：挖掘任务概念保留。** `mining_runs` 是"一次挖掘操作"的单元，`mining_run_documents` 是这次操作处理的文档清单。

| 表 | 关键列 | 关键约束 |
|---|---|---|
| `mining_runs` | `id`, `domain`, `channel`, `input_path`, `status`, `current_stage`, **`execution_engine∈{legacy,workflow}`**, `workflow_id/version/version_id/graph_hash`(绑定), `workflow_manifest_json`, `pause_step`, `metadata_json`(放 kb_id) | `execution_engine` CHECK；workflow_* 创建后不可改 |
| `mining_run_documents` | `run_id`, `document_key`, `raw_content_hash`, **`action∈{NEW,UPDATE,SKIP,REMOVE}`**, `status`, `document_id`, `document_snapshot_id` | `UNIQUE(run_id,document_key)` |
| `mining_run_stage_events` | `run_id`, `stage`(22值), `status` | legacy 引擎用 |
| `mining_workflow_node_events` | `run_id`, `node_id`, `operator_type`, `attempt_no`, `status`, `duration_ms` | workflow 引擎用；部分唯一`(run_id,node_id,attempt)` |
| `asset_source_batches` | `id`, `batch_code`, `source_type`, `domain` | `batch_code` UNIQUE |

**两种输入模式（都由 `action` 字段承载）**：
- **选文件挖**：用户圈 KB 下 N 个文档 → 这次任务的 `mining_run_documents` 就含这 N 条，action 多为 NEW/UPDATE。
- **整库增量挖**：用户选整个 KB → preflight 扫全部文档，按内容 hash 判定 action：未变=`SKIP`（复用旧快照，零成本）、变了=`UPDATE`、新增=`NEW`。整库增量 = 大量 SKIP + 少量 UPDATE/NEW，不是每次全量重挖。

> KB 触发的任务必须写 `execution_engine='workflow'` + 完整 workflow 绑定（这是现在 B2 的修法——当前 `mine_kb` 不写 engine 默认走 legacy）。

## M5. 知识快照与资产模块

**这是"知识"真正存放的地方。回答 Q3：同文件不同 pipeline → 不同资产，靠这层实现。**

### 三层快照（身份 / 内容 / 链接）

| 表 | 关键列 | 关键约束 | 写/读 |
|---|---|---|---|
| `asset_documents` | （见 M2，身份层） | `UNIQUE(kb_id,document_key)` | KB 写 / mining+serving 读 |
| `asset_document_snapshots` | `id`, `domain`, `normalized_content_hash`, `raw_content_hash`, `mime_type`, `title`, **`workflow_id/version/version_id/graph_hash`** | **两个部分唯一索引**（见下）；CHECK 绑定要么全空(legacy)要么全填 | mining 写 / build+serving 读 |
| `asset_document_snapshot_links` | `document_id`, `document_snapshot_id`, `source_batch_id`, `relative_path` | FK document `ON DELETE CASCADE` | mining 写 / build+serving 读 |

**`asset_document_snapshots` 的两个部分唯一索引（Q3 的核心）**：
```
uq_asset_snapshot_legacy_content    (domain, normalized_content_hash)                  WHERE workflow_graph_hash IS NULL
uq_asset_snapshot_workflow_content  (domain, normalized_content_hash, workflow_id,
                                     workflow_version, workflow_graph_hash)            WHERE workflow_graph_hash IS NOT NULL
```
含义：**同一文件内容 + 不同 workflow = 不同 snapshot 行，并存不覆盖**；同 workflow 重挖则命中复用（幂等）。

### 挂在快照上的知识资产

| 表 | 关键列 | 说明 |
|---|---|---|
| `asset_raw_segments` | `document_snapshot_id`, `segment_key`, `block_type`, `semantic_role`, `raw_text` | 原始切片 |
| `asset_raw_segment_relations` | `source_segment_id`, `target_segment_id`, `relation_type`(25值) | 片段间关系 |
| **`asset_retrieval_units`** | `document_snapshot_id`, `unit_type`, `text`, `search_vector`(tsvector), `entity_refs_json` | **能力基线**——每个被挖文档必有 |
| `asset_retrieval_embeddings` | `retrieval_unit_id`, `embedding_vector`(TEXT), `embedding_vector_vec`(vector(1024)) | HNSW 余弦索引在 `_vec` 列 |
| `asset_segment_entity_mentions` | `document_snapshot_id`, `segment_id`, `mention_text`, `resolved_entity_id` | 喂本体，带 `resolve_status` |

> **所有资产都 FK→`asset_document_snapshots.id`**。所以"同文件不同 pipeline 产出不同资产"在数据库里就是：两套 snapshot 行（S_A、S_B），各自挂各自的 segments/units/embeddings——完全不同的行，靠所属 snapshot 区分，snapshot 的 `workflow_graph_hash` 标明哪个 pipeline 产的。

## M7. 发布模块

把挖掘产出冻结成"对外可检索的版本"。**per-KB 一份 active release（R1，解 B1）。**

| 表 | 关键列 | 关键约束（现状 → 终态） |
|---|---|---|
| `asset_builds` | `id`, `build_code`, `status`, `build_mode∈{full,incremental}`, `domain`, `mining_run_id`, **`kb_id`(🆕)** | `build_code` UNIQUE |
| `asset_build_document_snapshots` | `build_id`, `document_id`, `document_snapshot_id`, `selection_status`, `reason` | PK`(build_id,document_id)` |
| `asset_publish_releases` | `id`, `build_id`, `channel`, `domain`, `status∈{staging,active,retired,failed}`, **`kb_id`(🆕)** | 现状`(domain,channel) WHERE active` → **终态`(kb_id,domain,channel) WHERE active`** |

**`asset_build_document_snapshots` 是 Q3 的另一半**：它指定"这篇文档当前用哪个 snapshot"。同一个文档有 S_A、S_B 两个快照时，build 在这里选 S_B（当前范式），那只有 S_B 的资产进 active release、被检索；S_A 不删、留历史。

**自动发布（"最新知识"对用户透明）**：挖掘 run 完成 → 自动 build（选当前范式 snapshot）→ 自动 publish（该 KB 的 active release 前移，旧 release retire）。约束 `(kb_id,domain,channel) WHERE active` 保证每库至多一个 active → **不撞别的库（B1 消灭）**。

## M9. 检索运行模块

| 表 | 关键列 | 关键约束 |
|---|---|---|
| `serving_query_logs` | `query_text`, `domain`, `channel`, `scope_json`, `release_id`, `result_*`, `duration_ms` | 索引`(channel,release_id)`、`(intent)` |
| `serving_query_cache` | `domain`, `release_id`, `query_embedding`(vector1024), `context_pack_json`, `expires_at` | ivfflat 余弦；**cache key 现不含 kb_ids（接入 kb_ids 时必须连同改）** |

**检索怎么按 KB 收窄**：入口带 `kb_ids` → `scope_resolve` 算子 → 按 kb_ids 查每个 KB 的 active release → build → `asset_build_document_snapshots` → 收集 `snapshotIds` → 下游检索算子用 `snapshotIds IN (...)` 过滤。
- 语义/全文算子：读 `asset_retrieval_units`，所有 KB 都贡献（能力基线）。
- 图谱算子：读域级 `ontology_*`，只有挖了图谱的 KB 的 snapshot 有 mentions 贡献，没挖的静默降级。

## 10. 一个文件的一生（全链路串讲）

| 阶段 | 碰哪些表 | 发生什么 |
|---|---|---|
| ① 上传 | `asset_documents` + `kb_folders` + 磁盘 | 建身份行（`document_key` 冻结 + `kb_id` + `storage_path`），不算 hash、不建快照 |
| ② 选范式 | `knowledge_bases.mining_workflow_id` | KB 绑定一个挖掘范式（可随时换） |
| ③ 挖掘（范式 A） | `mining_runs`(engine=workflow) → `mining_run_documents` → `asset_document_snapshots`(S_A, 绑 A) → `snapshot_links` → `asset_raw_segments / retrieval_units / embeddings` | 产出 S_A 及其名下资产 |
| ④ 再挖（范式 B） | 同上，产 `asset_document_snapshots`(S_B, 绑 B) | S_B 与 S_A 并存，各自独立资产。`document_key` 不变 |
| ⑤ 自动发布 | `asset_builds`(kb_id) → `asset_build_document_snapshots`(选 S_B) → `asset_publish_releases`(kb_id, active) | 该 KB 的 active release 指向 S_B；S_A 留历史不删 |
| ⑥ 前端改名/移动 | 只改 `asset_documents.storage_path/directory_path/document_name` | `document_key` 不变 → snapshot/资产全不断链 |
| ⑦ 检索 | `serving_query_*`；`scope_resolve(kb_ids)` → 各 KB active release → snapshotIds → 算子按能力降级 | 联合检索 = kb_ids 填多个库；语义全中，图谱谁有谁贡献 |

## 11. 直接回答你的三个问题

**Q2：挖掘任务概念留不留？**
留。`mining_runs`（任务）+ `mining_run_documents`（文档清单）是"一次挖掘操作"的正确单元。加 KB 后只改输入方式：**选文件挖**（任务含指定文档）或**整库增量挖**（preflight 自动判定 SKIP/UPDATE/NEW）。`action` 字段天然承载两种模式。任务对用户可见（就是他点的"挖掘"），不是隐藏的。

**Q3：同文件两次/两 pipeline 挖掘，不同资产怎么存？**
资产挂快照、快照绑 pipeline、同文档可有多快照：
- `asset_documents` 身份行**始终一条**（document_key 冻结）。
- 范式 A → `asset_document_snapshots` S_A（绑 A 的 graph_hash）→ S_A 名下 segments/units/embeddings。
- 范式 B → S_B（绑 B）→ S_B 名下**另一套**资产。
- `asset_document_snapshot_links` 两条：文档→S_A、文档→S_B。
- 当前生效由 `asset_build_document_snapshots` 决定（选哪篇文档用哪个 snapshot）。旧 pipeline 资产不删，仅不在 active release。
- 前端文件管理不影响挖掘：改的只是位置列，身份冻结，产物全挂身份上。

**图谱/本体**：域级共享（G1），不 per-KB——GraphRAG 的价值就在跨库实体归一。
