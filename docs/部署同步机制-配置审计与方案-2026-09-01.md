# 部署同步机制 — 配置审计与增量同步方案（2026-09-01）

> **实施状态：已完成并实测**（2026-09-01）。改动文件：`docker-compose.yml`、`docker/Dockerfile`、
> `docker/supervisord.conf`、`deploy-server.sh`、新增 `deploy-sync.sh`、`.gitignore`、`.dockerignore`。
> pack 在外网 Windows 实测产出 32MB 包（7 目录齐全、config 零条目、无 .env/pyc）；
> apply 在本地实测走通校验→解包→安全检查→目录交换→config 保留（容器重启步骤需内网验证）。
> 注意：**启用需最后一次全量镜像部署**（supervisord.conf 在镜像里，改它必须重建镜像）。

## 背景与问题

当前部署链路：外网 `deploy-build.sh` 构建几百 MB 离线镜像 → 人工传输到内网 → `deploy-server.sh` 加载部署。
痛点：日常小改动（几行 Python / 前端 / Java）也要走全量镜像，传输体积大、部署慢（容器重建 + 全量健康检查约 1-3 分钟）。

目标：**最小工作量同步**——把代码改动以小包（约 10-20MB）同步到内网服务器目录，秒级应用，不重建容器。

## 一、配置全景审计（2026-09-01 核查）

### 运行时配置唯一真相源：`main_control_service/config/`

| 配置 | 文件 | 内外网有差异 | 消费方 |
|------|------|:---:|--------|
| PG 连接 | `system/database.yaml` | ✅ | control/mining/serving（后两者经控制面 API 拉取同一份） |
| LLM 端点与密钥 | `system/llm_service.yaml` | ✅ | llm_service / mining / serving |
| 认证密钥 | `system/auth.yaml` | —（服务器本地 generate-once） | control |
| 域注册 | `domain_registry.yaml` | 可能 | control/mining/serving（per-domain 库路由） |
| 场景包 | `scenario_packs/*/domain.yaml` | 可能 | 全链路 |
| 白名单/存储/UI/挖掘/检索 | `system/{ip_whitelist,storage,ui,mining,serving}.yaml` | 可能 | 各服务 |

服务间地址全部是 `localhost:同容器`（supervisord.conf environment + compose），**无内外网差异**。

### .env 依赖审计结论

**运行时 6 个服务：零 .env 依赖。**

- `knowledge_mining/mining/infra/mining_config.py` — 明确"不再读 .env"，从控制面 `GET /api/v1/system/mining/raw` 拉取
- `knowledge_mining/mining/infra/pg_config.py` — 控制面 `database.yaml`（`_coerce_db_fields`）
- `llm_service/config.py` — 控制面；`${VAR}` 展开是可选注入点，非 .env 文件
- `agent_serving_java/src/main/resources/application.yml` — 明确"不再 import .env"，启动时 `GET /api/v1/serving-config` 拉取
- `mcp_server/*` — 纯 `os.environ.get(带默认值)`，由 supervisord.conf 设置
- `main_control_service/config.py` — 有 `env_file=".env"` 但为休眠开发便利：镜像只 COPY `.env.example`，容器 /app 无 .env；compose `environment:` 优先级更高。部署形态下不生效

**非运行时的 .env 触点（保留，不改造）：**

1. `deploy-server.sh` 的 `ensure_serving_secrets`：在**内网服务器本地**生成 `.env`（600 权限，gitignored）存 2 个 serving/mcp 内部密钥，供 docker-compose 插值。性质：本地生成、永不从外网同步、跨部署复用（与 auth.yaml generate-once 同模式）。
2. 根目录运维脚本 `reset_db.py` / `import_db.py` / `export_db.py` / `inspect_db.py`：读 `.env` 连库，手动运维用，不在服务启动路径。
3. 外网开发机自己的 `.env`：仅本地开发用。

## 二、已对齐的需求决策（2026-09-01 与用户确认）

| 决策点 | 结论 |
|--------|------|
| .env | **同步机制不碰 .env**——同步包不含 .env；内网服务器上 deploy-server.sh 自动生成的 .env 保留现状（它不从外网传，无内外网冲突） |
| 配置目录 | **同步包完全排除 `main_control_service/config/`**——内网配置永远不被外网内容触碰 |
| 部署原则 | 部署/同步一律不覆盖内网已有配置（现有 deploy-server.sh 默认路径与 --force 路径均已满足） |

## 三、同步方案设计

### 现状基础

Python 4 目录 + databases 已 bind-mount（docker-compose.yml），目录同步今天即成立；
前端（kb-ui-dist）与 Java（agent_serving.jar）烤在镜像里，靠 deploy-server.sh 的 `docker cp` 补丁式同步（容器重建即回退）。

### 改造点：目录即真相源

1. `docker-compose.yml` volumes 增加：
   - `./kb-ui-dist:/app/kb-ui-dist`
   - `./runtime:/app/runtime`（挂目录不挂单文件——单文件 bind-mount 在 rename 替换时失效）
2. `docker/supervisord.conf` serving 命令：`java -jar /app/runtime/agent_serving.jar`
3. `docker/Dockerfile` jar 落点改为 `/app/runtime/agent_serving.jar`（首次部署种子）；kb-ui-dist 保持
4. `deploy-server.sh`：首次补齐列表与 --force 暂存列表加入 `kb-ui-dist`、`runtime`；`sync_serving_jar` / `sync_kb_ui_dist` 改为宿主机侧落盘（根除 docker cp 回退陷阱）
5. 新增 `deploy-sync.sh`：
   - `pack`（外网执行）：打增量包 = 4 个 Python 目录（**排除 main_control_service/config/**）+ databases + `kb-ui/dist` + `agent_serving_java/target/*.jar` → tar.gz + sha256（约 10-20MB，对比几百 MB 镜像）
   - `apply`（内网执行）：校验 → 按 deploy-server.sh 的 backup/rollback 原子换目录模式 → 仅 `supervisorctl restart` 包内涉及的服务 → 快速健康检查。**不重建容器，约 15 秒**

### 改造后的日常流程

| 改动类型 | 流程 | 耗时 |
|---------|------|------|
| Python | pack → 传包 → apply（自动 restart 对应服务） | ~15s |
| 前端 | 同上（nginx 静态文件，无需重启） | ~15s |
| Java | 同上（restart serving） | ~20s |
| 依赖/Dockerfile/nginx/supervisord 变更 | 仍走 deploy-build.sh 全量镜像（低频） | — |

### 服务重启映射（apply 依据包内容自动判定）

| 包内路径 | 需 restart 的 supervisor 服务 |
|----------|------------------------------|
| `knowledge_mining/` | mining |
| `llm_service/` | llm_service |
| `main_control_service/`（排除 config 后的代码） | control → 下游全部（配置中心） |
| `mcp_server/` | mcp |
| `databases/` | 无（SQL 模板，按需手动） |
| `kb-ui-dist/` | 无（nginx 静态） |
| `runtime/agent_serving.jar` | serving |

注意：control 重启后 llm_service/mining/serving 会重新拉取配置，但 supervisor 不会自动级联——apply 需按依赖顺序（control → llm → mining → serving → mcp）restart 受影响集合。

### 传输通道

不变（现在怎么传镜像就怎么传包，体积从几百 MB 降到十几 MB）。若内外网间有实时共享目录，可在 apply 侧加 inotify 监听实现全自动。

## 四、现有脚本问题清单（审查发现）

| 级别 | 问题 | 处置 |
|------|------|------|
| 高 | docker cp 同步 jar/dist 有回退陷阱：容器重建后回退镜像旧版，靠脚本重新 cp 补救；手动 `docker compose up` 会静默回退 | 本方案 bind-mount 化根除 |
| 高 | 无轻量同步入口：所有路径都以 --force-recreate + 全量健康检查收尾 | 本方案 deploy-sync.sh 解决 |
| 中 | `deploy-build.sh` 用 `zstd -19`：GB 级镜像极慢，`-10` 压缩率差异小、时间差数倍 | 顺带改 -10 |
| 低 | `deploy-server.sh` 多个 `cmkb-*.tar.zst` 并存时 `find` 顺序任意 | 顺带按版本取最新 |
| 低 | `.dockerignore` 的 `tests/` 只匹配根目录，`mcp_server/tests/` 仍进镜像 | 顺带改 `**/tests/` |

## 五、边界与风险

- **Python 依赖变更不在增量包能力内**（pyproject.toml 变更需全量镜像走 deploy-build.sh）——pack 时检测 pyproject.toml 哈希变化并提示
- **jar 与镜像内 openjdk/JRE 兼容性**：外网构建 JDK 21（Adoptium）与镜像 openjdk-21-jre-headless 同大版本，低风险
- **kb-ui/dist 由外网构建**：Vite 产物与 Node 版本弱耦合，低风险
- **数据库 schema 变更**（databases/ 下 SQL 模板更新）不自动执行，仅同步文件，需按既有流程手动应用
