# CoreMasterKB 部署指南

> 面向外网开发机（Windows）→ 内网服务器（Linux）的完整部署手册。
> 每次部署照此执行即可。方案依据：`docs/部署同步机制-配置审计与方案-2026-09-01.md`
>
> **两句话总览**：
> - **日常改动**（Python / 前端 / Java 代码）→ 增量同步包，约 15 秒应用，不重建容器
> - **基础设施改动**（依赖 / Dockerfile / nginx / supervisor / 全新服务器）→ 全量镜像

---

## 0. 先判断走哪条路

```
这次改了什么？
│
├─ 只是代码（.py / .vue / .ts / .java）─────────────→ 【A. 增量同步】
│
├─ pyproject.toml / pom.xml / package.json（加依赖）
├─ Dockerfile / docker-compose.yml / nginx.conf / supervisord.conf
├─ 或换了全新服务器 / Docker 环境
│   ├─ 服务器上还没部署过任何版本 ─────────────────→ 【B. 全量镜像-首次部署】
│   └─ 服务器上已有旧版本 ─────────────────────────→ 【C. 全量镜像-升级】
│
└─ 只改了内网配置（database.yaml / llm_service.yaml 等）
    └─ 直接在服务器上改文件，然后 ──────────────────→ 【D. 只重应用配置】
```

## A. 增量同步（日常，约 15 秒）

### A1. 外网开发机（Windows）

```bash
# 改了 Java？先构建（没改就跳过）：
cd agent_serving_java
mvn -DskipTests package
cd ..

# 改了前端？先构建（没改就跳过）：
cd kb-ui
npm run build
cd ..

# 打增量包（jar/dist 都会带上）：
bash deploy-sync.sh pack

# 或者只改了 Python，包更小：
bash deploy-sync.sh pack --code-only
```

产出两个文件（仓库根目录）：
- `sync-<时间戳>.tar.gz` —— 约 15-35MB
- `sync-<时间戳>.tar.gz.sha256`

> **pack 会先提醒版本决策**（每次同步必问）：显示当前 `releases.json` 版本，
> 让你确认是否以该版本继续——**回车/y 继续，n 中止**。版本号本身在
> `releases.json` 里维护（`current` 指针 + `releases` 历史），**该升级时先让
> Claude 改好文件再 pack**，不在脚本里输。apply 后 control 重启，前端
> "新版本"弹窗与 `/health` 即上报包里的版本。非交互环境自动跳过确认
> （可用 `SYNC_FORCE_VERSION_ASK=1` 强制询问）。
>
> pack 还会自动：排除 `main_control_service/config/`（内网配置永不被覆盖）、
> 排除 `.env`、剔除 `__pycache__`/`.pyc`。
> 与**上次成功 pack 的基线**对比 `pyproject.toml` / `pom.xml` / `package.json`
> （基线存 `.cmkb-sync-last/`，自动维护）——有依赖变更会提醒改走全量镜像。

### A2. 传输

把上面**两个文件**一起传到内网服务器**仓库根目录**（你平时怎么传镜像就怎么传）。

### A3. 内网服务器（仓库根目录）

```bash
bash deploy-sync.sh apply sync-<时间戳>.tar.gz
```

脚本自动完成：sha256 校验 → 解包 → 安全复查（包内带 config/.env 直接拒绝）→
逐目录**同 inode 内容同步**（清子项+拷入，目录本身不 rename——bind-mount 锁
inode，rename 换目录会让容器内挂载脱钩被掏空；**config/ 场景包/domain_registry
原样保留**）→ 只重启内容有变化的服务（按依赖序 control → llm → mining →
serving → mcp，control 代码变更会级联全部）→ 健康检查（mcp 为任意 HTTP 回包）。

- 只改了前端：**不重启任何服务**，浏览器 Ctrl+F5 即见
- 只改了 Python 某一服务：只重启该服务（约 10 秒）
- 改了 Java：重启 serving（约 25 秒，Spring Boot 启动稍慢）
- 改了 `main_control_service/` 代码：重启 control 并级联全部下游

**验证**（脚本末尾会自动打印，也可手动）：

```bash
docker exec cmkb supervisorctl status        # 6 个服务应全 RUNNING
docker exec cmkb curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/   # 应 200
```

### A4. 出问题时

| 现象 | 处置 |
|------|------|
| 校验失败 | 重新传输，两个文件必须一起传 |
| 某服务重启后不健康 | 脚本会停在明确提示；查 `./logs/<服务>.log`，修好后 `docker exec cmkb supervisorctl restart <服务>` |
| 同步了错误内容 | 直接重新 pack + apply 一次正确内容即可（apply 幂等） |
| 想回到镜像内置版本 | 走 C 路线 `--force` |

## B. 全量镜像 — 首次部署（新服务器）

### B1. 外网：构建离线镜像

```bash
bash deploy-build.sh
```

产出：`cmkb-<版本>.tar.gz` + `.sha256`（几百 MB；`releases.json` 的 `current`
就是版本号，需改版本时先改它）。

> 压缩格式 gzip：内网只需最基础的 tar/gzip 即可加载（deploy-server.sh 自动识别
> .tar.gz 与历史 .tar.zst 两种格式）。外网打包端因此也**不需要装 zstd**。
>
> 依赖检查：pack/deploy-build 都以 `pyproject.toml` 为 Python 依赖唯一真相源
> （Dockerfile 用 tomllib 展开），新运行时依赖只改 pyproject，别手写安装清单。

### B2. 传输

`cmkb-<版本>.tar.zst` + `.sha256` 两个文件 → 内网服务器**空目录**（将作为仓库根，
如 `/opt/cmkb`）。同时还需要这几个部署文件（首次部署必需，之后走增量就不带了）：

```bash
docker-compose.yml
deploy-server.sh
deploy-sync.sh
```

### B3. 内网：首次部署

前置（一次性）：

```bash
# 服务器需有：docker、docker compose v2、zstd
# PostgreSQL 可从容器网络可达（pg_hba 放行 172.30.30.0/24 或你配置的子网）
```

```bash
cd /opt/cmkb   # 仓库根目录，镜像归档也在这里
bash deploy-server.sh
```

脚本自动完成：校验+加载镜像 → 从镜像补齐宿主机代码目录（含 `kb-ui-dist/`、
`runtime/`，容器启动时也会自举）→ 校验配置（缺失会从镜像模板补齐）→
auth.yaml 密钥首次生成 → 容器重建 → 按依赖顺序启动 6 服务 → 全量健康检查。

**部署后必做（内网真实配置）**——外网包里的配置只是模板：

```bash
# 编辑为内网真实值（这些文件永不被后续任何部署/同步覆盖）：
vi main_control_service/config/system/database.yaml      # 内网 PG 连接
vi main_control_service/config/system/llm_service.yaml   # 内网 LLM 端点/密钥
vi main_control_service/config/domain_registry.yaml      # 内网各领域库路由

# 应用配置并重启：
bash deploy-server.sh --apply-config
```

验证：

```bash
docker exec cmkb supervisorctl status                    # 6 服务全 RUNNING
# 浏览器访问 http://<服务器IP>:8080（或你设置的 CMKB_UI_PORT）
```

首次管理员密码：看 `main_control_service/config/system/auth.yaml`
（首次部署随机生成；`deploy-server.sh` 输出里也有提示）。

## C. 全量镜像 — 升级已有服务器（低频）

与 B 完全相同，只有两处不同：

```bash
# 1. 新镜像归档传到服务器仓库根目录后，**先删旧归档**（避免 find 挑错版本）：
rm cmkb-<旧版本>.tar.gz cmkb-<旧版本>.tar.gz.sha256

# 2. 想让代码目录也更新到镜像版本时加 --force（保留宿主机全部配置）：
bash deploy-server.sh --force
```

| 选项 | 行为 |
|------|------|
| （无参） | 加载新镜像、重建容器；宿主机代码目录**不动**（已是增量同步过的最新） |
| `--force` | 代码目录也换成镜像版本（**config 永远保留宿主机版本**） |
| `--force-config` | 用镜像模板覆盖配置（危险：会抹掉内网真实配置，仅配置结构升级时用，用前手动备份 config/） |

> 什么时候真的需要 C：加依赖、改 Dockerfile/nginx/supervisord/compose、
> 或想把服务器彻底拉回与镜像一致。

---

## D. 只改内网配置

```bash
# 服务器上直接改：
vi main_control_service/config/system/database.yaml

# 重建容器使 compose 环境重新插值 + 全量校验：
bash deploy-server.sh --apply-config
```

不想全量重建时，轻量方式（只重启对应服务）：

```bash
docker exec cmkb supervisorctl restart control   # 配置中心，llm/mining/serving 会重新拉取
```

## 附 1：Windows 本机调试（对照）

本机不需要 deploy-server.sh，直接：

```bash
docker compose build app
docker compose up -d
```

- 宿主机 `kb-ui-dist/`、`runtime/` 为空时，容器启动**自动从镜像种子补齐**（已防 403）
- 本机改前端后同步进容器：**不要 rename 替换目录**（Windows bind-mount 运行中不可 rename，会 500），
  用删除内容+拷入：

```bash
rm -rf kb-ui-dist/* && cp -a kb-ui/dist/. kb-ui-dist/      # 前端
cp agent_serving_java/target/agent-serving-*.jar runtime/agent_serving.jar   # Java
docker exec cmkb supervisorctl restart serving              # Java 需重启
```

## 附 2：服务重启映射（速查）

| 改动 | 重启 | 命令 |
|------|------|------|
| knowledge_mining/ | mining | `docker exec cmkb supervisorctl restart mining` |
| llm_service/ | llm_service | 同上换名 |
| mcp_server/ | mcp | 同上换名 |
| main_control_service/（代码） | control + 下游全部 | `deploy-sync.sh apply` 自动级联 |
| runtime/ jar | serving | `docker exec cmkb supervisorctl restart serving` |
| kb-ui-dist/ | 无 | 直接生效 |
| databases/（SQL 模板） | 无 | 文件同步，按需手动应用 schema |
| 内网配置 yaml | control（+--apply-config 重建容器） | 见 D |

## 附 3：故障速查

| 现象 | 根因 | 处置 |
|------|------|------|
| 前端 403 | 空 bind-mount 遮蔽产物（老镜像） | rebuild 镜像；或从镜像手动补齐宿主机目录 |
| serving FATAL | runtime/ 无 jar | 检查 `runtime/agent_serving.jar` 是否存在 |
| 部署脚本停在 PG 校验 | Docker 子网未放行/账号错 | `pg_hba.conf` 放行 `172.30.30.0/24`；核对 database.yaml |
| 端口冲突 | 80/其他端口被占 | 按脚本提示设 `CMKB_UI_PORT` 等 |
| 某服务反复重启 | 看真实日志 | `tail -50 logs/<服务>.log`（宿主机 ./logs/，不在 docker logs） |
| 想看实时日志 | — | `tail -f logs/mining.log` 等；supervisor 生命周期在 `logs/supervisord.log` |

## 附 4：Windows → Linux 传输的 CRLF 坑

Windows 上传的 `.sh` 若是 CRLF 换行，Linux bash 执行报 `$'\r': command not found`。
**从外网传脚本到服务器后，先转一次再执行**（保险起见养成习惯）：

```bash
sed -i 's/\r$//' *.sh
```

`docker-compose.yml` 一般容忍 CRLF，compose 报怪错时才需要同样处理。

> 根因与根治：仓库 `.gitattributes` 已强制 `* text=auto eol=lf`——**通过 git
> 检出/clone 得到的文件天然 LF，无此问题**。踩坑只发生在"直接拷贝 Windows
> 工作区文件上传"的场景（编辑器或工具把它写成了 CRLF）。外网侧若发现文件
> 被写成 CRLF，本地 `sed -i 's/\r$//' <文件>` 一次性修复。

## 附 5：不变式（脚本已强制，但请知悉）

1. **同步/部署永不覆盖内网配置**（`main_control_service/config/` 全量保留）
2. **永不携带/依赖 .env**（同步包双向排除；服务器本地 .env 只存 2 个自动生成的密钥，不从外网传）
3. **镜像内产物双份**（`/app/...` 运行路径 + `/image-seed/...` 种子自举，防空挂载 403）
4. 依赖变更（pyproject/pom/package.json）**必须走全量镜像**，增量包不含依赖安装
